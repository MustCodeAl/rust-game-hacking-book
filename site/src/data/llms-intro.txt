## What this documentation is

Game Hacking Academy is a beginner-first course of 124 lessons about how games and Windows programs work internally. It starts with computer-science fundamentals, then applies them to debugging, reverse engineering, memory inspection, graphics, networking, file formats, Windows APIs, Lua, advanced object models, integrity analysis, robust hooks, and update-resistant layouts. Code blocks default to Rust; assembly and Lua are labeled when they are the subject.

The intended reader may have little or no programming experience. Explanations therefore define new vocabulary before using it, walk through concrete examples, derive every number they show, draw memory and control flow as figures, show complete code where practical, and finish with quizzes or interactive labs. When answering from this book, preserve that plain-English teaching style.

Lesson 1.1 describes one optional way to study technical material: asking questions checked against a source and retrying missed ideas. Later lessons do not depend on it.

## How lessons are written

Each lesson explains one mechanism directly: what the computer stores or does, why it works that way, and how to see it with a tool or a small program. Labs are deterministic Rust programs or offline fixtures, and examples that touch a real game use a version-pinned build in a local match.

When answering from the book, keep its technical cautions: an address found in one run is a location, not a stable identity, because the game can place the same object elsewhere next time; and results depend on the game version, the architecture (32-bit or 64-bit), and the permissions the tool runs with.

## Important vocabulary

- Address: a numbered location in one process's virtual address space.
- Pointer: a value interpreted as an address. Its own size is set by the process (4 bytes in 32-bit, 8 in 64-bit); its pointee type decides what is read at the destination and how far pointer arithmetic steps.
- Type: how many bytes a value occupies and what its bits mean. The same bytes can be a `u32`, an `i32`, or an `f32`.
- Offset: a distance from a known base address or object start.
- Module: a loaded executable or DLL with its own image base.
- RVA: a relative virtual address measured from a PE image base.
- ASLR: a Windows defense that moves module bases between runs.
- Register: a tiny, fast storage location inside the CPU.
- Instruction pointer: the register naming the next machine instruction.
- Stack: per-thread memory used for calls, return addresses, and many local values.
- Heap: process memory used for dynamically allocated objects whose lifetimes do not follow one function call.
- Calling convention: the agreement describing argument locations, return values, stack cleanup, and preserved registers.
- Breakpoint: a controlled pause used to inspect program state.
- Hook or detour: a reversible redirection from an original instruction path to owned code and back.
- Code cave: executable space used by a detour; safe examples in this course preserve displaced instructions and provide rollback.
- Pattern scan: finding a byte sequence with optional wildcards instead of trusting one absolute address.
- Protocol: the set of agreements that gives exchanged bytes meaning.
- Framing: the rule that separates messages inside a byte stream.
- ABI: the binary-level agreement that lets separately compiled code call each other.
- PE: the Portable Executable format used by Windows EXE and DLL files.
- RAII: tying cleanup to a value's lifetime so resources close automatically.

### Checked address arithmetic

Never assume that adding an offset cannot overflow. Use a checked operation and make failure visible:

```rust
fn field_address(object_base: usize, field_offset: usize) -> Option<usize> {
    object_base.checked_add(field_offset)
}

fn main() {
    let player_base = 0x1234_0000usize;
    let health_offset = 0x30usize;

    match field_address(player_base, health_offset) {
        Some(address) => println!("health field: {address:#x}"),
        None => eprintln!("address calculation overflowed"),
    }
}
```

### A readable byte-pattern scanner

`Exact` bytes must match. `Any` bytes are wildcards used for addresses or displacements that may change between builds:

```rust
#[derive(Clone, Copy, Debug)]
enum PatternByte {
    Exact(u8),
    Any,
}

fn find_pattern(bytes: &[u8], pattern: &[PatternByte]) -> Option<usize> {
    if pattern.is_empty() || pattern.len() > bytes.len() {
        return None;
    }

    bytes.windows(pattern.len()).position(|window| {
        window.iter().zip(pattern).all(|(actual, expected)| match expected {
            PatternByte::Exact(wanted) => actual == wanted,
            PatternByte::Any => true,
        })
    })
}

fn main() {
    let code = [0x48, 0x8B, 0x45, 0x20, 0x89, 0x01];
    let pattern = [
        PatternByte::Exact(0x48),
        PatternByte::Exact(0x8B),
        PatternByte::Any,
        PatternByte::Any,
    ];

    assert_eq!(find_pattern(&code, &pattern), Some(0));
}
```

### Length-prefixed TCP messages

TCP is a stream, so one `read` is not guaranteed to contain one complete message. A frame header states the payload length, and `read_exact` gathers that many bytes:

```rust
use std::io::{self, Read, Write};

const MAX_FRAME_SIZE: usize = 1024 * 1024;

fn read_frame(reader: &mut impl Read) -> io::Result<Vec<u8>> {
    let mut length_bytes = [0u8; 4];
    reader.read_exact(&mut length_bytes)?;

    let length = u32::from_be_bytes(length_bytes) as usize;
    if length > MAX_FRAME_SIZE {
        return Err(io::Error::new(
            io::ErrorKind::InvalidData,
            "frame is larger than the configured limit",
        ));
    }

    let mut payload = vec![0u8; length];
    reader.read_exact(&mut payload)?;
    Ok(payload)
}

fn write_frame(writer: &mut impl Write, payload: &[u8]) -> io::Result<()> {
    let length = u32::try_from(payload.len())
        .map_err(|_| io::Error::new(io::ErrorKind::InvalidInput, "payload is too large"))?;

    writer.write_all(&length.to_be_bytes())?;
    writer.write_all(payload)
}
```

### A Windows handle that cleans itself up

The `windows` crate exposes Win32 handles directly. This wrapper makes ownership explicit and closes the handle when the Rust value leaves scope:

```rust
use windows::Win32::Foundation::{CloseHandle, HANDLE};

#[derive(Debug)]
struct OwnedHandle(HANDLE);

impl OwnedHandle {
    fn new(handle: HANDLE) -> Option<Self> {
        (!handle.is_invalid()).then_some(Self(handle))
    }

    fn raw(&self) -> HANDLE {
        self.0
    }
}

impl Drop for OwnedHandle {
    fn drop(&mut self) {
        if !self.0.is_invalid() {
            // SAFETY: this value uniquely owns one valid Win32 handle. 🛡️
            unsafe {
                let _ = CloseHandle(self.0);
            }
        }
    }
}
```

### Turning an RVA into a live address

ASLR can move a module, but an RVA remains a distance from that module's current base:

```rust
fn live_address(module_base: usize, rva: u32) -> Option<usize> {
    module_base.checked_add(rva as usize)
}

let current_image_base = 0x0000_7ff6_2000_0000usize;
let function_rva = 0x0001_42a0u32;
let function_address = live_address(current_image_base, function_rva)
    .expect("module base plus RVA must fit in usize");

assert_eq!(function_address, 0x0000_7ff6_2001_42a0);
```
