## Separate network layers before capturing

Lesson 8.1 showed that one game message can arrive across two TCP reads. A packet capture lets us inspect the bytes on the way, but its packet rows are not automatically game-message rows. We will send one distinctive lobby message, then follow its bytes in both directions.

An application message is not the same thing as an IP packet or TCP segment.
Each layer has a different job:

```text
game protocol message   login, chat, lobby update
TCP byte stream         ordered, reliable bytes between two sockets
IP packet               routed data between host addresses
link/loopback capture   what the capture interface records
```

TCP may split one game message across several segments or combine bytes from
several messages in one segment. Retransmissions can repeat packet data. The
receiving application sees an ordered stream, so protocol parsing needs its own
framing rule such as a length prefix or delimiter.

<SortBoard board="network-layers" label="Explore which network layer owns what" />

A **socket** is an operating-system object representing one endpoint. A TCP
connection is identified by source address, source port, destination address,
and destination port—the four-tuple used below.

## Follow a join request beyond loopback

Our capture stays local. To understand the wider journey, imagine a client
joining match 42 and downloading its map from `assets.example`. Configuration,
name lookup, delivery, and game permission solve different parts of that trip.

### Find a destination before connecting

On a typical IPv4 LAN, **DHCP** gives a device an address lease and network
configuration; options can supply a router and DNS servers. It configures the
device, not the remote game's identity. [DHCP](https://www.rfc-editor.org/rfc/rfc2131.html)
and its [options](https://www.rfc-editor.org/rfc/rfc2132.html) specify that exchange.
Static configuration and other address-assignment systems are also possible.

**DNS** resolves a name such as `assets.example` to records including IP
addresses. A resolver can reuse an answer until its cache lifetime expires;
name resolution does not deliver the map. The client then connects to the
chosen endpoint. [DNS concepts](https://www.rfc-editor.org/rfc/rfc1034.html)
explain this separate lookup.

HTTP is the web’s request/response protocol. **HTTPS** carries that exchange
over an authenticated, encrypted connection. A **CDN** can serve a cached map
from an edge location. A cache miss may require
an origin fetch; DNS answer caching and content caching have different
lifetimes. Account requests still need their own authentication and cache
policy. [Cloudflare's request journey](https://developers.cloudflare.com/billing/understand/how-charges-accrue/)
shows these boundaries.

### Wrap the bytes across a LAN

A **LAN**, or local area network, joins nearby devices through links such as
Ethernet or Wi-Fi. In this example, an Ethernet frame carries an IP packet,
which carries a UDP datagram, which carries game bytes. This wrapping is
**encapsulation**. A switch forwards link frames; a router forwards the IP
packet onto another link with a new link frame. Physical signaling carries the
bits on each link.

The **OSI model** names seven conceptual layers: application, presentation,
session, transport, network, data link, and physical. The Internet's **TCP/IP
model** commonly groups application work, transport, Internet/IP, and link
work. These models describe responsibilities, not seven mandatory headers.
Our existing layer board remains useful: identify the job before assigning a
name. [Internet host requirements](https://www.rfc-editor.org/rfc/rfc1122.html)
organize the protocol suite by these responsibilities.

### Choose the delivery contract, then the application protocol

If middle bytes are lost, **TCP** recovers them before exposing later bytes in
its ordered stream. **UDP** can deliver a later datagram without the missing
one; the game decides whether to replace stale state or add its own recovery.
Neither transport acknowledgment proves the server accepted a purchase.
[TCP](https://www.rfc-editor.org/rfc/rfc9293.html) and [UDP](https://www.rfc-editor.org/rfc/rfc768.html)
specify those different contracts.

<Frame caption="A, B and C are illustrative byte chunks on the TCP side and whole datagrams on the UDP side. Lost B delays later TCP bytes; raw UDP supplies no automatic retry. TCP application messages still need framing. Original CC0 artwork.">
  <img src={`${import.meta.env.BASE_URL}assets/images/original/network-foundations-tcp-udp.svg`} width="480" height="496" alt="TCP receives A, loses B, buffers C, and exposes B then C after recovery. UDP receives datagram A, loses datagram B, and can deliver C without recovering B. The game must decide whether a missing datagram needs a retry or a newer replacement." loading="lazy" decoding="async" />
</Frame>

A **socket** is the local operating-system endpoint already introduced above.
A **WebSocket** is a two-way framed-message protocol, useful for browser lobby
chat. The [RFC 6455](https://www.rfc-editor.org/rfc/rfc6455.html) handshake uses
HTTP/1.1 Upgrade; `wss` protects the exchange with **TLS**, Transport Layer Security, which
authenticates the server and protects data in transit. [HTTP/3 also has a WebSocket mapping](https://www.rfc-editor.org/rfc/rfc9220.html),
so an Upgrade handshake is not universal. Game authorization remains separate.

**QUIC v1** runs over UDP but supplies its own reliable streams and loss
recovery, using TLS 1.3 for connection security. **HTTP/3** maps HTTP requests
and responses onto QUIC. Loss affecting one stream need not block unrelated
stream delivery, although streams share connection congestion limits. QUIC is
not “unreliable HTTP,” and HTTP/3 is not a synonym for every game's UDP
protocol. The standards are [QUIC v1](https://www.rfc-editor.org/rfc/rfc9000.html),
[QUIC with TLS](https://www.rfc-editor.org/rfc/rfc9001.html), and [HTTP/3](https://www.rfc-editor.org/rfc/rfc9114.html).

<MarginNote kind="clarify">A socket names an endpoint; WebSocket names a message protocol. QUIC builds reliable streams over UDP. An encrypted channel still needs game-specific identity and action checks.</MarginNote>

### Other names belong at other boundaries

Publishing the map might use [FTP](https://www.rfc-editor.org/rfc/rfc959.html),
which separates control and data connections, or [SFTP](https://man.openbsd.org/sftp),
which transfers files over encrypted SSH. SFTP is different from [FTPS](https://www.rfc-editor.org/rfc/rfc4217.html),
FTP secured with TLS. A web server might use [FastCGI](https://fastcgi-archives.github.io/FastCGI_Specification.html)
to pass requests to a persistent application worker; the player's side still
uses HTTP. **Web3** applications may use [blockchain-backed records](https://ethereum.org/en/developers/docs/dapps/),
but a ledger is not a replacement for sockets or real-time match transport.
Likewise, [Base64](https://www.rfc-editor.org/rfc/rfc4648.html) only encodes bytes:
an encoded login value has not thereby been encrypted.

With those boundaries separate, return to the controlled local capture. We can
now ask which interface, direction, and protocol layer produced each row.

## Capture answers “what crossed,” not “why”

A network trace records bytes and timing at one capture point. It does not contain the sender's variable names, the receiver's interpretation, or any record of which UI action caused which packet. That link comes from changing one thing at a time:

1. capture a quiet baseline;
2. perform exactly one distinctive local action;
3. repeat the action with one changed input;
4. compare both directions and several repetitions;
5. confirm the candidate fields in the open-source client or server.

<MarginNote kind="brief">A capture records traffic. Controlled actions and repeat comparisons connect those bytes to meaning.</MarginNote>

## Reduce noise

Filter by the known local port. Wireshark has two filter boxes, and each has its
own syntax for the same job:

<CodeGroup sync="filter">
<Tab label="Display filter (hides rows afterwards)">

```text
tcp.port == 15000
```

</Tab>
<Tab label="Capture filter (never records the rest)">

```text
tcp port 15000
```

</Tab>
</CodeGroup>

A display filter can be changed at any time, because everything was recorded. A
capture filter keeps the file small, but a packet it dropped cannot be
recovered, so use the display filter while you are still learning what to look
for.

For the Wesnoth 1.14.9 lab, keep `15000`: that is `wesnothd`’s default listening port. Launch `wesnothd.exe`, choose **Connect to Server** in the game, and enter `localhost:15000`.

Perform the actions at known times, so each burst of packets can be matched to the action just before it:

```text
00:00 connect
00:02 enter username
00:05 join lobby
00:08 send "hello-17"
00:12 disconnect
```

A distinctive message such as `hello-17` is easier to find than “hi.”

## Direction matters

One connection has one four-tuple, and each direction reads it the other way round:

```text
client IP : client port → server IP : server port
server IP : server port → client IP : client port
```

The client port is often temporary. The server port is the stable listening port.

The server first owns a **listening socket** on port `15000`. Accepting a client
creates a separate connected socket while the listener remains available for
other clients. The client normally receives an ephemeral local port selected by
Windows.

## Follow the stream

Wireshark’s “Follow TCP Stream” view reassembles TCP bytes <HoverCard kind="tip" body="To open it, right-click any packet of the connection and choose Follow, then TCP Stream. The shortcut is Ctrl+Alt+Shift+T.">for easier inspection</HoverCard>.

<MarginNote kind="alternative">Picture TCP as one long ribbon: reads cut pieces from it, while your parser identifies complete messages.</MarginNote>

<Frame caption="Follow TCP Stream shows the reassembled bytes of one connection.">

![Following a TCP stream](/assets/images/6/2/bot8.png)

</Frame>

Remember: this is still a stream, not necessarily a list of messages. Look for:

- fixed-size headers;
- length fields;
- magic bytes;
- repeated separators;
- readable text;
- compressed-looking regions;
- request/response pairs.

“Follow TCP Stream” performs reassembly for inspection. Your client still
has to handle partial reads: `read()` may return fewer bytes than requested even
when more bytes will arrive later. `read_exact` is appropriate only after a
validated frame length tells you exactly how many bytes belong to the next
piece.

Reassembly also chooses an order from sequence numbers and removes retransmitted overlap. Preserve the original packet capture alongside any exported stream fixture so later questions about direction, timing, or retransmission can still be answered.

## Export a tiny fixture

Save only the bytes for one clearly labeled action. A small binary fixture is excellent for parser tests.

```rust
#[test]
fn parses_recorded_local_chat_frame() {
    let bytes = include_bytes!("fixtures/local-chat-frame.bin");
    let message = parse_frame(bytes).expect("fixture should parse");
    assert!(matches!(message, Message::Chat { .. }));
}
```

Do not store secrets, account tokens, or other people’s traffic in fixtures.

## Compare two captures

Repeat the same action with exactly one changed input:

```text
Capture A: send "red"
Capture B: send "blue"
```

Compare lengths and differing byte ranges. If only one region changes, it may contain the text. If the whole payload changes, compression or encryption may be involved.

<MarginNote kind="narration">Changing only one input gives differences a clearer meaning than comparing two sessions where everything changed.</MarginNote>

## Identify the real Wesnoth handshake

Add this display filter so Wireshark shows client/server data rather than every TCP acknowledgement:

```text
tcp.port == 15000 && tcp.flags.push == 1
```

The first client payload in a Wesnoth 1.14.9 connection is exactly four zero bytes:

```text
00 00 00 00
```

Replay only those four bytes from a tiny TCP client. The local server responds with 41 bytes across the observed replies, proving that the zeros begin protocol negotiation. The next client frame identifies version `1.14.9`; the following frame logs in with the chosen username.

After the four-byte frame length, both of those later frames begin with gzip magic bytes `1F 8B`. For example, a captured version frame begins:

```text
00 00 00 2F  1F 8B 08 00 ...
└─ length 47 ┘  └─ gzip data
```

Do the same controlled capture with usernames `IEUser` and `FFFAAAKKKEEE`. The second name makes repeated-character compression easier to notice. Put together, the Wesnoth 1.14.9 connection works like this:

```text
target: Wesnoth 1.14.9 + local wesnothd
transport: TCP
server: 127.0.0.1:15000
negotiation: 00 00 00 00
normal frame: u32 big-endian compressed length + gzip(Simple WML)
login order: negotiation → version → username → lobby
```

## Capture facts the parser needs

A useful frame fixture records:

- the start of one frame;
- the field that gives its size, or another reliable delimiter;
- its direction;
- one input and the bytes that changed because of it.
