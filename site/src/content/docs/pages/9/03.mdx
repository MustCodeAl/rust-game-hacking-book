## Identify one surface

Lesson 9.2 changed the `build=` character-stat line in Flare's `avatar.txt` save and reloaded the character. Another stored resource controls what a game draws: an image file. We can use the same identify → copy → change one thing → reload → verify method, this time looking for a visible mark on a texture.

In the offline Urban Terror target, choose a distinctive wall, sign, or object. Walk close enough to see its texture clearly.

In that tree:

<Steps>

1. delete `env\austria\austriasky_up.jpg`;
2. copy `env\austria\austriasky_dw.jpg`;
3. rename the copy to `austriasky_up.jpg`;
4. ZIP the archive’s **contents** (`botfiles`, `env`, `fonts`, and the other root folders), not the outer work folder;
5. name the new archive `zUrT43_001.pk3` and place it in `q3ut4`.

Start a local match on `ut4_austria` and look upward. The top of the sky now uses the downward-facing image. That unmistakable result proves you found, modified, and repacked the real game resource correctly.

## Run the complete PK3 replacer

Close Urban Terror and give the tool the real archive path:

```powershell
.\target\i686-pc-windows-msvc\release\urbanterror_pk3.exe `
  "C:\Games\UrbanTerror\q3ut4\zUrT43_001.pk3"
```

The program opens the PK3 as ZIP, reads `env/austria/austriasky_dw.jpg`, rebuilds every archive entry, substitutes those bytes only for `env/austria/austriasky_up.jpg`, flushes the new archive, and atomically installs it with `ReplaceFileW`. The untouched original becomes `zUrT43_001.pk3.gha-backup`, and the tool refuses to replace any other PK3 name or overwrite that backup.

The full implementation is [`urbanterror_pk3.rs`](/windows-labs/src/bin/urbanterror_pk3.rs). It uses the current `zip` crate API documented through Context7 and the shared Windows replacement helper in [`file_replace.rs`](/windows-labs/src/windows_impl/file_replace.rs).

<Accordion title="Complete lab source: urbanterror_pk3.rs">

<GitHub path="windows-labs/src/bin/urbanterror_pk3.rs" />

```rust
#[cfg(windows)]
fn main() -> anyhow::Result<()> {
    use std::{
        fs::{self, File},
        io::{Read, Write},
        path::{Path, PathBuf},
    };

    use anyhow::Context;
    use gha_windows_labs::replace_file_with_backup;
    use zip::{ZipArchive, ZipWriter, write::SimpleFileOptions};

    const UP: &str = "env/austria/austriasky_up.jpg";
    const DOWN: &str = "env/austria/austriasky_dw.jpg";
    const MAX_SKY_FACE: u64 = 32 * 1024 * 1024;

    fn read_down_face(path: &Path) -> anyhow::Result<Vec<u8>> {
        let mut archive = ZipArchive::new(File::open(path)?)?;
        let mut entry = archive
            .by_name(DOWN)
            .with_context(|| format!("{DOWN} is missing from the PK3"))?;
        anyhow::ensure!(
            entry.size() <= MAX_SKY_FACE,
            "sky image is unexpectedly large"
        );
        let mut bytes = Vec::with_capacity(usize::try_from(entry.size())?);
        entry.read_to_end(&mut bytes)?;
        anyhow::ensure!(!bytes.is_empty(), "downward sky image is empty");
        Ok(bytes)
    }

    let path = PathBuf::from(
        std::env::args()
            .nth(1)
            .context("usage: urbanterror_pk3 <path-to-zUrT43_001.pk3>")?,
    );
    anyhow::ensure!(
        path.file_name()
            .is_some_and(|name| name == "zUrT43_001.pk3"),
        "this lab accepts only zUrT43_001.pk3"
    );
    let replacement = read_down_face(&path)?;
    let temporary = path.with_extension("pk3.gha-new");
    let backup = path.with_extension("pk3.gha-backup");
    anyhow::ensure!(!temporary.exists(), "temporary PK3 already exists");

    let mut archive = ZipArchive::new(File::open(&path)?)?;
    let output = File::create(&temporary)?;
    let mut writer = ZipWriter::new(output);
    let mut replaced = 0_usize;

    for index in 0..archive.len() {
        let mut entry = archive.by_index(index)?;
        let name = entry.name().to_owned();
        let options = SimpleFileOptions::default()
            .compression_method(entry.compression())
            .unix_permissions(entry.unix_mode().unwrap_or(0o644));

        if entry.is_dir() {
            writer.add_directory(name, options)?;
            continue;
        }
        writer.start_file(&name, options)?;
        if name == UP {
            writer.write_all(&replacement)?;
            replaced += 1;
        } else {
            std::io::copy(&mut entry, &mut writer)?;
        }
    }
    anyhow::ensure!(replaced == 1, "expected one {UP} entry, found {replaced}");
    let output = writer.finish()?;
    output.sync_all()?;

    if let Err(error) = replace_file_with_backup(&path, &temporary, &backup) {
        let _ = fs::remove_file(&temporary);
        return Err(error);
    }
    println!(
        "Replaced {UP} with {DOWN}. Original archive saved at {}.",
        backup.display()
    );
    Ok(())
}

#[cfg(not(windows))]
fn main() {
    eprintln!("This PK3 replacement lab uses ReplaceFileW and must run on Windows.");
}
```

</Accordion>

The loop rebuilds every entry instead of modifying ZIP bytes in place. Only the exact `UP` path receives replacement bytes, and `replaced == 1` catches both “wrong archive” and “duplicate path” mistakes before Windows installs anything.

## Inspect image metadata

The `image` crate can load common formats:

```toml
[dependencies]
anyhow = "1"
image = "0.25"
```

With those dependencies in `Cargo.toml`, this function opens one image and
prints its dimensions and color format. The result tells you whether the file
still has the properties the game expects before you replace an asset.

```rust
use image::GenericImageView;
use std::path::Path;

fn inspect_texture(path: &Path) -> anyhow::Result<()> {
    let image = image::open(path)?;
    let (width, height) = image.dimensions();
    println!(
        "{}: {width}×{height}, {:?}",
        path.display(),
        image.color()
    );
    Ok(())
}
```

Some game-specific formats need dedicated tools. Do not rename a PNG to another extension and assume the bytes changed format.

## Create a marked copy

A tiny marker in one corner is enough to prove which image the game loaded,
without redesigning the whole texture. This function takes an RGBA image,
limits the marked square to 16 pixels on either side, and returns the changed
copy for the reversible archive replacement:

```rust
use image::{Rgba, RgbaImage};

fn add_corner_marker(mut image: RgbaImage) -> RgbaImage {
    let width = image.width().min(16);
    let height = image.height().min(16);

    for y in 0..height {
        for x in 0..width {
            image.put_pixel(x, y, Rgba([255, 64, 32, 255]));
        }
    }
    image
}
```

The marker is orange-red, <Color value="rgb(255, 64, 32)" />: red 255, green 64, blue 32, with alpha 255 (fully opaque). Write to a new path first and compare dimensions and color type.

## Loose files and archives

Some engines prefer a loose file over the same path inside an archive. Others require rebuilding the archive.

If extracting:

- keep the directory structure;
- reject absolute and parent-traversal paths;
- preserve the original archive;
- change one entry only;
- use the engine’s official packer when available.

## Texture coordinates explain repetition

A model stores UV coordinates that map its surface to the image. One texture can repeat, rotate, or cover many surfaces. Changing the image may affect more places than the one you first noticed. If the replacement appears upside down, the file and the engine disagree about which edge `v = 0` names (Lesson 7.1).

A coordinate outside 0 to 1 is handled by the texture's **addressing mode**. With *repeat*, `u = 2.5` is treated as 0.5, so the image tiles. With *clamp*, it is treated as 1.0, so the edge pixels smear outward.

## Models: reading a glTF file

A texture is one image. A 3D model is several arrays of numbers plus the rules that join
them. **glTF** is an open format for 3D models and scenes from the Khronos Group, the same
group that maintains OpenGL, and it is a good example because it is plain about its own
structure. A glTF model is a **JSON** description of what is in the model, in `.gltf` text
with its binary data alongside, or all packed in one `.glb` file. Reading it is the
two-stage parse from Lesson 9.1: first check that the bytes are valid JSON of the right
shape, then check that what the JSON says makes sense.

The JSON is a set of lists that point at each other by position. The smallest useful model
is one triangle:

```json
{
  "asset": { "version": "2.0" },
  "scene": 0,
  "scenes": [ { "nodes": [ 0 ] } ],
  "nodes": [ { "mesh": 0, "translation": [ 0, 2, 0 ] } ],
  "meshes": [ { "primitives": [ { "attributes": { "POSITION": 1 }, "indices": 0 } ] } ],
  "buffers": [ { "uri": "triangle.bin", "byteLength": 44 } ],
  "bufferViews": [
    { "buffer": 0, "byteOffset": 0, "byteLength": 6,  "target": 34963 },
    { "buffer": 0, "byteOffset": 8, "byteLength": 36, "target": 34962 }
  ],
  "accessors": [
    { "bufferView": 0, "componentType": 5123, "count": 3, "type": "SCALAR" },
    { "bufferView": 1, "componentType": 5126, "count": 3, "type": "VEC3",
      "min": [0, 0, 0], "max": [1, 1, 0] }
  ]
}
```

Follow the chain from the top. The scene lists node 0. Node 0 holds mesh 0, and moves it 2
units up with a `translation` (a node can also have a rotation, stored as a quaternion
from Lesson 7.1, a scale, and children, which is the parent and child arrangement of
Lesson 7.1). The mesh's one primitive says its vertex positions are in accessor 1 and its
indices are in accessor 0. An **accessor** says how to read a stretch of bytes: accessor 1
is `VEC3` (three numbers per item) of `componentType` 5126 (a 4-byte float), `count` 3, so
each vertex is 3 × 4 = 12 bytes and the three vertices take 3 × 12 = 36 bytes. Accessor 0
is `SCALAR` of 5123 (a 2-byte unsigned integer), count 3, which is 3 × 2 = 6 bytes, the three
indices. A **buffer view** is a slice of the buffer: view 0 is bytes 0 to 6 and view 1 is
bytes 8 to 44, because the indices are padded with 2 bytes so that the floats start on a
4-byte boundary. The buffer is 8 + 36 = 44 bytes in all.

Because a model file is untrusted input, a loader checks every one of those links. Does
the accessor name a buffer view that exists? Does its offset plus `count` × item size fit
inside that view? Accessor 1 needs 0 + 36 = 36 bytes and its view is 36 long, so it fits. A
file that claims `count` 1,000,000 for the same view needs 1,000,000 × 12 = 12,000,000
bytes, and must be rejected before anything is allocated or read.

The rest of a model hangs off the same pattern: **materials** (colours, textures, and
whether the surface is opaque, cut out, or blended, as Lesson 7.2 explained), **skins**
(the skeleton, with the bone indices and weights of Lesson 7.6), **animations** (lists of
times and values for a node's translation, rotation, or scale, played with the
interpolation of Lesson 4.7), and free-form **extras** where a game can store its own data.
A scene viewer is a tool that does nothing but load such a file and show it, which is the
quickest way to see what a model contains.

## Sounds: samples, mixing, and position

A sound is stored as a list of **samples**, measurements of the sound wave taken many
times a second. CD-quality audio takes 44,100 samples a second for each of 2 channels
(left and right), each sample 2 bytes. That is 44,100 × 2 × 2 = 176,400 bytes a second, or
10,584,000 bytes, about 10 MiB, a minute. A three-minute song would take about 30 MiB, so
music is stored compressed (Ogg Vorbis and MP3 are common) and **streamed**, decoded a
chunk at a time, while a short sound effect is decoded once and kept in memory.

Several sounds play at once, but the sound card takes one stream, so the engine **mixes**
them: for every sample it adds the playing sounds' samples, each scaled by its own volume.
With samples running from −1 to 1, two sounds at 0.7 and 0.6 add to 1.3, which is past the
limit, so it is cut to 1.0 and the sound distorts. Engines lower volumes or add a limiter
to avoid that.

The sound card asks for audio in small buffers. A buffer of 1,024 samples at 44,100 samples
a second lasts 1,024 ÷ 44,100 = 0.0232 seconds, about 23 ms. If the engine has not filled
the next one by then, the listener hears a click. So audio runs on its own thread with its
own deadline, apart from the frame loop, as Lesson 11.8 describes.

Some properties are simple to compute:

- **Pitch.** Playing samples faster raises the pitch: a rate of 2.0 is an octave higher, since
  every frequency doubles. A pure test tone of 440 hertz is generated as `sin(2π × 440 × t)`,
  and at 44,100 samples a second one cycle is 44,100 ÷ 440 ≈ 100 samples long.
- **Position.** A sound that comes from a place gets quieter with distance, say by
  `1 ÷ distance`, and is placed left or right by the dot product (Lesson 4.7) of the
  direction to it with the listener's right-hand direction. With the listener facing `+y`,
  so that right is `+x`, a sound at `(3, 4, 0)` is 5 away, in the direction `(0.6, 0.8, 0)`, so
  its pan is 0.6, to the right, and its loudness is 1 ÷ 5 = 0.2. Splitting that between the
  ears by `(1 − pan) ÷ 2` and `(1 + pan) ÷ 2` gives a left volume of 0.2 × 0.2 = 0.04 and a
  right volume of 0.2 × 0.8 = 0.16.
- **Triggers.** A sound effect usually plays in response to an event, such as "coin 42 was
  collected" (Lesson 1.3). The music follows the game's state, and changing tracks is a
  cross-fade like the animation blend of Lesson 7.6: halfway through a 2-second fade, the old
  track is at volume 0.5 and the new one at 0.5.

### Two ears and falloff

The pan above gives a single number for left and right. A **spatial audio** mode instead
puts two ears on the listener, a fixed gap apart along its right-hand direction, and
works out the volume at each ear from that ear's own distance. Take a gap of 2, so the
ears are at `(−1, 0, 0)` and `(1, 0, 0)`, and the same sound at `(3, 4, 0)`. The left ear
is `√((3 − (−1))² + 4²) = √32 = 5.66` away and the right ear is
`√((3 − 1)² + 4²) = √20 = 4.47` away. With the `1 ÷ distance` rule the left ear hears
1 ÷ 5.66 = 0.177 and the right ear 1 ÷ 4.47 = 0.224. The right ear is louder by a factor
of 0.224 ÷ 0.177 = 1.26, much less than the factor of 4 (0.16 ÷ 0.04) that the simple
pan gave, because two ears this close together differ little in distance.

How quickly a sound fades with distance is its **falloff**. Two common choices, for a
sound that plays at full volume out to 1 unit and, for the linear one, reaches silence
at 50 units:

<Panel title="Two falloff curves">

| Distance | Inverse: `1 ÷ d` | Linear: `1 − (d − 1) ÷ 49` |
|---|---|---|
| 5 | 1 ÷ 5 = 0.2 | 1 − 4 ÷ 49 = 0.92 |
| 10 | 1 ÷ 10 = 0.1 | 1 − 9 ÷ 49 = 0.82 |
| 50 | 1 ÷ 50 = 0.02 | 1 − 49 ÷ 49 = 0 |

</Panel>

Inverse falloff halves the volume each time the distance doubles, and it never reaches
silence, so a game also sets a distance beyond which the sound is not mixed at all,
which saves the work. Linear falloff stays loud nearby and reaches 0 exactly at its
limit.

Like a texture, a replacement sound has to match what the game expects: the same path and
format, and usually the same sample rate and channel count.

## Package as a mod

Prefer a mod directory containing only the changed file and a short manifest:

```text
name: orange-corner-texture
target: Urban Terror 4.3.4
source path: textures/example/wall.tga
original sha256: ...
changes: 16×16 orange marker in top-left
uninstall: remove the mod folder
```

Do not redistribute original copyrighted assets when a small patch, generated replacement, or installation script is enough.
