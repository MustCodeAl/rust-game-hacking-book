## Start from behavior

Use offline, 32-bit Wesnoth 1.14.9. Find the current player's gold again and
set a write breakpoint on its four bytes. Instead of recruiting, end a turn
so income changes that value.

<Frame caption="Wesnoth's income display at the end of a turn.">

![Wesnoth’s income display](/assets/images/2/9/wesnoth1.png)

</Frame>

When the breakpoint fires, inspect the instruction that reached the gold field. In the 32-bit Wesnoth 1.14.9 build used by this book, income reaches:

<Frame caption="The breakpoint fires on the instruction that adds income.">

![A breakpoint triggered by income](/assets/images/2/9/wesnoth2.png)

</Frame>

```nasm
009B4D00  add dword ptr [eax+4], edx
```

Read that line like a sentence: “add the income in `edx` to the 32-bit number four bytes after the object in `eax`.” `eax` points at the current side record, `eax + 4` is its gold field, and `edx` contains the income.

These addresses are exact only for Wesnoth 1.14.9 32-bit. If your instruction differs, use your build’s values instead of forcing these numbers onto it.

## Trace the object pointer

Set a breakpoint on the call above the income write. At entry, `eax` is zero; after stepping over the call, it holds the side-record pointer. Step into that call on the next turn. The useful path begins with:

```nasm
mov eax, dword ptr [ecx+60]
; later, follow that pointer and add 0xA90
; the gold field is another 4 bytes into the side record
```

At `0x009AE7F7`, read `ecx`. Restart Wesnoth, recreate the same local match, and break there again. In this book’s build, `ecx` remains `0x017EECB8`. The complete path is:

```text
[[0x017EECB8 + 0x60] + 0xA90] + 0x4
```

Because `0x017EECB8 + 0x60` is `0x017EED18`, later labs use the shorter form:

```text
[[0x017EED18] + 0xA90] + 0x4
```

Square brackets mean “read the pointer stored here.” A plus sign means “move this many bytes from that address.”

<MarginNote kind="alternative">Read the path like treasure-map directions: go to the first spot, read the note there, follow it, then take a few steps along.</MarginNote>

## A pointer path is a route through an object graph

Each dereference moves from one object to another. The observed root
`0x017EED18` is an **absolute address for the pinned course build**, not an
RVA. Confirm that it still points into the expected module in your run. A
portable profile would store the root's RVA and first discover the module's
current base, as Lesson 2.7 explained. The heap objects reached afterward may
move between runs, which is why the path reads their current addresses rather
than saving yesterday's final address.

A path is stable only under stated conditions. It may depend on:

- the exact executable build;
- a local match being active;
- the current player or side object existing;
- the same layout and pointer width;
- each intermediate page being readable at the moment of use.

Validate every edge, not only the final gold. A non-null pointer can still be stale or point to the wrong object. Check module ranges, page protections, alignment, and a few field invariants before trusting the final value.

<MarginNote kind="brief">A pointer path is a route through objects. Check every step, not only the final value, and note the conditions it depends on.</MarginNote>

## Restart tests

One successful run proves very little. Test:

<Steps>

1. close Wesnoth completely;
2. start it again;
3. begin a new local match;
4. confirm the pointer entry resolves;
5. repeat at least three times.

</Steps>

Also test a state where no match is active. A good tool should report “player object unavailable,” not crash or read address zero.

## Write the algorithm before the API

The code follows this plain algorithm:

```text
read the 32-bit pointer stored at 0x017EED18
if it is null, stop with a useful error
add 0xA90 and read the next 32-bit pointer
if it is null, stop with a useful error
add the final gold-field offset
read the 32-bit gold value
```

We can model failures precisely:

```rust
#[derive(Debug)]
enum ResolveError {
    ModuleNotFound,
    NullPointer { step: usize },
    AddressOverflow,
    ReadFailed { address: usize },
}
```

Here is the resolver without any Windows API noise. `read_u32` can use `ReadProcessMemory` in an external tool or direct reads inside an injected DLL:

```rust
const PLAYER_ROOT: usize = 0x017E_ED18;
const GAME_OFFSET: usize = 0xA90;
const GOLD_OFFSET: usize = 0x4;

fn wesnoth_gold_address(
    mut read_u32: impl FnMut(usize) -> Result<u32, ResolveError>,
) -> Result<usize, ResolveError> {
    let player = read_u32(PLAYER_ROOT)? as usize;
    if player == 0 {
        return Err(ResolveError::NullPointer { step: 0 });
    }

    let game_slot = player.checked_add(GAME_OFFSET)
        .ok_or(ResolveError::AddressOverflow)?;
    let side = read_u32(game_slot)? as usize;
    if side == 0 {
        return Err(ResolveError::NullPointer { step: 1 });
    }

    side.checked_add(GOLD_OFFSET)
        .ok_or(ResolveError::AddressOverflow)
}
```

The `Result` type makes failure data we must handle, not a surprise we hope never happens.

## What counts as “stable”

The path is stable only for the target version and states you tested. The
absolute root in this example also depends on the module loading where it did
in the verified course run; a relocated module requires base-plus-RVA
resolution. Game updates can change layouts and offsets. Document:

- game version and architecture;
- module name;
- offsets in traversal order;
- the expected final type;
- how many restarts passed;
- known states where the chain is unavailable.
