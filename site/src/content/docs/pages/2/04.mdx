## Find the instruction that changes gold

In the previous memory lab, we found the current gold. Now we want to know:

> Which instruction subtracts the price of a recruited unit?

Use the same offline Wesnoth 1.14.9 target and restore your clean VM snapshot before starting.
For a concrete run, suppose you start at 100 gold and recruit a unit
costing 15. The expected result is 85. Use the actual price and gold
shown in your match when checking the paused instruction.

The bytes in the dump are little-endian. If the gold is `100`, the 32-bit value `0x00000064` appears as:

```text
64 00 00 00
```

The least-significant byte comes first.

## Break on writes

Set a hardware breakpoint on **write**, covering four bytes at the gold address.
The lesson uses x64dbg, but any debugger that can watch an address will do:

<Tabs sync="debugger">
<Tab label="x64dbg">

Select the four bytes in the dump, right-click, and choose **Breakpoint**, then
**Hardware, Write**, then **Dword**.

</Tab>
<Tab label="WinDbg">

Type `ba w4` followed by the address, for example `ba w4 0A3C1230`, to break on a
four-byte write. Then type `g` to let the game run.

</Tab>
<Tab label="Cheat Engine">

Right-click the gold entry in the address list and choose **Find out what writes
to this address**. Cheat Engine lists each instruction that writes it, with a
count.

</Tab>
</Tabs>

A hardware memory breakpoint does not replace the game’s instruction bytes.
The debugger programs special CPU debug registers with an address, access type,
and width. When an instruction writes across that watched range, the CPU raises
a debug exception and Windows reports it to the debugger.

The width matters. Gold is believed to be a four-byte value, so watch all four
bytes. Watching one byte can still trigger, but it hides whether the game wrote
the complete integer or only part of it.

This breakpoint watches a **data address**, not one fixed instruction. If three
different functions write gold, the same watch can reveal all three. A software
breakpoint placed on a code address answers the opposite question: “When does
this exact instruction execute?”

<MarginNote kind="brief">Watching a data address finds every writer of a value. A code breakpoint tells you when one particular instruction runs.</MarginNote>

<Frame caption="Select the four bytes, right-click, then Breakpoint, Hardware, Write, Dword.">

![Setting a write breakpoint on gold](/assets/images/2/4/reversing8.png)

</Frame>

Resume the game and recruit one unit. The debugger should pause close to an instruction that resembles:

```nasm
sub dword ptr [reg+offset], eax
```

Do not copy the exact register or offset from this page. Read the
instruction in your own debugger. A hardware data breakpoint can report
an access after the instruction has run, so the highlighted next
instruction may not be the one that wrote gold. Use the breakpoint's
access information and nearby disassembly to identify the triggering
write, then confirm that its calculated destination is your gold
address. Builds and runs can differ.

## Ask the five assembly questions

Apply the five questions to the paused instruction:

1. **What is read?** The current gold and the price in a register.
2. **What is written?** Four bytes at the gold field.
3. **How many bytes?** `dword ptr` means 32 bits.
4. **Signed or unsigned?** Test nearby comparisons before deciding.
5. **Where next?** The following instruction unless a branch changes the path.

Now compare the price register with the unit’s price. In the example
run, it should be 15 and the destination should be the gold address
that changed from 100 to 85. Matching both is stronger evidence than
recognizing `sub` alone.

## Read an instruction as state transition

For `sub dword ptr [reg+offset], eax`, the complete before-and-after effect is:

```text
address = register value + offset
old = 32-bit value read from address
new = old - low 32 bits of eax
store new at address
update arithmetic flags
```

That last line matters. Later branches may inspect zero, sign, carry, or overflow flags. Replacing the subtraction changes both the stored gold and those flags. Before a temporary patch, step forward and check whether nearby conditional jumps consume them.

The effective address calculation does not dereference `reg` and then add an offset to the loaded value. It adds the offset to the register first, then reads memory at the resulting address. Keep “calculate an address” separate from “read the value at that address.”

## Read the brackets as an address calculation

For an instruction such as:

```nasm
sub dword ptr [esi+30h], eax
```

read it from the inside outward:

1. take the address currently stored in `esi`;
2. add hexadecimal offset `0x30`;
3. treat the four bytes at that final address as the destination;
4. subtract the lower 32 bits of `eax` from that destination;
5. store the result back to the same four bytes;
6. update CPU flags for later branches.

The bracketed expression accesses memory. Without brackets, `esi+30h` would be
an address calculation rather than a read or write of the bytes at that
address.

Read the live value of `esi` in the register panel and add `0x30` yourself. For
example, if `esi` holds `0x0A3C1200`, the destination is
`0x0A3C1200 + 0x30 = 0x0A3C1230`. If the sum equals the candidate gold address,
this instruction writes the gold you found.

<MarginNote kind="alternative">Think of the register as where a street starts and the offset as the house number along it. Add them to find the door, then read what is inside.</MarginNote>

Copy the original instruction bytes first, so you can write them back. Then temporarily replace the **entire** subtraction instruction with <HoverCard kind="example" body="The length comes from the encoding. `sub [edx+4], eax` is the three bytes `29 42 04`, so it takes three `90` bytes. `sub [edx+0x1234], eax` is the six bytes `29 82 34 12 00 00`, so it takes six. The disassembly's bytes column shows the count.">the same number of `nop` bytes</HoverCard>.

## Turn one discovery into a repeatable patch

Our tools will not hardcode “whatever address worked once.” They will:

1. open the controlled process;
2. locate a module or scan a known pattern;
3. confirm the expected original bytes;
4. apply a temporary patch;
5. restore the bytes on exit.

Checking the original bytes is crucial. Refusing to patch an unknown version is safer than writing to the wrong place.
