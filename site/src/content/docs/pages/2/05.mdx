Finding one instruction is useful. Understanding the surrounding feature is better.

## Start from a known anchor

In an offline Wesnoth 1.14.9 match, recruiting a unit reduces the player's
four-byte gold value by that unit's price. The instruction that writes the
reduced gold is our **anchor**. Set a code breakpoint on the instruction you
verified in the debugger, recruit one unit, and let the breakpoint fire.

The current function probably handles a small part of recruitment. To discover who asked for that work, look at the call stack or run until the function returns.

Now you are back in the caller. Repeat this carefully to move from the low-level write toward the broader decision that requested it.

## Why the caller is visible

When x86 executes `call`, it places a return address on the stack before jumping to the callee. That address points to the instruction the caller expects to run next. A debugger’s call stack combines return addresses with known module ranges and function information to show the nested route that reached the breakpoint.

The call stack a debugger shows is a reconstruction, and it may be incomplete. Optimizations can inline functions, reuse stack space, or omit traditional frame pointers. Confirm an important caller by returning to it or placing a breakpoint at its call site and reproducing the action.

## Establish context by following the observed call chain

Here, **establishing context** means connecting a stored change to the
specific player, requested action, operands, and checks that caused it.
At the gold write, knowing “subtract 25” is incomplete: is that an item
price, a fine, or a different player's payment?

The original course called the move from a small helper toward its callers
**bubbling**. Treat that name as a method, not a promise that every caller
has a recoverable source name. Record each confirmed level:

**Context cheatsheet:** keep these levels together when following a write toward its callers.

| Level | Question it can answer | Evidence to keep |
| --- | --- | --- |
| Gold write | Which field changed, and by how much? | Receiver address, amount, before/after values |
| Spending helper | Which check allowed the subtraction? | Taken comparison and its operands |
| Purchase handler | What did the amount mean? | Item price passed to the helper |
| Action dispatcher | What requested this handler? | Selected command and matching call site |

Reproduce one action, confirm its write, inspect the caller, and repeat until
you can explain that action. Compare a second action that shares the helper:
it can reach the same write for a different reason. A breakpoint above the
shared helper needs that caller context to distinguish them.

<CodeTrace trace="original-bubbling" />

The final steps inspect a recorded path; they do not rewind or repeat a
purchase. In a live debugger, **Run until return** executes the rest of the
current function. **Step over** executes a call and pauses after it returns;
**Step into** follows its executed instructions. None undoes previous writes.
Note the current values again after running, and distinguish an inferred call
stack from a call site you reproduced. Inlining and tail calls can remove an
ordinary call/return boundary.

<MarginNote kind="brief">Bubbling follows confirmed callers toward the action. Keep the player, arguments, checks, and result together so one shared helper is not mistaken for one feature.</MarginNote>

## Recognize dispatcher code

Menus often use a chain of comparisons:

```nasm
cmp eax, MENU_RECRUIT
je handle_recruit
cmp eax, MENU_DESCRIPTION
je show_description
cmp eax, MENU_CANCEL
je close_menu
```

The constants will not have friendly names in the debugger. You create those names from experiments.

Triggering one menu item at a time shows which branch each one takes. In one run
of this book's build:

```text
Action: Recruit
Compared value: 3
Taken destination: 0x00CC_A140

Action: Terrain description
Compared value: 5
Taken destination: 0x00CC_AF20
```

Those destinations belong to one run of one build, and yours will not match.
What carries over is the shape: two actions, two constants, two different
branch targets, all from the same comparison chain.

<CodeTrace trace="menu-dispatch" />

Once each constant is matched to an action, the anonymous numbers become an
enum:

```rust
#[repr(u32)]
enum MenuAction {
    Recruit = 3,
    TerrainDescription = 5,
}
```

The enum is your model, not a claim about the original source type.

<MarginNote kind="narration">Your names for 3 and 5 come from experiments, so they are a working model. If a new test breaks the model, rename it.</MarginNote>

The comparison value alone is not enough. Where it came from matters: a register, a stack argument, or a field inside a menu object, and whether another branch changed it before the dispatcher. Those details distinguish “menu command ID” from a temporary loop counter that merely happened to equal `3`.

## Separate “where” from “why”

The gold instruction tells you **where** a change happens. The menu dispatcher tells you **why** execution reached it.

That distinction matters:

- patching the subtraction changes the stored cost result;
- changing a branch may select a different feature;
- hooking the dispatcher lets you observe every menu action.

Do not make all three changes at once. Test one layer at a time.

This is also a lesson about **abstraction levels**. The subtraction is a low-level side effect. The recruitment function groups validation and side effects into one operation. The dispatcher chooses among operations. Moving upward explains more behavior but also adds more unrelated branches, so stop when the original question is answered.

<MarginNote kind="brief">The write shows where gold changes, and the callers show why. Stop climbing once you can answer your question.</MarginNote>

## Follow dependencies, not just nearby instructions

“Backward” does not simply mean scrolling upward in the disassembly. It means following the facts that had to be true for the anchor instruction to run.

- A **data dependency** asks where an operand came from. If `eax` is the price, find the instruction or argument that produced `eax`.
- A **control dependency** asks which comparison allowed this block to run. If a branch skipped the subtraction, determine what value controlled that branch.
- A **call dependency** asks which caller requested this operation and what arguments it supplied.

Compilers can move calculations away from the source statement that inspired them. The instruction immediately above the anchor may be unrelated, while the important value was loaded twenty instructions earlier or passed by the caller. Track one value and one decision at a time.

A practical stopping condition is: stop tracing callers when you can name the input, the decision, and the observable result in plain English. Going farther may reveal the whole menu framework, but it no longer answers the focused gold question.

<MarginNote kind="alternative">Think of tracing a delivery: who ordered it is the caller, where the goods came from is data, and which check let it ship is the branch.</MarginNote>

### The three questions, asked once

Put the anchor from Lesson 2.5 back on screen and ask all three of them about
it. Writing `sub dword ptr [esi+0x30], eax` in the middle, each question pulls
in a different direction:

```text
        call dependency          who asked for this work?
                 |               (the caller, and what it passed)
                 v
   data  -->  sub [esi+0x30], eax  <--  control
  where did                             which comparison let
  esi and eax                           this line run at all?
  come from?
```

They are genuinely different searches, and the answers usually live in
different places. `eax` may have been loaded two instructions above, or handed
in by the caller and untouched since. `esi` is the one that matters most here:
find where it was set and you have the object the field belongs to, which is
the whole of Lesson 2.8. The comparison that guarded the block may sit
immediately above, or in the caller, having already decided this purchase was
affordable before the call was made.

Answering them one at a time matters. The common way to get lost is to chase `eax` upward, notice an interesting branch
on the way, follow that instead, and end up unable to say which question you
were answering.

Use x64dbg’s restore command after every temporary patch.

3. no stale breakpoint remains.

## A plain-English function sketch

The recovered behavior fits in a few lines of pseudocode:

```text
when the player chooses a menu item:
    if it is Recruit:
        check the tile
        check the price
        create the unit
        subtract gold
    otherwise:
        run the matching menu action
```

Pseudocode separates the idea from register names and addresses, so the same sketch describes the function in any build even though every address changes. Parts whose purpose is not known yet can keep neutral names instead of invented ones:

```text
if candidate_action == 3:       # Recruit in all three trials
    check unknown_flag          # the branch exists; its purpose is unknown
    call create_unit_candidate  # a unit appeared every time this ran
    subtract gold
```

## From a write to a menu action

The gold write supplied a known starting instruction. Its return address and
call stack led to the caller; recruiting and opening Terrain Description
supplied contrasting cases for the menu branch. The small pseudocode model
names only behavior those cases supported. That route from an observed write
to a caller, branch, and named action also works when the compiler has removed
the original source names.

That explanation identifies the action and its checks, but the address of its instruction still belongs
to one run. The next question is how to find the same game state after a restart:
why addresses move, and which relationships between objects can survive the
move. Once those are clear, we can return to changing control flow itself.
