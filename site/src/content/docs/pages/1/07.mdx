Before using a scanner or debugger on the course game, set up a place
where the game, tools, and starting conditions can be repeated. This
lets you tell a real game change from a difference in the environment.

Use a separate Windows virtual machine for the book. A **virtual machine** (VM)
is a computer simulated inside your main computer. It can run its own copy of
Windows and can be reset without reinstalling your everyday system.

## Why the VM is useful

A VM gives the experiments a controlled environment:

- old game builds and debugging tools stay separate from personal files;
- a snapshot can restore a known state after a crash or bad configuration;
- the Windows and tool versions stay fixed, so results repeat;
- optional connections to the host can stay disabled until needed.

A snapshot is not a security guarantee and does not make every action harmless.
It is a recovery point. Test that you can restore it before depending on it.

<MarginNote kind="brief">A VM with snapshots is an undo button for experiments. It is a recovery point, not a force field, so test the restore.</MarginNote>

The same caution covers what you bring into the VM. A program can do exactly
what it advertises and something else at the same time: a "free trainer" that
really does give you gold while it quietly copies the passwords saved in your
browser. That is called a **trojan**, after the wooden horse, and it is one of
the most common ways players lose accounts, because the cheat working is exactly
what makes people trust it. Every tool in this book comes from its official
project page or is one you build yourself.

## Create the Windows VM

<HoverCard kind="recommendation" body="This lesson’s screenshots and `VBoxManage` commands use VirtualBox, so its menus match what you see here. VMware and Hyper-V work too, but you then find the matching menu yourself.">VirtualBox</HoverCard>, VMware, or Hyper-V can work. A practical starting configuration is:

- 2 or more virtual CPU cores;
- 4–8 GB of RAM;
- about 50 GB of storage;
- graphics acceleration if a target game requires it.

Install Windows, apply updates, and create a normal user account. Run an
individual tool with additional rights only when its operation requires them.

Keep shared folders, clipboard sharing, drag-and-drop, and USB passthrough off at
first. Enable a connection only when you need it and know what crosses it.

Inside the VM, install:

4. <HoverCard kind="reference" href="https://www.cheatengine.org/" body="A memory scanner and debugger, used here for the first scans. Read each installer screen, and decline any offer of extra software.">**Cheat Engine**</HoverCard> for the first value-scanning lessons;
5. <HoverCard kind="reference" href="https://www.wireshark.org/" body="A free tool that records and displays network traffic. The networking lessons later in the book use it on your own computer.">**Wireshark**</HoverCard> for later local network captures;
6. <HoverCard kind="reference" href="https://git-scm.com/" body="The version-control tool. The labs expect the course repository at one exact revision, so your results match the lessons.">Git</HoverCard>, so you can use the exact course source revision.

Open PowerShell and check the compiler tools:

```powershell
rustc --version
cargo --version
```

Then verify that a tiny program builds:

```powershell
cargo new first_lab
cd first_lab
cargo run
```

You should see `Hello, world!`. If this step fails, fix the toolchain before
adding debuggers, games, or course code to the problem.

## Install the 32-bit Windows target

The specific Wesnoth, AssaultCube, Urban Terror, Wyrmsun, and Flare builds used
in the historical lessons are 32-bit Windows programs.

```powershell
rustup target add i686-pc-windows-msvc
```

Read the target name in parts:

- `i686` — 32-bit x86 instructions and plain pointers, which store
  32-bit addresses;
- `pc-windows` — Windows is the target operating system;
- `msvc` — use Microsoft's Windows ABI and linker toolchain.

Code loaded *inside* a process must match that process's architecture. A 64-bit
DLL cannot be loaded into a 32-bit game. Later code changes, register choices,
stored-address widths, and calling conventions also depend on the architecture.

<MarginNote kind="alternative">Think of plugs and sockets: a 64-bit DLL is a plug that will not fit a 32-bit game's socket, however well it is made.</MarginNote>

An external tool can sometimes have a different bitness because Windows copies
bytes across the process boundary. The course keeps its Windows labs 32-bit so
addresses and machine-code examples stay consistent. For another game build,
inspect its executable and choose the matching target instead of copying this
choice blindly.

From the repository
root, run:

```powershell
cd windows-labs
cargo check --target i686-pc-windows-msvc --all-targets
```

`cargo check` parses and type-checks the programs without producing a final
optimized build. It is the fastest first check for a compiler or dependency
problem.

The workspace uses the `windows` crate for typed Windows API declarations and
`anyhow` to attach useful context to errors. Cargo reads those dependencies from
`Cargo.toml`; you do not need to copy a long feature list from the lesson.

When a lesson needs an executable or DLL, build the release version:

```powershell
cargo build --release --target i686-pc-windows-msvc
```

That command produces a 32-bit Windows build even if the development VM is
64-bit. If it fails, the first error tells you whether the target toolchain,
project code, or a Windows library needs attention; a successful build alone
does not prove the tool can attach to the course game.

## Four Cargo commands you will use often

```powershell
cargo check   # Find type and API errors quickly
cargo run     # Build and run one program
cargo test    # Run automated checks
cargo fmt     # Apply the standard code format
```

Read the first compiler error before later errors. One missing type or bracket
can cause many follow-up messages.

## Create recovery snapshots

Take at least two snapshots:

- **Clean Windows** — after Windows updates, before the lab tools;
- **Ready for lessons** — after tools, the 32-bit target, and course code work.

Name snapshots by what they contain. A date alone does not explain which state
is safe to restore.

## A snapshot rewinds one VM; a clone creates a second VM

Use a **snapshot** to return one VM to recorded files and settings. Use a
**clone** when you want a separate experiment copy beside the baseline.
VirtualBox offers two disk arrangements: a **full clone** copies the
dependent virtual disks; a **linked clone** writes into its own differencing
disks while relying on source base disks. Keep that base available. The
[VirtualBox cloning guide](https://docs.oracle.com/en/virtualization/virtualbox/7.2/user/working-with-vms.html#cloning-virtual-machines)
describes these choices and its network-adapter address policy.

Disk separation is one boundary. Before starting both copies, review their
network adapter MAC addresses, guest host names and fixed IP settings, and
host sharing. A MAC address identifies an adapter on its local network;
cloning disk content alone does not make all copied network settings unique.
Changes in a shared host folder are outside the guest disk snapshot.

## What a result depends on

When you later record an **address** (a location in the running game), an
**offset** (a distance from a chosen start), or a **byte pattern** (a sequence
to search for), record the exact environment too. The next lesson develops
these ideas; their usefulness depends on:

- the game name, exact build, and architecture, because a different build can
  move every function and field;
- the executable's <HoverCard kind="example" body="In PowerShell, `Get-FileHash .\wesnoth.exe` prints the file’s SHA-256 hash. The same bytes always give the same hash, and changing a single byte gives an entirely different one.">file hash</HoverCard>, a short fingerprint computed from its bytes:
  matching hashes are strong evidence that two copies use the same build even
  when their version labels are ambiguous;
- the Windows version, because system DLLs change between updates;
- the repository commit and the tool and debugger versions;
- the starting save, map, or settings;
- the VM snapshot the machine started from.

The snapshot restores files and installed tools, and source control restores
the exact code. The build and file hash tell you whether an address found last
week still applies to the game in front of you.

<MarginNote kind="narration">A note saying gold lives at some address is nearly useless a week later unless it also records which exact build it came from.</MarginNote>
