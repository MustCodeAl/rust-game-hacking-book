An address names a location, while a type tells a program what its bytes
mean. We will use a memory scanner on Wesnoth: observe a gold value,
search for matching bytes, make one in-game change, and filter the results.

The goal is not merely to reach a final address. The goal is to understand why
each scan removes some candidates and why one test still does not prove that a
candidate is the main game-play value.

## Prepare the target

Use the course build of Wesnoth 1.14.9 in the Windows VM. Start a local match and
pause before recruiting a unit.

<Frame caption="The paused Wesnoth match. The gold number on screen is what the scan will look for.">

![A Wesnoth match showing the gold value](/assets/images/1/5/wesnoth1.png)

</Frame>

Suppose the screen shows 100 gold and the unit you plan to recruit costs 15.
After recruiting, the visible value should become 100 − 15 = 85.

## Attach Cheat Engine to the game process

Open Cheat Engine, choose the process button, and select the running Wesnoth
process.

<Frame caption="Cheat Engine's process list, with the running Wesnoth chosen.">

![Choosing the Wesnoth process](/assets/images/1/5/wesnoth2.png)

</Frame>

Attaching tells Cheat Engine which process address space to read. It does not
yet tell the scanner where gold is or how it is stored.

## Perform the first value scan

<Badge text="Windows VM" variant="note" />

Enter the visible gold amount. Use:

- **Value Type:** <HoverCard kind="explanation" body="Four bytes hold one 32-bit whole number, the same size as Rust’s `i32` or `u32`. The scanner must read all four bytes at an address to see the number the screen shows.">4 Bytes</HoverCard>;
- **Scan Type:** <HoverCard kind="alternative" body="If a game never shows the number, scan for an unknown initial value instead. After each change in the game, keep the addresses that changed, increased, decreased, or stayed the same.">Exact Value</HoverCard>;
- **Value:** the current gold amount.

Start the first scan.

<Frame caption="Straight after the first scan, many addresses hold the same number.">

![The first scan for gold](/assets/images/1/5/wesnoth3.png)

</Frame>

The scan will probably find many addresses. That is expected. The number 100 can
appear in timers, object fields, capacities, interface data, and unrelated
allocations.

At this point, each result proves only this:

> These four bytes were readable as the integer 100 when the scanner checked
> them.

It does not prove that the address controls gold.

## Change the game once

Return to Wesnoth and perform the planned action. Recruit the unit and read the
new gold value off the screen.

<Frame caption="After recruiting, the new gold amount is the next value to search for.">

![Gold after recruiting a unit](/assets/images/1/5/wesnoth4.png)

</Frame>

If the value changed from 100 to 85, return to Cheat Engine, enter 85, and choose
**Next Scan**.

The scanner does not search the whole process from the beginning. It checks the
previous candidate addresses and <HoverCard kind="example" body="Say the first scan found three addresses holding 100: A, B, and C. After the purchase only B and C hold 85, so A is dropped, and the next scan checks just B and C.">keeps only those that now contain 85</HoverCard>. In set
notation:

```text
new_candidates = old_candidates ∩ addresses_currently_equal_to_85
```

You do not need the symbol memorized. It means “keep items that are in both
groups.”

<CodeTrace trace="scan-narrowing" />

## Repeat with a different change

Make another controlled change with a different result. For example, recruit a
unit with another cost or end a turn if the scenario changes gold in a known
way. Enter the new gold value and perform another **Next Scan**.

<Frame caption="After Next Scan the candidate list is much shorter.">

![A narrowed list of candidate addresses](/assets/images/1/5/wesnoth6.png)

</Frame>

Using different values is important. If you repeat only 100 → 85 → 100, an
unrelated value that happens to follow the same pattern can remain in the list.

Continue until you have a small number of candidates. Do not assume the first
remaining address is correct.

## Test one candidate reversibly

Add one candidate to the address list. Before changing it:

<Steps>

1. copy its current value so you can put it back;
2. confirm the game still shows the expected gold;
3. choose a small replacement value;
4. write the replacement once;
5. observe the screen and one real purchase;
6. <HoverCard kind="recommendation" body="Do this before any other test, even if the change looked harmless. A leftover value can make the next test start from a different state, and then two results can no longer be compared.">restore the original value</HoverCard>.

</Steps>

<Frame caption="Wesnoth after one candidate was edited: the display shows the new value.">

![The edited gold value in Wesnoth](/assets/images/1/5/wesnoth9.png)

</Frame>

Different results support different explanations:

| What happens | Likely meaning |
|---|---|
| the number and purchase rules change | strong candidate for game-play state |
| only the text changes | likely a display copy |
| the value changes back on the next update | another system recomputes or owns it |
| nothing visible changes | unrelated value or a copy used elsewhere |
| nearby behavior breaks | wrong address, type, or field width may have been changed |

A single run can mislead, because an unrelated value might change at the same
moment by coincidence. Getting the same result again from the same starting
state makes that explanation less likely.

## Why several copies may all be related

The game can legitimately keep more than one gold-related value:

- the current simulation value;
- a previous value used by an animation;
- text prepared for the interface;
- a value in a replay, event, or network message;
- a temporary calculation.

That is why value scanning is usually the start of reverse engineering. A write
breakpoint later shows which instruction changes the strongest candidate. The
surrounding instructions can reveal the object base and other fields.

## Treat the address as temporary

The address you found belongs to this run of the game. After a restart, gold
may live somewhere else, because the process layout and the heap can change
between runs. A later lesson on [building and loading a program](/pages/1/10/)
explains why some distances stay fixed within one build even when absolute
addresses move. First, a debugger lets us follow the candidate value to the
instruction that changes it.

## What the scan established

The first scan returned readable candidates that matched while it ran;
it did not identify “the gold address.” Each controlled game change
filtered that candidate set. Changing one survivor and then making a
real purchase showed whether it affected gameplay, only the display,
or neither. Restoring the original value leaves the game in a known
state for another run.

The candidate address tells us where to look, but not why the value changes.
When a purchase subtracts gold, which instruction performs the subtraction,
and what decides whether the player can afford it? [What a Debugger Can
Reveal](/pages/2/01/) begins Chapter 2 with that question. We will pause the
program at the change, then learn how source code becomes the instructions
the debugger shows.
