A memory reader and a packet parser both receive sequences of bytes.
Before using those bytes, they need to check the available length, decide
how to group elements, and choose the numeric interpretation. Ordinary
Rust collections let us learn those decisions in a small local example.
The [previous lesson](/pages/1/13/) explains the `Option` and `Result`
values returned when a check fails.

## Choose a collection for the question

The guarded purchase in [Lesson 1.4](/pages/1/04/) used two `Player` records,
Ada and Bo. A fixed array was enough when we knew there were exactly two. What if players can join, we need one player's score by name,
or we must handle pending actions in arrival order? Those are different
questions, and different collections make each one natural:

| Collection | Picture it as | Good first use | Important limit |
| --- | --- | --- | --- |
| Array, `[T; N]` | numbered slots with a fixed count | two known players, three prices | its count does not grow |
| Vector, `Vec<T>` | numbered slots that can grow | players joining or a history of health samples | removing from the middle shifts later items |
| Hash map, `HashMap<K, V>` | a key pointing to its value | find Ada's gold by her name or ID | a key may be missing; order is not the promise |
| Queue, `VecDeque<T>` | a line of waiting items | handle actions in arrival order | it is for the next item, not fast arbitrary lookup |
| Grid | rows and columns | map tiles at `(row, column)` | boundaries must be checked |
| Graph | places and their connections | waypoints and reachable paths | you must store and inspect the connections |

`T` stands for the kind of item stored. A vector of `u32` values, for
example, is written `Vec<u32>`. `K` and `V` stand for a map's key and
value types. A queue can be implemented with Rust's `VecDeque`, which
lets us add at the back and take from the front.

The array we used has a fixed number of slots. A vector keeps numbered
slots but can grow, which fits a history of gold samples:

```rust
let mut recent_gold = vec![100, 75];
recent_gold.push(65);
```

A hash map answers “what value belongs to this key?” A queue answers
“what item arrived next?” The following Rust fragments use all three,
including a lookup or queue removal with no answer.

A grid can be a vector of rows, so `tiles[row][column]` reaches a tile.
A graph stores which waypoints connect; [Lesson 4.8](/pages/4/06/) uses
one to search for a route. These are arrangements of data, not magic
algorithms. Choose by the operation you need: **next by position, look up
by key, take the oldest, or visit neighbors**. [Lesson 3.10](/pages/3/05/)
shows how their layouts can be recognized in a running game.

<MarginNote kind="alternative">Picture a vector as numbered lockers, a hash map as a coat check where a ticket finds your coat, and a queue as a line at a shop.</MarginNote>

```mermaid
flowchart TD
    Ask["What do I need to find?"] --> Pos{"a numbered position?"}
    Pos -->|yes| Vec["array or vector"]
    Pos -->|no| Key{"a named key?"}
    Key -->|yes| Map["hash map"]
    Key -->|no| Next{"the next waiting item?"}
```

## Try the growable collections in Rust

Different questions call for different collections. A vector keeps a
growable sequence of samples. A hash map finds a value by a key. A queue
keeps actions in arrival order. These fragments reuse the Primer's Mira
stamina values, separately from its complete two-runner program. The `use`
line makes the two standard
library collection types available by their short names:

```rust
use std::collections::{HashMap, VecDeque};

let mut recent_stamina = vec![12, 8];
recent_stamina.push(6);
let second_sample = recent_stamina[1];
println!("Second sample: {second_sample}");

let mut stamina_by_name = HashMap::new();
stamina_by_name.insert("Mira", 8);
if let Some(amount) = stamina_by_name.get("Mira") {
    println!("Mira has {amount} stamina");
}

let mut pending = VecDeque::new();
pending.push_back("dash");
pending.push_back("rest");
if let Some(action) = pending.pop_front() {
    println!("Next action: {action}");
}
```

`vec!` starts a growable vector with two samples, `push` adds a third,
and `[1]` selects the second sample because positions start at zero.
The hash map associates the key `"Mira"` with 8, so `get("Mira")` can
find the amount without scanning a list of names. The queue adds actions
at the back and takes the oldest from the front; after the first pop,
`"rest"` is still waiting.

Both the map lookup and the queue removal may fail to produce an item:
the name might be absent or the queue empty. Their results therefore
use `Some(value)` or `None`. [Lesson 3.2](/pages/1/13/) develops that
possible-value shape with checked subtraction and fallible operations.
The grid/graph distinction above connects these choices to map tiles and paths.

## Read an iterator chain one item at a time

An **iterator** yields a sequence of items on demand. `filter` keeps items
that satisfy a predicate, `map` transforms each kept item, and `fold`
combines items into one running answer. The closures describe those
operations; a consuming operation such as `fold` drives the sequence.

<SpeedType id="rust-filter-map-fold" title="Keep, transform, and add" recall={[{text:"filter(|cost| *cost <= budget)",hint:"Keep costs that fit the unchanged per-item budget; the predicate borrows each item."},{text:"map(|cost| cost * 2)",hint:"Double each cost that passed the predicate."},{text:"fold(0, |sum, cost| sum + cost)",hint:"Start at zero and accumulate each transformed cost."}]}>

```rust
fn doubled_total(budget: u32) -> u32 {
    let prices = [3_u32, 8, 12];
    prices.into_iter()
        .filter(|cost| *cost <= budget)
        .map(|cost| cost * 2)
        .fold(0, |sum, cost| sum + cost)
}
```

</SpeedType>

For a budget of 8, `filter` keeps 3 and 8, `map` produces 6 and 16, and
`fold` produces 22. This is a query, not a purchase: each price is checked
against the same unchanged budget. It does not ask whether buying all the
items together would be affordable.

`into_iter` consumes this array and yields its `u32` values. `filter`
passes a reference to its predicate so an item can still be yielded after
the check; `*cost` reads the borrowed number. `map` then receives each
kept number by value. If you need to borrow the collection instead, start
with `.iter()`; for copyable numbers, `.iter().copied()` yields values
while keeping the original collection.

### Express a repeated query with an iterator

A second query counts runners with at least 4 stamina. Unlike the doubled
total above, its result is how many items pass the predicate:

<SpeedType id="rust-filter-ready" title="Count runners with enough stamina" recall={[{"text": "filter", "hint": "Keep only values that satisfy a condition."}, {"text": "*stamina >= 4", "hint": "Read the borrowed number and compare it with the dash cost."}, {"text": "count", "hint": "Consume the kept items and return how many there are."}]}>

```rust
let stamina_samples = [8_u32, 3, 6];
let ready = stamina_samples
    .iter()
    .copied()
    .filter(|stamina| *stamina >= 4)
    .count();
println!("{ready} runners can dash"); // 2
```

</SpeedType>

`.iter().copied()` keeps the original array while yielding cheap `u32`
copies. The filter predicate still borrows each candidate, so `*stamina`
reads its number. `count` consumes the kept values. The equivalent loop is:

```rust
let stamina_samples = [8_u32, 3, 6];
let mut ready = 0;
for stamina in stamina_samples {
    if stamina >= 4 {
        ready += 1;
    }
}
// ready is 2
```

Both forms produce 2. Choose the form that makes the question and each
value transformation clearest.

## Use `windows` for neighboring samples

Suppose three position samples are 2, 6, and 10. We want each change
between adjacent samples. `windows(2)` yields borrowed slices `[2, 6]`
and `[6, 10]`. They overlap because the middle sample belongs to both
neighbor pairs.

```rust
fn movement_deltas(positions: &[i32]) -> Vec<i32> {
    positions.windows(2)
        .map(|pair| pair[1] - pair[0])
        .collect()
}
```

Every yielded window has exactly two elements, so its two indexes are
valid. The example's small coordinates also keep the subtraction in
`i32` range; arbitrary external coordinates need a checked subtraction
or a wider type. `collect` consumes the iterator into a new `Vec<i32>`.
A slice shorter than the window size yields no windows. A zero window
size would panic, so validate a reader-supplied size before calling it.

## Use `chunks_exact` for complete records

`chunks_exact(2)` divides a buffer into separate two-byte groups.
Unlike windows, the groups do not overlap. A final single byte does not
form a complete record. Rust exposes it through `remainder()` so the
parser can decide whether to reject it or buffer it for later.

```rust
fn decode_records(bytes: &[u8]) -> Result<Vec<u16>, &'static str> {
    let records = bytes.chunks_exact(2);
    if !records.remainder().is_empty() {
        return Err("partial record");
    }
    Ok(records
        .map(|pair| u16::from_le_bytes([pair[0], pair[1]]))
        .collect())
}
```

The buffer `[4, 0, 9, 0]` decodes as two little-endian numbers, 4 and 9.
Appending `255` makes this complete-packet parser return an error. For a
stream being received in pieces, keeping that byte for the next read may
be appropriate; [Lesson 8.1](/pages/6/01/) explains that distinction.
This function fixes the group size at two. A zero size would panic.

<MarginNote kind="clarify">chunks_exact does not certify that the entire buffer contains complete records. Checking the remainder supplies that guarantee.</MarginNote>

## Check slice bounds before decoding a number

A **slice** borrows a contiguous sequence and includes its length.
`bytes[3]` assumes index 3 exists; it panics if that assumption is false.
`bytes.get(3)` instead returns `Some(&byte)` or `None`. The same checked
operation accepts a range: `get(..4)` asks for the first four bytes.

<SpeedType id="rust-read-bounded-gold" title="Decode four checked bytes" recall={[{text:"bytes.get(..4)?",hint:"Ask for a checked four-byte prefix; return None if it is too short."},{text:"try_into().ok()?",hint:"Convert the slice into an exact array and keep only a successful conversion."},{text:"u32::from_le_bytes(raw)",hint:"Interpret the low byte first without relying on the host CPU."}]}>

```rust
fn read_gold(bytes: &[u8]) -> Option<u32> {
    let raw: [u8; 4] = bytes.get(..4)?.try_into().ok()?;
    Some(u32::from_le_bytes(raw))
}
```

</SpeedType>

The range check establishes the length. `try_into` produces an exact
`[u8; 4]` array from that slice; `.ok()` turns its `Result` into an
`Option`, and `?` exits if it is missing. `from_le_bytes` interprets
`[0x2C, 0x01, 0, 0]` as 300. `300_u32.to_le_bytes()` reverses that
conversion and produces the same four bytes. Use `from_be_bytes` and
`to_be_bytes` when the format says the high byte comes first.

<Frame caption="The same low-byte-first conversion with a second number: decimal 100 is hexadecimal 0x64, so its four-byte field is 64 00 00 00.">
  <img src={`${import.meta.env.BASE_URL}assets/images/original/little-endian.svg`} width="480" height="190" alt="A four-byte little-endian field for decimal 100 has 64 at offset zero, followed by three zero bytes." loading="lazy" decoding="async" />
</Frame>

Reading the first four bytes leaves any later bytes unused. A format
that requires exactly four bytes must also check the total length.
Byte conversion interprets a number; it does not decide whether that
number is a valid health amount, length, or address.

## Choose how integer limits are handled

An unsigned eight-bit value, `u8`, holds 0 through 255. The mathematical
sum `250 + 10` is 260 and does not fit. Rust supplies explicit arithmetic
policies so the programmer chooses the intended behavior:

```rust
let count = 250_u8;
let checked = count.checked_add(10);       // None
let wrapping = count.wrapping_add(10);     // 4
let saturating = count.saturating_add(10); // 255
```

`checked_*` reports that an answer cannot be represented. `wrapping_*`
keeps the low bits, making this sum 4 after passing 255. `saturating_*`
stops at the type's limit. Use checked arithmetic for a size or balance
that must be rejected if it overflows; wrapping for an intentionally
cyclic counter; saturating for a bounded meter.

Plain integer overflow may panic when overflow checks are enabled or
wrap when disabled. Explicit methods make the behavior independent of
that build setting. Saturation is to the type limit: a game with maximum
health 100 still needs a separate clamp to 100, even if health is a `u8`.

## Separate in-memory layout from a file format

Rust's ordinary struct representation does not promise a C field layout.
`#[repr(C)]` requests the target platform's C ordering and alignment:

```rust
#[repr(C)]
struct Record {
    tag: u8,
    gold: u32,
    zone: u16,
}
```

On the Windows x64 target used in this book, `tag` is at offset 0,
`gold` at offset 4, and `zone` at offset 8. Three padding bytes align
`gold`; two tail padding bytes make the full size 12. The same fields
written consecutively into a file would occupy only 7 bytes. Padding
is part of the type's memory layout, not an implied serialized field.

```rust
let gold_offset = std::mem::offset_of!(Record, gold);
let record_size = std::mem::size_of::<Record>();
let record_alignment = std::mem::align_of::<Record>();
```

These operations measure the compiled type on the current target.
`repr(C)` does not select byte order, prove that remote bytes contain
valid field values, or make every C++ class compatible with this struct.
Decode external file or packet fields explicitly rather than copying
the raw bytes of a Rust struct, including its padding.

<MarginNote kind="code">An offset describes where a field is within a particular layout. Keep the target architecture and format version with that offset.</MarginNote>

## Cheatsheet: sequences and representations

| Need | Expression | Boundary to check |
| --- | --- | --- |
| Keep selected items | `.filter(predicate)` | Predicate borrows its item. |
| Transform each item | `.map(function)` | Runs as the iterator is consumed. |
| Accumulate an answer | `.fold(start, combine)` | Arithmetic must fit or use an explicit policy. |
| Compare neighbors | `.windows(n)` | `n` must be positive; windows overlap. |
| Decode fixed records | `.chunks_exact(n)` | `n` must be positive; inspect the remainder. |
| Borrow checked elements | `.get(index_or_range)` | Returns `None` outside the bounds. |
| Convert an exact field | `from_le_bytes` / `to_le_bytes` | Follow the format's byte order and width. |
| Reject overflow | `checked_*` | Caller handles `None`. |
| Cycle through bit patterns | `wrapping_*` | Wraparound must be intended. |
| Stop at the type limit | `saturating_*` | The game limit may be smaller. |
| Match C layout | `#[repr(C)]` | Target alignment and padding still apply. |

The [Iterator reference](https://doc.rust-lang.org/std/iter/trait.Iterator.html),
[slice reference](https://doc.rust-lang.org/std/primitive.slice.html), and
[type-layout reference](https://doc.rust-lang.org/reference/type-layout.html)
give the complete definitions. Next, [borrows and interfaces](/pages/1/15/)
explain how functions share this data without losing its owner.
