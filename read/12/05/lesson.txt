State Machines for Lua Automation

Imagine a helper script that selects the next living unit in a local game. It can observe a snapshot, request one selection, and wait for confirmation. If it repeats the request as fast as the interpreter can run, it may never observe the result or respond to a stop signal. Named states give each step a place and a condition for moving on.

Section: One update performs bounded work.

Each host call supplies a current snapshot and runs at most one branch. This sketch uses the State table above, the host’s game.request, and the choose_nearest_living helper defined below. The result is false only when the bot has stopped; otherwise the changed bot record says which phase comes next.

The host calls update at a controlled rate. The script does not own an infinite loop and cannot flood actions between frames.

OBSERVE stores one snapshot. CHOOSE reads that same version, and REQUEST tags its proposed action with the stored sequence number; the host checks the request against current game state before acting. Later WAIT calls use the latest snapshot to see whether selection was confirmed. Keeping those two snapshots distinct is why a stale choice cannot silently become authority.

Bounded work makes scheduling visible. One call performs at most one transition and proposes at most one action. The host can measure it, stop between calls, and prevent a fast script loop from starving rendering or input processing.

Section: Give stop the highest priority.

Before every update, the host can check:

user pressed the stop hotkey;

game process exited;

profile no longer matches;

script exceeded an error limit;

action request was rejected;

snapshot has been invalid for too long.

Any of these moves the host to stopped even if Lua wants to continue. The script is a guest, not the authority over shutdown.
