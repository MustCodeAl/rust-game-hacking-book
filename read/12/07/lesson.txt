From Lua Source to a Tiny Virtual Machine

The earlier Lua lessons used scripts from the outside and defined what the game host would let them do. The computability lesson then showed how one program can execute another—and why no perfect termination checker can replace a work budget. Now look inside the interpreter. The same small expression has to become operations a virtual machine can execute, and those operations still need limits and useful errors.

Section: An interpreter is a pipeline.

When Lua reads total equals 5 + 2, it does not ask the CPU, central processing unit, to execute the characters + and equals directly. Several layers turn text into actions:

a lexer groups characters into tokens such as name, equals, integer, plus, integer;

a parser checks that the token order follows the language grammar;

a compiler turns the meaning into compact bytecode instructions ;

a virtual machine executes those bytecodes using values, a stack , and an instruction pointer .

Diagram. From source text total equals 5 + 2 to tokens: name, equals, integer, plus, integer. The connection is labelled: lexer. From tokens: name, equals, integer, plus, integer to checks grammar. The connection is labelled: parser. From checks grammar to bytecode instructions. The connection is labelled: compiler. From bytecode instructions to executes using values, a stack, and an instruction pointer. The connection is labelled: virtual machine.

Real Lua is carefully optimized. Our tiny VM, virtual machine, is intentionally smaller so every moving part fits on one page.

These stages are common, but they are not the definition of every interpreter. One interpreter may walk a syntax tree directly; another may compile to bytecode first; a just-in-time compiler may later translate hot bytecode into native machine code. The language’s meaning can stay the same while its implementation changes.

Do not explain Lua semantics by accident from one current bytecode layout. The source rule is the contract; tokens, syntax trees, bytecodes, stacks, and native instructions are replaceable representations used to carry it out.

The same pipeline can be viewed from the host’s side. Lua 5.4 typically recognizes names and numbers with a lexer, checks expressions and statements with a parser, compiles them to bytecode, and executes those instructions in its VM. The VM maintains Lua values, call frames, and its own program counter; the host supplies functions that may be called during execution:

Diagram. From Source text to Lexer: characters to tokens. From Lexer: characters to tokens to Parser: tokens to syntax. From Parser: tokens to syntax to Compiler: syntax to bytecode. From Compiler: syntax to bytecode to Virtual machine executes instructions. From Virtual machine executes instructions to Host functions and game state.

Some hosts cache bytecode; others compile source each time it loads. LuaJIT may additionally translate hot paths into native machine code. Identify the runtime before assuming its internal representation matches this teaching VM.

Constant(2) means “copy constant number two onto the value stack.” Add pops two integers and pushes their sum. JumpIfFalse(9) changes the VM instruction pointer when the popped condition is false.

An enum makes this teaching VM easy to inspect. A full game-scripting interpreter may encode opcodes and operands more densely after profiling shows that bytecode size or dispatch speed matters.

That 9 is not decoration. Jump operands are positions in the bytecode vector, so they only mean anything once you can see the whole program. Here is the lab’s example, if (5 + 2) greater than 6 then print(1) else print(0), after compilation. The constants are collected into a pool, and the instructions refer to them by index:

Section: Model the VM as state plus one transition function.

At any instant, this tiny machine is completely described by a small state:

One interpreter-loop iteration reads the current instruction and changes that state. Constant advances the pointer and grows the stack. Add removes two values and adds one. Jump changes the pointer. Print moves a value to observable output. Halt ends the transition loop.

This state-machine view is more reliable than imagining that the VM “somehow runs Lua.” It lets you state an invariant for every instruction: required stack inputs, resulting stack height, legal jump targets, possible error, and instruction-pointer change.

Section: The value stack carries temporary results.

Indices 0 to 4 of that listing compute (5 + 2) greater than 6. Watching the stack through those five steps shows where the intermediate values live:

Table columns: Step; Bytecode; Stack after step.

Step: 1; Bytecode: constant 5; Stack after step: 5.

Step: 2; Bytecode: constant 2; Stack after step: 5, 2.

Step: 3; Bytecode: add; Stack after step: 7.

Step: 4; Bytecode: constant 6; Stack after step: 7, 6.

Step: 5; Bytecode: greater-than; Stack after step: true.

Labelled memory diagram. top to : 2; cell 2: 5. The value stack right after step 2 (Constant(1) pushed 2 on top of the 5 pushed in step 1).

Add pops the right side first because it was pushed last. This last-in, first-out order is the same basic idea as a call stack, although a real VM may use separate regions or registers for different jobs.

Diagram walkthrough: Watch the value stack evaluate (5 + 2) greater than 6. Step 1: Execute Constant(0). State: ip=1; stack=[5]. Constant-pool entry 0 holds 5. Copy it onto the initially empty value stack; the instruction pointer now identifies bytecode 1. Step 2: Execute Constant(1). State: ip=2; stack=[5, 2]. Constant-pool entry 1 holds 2. Push it above 5, leaving 2 as the next value that a pop will remove. Step 3: Execute Add. State: ip=3; stack=[7]. Pop right operand 2, then left operand 5. Check that both are integers and push their sum, replacing two temporary values with one. Step 4: Execute Constant(2). State: ip=4; stack=[7, 6]. Constant-pool entry 2 holds 6. Push it above the sum so GreaterThan can compare the left value 7 with the right value 6. Step 5: Execute GreaterThan. State: ip=5; stack=[true]. Pop the two integers and push the Boolean result of 7 greater than 6. The stack now carries a condition rather than the numeric operands. Step 6: Follow the then branch. State: output=[1]; halted. JumpIfFalse consumes true and keeps the then path. Constant(3) supplies 1, Print consumes it, and Jump(11) skips the else branch to Halt. The first five stages match bytecodes 0–4 and the stack table above. The last stage groups the selected branch through Print and Halt; the constant pool and value stack have different jobs.

A larger Lua VM also needs an environment that maps names to values. Functions capture environments through closures, tables hold references to other values, and garbage collection decides when unreachable heap objects can be reclaimed. Those features enlarge the state, but they do not change the basic model: each operation checks its inputs and moves the machine from one valid state to the next.

Section: Separate four kinds of failure.

Keeping stages separate produces clearer errors:

Table columns: Stage; Example failure.

Stage: Lexing; Example failure: unfinished quoted string.

Stage: Parsing; Example failure: if without the required structure.

Stage: Bytecode validation; Example failure: jump target outside the program.

Stage: Execution; Example failure: adding a Boolean to an integer or exhausting the budget.

If all four become “script failed,” the host cannot tell whether the author wrote invalid Lua, the compiler produced invalid code, or a valid script exceeded the game tool’s resource policy.
