Lesson 4.7 / Listening edition

From Coordinates to Target Selection

Trace player and enemy positions in offline Flare, then choose actions from validated coordinates rather than fixed timings.

About 21 minutes

Coordinates give a position meaning, and subtracting two positions gives the direction and distance between them. Now we can use those ideas to choose an action in a moving game. The earlier Wyrmsun macro reacted to a discrete result: a unit was recruited or it was not. In Flare, an enemy keeps moving. A fixed instruction such as “hold right for one second” can be correct at the start and wrong a moment later. Position becomes an observation the bot must refresh before choosing its next action.

Section: Begin with coordinates you can control.

Use Flare 1.12 in an offline test area. Stand at an easy location, move only left and right, and scan for a changing floating-point value.

Image description: Searching for the player position

Then hold the first coordinate steady and move only up and down. Two independent experiments help distinguish x from y.

Image description: Narrowing the coordinate candidates

Validate each candidate at several positions. Teleporting a candidate a tiny distance in a disposable lab can confirm it, but restore the original value immediately.

Section: Find related objects.

Once the player position is known, inspect nearby fields and the code that reads them. Repeat the same process for:

one enemy position;

the current cursor or destination position;

an “is alive” or active flag.

Image description: Inspecting nearby position data

Do not assume every object shares the same layout. Confirm offsets separately.

Section: Copy memory into snapshots.

Copy each confirmed position into a small Vec2 value, then group the player, enemies, and cursor in one WorldSnapshot. This is the input to decision logic: the bot works from local values captured together and does not keep a remote pointer alive while it chooses what to do.

The action does not prove success. Movement may be blocked, the target may disappear, or the snapshot may already be stale. After every request, wait for a specific observation that confirms or rejects it before choosing the next action.

Keep time in the model. Store when the snapshot was captured, when the action was requested, and how long confirmation remains valid. A perfect position from half a second ago can be worse than a slightly noisy current position.

Section: Separate decision from action.

decide turns a snapshot into an intent, never an input event. An invalid player position means Stop; no valid enemy means Wait; otherwise the nearest enemy becomes MoveTo(position). The platform-specific action layer can later decide how to carry out that intent.

Section: Add guardrails.

Stop when:

the match or level is no longer active;

any base pointer becomes null;

coordinates are non-finite or out of bounds;

the player has not moved after several attempts;

the user requests stop;

the target version check fails.

At those sites, the useful fields are:

mouse X/Y: [ebp + hexadecimal 6 6 4] and [ebp + hexadecimal 6 6 8] ;

player X/Y: [ecx + hexadecimal 2 4 0] and [ecx + hexadecimal 2 4 4] ;

current entity X/Y: [ebx - 4] and [ebx] .

Store the captured addresses as atomics or copy the values into an owned snapshot. Do not let the worker hold a pointer while a hook is changing it.
