Lesson 4.5 / Listening edition

Maps as Grids of Game State

Understand a map as indexed game state, then trace and visualize one tile's visibility in an offline lab.

About 16 minutes

A player record is one object. A map asks the same memory question thousands of times: which tile is this, and what does this player know about it? In a Wesnoth match, terrain and visibility may describe the same location but live in different layers of state. Coordinates give us a way to relate them.

On a three-column, two-row map, tile (2, 1) becomes index 1 times 3 + 2 equals 5. Tile (3, 1) is outside the map and returns None. The checked multiplication also refuses dimensions so large that the index would overflow usize.

In brief: A flat list can hold a grid: a tile’s index is its row times the width plus its column. Check the bounds before you use it.

Never trust coordinates from remote memory until they pass bounds checks.

Section: A grid needs a coordinate contract.

The formula only works after you know what x, y, width, and the base address mean. Games may store rows from top to bottom or bottom to top, pad each row, split terrain and visibility into separate layers, or keep one visibility layer per team.

For a candidate grid, recover these facts separately:

origin: which tile is (0, 0);

axis direction: which way increasing x and y move;

stride: how many elements or bytes separate two rows;

element width: how many bytes represent one tile;

layer: terrain, occupancy, visibility, or another property;

owner: global map state or one player’s derived view.

If the row stride includes padding, y * width + x is wrong even when the first row looks perfect. The byte address becomes base + y * row_stride + x * element_size. Verify it with tiles on different rows and near both edges of the map.

Predict first

A map is 3 tiles wide and 2 tall, one byte per tile. The game pads every row to 4 bytes, so each row ends with one unused byte.

Counting from byte 0, which byte holds tile (2, 1)?

Answer: Byte 6. Skip one whole row of 4 bytes (1 times 4 equals 4), then move 2 tiles along it: 4 + 2 equals 6. Bytes 3 and 7 are the padding.

Visibility is often a derived view of terrain, units, teams, and line-of-sight checks for range and blocking terrain. A cached visibility layer can be useful to read without being the source of truth, because the game rebuilds it from those inputs. What matters is which system recomputes it and when.

Alternative: Think of fog as a sheet of tracing paper over the map: the terrain underneath is shared, but each player has their own sheet showing what they have seen.

Section: Find one known tile.

In an offline Wesnoth match, compare a currently visible tile with a tile hidden by fog. Search for the observed visibility value, reveal or hide the tile through normal gameplay, and filter again.

Repeat with several tiles. You are testing whether candidates belong to:

one tile;

one row;

one player’s visibility layer;

a cached drawing value;

the authoritative map state.

Section: Break on a normal update.

Set a write breakpoint on a confirmed tile and move a unit so visibility updates.

Look for:

a base pointer to map data;

row or column math;

a player or team index;

the value written for hidden, explored, and visible states.

Do not assume a value such as this value means “visible.” It may mean -1, a bit mask, or an uninitialized sentinel. Collect examples for every state you name.

Section: What the grid model teaches.

Fog of war is a per-player view over shared map data. The experiment shows how a grid and per-player visibility state can be represented; a different build may pack the same relationship into different bytes.
