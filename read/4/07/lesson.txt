When Changed State Becomes an Event

A route planner can compute one good path and still make a bad bot if it treats every read of the same target position as a fresh command. The difference between “the enemy is at this tile” and “the enemy just moved to this tile” is the beginning of an event-driven design.

The event says what changed, while a snapshot says what is true now. Keeping both ideas separate prevents a bot from performing the same action on every poll.

A responsive loop should turn noisy polls into one deliberate action in stages, rather than connecting every poll directly to a click:

Diagram. From Poll a snapshot to Validate its fields. From Validate its fields to Compare with accepted state. From Compare with accepted state to Wait for a stable change. From Wait for a stable change to Emit one event. From Emit one event to Check safety and cooldown. From Check safety and cooldown to Perform one action.

Validation protects the model, debouncing protects it from flicker, and the cooldown prevents a valid event from producing frantic repeated input.

Section: Level facts and edge facts answer different questions.

A snapshot contains level facts: “the menu is open” or “gold equals 145.” An event describes an edge between two accepted snapshots: “the menu opened” or “gold increased by 25.”

That difference controls behavior. A level-triggered rule such as if menu_open { click() } may click on every poll. An edge-triggered rule acts only on the transition from closed to open. Neither form is always better:

use a level fact to keep a safety condition true, such as “stop while the target is absent”;

use an edge event for one-time work, such as recording that a turn began;

use both when an action needs a starting event and an ongoing confirmation.

Here are six polls of menu_open and what each kind of rule does with them:

Labelled memory diagram. poll 1: false; poll 2: false; poll 3: true, highlighted; poll 4: true; poll 5: true; poll 6: false, highlighted. Groups: level rule: clicks on 3 polls; edge: MenuOpened; edge: MenuClosed. The level rule fires on every poll where the menu is open, so one opening produces three clicks. The edge rule compares each poll with the one before and fires only at the two highlighted polls, where the value changed.

Events are interpretations, not raw truth. If the observer misses snapshots, 120 to 145 proves the endpoints but not whether the game passed through 130. Name an event GoldChanged, not GoldEarned, unless something else shows why it changed.

Section: Diff two validated snapshots.

Compare two snapshots only after each has passed its own read and identity checks. If gold changes from 120 to 145 while menu_open changes from false to true, diff returns both GoldChanged { before: 120, after: 145 } and MenuOpened. Repeated identical snapshots return an empty vector, so the bot has no new event to act on.

Animated diagram: A value becomes an event only at its edge. A baseline snapshot of 120 gold and a closed menu is compared with a new snapshot of 145 gold and an open menu. In this example nothing else has changed. Step 3: diff compares the fields. Gold differs, from 120 to 145, a change of 25. The menu went from false to true. It compares endpoints only, so it cannot say why gold changed. Step 4: Each difference becomes a named event. The variant carries the data the action layer needs, such as the before and after gold. Step 5: The accepted snapshot becomes the new baseline: 145 gold, menu open. That opening has already been reported once. Step 6: If the next accepted snapshot is identical, diff returns an empty list. The menu is still open, but that is a level, not a new edge, so there is no second MenuOpened. Level state remains true across polls; an edge event describes the transition between accepted states.

Section: Debouncing asks for stability.

Some values flicker while a game changes scenes. Debouncing waits for the same candidate value to appear several times before accepting it.

It helps to know why a value flickers, because that tells you how long to wait. During a scene change the game is often rebuilding the very object you are reading. The pointer is briefly null, or it points at a freshly allocated record whose fields have not been filled in yet. Your read succeeds and hands back a real number that was never a real game state:

The strange value on poll 4 is the byte hexadecimal C D, which Microsoft’s debug heap writes into every fresh allocation, repeated four times. One hexadecimal C D is 12 times 16 + 13 equals 205, so the four bytes read as 205 times 256 to the power of 3 + 205 times 256 to the power of 2 + 205 times 256 + 205 equals 3,452,816,845.

A debouncer keeps two things: the last accepted value, and a candidate value with a count. Each poll does one of three things. A poll equal to the accepted value clears the candidate. A poll equal to the candidate adds one to its count. Any other value becomes a new candidate with a count of 1. When the candidate’s count reaches the required number, it becomes the accepted value and the debouncer reports one change.

Labelled memory diagram. poll 1: 100; poll 2: 0; poll 3: 0; poll 4: hexadecimal C D C D C D C D; poll 5: 100; poll 6: 80; poll 7: 80; poll 8: 80, highlighted. Groups: candidate 0: count 1, 2; new candidate: 1; candidate 80: count 1, 2, 3; accepted stays 100: no event; accepted becomes 80. No glitch value lasts three polls in a row, so none of them reaches the bot, and poll 5 clears the candidate by matching the accepted 100. The real change is accepted on its third matching poll, poll 8, and produces exactly one event.

Debouncing buys correctness with latency, and the cost is easy to work out. At twenty polls per second, polls are 1000 divided by 20 equals 50 milliseconds apart. The change is accepted on the third poll that shows it, which comes two gaps, 2 times 50 equals 100 milliseconds, after the first. That first poll can itself arrive up to 50 milliseconds after the real change, so every genuine change reaches the bot 100 to 150 milliseconds late. “Three polls” means nothing without the polling rate: at 100 polls per second the gaps are 10 milliseconds, and the same rule costs only 20 to 30 milliseconds.

That delay is cheap for “the match ended” and far too slow for “an enemy appeared.” Choose the requirement per value rather than once for the whole bot, and use debouncing for noisy or safety-critical transitions, not for every coordinate in a smooth animation.

Section: Add cooldowns after actions.

After requesting “end turn,” wait until a snapshot shows that the turn changed. Do not send the same input again merely because the next 50 milliseconds poll still shows the old turn.

A useful action record contains:

the requested action;

the time it was requested;

the state change that will confirm success;

a timeout;

a cancellation reason.

The pending action is a small state machine of its own. While it exists, the bot sends nothing, and each poll either confirms it, counts it down, or times it out:

Diagram labels, in drawing order: bot sends end turn once; old turn and polls_left above 0, count down by 1; turn changed, confirmed; old turn and polls_left is 0, timed out; Idle; Pending.

The timeout is a number of polls, so it becomes a time through the polling rate: starting from polls_left: 20 at one poll every 50 milliseconds gives the game 20 times 50 equals 1000 milliseconds, one second, to show the new turn.

Section: A safe responsive loop.

Copy and validate a snapshot.

Diff it against the previous accepted snapshot.

Debounce noisy state.

Feed events to the state machine.

Propose at most one bounded action.

Wait for its confirmation or timeout.

Stop immediately if the target disappears or the user cancels.

This design is useful far beyond game automation. File watchers, user interfaces, network clients, and monitoring tools all turn repeated polls into meaningful events while controlling duplicate work.

Make repeated requests idempotent when you can: sending the same request twice should have the same final effect as sending it once. “Select entity 7” can be idempotent; “move selection to the next entity” is not. Idempotence does not replace cooldowns, but it limits damage when a timeout hides a successful first action.
