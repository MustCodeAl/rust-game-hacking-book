Lesson 3.7 / Listening edition

When Game Values Are Encoded

Learn the difference between representation and security, trace small encode/decode paths, and implement a reversible value plus integrity check.

About 38 minutes

Section: Obfuscation changes the representation.

A game does not have to store health as the obvious integer 125. It might XOR the value with a key, rotate the bits, split it across fields, or store both a value and a check value.

This is obfuscation: it makes a value less obvious. If the running program can decode it, an analyst can usually trace that decoding logic too. Obfuscation is not the same as encryption, and neither one automatically makes a program fair or secure.

We use the book’s own toy type. Do not use this lesson to defeat protection in a third-party competitive game.

Searching memory for the number 125 may fail because that representation never exists for long. A better question is:

That last property is the important one: decoding the encoded value must recover the starting value for many inputs, not only one lucky example.

Follow the loop’s 100 case with its key hexadecimal A 1 B 2 C 3 D 4. The changing numbers below are all 32-bit values; the final result must return to the starting one:

Diagram walkthrough: Undo a transformation in the opposite order. Step 1: Start with the logical value. State: value: 100; key: hexadecimal A 1 B 2 C 3 D 4. Use value 100 and key hexadecimal A 1 B 2 C 3 D 4, the same key passed to both functions in the test loop. Step 2: XOR with the key. State: after XOR: hexadecimal A 1 B 2 C 3 B 0. 100 XOR hexadecimal A 1 B 2 C 3 D 4 gives hexadecimal A 1 B 2 C 3 B 0. This intermediate value is what encode rotates next. Step 3: Store the rotated representation. State: encoded: hexadecimal D 9 6 1 D 8 5 0. Rotate the 32-bit intermediate left by seven positions. The encoded value is hexadecimal D 9 6 1 D 8 5 0, which differs from the logical value 100. Step 4: Undo the rotation first. State: after rotate: hexadecimal A 1 B 2 C 3 B 0. decode rotates hexadecimal D 9 6 1 D 8 5 0 right by seven positions. That recovers the intermediate hexadecimal A 1 B 2 C 3 B 0 before applying the key. Step 5: XOR with the same key again. State: decoded: 100. hexadecimal A 1 B 2 C 3 B 0 XOR hexadecimal A 1 B 2 C 3 D 4 returns 100. The round-trip assertion checks this result against the original input. Encoding applies XOR then rotation; decoding reverses the order. This reversible toy representation is not a security guarantee.

This tag is educational, not cryptographically secure. An attacker who understands make_tag can calculate a matching tag. The useful lesson is structural: if a changed value is immediately rejected, look for another field or function that validates it.

Section: Dynamic keys change over time.

Some programs change a key when a level loads, an object is created, or a value is written. Reading the same field at several moments shows which events change the key:

Table columns: Moment; Logical value; Encoded bytes; Suspected key source.

Moment: spawn; Logical value: 125; Encoded bytes: E9 88 …; Suspected key source: constructor argument.

Moment: damage; Logical value: 100; Encoded bytes: 75 84 …; Suspected key source: same object field.

Moment: reload; Logical value: 125; Encoded bytes: different; Suspected key source: new session state.

Do not assume a value has “random encryption” merely because its bytes change. The cause may be an ordinary per-object key, a pointer-relative cookie, a checksum, or unrelated neighboring data.

Section: The analysis, step by step.

Start from the exact build and one object address.

Trigger one controlled change in your own target.

Capture the encoded field before and after.

Find the code that reads the field for a meaningful decision.

Trace every operand feeding the decoded result.

Express the operations as a small pure function.

Test the inverse over many inputs.

Look for validation or duplicate fields.

Section: What not to conclude.

❌ “XOR means this is secure encryption.”

✅ XOR can be one reversible step; security depends on a complete, reviewed construction and key handling.

❌ “The value changed, so my offset is wrong.”

✅ The representation or key may have changed.

❌ “One successful decode proves the formula.”

✅ Test several values, sessions, and objects.

❌ “An integrity field is impossible to reproduce.”

✅ First determine whether it is a checksum, a keyed MAC (message authentication code, which needs a secret key), or an authenticated-encryption tag.
