Lesson 3.2 / Listening edition

How Bytes Become Numbers and Pointers

Work out by hand how whole numbers, negative numbers, and f32 floats are stored, and exactly what a pointer's type controls.

About 24 minutes

The safe boundary keeps an address separate from an owned byte buffer. We still need to know how the copied bytes become a number or another address. The introductory memory lesson made two claims without proving them. The four bytes 00 00 20 41 are the whole number the large number shown when a u32 reads them, and 10.0 when an f32 reads them. And a pointer’s type decides what is read at the far end, while the pointer’s own size stays fixed.

This lesson proves both, one bit at a time, until you can work out every number yourself. It also explains how a whole number stores a minus sign.

Section: Every bit position is a power of two.

The memory introduction read a byte by adding up place values: 128, 64, 32, 16, 8, 4, 2, and

Each one is two times the one to its right, so each can be written as a number of twos multiplied together.

Number the positions from the right, starting at 0. Position n is then worth 2 multiplied by itself n times, which is written 2ⁿ:

Counting from 0 is what makes that line up: the rightmost position is 2 to the power of 0, and 2 to the power of 0 is 1, because no twos have been multiplied in yet.

Wider values keep going. A 32-bit value has positions 0 to 31, and its leftmost position is worth 2 to the power of 31 equals the large number shown.

The same notation counts patterns. Every extra bit doubles the number of patterns, so n bits make 2ⁿ of them: 8 bits make 2 to the power of 8 equals 256, and 32 bits make 2 to the power of 32 equals the large number shown. Those are the ranges in the introductory type table.

Section: Negative whole numbers.

A u32 spends all 32 bits on size, so it has no way to say “minus”. An i32 needs one, and it gets it with a simple change: the leftmost position is worth a negative amount. Every other position keeps its ordinary value.

It is easiest to see in a single byte, the i8 type. There, the leftmost position is worth minus 128 instead of +128:

Read as a u8, the same hexadecimal F F is 255. Read as an i8, it is minus 1. Nothing about the byte changed; only the value given to its leftmost position did.

In brief: A signed number is the same bits with a negative weight on the leftmost position, so hexadecimal F F is 255 or minus 1 depending on the type.

An i32 works the same way across four bytes, with its leftmost position worth minus 2 to the power of 31 equals minus the large number shown. So the bytes FF FF FF FF are the large number shown as a u32 and minus 1 as an i32. This scheme is called two’s complement. Its big advantage is that the C P U, central processing unit, can use one adding circuit for both types: add 1 to hexadecimal F F and the result carries out of the byte and leaves hexadecimal 0 0. Read as an i8, that is the correct answer to minus 1 + 1. Read as a u8, it is 255 + 1 wrapping around to 0, because 256 does not fit in a byte.

The i32 range falls straight out of this. The most negative value has only the leftmost bit set: minus the large number shown. The most positive value has every bit set except the leftmost. Those 31 bits add up to one less than 2 to the power of 31, for the same reason 64 + 32 + 16 + 8 + 4 + 2 + 1 made 127, one less than 128. So the top of the range is the large number shown.

Section: Fractions: how an f32 splits its 32 bits.

A whole number cannot hold 3.5 or 0.25. For that, an f32 uses its 32 bits in a completely different way. It follows a standard called IEEE 754, which is the rulebook nearly every C P U uses for fractional numbers.

The 1 in front of the point is missing from that list on purpose; step 5 below explains why it never needs storing. An f32 stores exactly those three things, in three fields that together use all 32 bits:

Here is 10.0 as it sits in memory: the bytes 00 00 20 41. Little endian put the least-significant byte first, so written most-significant first, the way you write a number, they are 41 20 00 00. In binary, hexadecimal 4 1 is 0100 0001 and hexadecimal 2 0 is 0010 0000.

Section: Step 2: read the exponent field as a whole number.

The next eight bits, 1000 0010, are an ordinary unsigned whole number, read with the same place values as any byte:

That is where the 128 and the 2 come from. The leftmost bit of an eight-bit field sits in position 7 and is worth 2 to the power of 7 equals 128. The second bit from the right sits in position 1 and is worth 2 to the power of 1 equals 2. No other bit is set, so the field holds 128 + 2 equals 130.

The real power of two is not 130. It is the stored number minus 127:

That 127 is called the bias, and it exists to solve a real problem. An eight-bit field can only store 0 to 255, with no minus sign. But exponents need to be negative too, because numbers smaller than 1 are written with a negative power of two, the way 0.0025 needed 10⁻³:

One fix would be to spend one of the eight bits on a minus sign. IEEE 754 does something neater: it shifts the whole range. Every stored exponent is the real exponent plus 127, so the reader subtracts 127 to get it back.

127 is used because it sits in the middle of 0 to 255, so there are about as many negative exponents as positive ones. The stored values 0 and 255 are kept aside for special cases, covered later in this lesson, which is why the table stops at 1 and 254.

The shift has a bonus. Because a bigger stored exponent always means a bigger number, two positive f32 values compare in the same order as their raw bit patterns do, which lets hardware compare floats cheaply.

Section: Step 4: read the fraction field.

The last 23 bits are the digits after the binary point. In decimal, the digits after the point are worth a tenth, a hundredth, a thousandth — each position a tenth of the one before. In binary each position is worth half the one before:

So the fraction 010 0000 … means 0 times ½ + 1 times ¼ + nothing else equals 0.25. That matches the .010 in 1.010 times 2 to the power of 3 from the start of this section.

Section: Step 5: put back the hidden 1.

Scientific notation always leaves one non-zero digit in front of the point. In decimal that digit can be anything from 1 to 9. In binary the only non-zero digit is 1, so in front of the point there is always a 1.

A bit that is always 1 tells you nothing, so an f32 does not store it. It is called the hidden bit, and the reader adds it back:

Section: What the rest of the fraction bits are for.

For 10.0, only one fraction bit is set and the other 22 are 0. They are not wasted. They hold finer and finer halves — ⅛, 1/16, 1/32, all the way down to 1/the large number shown — and 10.0 simply does not need any of them, because it is exactly 1.25 times 8. That is like writing 1.the numeric value shown in decimal: the extra zeros are real digits that happen to be zero.

Most numbers are not that tidy. Take 10.1. It is 1.2625 times 8, so the fraction has to be 0.2625. In binary, 0.2625 never ends: its digits settle into 0011 repeating forever, the same way 1 divided by 3 is 0.333… forever in decimal. The 23 bits store as much of it as fits, rounded at the last bit:

The stored fraction is 0.the numeric value shown…, so the value is 1.the numeric value shown… times 8 equals 10.the numeric value shown…, the closest an f32 can get. A debugger that prints enough digits shows 10.the numeric value shown. This is why float values found in games are rarely round, and why memory scanners let you search for a float within a small range instead of only an exact value.

The last fraction bit sets how fine that precision is. It is worth 1/the large number shown, and for numbers near 10 it is multiplied by 2 to the power of 3 equals 8, so neighbouring f32 values near 10 are about 0.the numeric value shown apart. That works out to roughly seven significant decimal digits.

Narration: Because most fractions are rounded, two floats that print alike can differ in the last bit. Exact equality tests can fail, so programs often allow a tiny margin.

Additional detail: Where the binary digits of 0.2625 come from.

To turn a fraction into binary digits, double it again and again. Each time the result reaches 1 or more, the next binary digit is 1 and you keep only the part after the point. Otherwise the digit is 0.

After the eighth line the leftover is 0.2 again, just as it was after the fourth line. So lines five to eight repeat forever, producing 0011 over and over: 0.2625 is 0.0100 0011 0011 0011 … in binary. The fraction field holds the first 23 of those digits, rounded at the last one.

Doubling works because each doubling moves the binary point one place to the right, pulling the next digit in front of it.

The exponent-0 rule also explains what the bytes for an integer 100 mean as a float. Read 64 00 00 00 as an f32 and, most significant first, it is this value: sign 0, exponent field 0, fraction 100 out of the large number shown. With the hidden digit off and the power fixed at 2⁻¹²⁶, the value is 100 divided by the large number shown times 2⁻¹²⁶, about 1.4 times 10⁻⁴³: a decimal point, then 42 zeros, then 14. A u32 read of the same bytes gives 100.

Section: What a pointer’s type tells the program.

Suppose a pointer holds hexadecimal 5 0 0 0, where the bytes are 00 00 20 41:

Following that address through a *const u32 reads all four bytes as the large number shown. Through a *const f32, the same four bytes mean 10.0. Through a *const u8, it reads only the first byte, 0. The pointee type decides how many bytes to read at the destination and how to interpret them. Two more facts complete the picture: why the pointer’s own size never changes, and how the pointee type controls a pointer that moves.

Section: The pointer’s size comes from the process.

A pointer has to be able to hold any address the process might use. A 32-bit process numbers its memory with 32-bit addresses. That gives it 2 to the power of 32 equals the large number shown possible addresses, from 0 to the large number shown, and a pointer needs all 32 bits — 4 bytes — to name any one of them. What it points to plays no part: a pointer to a single byte and a pointer to a 2,000-byte player object are both 4 bytes. A 64-bit process uses 64-bit addresses, so every pointer in it is 8 bytes.

Rust’s usize, the pointer-sized whole number from Lesson 3.1, follows the same rule: 4 bytes in a 32-bit program, 8 in a 64-bit one. So a 64-bit tool reading a 32-bit game’s pointers must read 4 bytes for each one, even though its own usize is 8.

Section: The pointee type sets the step size.

The pointee type also decides how far a pointer moves. Adding 1 to a pointer means “the next value of this type”, not “the next byte”. Rust writes this p.add(1), and makes you wrap it in unsafe, because the compiler cannot check that the new address still lands inside the list:

hexadecimal 0 A is 10, hexadecimal 1 4 is 16 + 4 equals 20, and hexadecimal 1 E is 16 + 14 equals 30. A pointer to a 64-byte structure would step 64 bytes at a time.

Alternative: Think of stepping along a row of equal boxes: add 1 and you reach the next box, however big. Bigger boxes mean longer steps in bytes.

Section: None of this is stored in memory.

The pointee type lives in the source code and in the compiler, which uses it to choose the right instructions: a four-byte whole-number read, a float load, or a one-byte read. The compiled game keeps only those instructions. When you study a game, you work out what a pointer points to the same way you work out any other type: from what the code does at the destination.

The same bytes can describe a whole number, a fraction, or an address, depending on the width and interpretation selected by the code. Knowing that representation still does not prove which object the bytes belong to or whether its address remains valid.
