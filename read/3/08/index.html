Lesson 6.1 / Listening edition

What a D L L, dynamic link library, Function Promises Its Caller

Infer an exported function's parameters, calling convention, result, and responsibility for memory cleanup before wrapping it in a small typed API.

About 28 minutes

The executable-analysis chapter showed how a D L L export name leads to a function address. Finding that address does not tell us how to call the function. Before our code becomes a library inside another process, we need the agreement between caller and callee: what values cross the boundary, where they arrive, and who owns any memory they refer to.

The earlier text lesson supplied one part of this agreement: a string pointer had to refer to the right encoding and remain valid for the call. A D L L export requires the same care even when its name is visible.

Section: A function name is not a contract.

A D L L export table may reveal a name such as gha_start, GetPlayer, or FormatMessage. That name only tells you that other code can locate the function. It does not fully explain:

which arguments the caller passes;

where those arguments arrive;

what the return value means;

which side owns pointed-to memory;

whether the call changes global state;

whether it is safe to call more than once.

Recovering that call contract is interface reversing. We will practice on this book’s own Windows D L L, where the source is available afterward for checking our conclusions.

Section: Reconstruct four parts of every boundary.

Treat a machine-level function boundary as four connected contracts:

Representation: How many bits does each value use, and is it an integer, float, pointer, flag set, or structure?

Transport: Which registers or stack locations carry arguments and results?

Ownership: Who allocates, may mutate, and eventually releases pointed-to data?

Lifetime: For how long do those addresses and returned views remain valid?

Calling conventions mainly answer transport. They do not answer ownership or lifetime. A function can correctly receive a pointer in r c x and still crash later because the caller freed the buffer too early. Likewise, a return value in r a x might be a borrowed pointer, an owned allocation, a handle, or merely a status code.

In brief: A callable address still needs a correct signature, memory ownership, and a lifetime agreement.

Each part of the contract follows from something the machine code does. A callee that reads four bytes through the pointer and never stores it needs only a short read-only borrow. A callee that saves the pointer in a global needs the data to outlive the call.

Section: Begin with the caller.

On 64-bit Windows, the first four integer or pointer arguments normally arrive in r c x, r d x, r 8, and r 9. A return value normally leaves in r a x. On 32-bit Windows, several calling conventions exist, so also inspect stack cleanup and decorated export names.

Section: Prove the calling convention.

A source-level A P I can say that a function accepts one address and returns a number. The A B I answers the machine-level question of where that address arrives. On a 32-bit build, one convention might put it in a register while another expects it on the stack. The functions can look identical at the source level, yet the callee reads the wrong location if caller and callee disagree.

Alternative: Picture the A B I as labelled delivery slots: agreeing on the parcel means little if each side uses a different slot.

A wrong A B I can appear to work in one small test and still corrupt registers or the stack. The call itself may return without crashing; the damage shows up later, when an unrelated function reads garbage from a register it expected the callee to preserve, or when a mismatched stack-cleanup convention leaves e s p off by a few bytes and a later ret lands somewhere nonsensical. Check:

Which architecture is the caller and D L L?

Who removes stack arguments on 32-bit builds?

Does the callee return with a plain ret or ret N?

Does a decorated name encode argument bytes?

Do several calls return with the stack pointer unchanged?

For x64 Windows there is one main user-mode convention, but argument type and ownership can still be wrong.

Section: Working practices for an undocumented D L L.

Never guess a function pointer type and “try it” in an important process.

Use the disposable course fixture; a contract recovered from it applies to that exact build.

Treat every pointer’s size, mutability, lifetime, and ownership as a separate question.

Preserve an Unknown result path.

Keep loading, resolving, converting, calling, and unloading as visible stages.

This same method works for undocumented game plug-ins, supported mod SDKs, and old middleware. The goal is not merely to make one call succeed. The goal is to explain the interface well enough that a small wrapper can enforce it.

The contract gives a function address meaning: it tells a caller which values are allowed and which obligations survive the call. In-Process DLLs and Loader Boundaries builds the small D L L used here. Its explicit start and stop functions turn the recovered agreement into an interface whose loading, work, and cleanup can be followed in order.
