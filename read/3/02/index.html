Lesson 3.3 / Listening edition

How External Tools Read Game Memory

Open the target, read a verified address, and write through a small checked process-memory wrapper.

About 24 minutes

Section: External means “a separate process”.

Our tool runs beside the game, not inside it. Windows must grant a process handle with specific rights before the tool can read or write memory.

An address makes sense only in a process’s address space. The number hexadecimal 5 0 0 0 can exist in both processes without naming the same bytes. The process matters as much as the numeric address:

Windows maps virtual addresses separately for each process. Reading a local pointer with the same number would inspect the tool’s own memory. A process handle names the target and carries the rights granted for this opening; the Windows read uses that handle with the target address and a byte count. Lesson 11.6 later examines handles in more depth.

That read is the Windows function ReadProcessMemory. Its arguments split cleanly into what belongs to the game and what belongs to the tool:

ReadProcessMemory, argument by argument

hProcesshandlerequired

The process handle, opened with the right to read (PROCESS_VM_READ). It says which process’s address map to use.

lpBaseAddressaddress in the gamerequired

Where to start reading. To the tool this is only a number, so it is never dereferenced locally.

lpBufferaddress in the toolrequired

Where Windows stores the copied bytes: memory the tool owns, with room for at least nSize bytes.

nSizebytesrequired

How many bytes to copy.

lpNumberOfBytesReadbytes, optional

Where Windows reports how many bytes were actually copied. A tool that ignores it can decode stale bytes left in its buffer.

return valuenonzero on success

Zero means the read failed. GetLastError then says why, such as ERROR_PARTIAL_COPY (299) when only part of the range could be read.

For this lab, the program discovers wesnoth.exe with the Windows ToolHelp A P I, application programming interface,, opens it, resolves the verified pointer chain, and performs the guarded write. There is no P I D, process identifier, or raw-address placeholder for the reader to fill in.

An external tool cannot dereference a target-process pointer directly. Windows mediates the boundary, and the handle represents the particular access the observer was granted:

The returned bytes belong to the observer, but their interpretation is valid only for the target build and moment that justified the layout. A write is a separate, stronger capability and needs its own expected-value check.

In brief: An external tool asks Windows to copy bytes out of the game, then reads its own copy. A write is a stronger power and needs its own check.

Section: Own the handle with a type.

A Windows handle is an opaque ticket stored in one process’s handle table. It is not the process, file, event, or section itself, and it is not an address you should dereference. Windows uses the ticket to find the kernel-managed object and to remember which access rights this particular opening received. Two handles can therefore name the same object while granting different permissions.

That gives a handle four rules:

Scope: a handle value is normally meaningful only in the process whose handle table contains it. DuplicateHandle can deliberately create another.

Rights: OpenProcess(PROCESS_VM_READ...) asks for a capability. The returned handle carries only the rights Windows granted for that opening.

Lifetime: the handle stays valid until its owner closes it. Closing the last handle to many kernel objects lets Windows destroy that object.

Correct closer: many kernel-object handles use CloseHandle, but not every Windows value does. SOCKET, HKEY, HMODULE, and HWND follow their own APIs and ownership rules. Never call CloseHandle merely because a type’s name begins with H.

Section: Make failure useful.

Test these cases:

wrong P I D;

target closed;

malformed hex address;

unreadable address;

expected value does not match;

pointer in the chain is zero.

A good low-level tool is not the one that never sees errors. It is the one that sees errors clearly and stops before making a bad write.
