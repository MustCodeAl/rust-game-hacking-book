OpenGL Draw Calls and State

Understand what indexed OpenGL draws request, how bound state and shader inputs change their meaning, why many small draws cost frame time, and why observation must keep the render thread moving.

Section: C P U, central processing unit, submission and G P U execution overlap.

The C P U usually records commands faster than the G P U completes them. A draw call returning does not mean its pixels are finished. Reads that force the G P U to catch up can stall both processors. The hook sees submitted work: it runs when the C P U queues a draw, not when the G P U finishes its pixels.

Section: A hook sits on the program’s critical path.

The render thread has a deadline: finish enough work for the next frame. A hook adds work to a path that may execute thousands of times per second. Even memory-safe code can cause stutter if it allocates, waits for a lock, formats strings, or writes files there.

Narration: A tiny delay repeated for thousands of draws can consume the frame budget. Move formatting and disk writes away from the render thread.

Split the design into two rates:

the capture path copies a tiny fixed-size sample and returns immediately;

the analysis path runs later on a worker and may aggregate, label, or save bounded results.

The render thread’s work ends at try_send; everything slow happens on the worker’s schedule. Measure both dropped samples and time spent in the hook. A dropped sample leaves a gap in the log, while blocking slows the very frames you are trying to measure.

Section: Shaders turn vertex records into pixels.

A shader is a small G P U program invoked many times in parallel. Two stages are central here:

a vertex shader reads one vertex (and often matrices) and produces clip-space position plus values to interpolate;

a fragment shader runs for candidate covered samples and produces a color, depth, or another render-target output.

Values such as texture coordinates and normals are interpolated across a triangle. The fragment shader usually does not receive the original vertex value. This is why a draw’s texture, program, uniforms, and vertex layout are part of its identity.

Older fixed-function OpenGL calls hide these programs behind predefined state, but the pipeline still performs equivalent transformations and color calculations.

Section: What a shader reads.

A shader works only with what the draw has bound for it:

Interpolated inputs, the per-vertex values blended across the triangle.

Uniforms, values that are the same for every invocation of one draw, such as the matrices, a light’s colour, or the time since the game started.

Textures and buffers, images it can sample at a (u, v) position and arrays of data it can read, bound before the draw as part of the state from Lesson 7.2.

A small fragment shader that turns a texture grey shows how little a shader can be. It weights the red, green, and blue of the pixel by how bright the eye finds each:

For a pixel of (200, 100, 50), the grey is 0.299 times 200 + 0.587 times 100 + 0.114 times 50 equals 59.8 + 58.7 + 5.7 equals 124.2, so the pixel becomes about (124, 124, 124). A shader that reads the time as a uniform can animate: a brightness of 0.5 + 0.5 times sin(time) is 0.5 at time 0 and 1.0 at time 1.5708 (a quarter of a turn in radians), and it repeats.

Shaders are written in a shading language: GLSL for OpenGL, HLSL for Direct3D, WGSL for WebGPU. A driver, or the engine ahead of time, compiles them to the G P U’s own instructions. Engines that support several graphics APIs often write a shader once and translate it for each.

Section: Variants, instancing, and shaders that do not draw.

Variants. One shader source can have switches, written as #ifdef lines, such as “has a normal map” or “has fog.” Each combination compiles to a separate program, so three switches give 2 times 2 times 2 equals 8 variants. Engines compile the ones a scene needs, which is why a game can hitch the first time something new appears.

Instancing. To draw 1,000 copies of one tree mesh, the game makes one draw call with 1,000 instances. A buffer holds each copy’s transform, a 4 times 4 matrix of 16 four-byte floats, which is 64 bytes, so 1,000 copies take 64,000 bytes. Earlier we saw that one draw can contain many objects; instancing is the deliberate version of it.

Compute shaders. A compute shader is not part of drawing. It is a general G P U program that runs once for each item in a grid of work, reading and writing buffers. Engines use it for particles, culling, mesh deformation, and post-processing.

Post-processing shaders. A fragment shader run over a full-screen rectangle, reading the finished picture as a texture, produces effects such as bloom and colour grading (Lesson 7.2).

Extending the standard material. Engines let a game add its own shader code and extra vertex data, such as a per-vertex wind weight, to a standard material instead of rewriting it.

Section: Why many small draws cost frame time.

Each draw call costs the C P U something even if the G P U’s share is tiny, because the driver checks the bound state and builds the commands. Suppose, as an illustration, one draw costs 5 microseconds of C P U time. Then 10,000 draws cost 10,000 times 5 equals 50,000 microseconds, which is 50 milliseconds, three frames of the 16.67 milliseconds budget from Lesson 4.1, with the G P U waiting. Instancing, merging meshes that share a material, texture atlases, and culling (Lesson 7.2) all exist to cut the number of draws.

A stress test finds the limit by multiplying one thing, such as cubes, sprites, lights, animated characters, or text, and watching the frame time. If 1,000 cubes take 4 milliseconds and 4,000 take 16 milliseconds, each costs 0.004 milliseconds and the 16.67 milliseconds budget runs out at about 16.67 divided by 0.004 equals 4,167 cubes. Halving the window’s pixel count tells you which processor is the limit: if the frame time does not change, the C P U, not the G P U, is the bottleneck.

This is a classification problem. A threshold such as count greater than 500 separates the examples you observed, not necessarily the concept “player.” Test it against weapons, detailed scenery, menus, different models, and different graphics settings. Report false positives (something your classifier caught that is not a player) and false negatives (a player your classifier missed) instead of quietly turning a correlation into a definition.

glDepthRange(near, far) controls where a fragment’s depth lands in the depth buffer after projection, by remapping the normalized -1..1 range onto whatever window-space interval you pass in. The default call is glDepthRange(0.0, 1.0): keep every fragment’s real depth. Calling glDepthRange(0.0, 0.0) instead collapses that mapping to a single point — every fragment’s stored depth becomes 0.0, the value reserved for the nearest possible surface, no matter how far away the vertex actually was. On its own that would not help, because the depth test would still reject a highlighted fragment sitting behind whatever was already drawn there. Switching glDepthFunc from GL_LEQUAL to GL_ALWAYS removes that objection: the test now passes unconditionally, so the fragment collapsed to depth zero is drawn regardless of what is already in the buffer. It is the combination — flatten the depth, then stop testing it — that pushes highlighted geometry through walls; neither call does it alone.

Section: Restore graphics state.

OpenGL is a state machine: a call changes settings that remain active until another call changes them. This middle-of-function cave cannot surround one typed glDrawElements call, so it restores the normal state when the next non-highlighted draw arrives and when the feature is disabled. Pressing End also disables the mode before removing the code patch. That ordering prevents the game from being left with GL_ALWAYS active.

State restoration must match what was changed. A robust typed wrapper queries or tracks the previous depth function, depth range, enabled client arrays, color, and bindings. Restoring guessed “defaults” works only until another legitimate render pass enters with different state. A middle-of-function cave has fewer safe options, which is a real limitation of that interception point rather than an implementation detail to ignore.
