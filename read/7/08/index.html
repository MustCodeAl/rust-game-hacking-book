Lesson 14.2 / Listening edition

Call Tracing and Bounded Logs

Connect scanning, decoding, breakpoints, and bounded logging to a trace of calls made by a running game.

About 35 minutes

Section: Define the question.

A call logger should not mean “break on every call in the whole process.” That would be noisy and slow.

Choose:

one module;

one executable section;

one known caller range or target function;

one small time window;

a maximum number of events.

This scope is not just a performance setting. It gives the log a meaning. “These calls happened while one turn ended inside this verified module range” is a result you can reproduce. “The process called thousands of things” is mostly noise.

In brief: A useful trace answers one bounded question; collecting everything can bury the behavior you wanted to understand.

Section: What a call instruction really does.

A function call has two jobs:

remember the address of the instruction that should run afterward;

move the instruction pointer to the called function.

On 32-bit x86, a common direct call begins with opcode E8 followed by a signed 32-bit relative displacement. The C P U, central processing unit, adds that displacement to the address immediately after the call. A disassembler performs this calculation and exposes the final target.

Predict first

At this value the five bytes are E8 4B 00 00 00: the opcode E8, then the displacement this value stored lowest byte first.

Which address does this call go to?

Answer: this value. The next instruction is at this value + 5 equals this value, and this value + hexadecimal 4 B equals this value. The call also pushes this value, so ret comes back there.

An indirect call such as call e a x or call [e c x+8] gets its destination from a register or memory at runtime. Static bytes alone do not reveal one final target, so the first course logger deliberately records only direct calls.

Section: Static discovery and live observation are different jobs.

The logger does not place a breakpoint on every byte equal to E8. That byte may appear inside an immediate value or data. Instead, iced-x86 walks complete instructions and reports their flow-control kind.

Section: Bound the software breakpoints.

Options include:

one breakpoint on a specific call site;

one breakpoint at a target function entry;

a small rotating set;

an in-process instrumentation hook for a practice program.

Start with one entry breakpoint while learning the state machine. The completed course tool expands to verified direct calls in readable executable regions, excludes known noisy sites, deduplicates addresses, and applies a hard 2,000-breakpoint cap. More instrumentation multiplies state and performance cost.

A software breakpoint changes the first byte of an instruction to hexadecimal C C, the one-byte int3 instruction. When the C P U executes it, Windows pauses the thread and reports EXCEPTION_BREAKPOINT to the debugger. The original E8 must be remembered so the real call can still execute and can later be restored.

Section: The two-event breakpoint cycle.

One breakpoint hit is not enough. If the debugger immediately writes hexadecimal C C back at the same address and continues, the thread hits it forever. The logger temporarily restores the call and single-steps exactly one instruction:

Alternative: Treat restore and re-arm as two separate stops: the original call needs a brief clear path before the breakpoint can watch it again.

At the breakpoint event, Windows reports the address of int3. The logger:

confirms the address belongs to its breakpoint map;

restores the original E8 byte;

opens the event thread and reads its CONTEXT;

rewinds e i p to the call address;

sets bit 8 of e f l a g s, the trap flag;

records that this thread is stepping this call;

continues the event.

The C P U now executes the real call. Because the trap flag is set, Windows pauses after that one instruction with EXCEPTION_SINGLE_STEP. At this moment e i p contains the call destination. The logger clears the flag, reinstalls hexadecimal C C at the call site, removes the thread from the stepping map, and prints the source and destination.

The stepping map is keyed by thread ID because several game threads can hit different breakpoints. A single global “currently stepping” variable would mix their state.

Section: Protect the target.

Stop logging when:

the event cap is reached;

the time window expires;

the target exits;

event drops exceed a threshold;

the user requests stop;

a breakpoint cannot be restored.

These conditions form the logger’s safety envelope. The event cap bounds memory and terminal output. The time cap bounds disruption. The drop threshold detects a writer that cannot keep up. A restoration failure stops the experiment because continuing would leave the target executing altered code whose ownership is uncertain.

Section: Divide responsibility with explicit types.

The complete executable uses two maps:

Code example. The code’s comments explain: 🔁 Address to displaced byte: everything needed to restore target code. 👣 Thread to call site: which original instruction is between restore/re-arm.

breakpoints maps each call address to its original byte. A BTreeMap also restores in deterministic address order, which makes diagnostics repeatable. stepping maps a thread ID to the call it is temporarily executing. A HashMap gives direct keyed lookup when the single-step event arrives.

The types prevent two different facts from being blurred together: “this address is patched” and “this thread is between restore and re-arm.”

Section: The Windows debug-event contract.

WaitForDebugEvent returns one pending event. Until the debugger calls ContinueDebugEvent, target threads remain stopped. Therefore every successful wait must lead to exactly one continue, including error paths.

Some event variants transfer handles to the debugger. The logger closes process, thread, and image-file handles after reading the active union member selected by dwDebugEventCode. It does not guess which union field is valid.

The AttachGuard is the last line of cleanup. If ordinary error propagation leaves the event loop, Drop attempts to detach. Breakpoint restoration still happens explicitly first because detaching a process whose code still contains course hexadecimal C C bytes would be unsafe.

It excludes two known noisy call sites from the historical lab. When a call fires, it restores E8, rewinds e i p, sets the trap flag, executes the real call once, records the destination e i p, reinserts hexadecimal C C, and continues.

Section: Compare a trace with a run that changed nothing.

One trace lists what ran while it recorded, but not which calls the action caused: most of them belong to drawing, input and timers that run anyway. To separate the two, fix the scenario first (the build, the save, the logging window and the event cap) and record it twice without changing anything. Then record it once more with a single change, such as recruiting one unit before ending the turn.

The two unchanged runs show how far the counts move on their own. A function the game calls once per frame runs as many times as frames fit in the window, and that depends on timing, so even identical runs disagree. A count in the changed run points at the change only when it falls outside the range the unchanged runs produced.

Predict first

Two runs that only end the turn called wesnoth.exe+hexadecimal 0 E 7 7 1 0 212 and 219 times. A third run that first recruits one unit called it 215 times.

Does recruiting change how often +hexadecimal 0 E 7 7 1 0 runs?

Answer: The counts cannot tell: 215 lies inside the 212 to 219 of the identical runs. A count points at the change only when it falls outside what unchanged runs produce. 215 is inside, so this function may or may not take part in recruiting, and these counts cannot separate the two.

Additional detail: Optional build reference: read the complete source in six passes.

The full call_logger.rs is longer than the scanner because it owns a live state machine. Read it in this order:

Constants and guards — caps, trap flag, known exclusions, detach cleanup.

Thread context helpers — open only the event thread and get or set its suspended register state.

Static discovery — copy executable regions and let iced-x86 return verified call instructions.

Breakpoint transaction — save E8, install hexadecimal C C, and roll back already-installed sites on partial failure.

Exception state machine — pair each breakpoint event with a later per-thread single-step event.

Event loop and shutdown — continue every event once, close transferred handles, restore bytes, and detach.

Do not begin at main and dive into every Windows name. First locate these six responsibilities; then read the helper used by the phase you are studying.
