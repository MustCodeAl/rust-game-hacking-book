Lesson 5.2 / Listening edition

File Offsets, RVAs, and Live Addresses

Connect positions in a PE file to relative virtual addresses and the addresses Windows gives its loaded modules.

About 28 minutes

Section: Keep four address terms separate.

The PE, portable executable, map in Lesson 5.1 told us that an instruction can have one position in the EXE file and another in a running process. Suppose your debugger recorded an instruction at hexadecimal 0 0 7 C C D 9 1 yesterday. To find it after restarting the game, you need to know which part of that number belonged to the module and which part Windows chose for that run.

We will use four names for the four different positions involved:

a preferred image base is where the file would like to be loaded;

a live module base is where Windows placed it in this process run;

an RVA, relative virtual address, is a distance from the beginning of the module;

a virtual address is the final live address used by the CPU, central processing unit, .

An RVA is not a pointer stored in the game. It is arithmetic describing a location inside one loaded image. The PE file’s section table maps RVAs to sections such as code or data.

Do not confuse an RVA with a file offset. A file offset counts bytes in the EXE on disk. An RVA counts from the mapped image base after Windows has arranged sections according to virtual addresses and alignment. They can differ.

The complete vocabulary is worth making explicit:

Table columns: Name; Coordinate system; Typical formula.

Name: File offset; Coordinate system: Bytes from the start of the file on disk; Typical formula: section.raw_ptr + offset_in_section.

Name: RVA; Coordinate system: Bytes from the start of the mapped image; Typical formula: section.virtual_address + offset_in_section.

Name: Preferred VA; Coordinate system: Address requested by the PE headers; Typical formula: preferred_image_base + RVA.

Name: Live VA; Coordinate system: Address in this process now; Typical formula: live_module_base + RVA.

These are coordinates in different spaces. Adding a live module base to a file offset is the binary-analysis version of adding meters to seconds: the numbers fit in an integer, but the operation has no useful meaning.

The other illustrated RVA, hexadecimal 2 8 8 0, fails the raw-byte check: its hexadecimal 8 8 0 section offset lies in the zero-filled virtual tail.

A rigorous parser checks every subtraction and addition, validates section ranges against the actual file length, and rejects overlapping or impossible metadata. PE headers describe a file; they do not deserve blind trust merely because Windows-shaped field names were decoded.

ASLR, address space layout randomization,, Address Space Layout Randomization, changes the live base, while a game update can change the RVA. Checking both facts keeps an old note from turning into a believable but wrong address.

Section: Why an address moves.

Old notes often show an address such as hexadecimal 0 0 7 C C D 9 1. That may be the address from one run, not a permanent location.

Windows can load an executable at a different base address each run; that is what ASLR randomizes. The useful part that usually stays the same for an exact build is the distance from the module’s beginning: the Relative Virtual Address.

ASLR makes fixed absolute addresses less predictable. Windows can relocate an image when its PE metadata supports relocation. The module’s internal layout for that exact file usually stays the same, so base-plus-RVA reaches the same instruction even when the base changes.

Section: RVA is not a version check.

An RVA can move when the game is rebuilt. Keep all three checks:

exact supported game version;

live module base plus the version’s RVA;

exact original bytes or a unique pattern at the final address .

That is why the code-cave installers reject unknown bytes instead of hoping the address is close enough.
