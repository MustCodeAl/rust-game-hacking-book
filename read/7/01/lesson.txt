What a Windows Executable Contains

Section: Why an EXE needs a map.

A Windows .exe is not one solid blob of C P U, central processing unit, instructions. It is a Portable Executable, usually shortened to P E, portable executable. Its headers tell Windows where the code, read-only data, writable data, imports, resources, and relocation information live.

First we will learn the file’s map and use it to translate positions on disk into live addresses. Then we will ask two different runtime questions: where are candidate bytes or values, and which instructions actually execute? Scanners, a disassembler, a debugger, and E T W, Event Tracing for Windows, each answer a different part. Knowing the map keeps their addresses anchored to a real build.

The same section occupies a place in the file and a place in memory, and those two places are numbered differently. A position in the file is a file offset. A position in the loaded image is an R V A, relative virtual address,, a relative virtual address, meaning a distance from wherever Windows put the module. The layouts differ because sections have separate file and virtual alignments, zero-initialized data may occupy memory without taking equal file space, and Windows may apply relocations and resolve imports after mapping. A section row supplies the mapping information for converting a location in one layout to the corresponding location in the other; the numbers are related but not interchangeable.

Alternative: Think of printed page numbers versus e-book page numbers: one text, two numbers, and a contents table converts between them. The section table does that job.

Section: Find the P E and COFF headers.

The COFF header, named for the older Common Object File Format it comes from, is the small fixed block right after the four-byte P E\0\0 signature. It gives the basics a parser needs before anything else: which C P U the machine code targets, how many section rows follow, and how large the next header is.

Section: Linked code still needs a file-to-image map.

Static linking copies the needed library implementation into the output module. D L L, dynamic link library, linking keeps that implementation in another module and records how to find its exported functions. An import library can help link an EXE to a D L L without copying the D L L’s implementation into the EXE. Microsoft’s D L L overview describes load-time and run-time linking. Once loaded, the D L L uses the calling process’s virtual address space and the calling thread’s stack.

Whichever linking choice produced the module, its file bytes still need the section map. For an illustrative .text row with raw start hexadecimal 4 0 0 and R V A start hexadecimal 1 0 0 0, file byte hexadecimal 5 2 0 is hexadecimal 1 2 0 bytes into the section. Its R V A is hexadecimal 1 1 2 0; at live base this value, its virtual address is this value. This example assumes the byte lies inside that section’s file-backed data.

In brief: Static storage is a lifetime term; static linking is a packaging choice. Neither makes a file offset equal to a live virtual address.
