Lesson 5.1 / Listening edition

What a Windows Executable Contains

Use the PE header and section map to understand where a Windows executable keeps code, data, imports, and addresses.

About 24 minutes

Section: Why an EXE needs a map.

A Windows .exe is not one solid blob of C P U, central processing unit, instructions. It is a Portable Executable, usually shortened to P E, portable executable. Its headers tell Windows where the code, read-only data, writable data, imports, resources, and relocation information live.

First we will learn the file’s map and use it to translate positions on disk into live addresses. Then we will ask two different runtime questions: where are candidate bytes or values, and which instructions actually execute? Scanners, a disassembler, a debugger, and E T W, Event Tracing for Windows, each answer a different part. Knowing the map keeps their addresses anchored to a real build.

The same section occupies a place in the file and a place in memory, and those two places are numbered differently. A position in the file is a file offset. A position in the loaded image is an R V A, relative virtual address,, a relative virtual address, meaning a distance from wherever Windows put the module. The layouts differ because sections have separate file and virtual alignments, zero-initialized data may occupy memory without taking equal file space, and Windows may apply relocations and resolve imports after mapping. A section row is the rule for converting a location in one layout to the corresponding location in the other; the numbers are related but not interchangeable.

Section: Find the P E and COFF headers.

The COFF header, named for the older Common Object File Format it comes from, is the small fixed block right after the four-byte P E\0\0 signature. It gives the basics a parser needs before anything else: which C P U the machine code targets, how many section rows follow, and how large the next header is.

The cap of 96 is deliberately boring. Real course targets do not need thousands of sections, so a wild count means the offset is wrong or the file is damaged.

Section: Tell PE32 from PE32+.

The optional-header magic is hexadecimal 1 0 B for PE32 and hexadecimal 2 0 B for PE32+. Because their fields have different sizes, the image-base offset changes:

The games used by the memory-patching chapters are the specified 32-bit course builds, so their magic should be hexadecimal 1 0 B. The parser supports both formats because a tool should explain what it found instead of guessing.
