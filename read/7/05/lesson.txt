Memory Regions and Value Scanning

Section: The scanner pipeline.

The pattern scanner in Lesson 5.4 searched executable bytes for a known instruction shape. The first gold scan from Chapter 1 asked a different question: “Which readable data locations currently hold the visible value 100?” A memory scanner answers that question by collecting candidates, then checking which of those same addresses follow the gold as it changes to 85 and 92.

That difference determines the pipeline. We describe readable memory, copy bounded chunks, interpret four bytes as a value, and retain only candidates that follow the controlled change:

Diagram. From Enumerate regions to Keep readable data. From Keep readable data to Copy bounded chunks. From Copy bounded chunks to Decode typed values. From Decode typed values to Store candidate addresses. From Store candidate addresses to Filter with the next scan.

The Windows calls are only the outer shell. Candidate filtering uses checked local slices.

🔎 A filter pass re-reads only the addresses already on the candidate list, so it can remove candidates but never add them. If the list grows, the program rescanned memory instead of filtering; if it stops shrinking, check the value type, the range, and the filtering rule.

Section: What the scanner is searching.

A process does not own one giant, equally readable byte array. Windows divides its virtual address space into pages and reports neighboring pages with similar state as regions.

Table columns: Region fact; Question it answers.

Region fact: State; Question it answers: Is this address range committed, reserved, or free?.

Region fact: Protection; Question it answers: Can the target read, write, or execute it? Is it guarded?.

Region fact: Base address; Question it answers: Where does the region begin?.

Region fact: Region size; Question it answers: Where must the region walk advance next?.

VirtualQueryEx describes these facts; it does not copy the target bytes. ReadProcessMemory performs the copy later. Keeping “describe” and “read” as separate steps makes failures easier to explain.

A number such as 100 is also not self-identifying. The bytes 64 00 00 00 represent 100 only when interpreted as a little-endian u32. The same four bytes can be part of a pointer, an instruction, a larger number, or unrelated data. That is why the first scan returns candidates rather than an answer.

Section: Repeated scans are set intersection.

Imagine the first scan finds 40,000 addresses containing 100. You spend 15 gold and scan for 85. Most unrelated addresses do not make that exact transition, so perhaps 18 survive. Earn 7 gold and scan for 92; perhaps one remains.

Diagram. From all readable addresses to 40,000 candidates. The connection is labelled: scan: value equals 100. From 40,000 candidates to about 18 candidates. The connection is labelled: value became 85. From about 18 candidates to 1 candidate. The connection is labelled: value became 92.

Each scan keeps only the addresses that already survived every earlier one — the candidate set only shrinks.

The scanner never rescans the whole process after the first pass. It re-reads only the surviving addresses. This makes later passes faster and preserves the history needed for filters such as increased, decreased, changed, and unchanged.

Section: How the work grows.

How much faster is worth working out, because the same reasoning decides whether any tool feature is usable. Suppose the game has 400 MiB of readable memory and each candidate is a 4-byte value:

Table columns: Pass; What it reads; Bytes read.

Pass: first scan; What it reads: every readable byte: 400 times 1,048,576; Bytes read: 419,430,400.

Pass: second scan; What it reads: 40,000 candidates times 4 bytes; Bytes read: 160,000.

Pass: third scan; What it reads: 18 candidates times 4 bytes; Bytes read: 72.

The second pass reads about 2,600 times less than the first (419,430,400 divided by 160,000 approximately 2,621), and it no longer depends on how big the game is at all, only on how many candidates survived.

The first scan’s cost grows in step with its input: give the game twice the memory and the scan reads twice the bytes. Programmers write that as O(n), read “order n”, where n is the size of the input. Some costs do not grow at all: finding one candidate’s previous value in a hash table keyed by address takes about the same time with 40 candidates or 40,000, as Lesson 3.6 explains. That is O(1) on average: hashing one address chooses a bucket instead of reading the entire candidate list. Collisions and a badly overloaded table can make individual lookups slower, so this is not a promise of identical timing. And a loop inside a loop multiplies. Comparing every one of the 40,000 candidates with every other takes 40,000 times 40,000 equals 1,600,000,000 comparisons, 40,000 times the work of reading the list once, and doubling the candidates makes it four times worse. That is O(n²). Before adding a scan feature, ask what happens to the work when the memory or the candidate list doubles.

Section: Scan copied chunks.

Suppose the visible gold value is 1,000. The number becomes four little-endian bytes, E8 03 00 00, and the scan compares that byte pattern with each four-byte window in a copied chunk. Its base argument is the target address where that copied chunk began, so a match at local offset 12 becomes target address base + 12:

For an aligned-only scan, step by four. For a general scan, windows(4) checks every byte offset.

wanted.to_le_bytes() creates the exact four-byte representation used by the 32-bit Windows course games. .windows(4) yields overlapping four-byte slices, so a value may start at any byte. When a match appears, base + offset translates the local slice position back into the target’s virtual address.

The complete program reads 1 MiB chunks. Adjacent chunks overlap by three bytes because a four-byte value can begin in the final three positions of the earlier chunk. Without that overlap, a value split across the boundary would never exist in either local buffer as a complete four-byte window.

Labelled memory diagram. A[end minus 3]: E8, highlighted; A[end minus 2]: 03, highlighted; A[end minus 1]: 00, highlighted; B[0]: 00, highlighted. Groups: the u32 value 1,000 (bytes E8 03 00 00), split across the boundary. For example: if the value 1,000 begins three bytes before the end of chunk A, three of its bytes are the last bytes read into chunk A's buffer and the fourth is the first byte of chunk B's buffer. The 3-byte overlap gives the scanner one buffer where a complete u32 window still exists.

Section: Expect regions to disappear.

The target can free or change a region between enumeration and reading. Treat an unreadable candidate as removed, not as a reason to crash the scan.

This is a normal race, not necessarily a bug. Between the region query and the read, the game can free an allocation, change its protection, or exit. The scanner’s snapshot is always slightly behind the running process. A robust tool reports skipped work and continues with the candidates it can still read.

Section: Bound the work.

Set limits for:

maximum region size per read;

chunk size, such as 1 MiB;

total candidates;

total scan time;

supported value types .

A scan for a common value such as zero can produce millions of matches. Refuse or require a narrower range rather than exhausting memory.

Limits are correctness rules:

a chunk limit bounds each allocation and Windows copy;

a region limit avoids one suspicious mapping monopolizing the scan;

a candidate limit bounds local memory and later re-read time;

an output limit keeps the terminal usable;

a time or cancellation limit gives control back to the learner.

Without these limits, perfectly memory-safe code can still make an unusable program.

If the current value no longer equals candidate.previous, the address may be stale or the rule may have changed; the write must stop rather than overwrite newer state.

Section: Separate types.

Use a trait or enum for u8, u16, u32, i32, and f32 rather than casting everything to one type. Float searches need special handling for NaN and approximate comparisons.

Start with one type and make it correct. A small scanner with clear errors is a stronger project than a giant clone with undefined behavior.

For floating-point scans, exact byte equality is sometimes useful and sometimes misleading. NaN does not equal itself, -0.0 and 0.0 compare equal despite different bit patterns, and visible decimal text may round the stored value. A future ValueKind should state whether it compares bits, exact numeric values, or values within a tolerance.

This ordering explains why the program is more than a ReadProcessMemory loop. Its real job is maintaining trustworthy candidate state while the target keeps changing.

Section: Diagnose by phase.

Table columns: Symptom; Phase to inspect.

Symptom: Zero first-pass candidates; Phase to inspect: Value type, endianness, range permissions, or target build.

Symptom: Candidate cap reached; Phase to inspect: Initial value is too common; start from a less common value.

Symptom: Good first pass, zero second pass; Phase to inspect: Entered value, timing, or a value stored in another representation.

Symptom: Read failures grow rapidly; Phase to inspect: Target exited or memory layout changed during the scan.

Symptom: One address survives but write is refused; Phase to inspect: The value changed after filtering; scan again.

The refusal cases are successful safety behavior. They stop the program from writing to an address whose last read is out of date.
