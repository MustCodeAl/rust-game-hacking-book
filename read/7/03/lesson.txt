DLL, dynamic link library, Exports and Forwarded Names

Section: An export table is a DLL’s public index.

An import says, “my program needs this name from another image.” An export says, “other images may ask me for this name or ordinal.”

Windows uses these tables while loading executables and DLLs. Reverse engineers inspect them to understand a game’s dependencies, plug-in interfaces, graphics libraries, and engine boundaries before reading assembly.

An export table connects three parallel ideas:

Table columns: Piece; What it contains.

Piece: Name pointer table; What it contains: RVAs of public ASCII names such as SDL_Init.

Piece: Ordinal table; What it contains: Small indexes corresponding to those names.

Piece: Export address table; What it contains: RVAs of code, data, or forwarder strings.

Not every export needs a name. A DLL can export by ordinal only. This beginner tool lists named exports and reports the total number of address entries so the difference stays visible.

An ordinal is not simply a row’s position in the address table. The export directory also stores an ordinal base, commonly 1, and an export’s real public ordinal is ordinal_base + its index in the address table. A caller asking for “ordinal 5” with a base of 1 wants functions[5 - 1], not functions[5]. The parser below reads that base once and adds it back in for every named export so the printed ordinals match what the DLL actually publishes.

Labelled memory diagram. functions[0]: ordinal 1; functions[1]: ordinal 2; functions[2]: ordinal 3; functions[3]: ordinal 4; functions[4]: ordinal 5, highlighted. With ordinal_base equals 1, the export published as “ordinal 5” sits at index 4: functions[5 - 1], not functions[5].

Section: RVA, relative virtual address, is not a file offset.

An RVA, or relative virtual address, measures from the start of the mapped image, regardless of the live base Windows chose. A file offset measures from byte zero in the file on disk.

You cannot safely treat every RVA as a file offset. Sections can have different virtual and raw positions, and some virtual bytes have no stored file bytes at all.

The parser accepts an RVA only when it falls inside a section and its distance is smaller than SizeOfRawData. That last check prevents the parser from pretending zero-filled virtual padding exists in the file.

Treat every address-like number as belonging to a named coordinate system:

file offsets index the byte slice on disk;

RVAs index the mapped image relative to its base;

virtual addresses identify locations after the loader chooses a base;

table indexes select entries, not bytes.

Do not pass all four around as plain usize values. Small wrapper types such as FileOffset(u32) and Rva(u32) make accidental mixing visible and force conversions through one checked function.

The conversion is a partial function: some valid mapped RVAs have no file bytes, and malformed files may describe overlapping sections. Returning Option or Result is more accurate than inventing an offset.

Section: PE32 and PE32+ move the data directories.

The optional header is shaped differently for 32-bit PE32 and 64-bit PE32+. The magic value tells us which layout we have:

hexadecimal 1 0 b: PE32, data directories begin 96 bytes into the optional header;

hexadecimal 2 0 b: PE32+, data directories begin 112 bytes into the optional header.

Hard-coding one screenshot’s “export table is hexadecimal 7 8 after the PE, portable executable, signature” is brittle because that shortcut mixes header landmarks and assumes one layout.

Section: A forwarded export points to another name.

An export-address entry usually holds an RVA for code or data. If the RVA points back inside the export-directory range, it is a forwarder string instead, such as KERNELBASE.VirtualQueryEx or NTDLL.RtlSomething.

The loader follows that string to another DLL export. This is how Windows can keep a familiar public name while moving the implementation behind it.

Diagram. From AddressOfFunctions[i] a function RVA to inside export_rva..export_end?. From inside export_rva..export_end? to RVA of real code or data. The connection is labelled: no. From inside export_rva..export_end? to forwarder string, e.g. KERNELBASE.VirtualQueryEx. The connection is labelled: yes.

Section: Every byte from a file is untrusted input.

Even a game DLL you intended to inspect might be truncated, damaged, from the wrong build, or simply not a PE file. A parser should fail with a useful message instead of panicking or allocating several gigabytes because a count field contained nonsense.

This implementation uses five guardrails:

bytes_at checks every slice boundary.

checked_add catches integer wraparound.

The optional-header magic chooses the correct layout.

Section and export counts have teaching-tool limits.

Strings must terminate within 4096 bytes.

Validate from the outside inward. Prove the DOS header range before reading its PE offset, prove the PE and optional-header ranges before reading directories, then prove section and export ranges. A later valid-looking signature cannot make an earlier out-of-bounds read safe.

Section: Questions to answer from the output.

Does the file publish named exports, ordinal-only entries, or neither?

Which names look like a supported plug-in or library boundary?

Does an entry point to code/data or to a forwarder string?

Is the file PE32 or PE32+, and does that match the game build?

Can the same DLL name from two game installations have different exports?

Do not call an export merely because its name looks interesting. A name does not reveal the complete function signature, ownership rules, calling convention, or whether the API, application programming interface, is intended for outside use.
