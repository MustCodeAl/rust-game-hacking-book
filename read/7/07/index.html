Lesson 5.7 / Listening edition

Debug Events and Software Breakpoints

Understand how Windows debug events, breakpoint bytes, and thread state let a debugger pause and resume a real instruction.

About 24 minutes

Section: A debugger is an event loop.

The scanner in Lesson 5.5 found where a value was stored; the disassembler in Lesson 5.6 named instructions near an address. To learn which instruction actually changes Wesnoth’s gold during one turn, we need to pause when that instruction runs and inspect the live registers. A debugger provides that pause.

Windows reports events such as process creation, DLL, dynamic link library, loading, exceptions, and process exit. A breakpoint is one such event that this tool deliberately causes and then handles.

Diagram. From WaitForDebugEvent to Decode event. From Decode event to Inspect or update state. From Inspect or update state to ContinueDebugEvent. From ContinueDebugEvent to WaitForDebugEvent.

If the debugger forgets to continue an event, the target remains frozen.

Section: Own breakpoint state.

A software breakpoint replaces one instruction byte with hexadecimal C C. To let the original instruction run later, the debugger must remember both its address and that displaced byte. Section: Handle the int3 pause.

When a software breakpoint installed by this debugger fires:

suspend the relevant flow through the debug event;

restore the original byte;

move the instruction pointer back by one byte;

enable the CPU, central processing unit, trap flag for one instruction;

continue.

The next single-step exception lets the debugger reinsert hexadecimal C C and clear the trap flag.

This two-step cycle is why a breakpoint has state; it is not just one changed byte.

Section: Distinguish your exceptions.

Not every breakpoint exception belongs to your debugger. Windows and the target may use breakpoints internally.

Check:

exception code;

address;

whether the address is in your breakpoint map;

first-chance status;

current phase and thread.

Pass unhandled exceptions onward with the correct continue status.

Section: Debugging changes what you observe.

A debugger is a measuring instrument, and every instrument affects its subject somehow. A software breakpoint temporarily replaces one instruction byte. Pausing one thread can delay rendering, audio, input, or network work. Single stepping makes a short path take far longer than normal, and Windows can expose whether a process is being debugged.

That creates an important distinction:

Table columns: Result; What it shows.

Result: The behavior happens both attached and detached; What it shows: It is probably part of the target rather than a pause artifact.

Result: Only elapsed time changes while attached; What it shows: The debugger changed scheduling or timing.

Result: A flag or exception path changes while attached; What it shows: The target can observe the debugging environment.

Result: A byte differs at your breakpoint address; What it shows: Your debugger deliberately changed code to gain control.

On the course target, run the same input once without a debugger and once attached, logging inputs, chosen branches, elapsed time, and output both times. A difference that appears only while attached comes from the measurement, not from the game’s normal logic. That effect is called instrumentation bias: the tool used to measure a program changes what the program does.

Debugger-aware behavior usually comes from a small set of sources: flags, handles, exceptions, timing, instructions, memory, and interaction with the desktop. A change that appears only while attached traces back to one of them. This lesson intentionally does not turn those sources into concealment or bypass instructions.

Section: Keep FFI wrappers narrow.

Each wrapper should document handle ownership, pointer validity, buffer size, and structure initialization.

Section: Cleanup.

On detach or exit:

restore every armed breakpoint;

flush the instruction cache;

continue any pending event;

detach if the target is still running;

close every process and thread handle.

A debugger that pauses correctly but cannot cleanly detach is not finished.
