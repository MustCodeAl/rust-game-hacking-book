Lesson 9.3 / Listening edition

Protocol Capture and Message Framing

Learn how a short local capture reveals message direction, boundaries, and the bytes associated with one game action.

About 17 minutes

Section: Separate network layers before capturing.

Lesson 9.1 showed that one game message can arrive across two T C P, transmission control protocol, reads. A packet capture lets us inspect the bytes on the way, but its packet rows are not automatically game-message rows. We will send one distinctive lobby message, then follow its bytes in both directions.

An application message is not the same thing as an i p packet or T C P segment. Each layer has a different job:

T C P may split one game message across several segments or combine bytes from several messages in one segment. Retransmissions can repeat packet data. The receiving application sees an ordered stream, so protocol parsing needs its own framing rule such as a length prefix or delimiter.

A socket is an operating-system object representing one endpoint. A T C P connection is identified by source address, source port, destination address, and destination port—the four-tuple used below.

Section: Follow a join request beyond loopback.

Our capture stays local. To understand the wider journey, imagine a client joining match 42 and downloading its map from assets.example. Configuration, name lookup, delivery, and game permission solve different parts of that trip.

Section: Find a destination before connecting.

On a typical IPv4 LAN, DHCP gives a device an address lease and network configuration; options can supply a router and DNS servers. It configures the device, not the remote game’s identity. DHCP and its options specify that exchange. Static configuration and other address-assignment systems are also possible.

DNS resolves a name such as assets.example to records including i p addresses. A resolver can reuse an answer until its cache lifetime expires; name resolution does not deliver the map. The client then connects to the chosen endpoint. DNS concepts explain this separate lookup.

HTTP is the web’s request/response protocol. HTTPS carries that exchange over an authenticated, encrypted connection. A CDN can serve a cached map from an edge location. A cache miss may require an origin fetch; DNS answer caching and content caching have different lifetimes. Account requests still need their own authentication and cache policy. Cloudflare’s request journey shows these boundaries.

Section: Wrap the bytes across a LAN.

A LAN, or local area network, joins nearby devices through links such as Ethernet or Wi-Fi. In this example, an Ethernet frame carries an i p packet, which carries a U D P, user datagram protocol, datagram, which carries game bytes. This wrapping is encapsulation. A switch forwards link frames; a router forwards the i p packet onto another link with a new link frame. Physical signaling carries the bits on each link.

The OSI model names seven conceptual layers: application, presentation, session, transport, network, data link, and physical. The Internet’s T C P/i p model commonly groups application work, transport, Internet/i p, and link work. These models describe responsibilities, not seven mandatory headers. Our existing layer board remains useful: identify the job before assigning a name. Internet host requirements organize the protocol suite by these responsibilities.

The journey of one game messageHeaders are added on the way down, then removed on the way up. Play it step by step, or change the message size.

A 24-byte message becomes a 32-byte datagram, a 52-byte i p packet and a 70-byte frame: 46 of 70 bytes (66 percent) are wrapping.

Section: Sending computer.

User space Game code calls send()The message sits in the program’s own memory. The program hands it to the socket A P I, application programming interface; it builds no headers itself.

Kernel The kernel copies it into the socket’s send bufferThe operating system copies the bytes out of the program’s memory into a buffer owned by the socket. send() can return once the copy is made; that says nothing about arrival.

Kernel The transport layer adds its headerUDP adds 8 bytes: ports, length, checksum. T C P adds 20: ports, sequence and acknowledgement numbers, flags, window, checksum. The result is a datagram (U D P) or a segment (T C P).

Kernel The i p layer adds the i p headerTwenty bytes with the source and destination addresses, a time-to-live and the protocol number. The kernel also consults its routing table to choose the next hop and the outgoing interface. The result is a packet.

Kernel The packet waits in an output queueWhen several packets are ready, a queue decides which one the card gets next. Linux calls this the queueing discipline, or qdisc. Other systems have comparable queues under other names.

Kernel The link layer wraps it in an Ethernet frameA 14-byte header holds the next hop’s MAC address, this card’s MAC address and the EtherType (hexadecimal 0 8 0 0 means IPv4). A 4-byte check sequence goes at the end, usually computed by the card. A frame shorter than 64 bytes is padded.

Network card The driver hands the frame to the card, which sends bitsThe driver places a descriptor for the frame in a ring buffer in memory. The card reads the frame by direct memory access and turns each byte into signals on the cable or radio: bits.

Section: Between the computers.

On the wire A switch forwards the frameA switch reads only the Ethernet header and sends the frame out of the port where the destination MAC address was last seen. The i p packet inside is untouched.

On the wire A router moves the packet onto the next linkThe router throws away the old Ethernet header and check sequence, lowers the i p time-to-live by one, recalculates the i p header checksum and wraps the same packet in a new frame. The transport header and the data are not touched.

Section: Receiving computer.

Network card The receiving card accepts the frameThe card checks the destination MAC address and the check sequence; a damaged frame is dropped. A good frame is written into a ring buffer in memory by direct memory access, and the card raises an interrupt.

Kernel An interrupt, then deferred processingThe C P U, central processing unit, pauses its work to run a short interrupt handler, which schedules the longer work for later. On Linux that is a softirq run by ksoftirqd; on Windows it is a deferred procedure call. That work empties the ring buffer.

Kernel The Ethernet header is removedThe EtherType says the payload is IPv4, so the packet goes to the i p layer. The link header and trailer have done their one-hop job.

Kernel The i p header is checked and removedThe kernel verifies the header checksum and that the destination address is this computer, then reads the protocol number (17 means U D P, 6 means T C P) to choose the transport layer.

Kernel The transport layer finds the socketThe destination port (for T C P, the whole four-tuple) identifies the socket. T C P also acknowledges, reorders and discards duplicates. The data is placed in the socket’s receive buffer.

User space Game code calls recv()The kernel copies the bytes from the receive buffer into the program’s memory. Only now does the program see them. With T C P, one recv() need not return exactly what one send() sent, so the game must mark its own message boundaries.

Complete journey shown.

Maximum data in one Ethernet frame: 1,500 bytes of i p packet, so 1460 bytes of T C P data or 1,472 bytes of U D P data without fragmentation.

The same game bytes are wrapped inside a U D P datagram or T C P segment, an i p packet and an Ethernet frame. A router replaces the link wrapper for the next hop. The OSI/T C P-i p mapping is conceptual, not a literal count of wire headers.

Section: Choose the delivery contract, then the application protocol.

If middle bytes are lost, T C P recovers them before exposing later bytes in its ordered stream. U D P can deliver a later datagram without the missing one; the game decides whether to replace stale state or add its own recovery. Neither transport acknowledgment proves the server accepted a purchase. T C P and U D P specify those different contracts.

One lost packet: T C P waits, U D P moves onFive messages leave one per tick and need one tick to arrive. Packet 3 is lost on its first try. Choose other packets, or move through time.

Section: T C P Gives the game bytes in order, so one missing packet holds back everything after it..

Section: U D P Gives the game each datagram as it arrives, in whatever order, and never resends..

1 sent

1 lost on the way

1 sent again by T C P

1 reaches the computer

1 held back

1 handed to the game

T C P resends message 3 and gives the game all 5 in order, finishing at tick 7. Messages that had already arrived were held back: message 4 waits 3 ticks; message 5 waits 2 ticks. U D P gives the game messages 1, 2, 4 and 5 as each arrives and never delivers 3 on its own: the game decides whether to ask again or move on to newer data.

The timer is a simplification: real T C P can resend sooner when later packets arrive and the receiver keeps repeating the same acknowledgement. The ordering rule is real. T C P also needs a three-packet handshake before its first data; U D P can send at tick 0.

Additional detail: What each wrapper costs: a 8-byte U D P header or a 20-byte T C P header.

Section: T C P dot 20 bytes without options.

T C P application messages still need framing: a lost packet changes timing, not message boundaries.

A socket is the local operating-system endpoint already introduced above. A WebSocket is a two-way framed-message protocol, useful for browser lobby chat. The RFC 6455 handshake uses HTTP/1.1 Upgrade; wss protects the exchange with TLS, Transport Layer Security, which authenticates the server and protects data in transit. HTTP/3 also has a WebSocket mapping, so an Upgrade handshake is not universal. Game authorization remains separate.

QUIC v1 runs over U D P but supplies its own reliable streams and loss recovery, using TLS 1.3 for connection security. HTTP/3 maps HTTP requests and responses onto QUIC. Loss affecting one stream need not block unrelated stream delivery, although streams share connection congestion limits. QUIC is not “unreliable HTTP,” and HTTP/3 is not a synonym for every game’s U D P protocol. The standards are QUIC v1, QUIC with TLS, and HTTP/3.

Two message paths, two socket typesBoth end at a socket, but the layers above it differ. Point at a layer to read what it does.

Section: Other names belong at other boundaries.

Publishing the map might use FTP, which separates control and data connections, or SFTP, which transfers files over encrypted SSH. SFTP is different from FTPS, FTP secured with TLS. A web server might use FastCGI to pass requests to a persistent application worker; the player’s side still uses HTTP. Web3 applications may use blockchain-backed records, but a ledger is not a replacement for sockets or real-time match transport. Likewise, Base64 only encodes bytes: an encoded login value has not thereby been encrypted.

With those boundaries separate, return to the controlled local capture. We can now ask which interface, direction, and protocol layer produced each row.

Section: Capture answers “what crossed,” not “why”.

A network trace records bytes and timing at one capture point. It does not contain the sender’s variable names, the receiver’s interpretation, or any record of which UI action caused which packet. That link comes from changing one thing at a time:

capture a quiet baseline;

perform exactly one distinctive local action;

repeat the action with one changed input;

compare both directions and several repetitions;

confirm the candidate fields in the open-source client or server.

In brief: A capture records traffic. Controlled actions and repeat comparisons connect those bytes to meaning.
