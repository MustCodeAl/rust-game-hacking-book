Message Parsing and Serialization

Connect raw chat frames to typed messages through bounded parsing, serialization, and round-trip checks.

About 30 minutes

Section: Parse the real Wesnoth frame.

The first four bytes do not include themselves in the length. If the header ends in 4E, the following gzip member is 78 bytes and the complete T C P, transmission control protocol, payload is 4 + 78 equals 82 bytes. The length is big endian, so 78, hexadecimal this value, appears on the wire as 00 00 00 4E; u32::from_be_bytes states that order directly.

Lesson 9.1 showed why a receiver needs this prefix: it accumulates bytes until it has the four-byte header, then exactly the advertised number of payload bytes, however T C P splits them across reads.

The header is a claim from the sender, not permission to allocate whatever it asks for:

Predict first

This receiver refuses any length above its limit, MAX_FRAME equals the large number shown bytes. Its buffer holds the header FF FF FF FF and then four payload bytes.

What should it do now?

Answer: Refuse the frame now. FF FF FF FF is 255 times the large number shown + 255 times 65,536 + 255 times 256 + 255 equals the large number shown, which is above the large number shown. The header alone decides it, so the receiver refuses before allocating or waiting.

The header says 5 and 5 payload bytes are here, so 4 + 5 equals 9 bytes form one complete frame.

Code that allocates from that claim could request nearly four gigabytes. First reject any length above the configured maximum; only then wait for the advertised number of payload bytes, with a bounded buffer and a way to stop a stalled connection. Having only some payload bytes so far does not by itself prove a network frame is false, because T C P may deliver the rest later. After a complete frame is assembled, the parser checks its exact length before decoding it. This separates byte validation from the later question of whether the decoded chat message makes sense.

This separation is a debugging tool. If the first four bytes advertise an impossible size, inspect framing. If decompression fails, inspect the wrapper and payload. Calling every failure a “packet problem” hides the layer that actually broke.

Takeaway: treat malformed input as a parse error, and check the complete frame boundary.

Network input is allowed to be short, oversized, or malformed. Indexing panics when a boundary is wrong, and unwrap() erases the difference between bad input and a programmer bug. The cursor makes failure a normal Result, advances only after a successful bounded read, and lets the caller reject hidden trailing data after one complete frame.

The lifetime 'a says every slice returned by the cursor borrows from the original input. The cursor owns only a position number; it does not copy payloads or create references that outlive the frame.

take is the one place that advances parsing state. checked_add stops a hostile count from wrapping the end to a small position, and get returns None for a range past the buffer. Later field readers get a simple promise: success consumes exactly the requested bytes; failure consumes nothing and returns an error.

try_into() converts a four-byte slice into [u8; 4], the fixed-size array required by from_be_bytes. The conversion can only succeed after take(4), but keeping the error path explicit makes the invariant visible instead of using unwrap().

Every read checks its boundary. Now decompress only the advertised bytes and cap the output:

Code example. The code’s comments explain: 🛡️ Reject the advertised allocation before slicing or decompressing. 📏 Read one byte beyond the limit. Reaching that extra byte proves the decompressed message is oversized without allocating without bound.

There are two separate size limits here:

compressed_len limits how many bytes the parser accepts from the frame;

the take(MAX_FRAME + 1) wrapper limits how many bytes decompression may produce.

Both matter because a small compressed input can expand into a very large output. Reading one byte beyond the limit lets the parser distinguish “exactly at the limit” from “too large” without allocating an unbounded vector.

There is a third limit outside this pure function: the connection’s accumulated input buffer. A peer could advertise a legal one-megabyte frame and then send one byte every few seconds. The stream reader needs a maximum buffered size, read timeouts or cancellation, and a policy for a connection that never finishes its frame. Parsing bounds protect completed inputs; transport bounds protect the time and memory spent waiting for them.

The trailing-byte check makes this function parse one complete frame. Without it, a valid prefix could hide extra bytes that the caller mistakenly ignores. A streaming connection reader should split the stream into exact frame slices first and call this parser once per slice.

Simple W M L nests these bracketed tags and quoted fields as a tree. This lesson handles the one chat-message shape needed by our local Wesnoth proxy. If you extend the tool to inspect maps, units, or arbitrary add-on messages, use a real tokenizer that handles escaping, nested nodes, repeated fields, and comments instead of adding more substring searches.

The receiver also has an expected schema, even when no formal schema file exists. That schema includes field names, allowed repetitions, value types, and which fields are required. The sender writes one version of that agreement; the receiver reads according to the version it understands.

When a game update adds a field, ask two different compatibility questions:

Can the new reader still understand old messages?

Can the old reader safely ignore or default the new field?

Those questions are not the same. A tolerant tree format may ignore an unknown optional field, but renaming a required field can break both directions. For a versioned research tool, keep captured fixtures from every supported game build and record which message shape each fixture uses instead of guessing that one parser is universal.

Encoding runs the decoding pipeline in reverse:

validate values before placing them inside quoted W M L fields;

serialize the typed message into UTF-8 text;

finish the gzip stream so its footer is present;

convert the compressed size to u32 without truncation;

reserve one vector for header plus payload;

append the big-endian length and compressed bytes.

Vec::with_capacity is an optimization, not a safety requirement. It avoids reallocating as the two pieces are appended. u32::try_from is a correctness requirement because as u32 could silently discard high bits for an oversized buffer.

GzEncoder produces the correct gzip wrapper; a plain zlib stream is not interchangeable here. The first two compressed bytes should be 1F 8B.

Gzip and zlib can both use the DEFLATE compression algorithm but wrap it in different headers and checksums. “Same compression algorithm” does not mean “same wire format.” Matching the observed wrapper is part of implementing the protocol.

Narration: Encoding then decoding your own message checks consistency; captured fixtures also check whether both directions share the same mistaken assumption.

A round trip proves that the encoder produces something this decoder accepts. It does not prove compatibility by itself, because two functions could share the same mistake. Keep at least one captured fixture from the real local session and verify that the decoder accepts it. Then send an encoded message to the controlled server and confirm that another capture has the expected four-byte prefix and gzip header.

The goal is not merely to make one capture parse. It is to define exactly which byte strings are accepted and how malformed data fails.

The buildable protocol module is wesnoth_protocol.rs. It contains bounded frame reads, gzip encode/decode, output-size caps, strict trailing-byte checks, W M L field sanitation, send_wml, encode_chat, and round-trip/error tests. Both the real chatbot and proxy import this same implementation instead of copying a shortened lesson version.

Section: Read the module by responsibility.

Start with the pure functions that accept and return byte vectors; they are easiest to test. Next read the exact stream functions that repeatedly call read_exact for a header and payload. Finally read send_wml, which owns the complete serialization-and-write transaction.

This order keeps three kinds of failure distinct:

transport failure: the socket closed or timed out;

framing failure: the advertised message length was impossible;

content failure: gzip, UTF-8, or W M L data was invalid.

Preserving those categories in error messages is part of the explanation. If everything becomes “chat failed,” a learner cannot tell whether to inspect Wireshark, the frame cursor, or the message serializer.
