Named Pipes and Local Message Framing

Compare byte and message modes in Windows named pipes, then account for framing, bounded reads, connection races, and handle ownership.

About 38 minutes

Section: A named pipe is a local client/server channel.

Shared memory in Lesson 8.7 gave two programs views of the same bytes, but a concurrent writer needed an additional timing agreement. For one request followed by one reply, a named pipe gives us a connection with an explicit read/write order.

A named pipe server creates a known pipe name and waits. A client opens that name. After they connect, both sides can exchange bytes through ordinary Windows read and write calls.

The pipe transports bytes; the frame format supplies the length and validation rules that make those bytes meaningful to both programs.

🔌 IPC idea: define a small message format instead of sharing addresses. Each process keeps ownership of its own memory and exchanges bounded copies.

Section: Message mode preserves write boundaries.

Windows pipes can operate in byte mode or message mode.

Byte mode is a stream. One read can receive part of a write or data from several writes.

Message mode preserves message boundaries. A read receives one message, provided the buffer is large enough.

The lab selects PIPE_TYPE_MESSAGE when creating the server and PIPE_READMODE_MESSAGE for both ends.

It still adds a four-byte length header. Why use both? Message mode keeps transport boundaries, while the length header validates the application protocol. The receiver can reject a damaged or unexpected frame instead of trusting every byte Windows delivered.

Section: Treat IPC data like untrusted input.

“Local” does not mean “automatically trustworthy.” Another program in the same account or session might know or guess the pipe name.

The receiver checks all of these facts before making a String:

At least four header bytes arrived.

The declared text length is no more than 1024 bytes.

The received frame size equals 4 + declared length.

The text bytes are valid UTF-8.

The server accepts one client, handles one request, sends one fixed reply, and exits. Small limits make the behavior easy to reason about.

Section: Keep the pipe local and never impersonate.

Named pipes can support remote clients. This lab includes PIPE_REJECT_REMOTE_CLIENTS, so Windows rejects them automatically.

Section: Understand the connection race.

A client can open the pipe after CreateNamedPipeW creates it but just before the server calls ConnectNamedPipe. Windows then returns ERROR_PIPE_CONNECTED. That does not mean the connection failed—it means the client already won the race.

Section: How to grow this design safely.

A larger tool could add a version number and an enum of allowed messages such as TurnStarted, MapLoaded, or PlayerPositionFromSupportedMod. It should authenticate sensitive clients, set an explicit security descriptor, rate-limit messages, keep bounded queues, and separate parsing from actions.

Do not accept a command string and pass it to PowerShell or cmd.exe. Define a small message enum and reject unknown variants. Data should select one defined action, not become code.
