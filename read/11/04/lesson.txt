Control Gaps in Toy Defenses

The earlier chapters showed how a value, hook, or object layout can change while a game still appears to run normally. The next question is whether a check guards the effect it claims to guard. A perfect module inventory cannot rescue a rule that checks the wrong path. Three deliberately weak rules in a small program make that gap visible before we examine game logic controls and further trust-boundary failures.

Section: Research the failure without targeting a real defense.

This lesson uses a tiny program with no Windows APIs, drivers, processes, networking, persistence, or security-product interaction. The “attacker” is a test function calling an intentionally bad policy. That lets us study the computer-science shape of an evasion while keeping the recipe useless against a real anti-cheat or endpoint defense. 🧪

Section: The anatomy of a bypass.

Published evasion write-ups are usually operational recipes. Underneath the commands, each one describes the same parts, and this lab’s bypass contains every one of them:

Table columns: Part; In this lab.

Part: The promise the control made; In this lab: Read-only mode prevents state change.

Part: What the control actually checked; In this lab: One command name.

Part: The equivalent effect it missed; In this lab: Another command reached the same sink.

Part: The observable result; In this lab: The weak policy returned true for ApplyPatch.

Part: Where the invariant belongs; In this lab: At the shared state-changing boundary.

Part: The regression test that keeps it fixed; In this lab: Every ChangesState variant is denied in read-only mode.

Described by its parts, a bypass is a gap between what a control promised and what it checked. That is something a defender can close, and nothing in the description is a step that could be aimed at someone else’s machine.

Section: A detector observes proxies, not intent.

No program can directly read a person’s intent. A detector measures observable signals—for example a debug flag, an unusual timing gap, a changed byte, an unexpected handle, or a forbidden state transition—and applies a rule. That rule can be wrong in two directions:

Table columns: Outcome; Plain-English meaning.

Outcome: True positive; Plain-English meaning: The measured signal and prohibited condition are both present.

Outcome: False positive; Plain-English meaning: A harmless tool or environment produces the same signal.

Outcome: True negative; Plain-English meaning: Normal behavior is accepted.

Outcome: False negative; Plain-English meaning: The prohibited effect occurs without the expected signal.

This is why a strong repair protects the important effect boundary instead of trusting one environmental clue. In the toy lab, “state must not change in read-only mode” is an invariant. A process name, timing threshold, or single flag is only a signal that often accompanies a violation; it is not the invariant itself.

The four-outcome table above is called a confusion matrix. Testing a rule against a controlled fixture fills it in one condition at a time: attached and detached runs, slow and fast machines, and the diagnostic tools a legitimate user is expected to run. A rule that fires on a legitimate debugger or profiler lands in the false-positive row, and that is a compatibility bug worth fixing rather than proof that every observer is hostile.

Use signal families as a checklist for honest tests and false-positive review, not as a list of concealment tricks. The goal is to understand what the detector actually measures and then protect the real invariant at the shared boundary.

Section: What the three failures share.

A name can change, an earlier validation can go stale, and a denied decision can disappear from the record. Authorize the effect at its shared boundary, record both allowed and denied outcomes, and keep the failed case as a regression test. The toy boundary makes each failure observable without conflating it with the behavior of a real game’s defenses.
