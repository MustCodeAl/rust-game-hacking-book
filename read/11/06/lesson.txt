D M A, direct memory access, and Physical Memory

The kernel boundary also determines how devices reach memory. A process sees virtual addresses; a device moves bytes through a physical-memory path with its own access rules. Understanding both maps makes an offline capture interpretable without assuming that a game address is a R A M, random access memory, offset.

Section: D M A is a way devices move data.

D M A means direct memory access. A capable device can transfer data without asking the C P U, central processing unit, to copy each byte. Storage, networking, graphics, and other high-throughput devices use D M A because involving the C P U in every tiny move would waste time.

Here D M A refers to device transfers. It is different from dynamically allocating memory in a program, where the program asks its allocator for space and receives an address. The shared word memory does not make those the same operation.

D M A is not automatically a cheat or an attack. It is a hardware feature. Security problems appear when a device can reach memory it should not reach, or when software trusts a device too much.

This chapter uses ordinary offline capture files from an owned machine, virtual machine, or synthetic test. It does not configure D M A hardware, install a kernel driver, disable an IOMMU, access a live game, or bypass anti-cheat.

Section: Physical and virtual addresses are different maps.

A C P U process usually uses virtual addresses. The memory-management unit translates them through page tables to physical addresses in R A M.

Two processes may both use virtual address hexadecimal 1 0 0 0 because they supply different page-table roots. The access type matters too: a mapping may permit a read but reject a write or instruction fetch. A virtual address by itself therefore does not name a location: the address space and the access rules are part of its meaning.

It is like asking for apartment 1000 without naming the building. The apartment number is useful only after the building is chosen; likewise, hexadecimal 1 0 0 0 is useful only with the correct page-table root. The analogy is limited: page tables can remap or remove a page while a program runs, and they separately record whether a read, write, or instruction fetch is allowed. Section: c r 3 points to the first translation table.

On ordinary x86-64 systems using four-level paging, the C P U’s c r 3 register identifies the physical base of the top table. The virtual address supplies four nine-bit indices and a twelve-bit offset:

Each table has 512 eight-byte entries. A normal translation reads one entry at each level, checks its present bit, takes the next table’s physical address, and finally adds the page offset.

Large pages can finish earlier: a page-directory-pointer entry may map 1 GiB, and a page-directory entry may map 2 MiB.

Section: An IOMMU gives devices their own map.

An IOMMU is an input/output memory management unit. It does for devices what the page tables above do for processes: it sits between a device and physical memory and translates the addresses the device asks for, so the operating system can limit a device to approved physical regions instead of letting it reach all R A M.

Alternative: An IOMMU supplies a device’s approved map, just as C P U page tables supply a process’s map; neither address should be assumed to name unrestricted R A M.

Windows exposes protections including Kernel D M A Protection on supported hardware. Microsoft explains that it uses the IOMMU to isolate capable peripherals and protect against malicious D M A devices. Read the current Microsoft overview for requirements and behavior.

If a protected machine blocks D M A, that is the system working correctly. Keep the protections enabled and use the synthetic capture created by the tests or an offline hypervisor capture.

Section: A capture is a snapshot, not a live process.

An offline image has important limits:

threads do not run while you inspect it;

pages may have changed immediately after capture;

some virtual pages may be absent, swapped, compressed, or intentionally omitted;

you need the correct c r 3 and architecture details;

device memory and C P U caches may not be represented;

the capture may contain private data unrelated to the lesson.

A capture holds whatever was in R A M, including private data unrelated to the lesson, so it is stored securely and deleted when the lab no longer needs it. It also cannot be interpreted on its own. Its origin, capture time, build, architecture, capture method, and a cryptographic hash travel with the file, because a c r 3 value or a structure layout means something only for the machine state it came from, and the hash is what shows the bytes have not changed since.

Narration: A saved c r 3 and object layout are meaningful only beside the capture they describe. Mixing records from different moments can produce a convincing but wrong result.

Section: What “using D M A” means in this book.

The useful computer-science problem is translating and validating captured memory. The complete implementation:

opens a normal file read-only;

accepts a physical c r 3 value and virtual address;

walks x86-64 page tables inside that file;

checks present bits and bounds;

supports 4 KiB, 2 MiB, and 1 GiB mappings while leaving live C P U access permissions as a separate question;

prints a bounded hexdump.

No hardware-specific SDK is needed. This keeps the lesson reproducible and focuses attention on address translation rather than stealth, firmware, or bypasses.

For the exact paging bit definitions, use the current Intel Software Developer Manuals as the primary architecture reference.
