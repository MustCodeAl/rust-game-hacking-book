System Calls and Privilege Checks

Lesson 12.4 showed the processor keeping user-mode code away from the kernel and drew one ReadProcessMemory call crossing into the kernel and back. This lesson opens both up. It reads the bits the processor actually checks, then follows that one call a layer at a time, with every value the kernel compares along the way.

Section: The current level is two bits of a register.

The processor keeps the current privilege level in the lowest two bits of the cs register, which tells the processor which code segment it is running. Two bits can hold 2 times 2 equals 4 patterns, 00, 01, 10, and 11, which is exactly why there are four rings.

Open any 64-bit program in x64dbg and the register panel shows cs as 0033:

hexadecimal 3 3 is 3 times 16 + 3 equals 51. Each hex digit stands for four bits, so hexadecimal 3 3 is 0011 0011. Its lowest two bits are 11, which is 2 + 1 equals 3: ring 3, user mode. The kernel’s own code segment is hexadecimal 1 0, which is 0001 0000; its lowest two bits are 00, ring 0.

A program cannot promote itself by loading hexadecimal 1 0 into cs. The processor refuses any change of code segment that would raise the privilege level, except through a few entry points that the kernel prepared in advance. The most important of them is the syscall instruction, and the rest of this lesson follows one trip through it.

Section: One bit marks a page as the kernel’s.

Lesson 12.4 said that a page-table entry’s user/supervisor bit, bit 2, decides whether ring 3 may touch the page. An entry combines the address of a physical page with flags describing that mapping. For the ordinary 4 KiB pages used here, the page address is aligned on a 4,096-byte boundary, leaving the low twelve bits available for flags. Chapter 12’s address-translation lesson will follow a complete walk; here we need only the permission flags in the lowest byte:

hexadecimal 6 7 is 6 times 16 + 7 equals 103, and 103 equals 64 + 32 + 4 + 2 + 1, so bits 6, 5, 2, 1, and 0 are set. Bit 0 says the page is present, bit 1 that it may be written, and bit 2 that ring 3 may use it. The processor itself sets bit 5, accessed, the first time the page is used, and bit 6, dirty, the first time it is written. Bits 3, 4, and 7 control caching and are 0 here.

A page that holds kernel data looks almost the same:

hexadecimal 6 7 minus hexadecimal 6 3 equals 4, and 4 equals 2 to the power of 2, so exactly one bit differs between these two example leaf entries: bit 2. A kernel page can be present, writable, and recently used, and still refuse access from ring 3. In a real page-table walk, the processor also considers permissions in the entries at higher levels; a single leaf byte is a teaching example, not a complete access decision.

Section: Inside your process.

The first line exists because of the first thing syscall does. The Windows x64 calling convention passes a function’s first argument in r c x, but syscall overwrites r c x with the return address, so the stub moves the argument to r 1 0 first, and the kernel knows to look for it there.

Narration: The system-call instruction overwrites r c x, so the stub preserves the first argument in r 1 0. Missing that move would change what the kernel receives.

The number in e a x is a system service number, an index into the kernel’s table of routines. The numbers are internal to Windows and change between builds, which is why this book never copies one into a program. In a debugger the stub also shows a test and a jump to an older entry instruction, int 2Eh, that some configurations use; either way, the processor arrives at an address the kernel chose.

Section: Crossing over.

The kernel’s entry code assumes that everything user mode handed it could be hostile. It switches from the program’s stack to a kernel stack that belongs to the thread, because the program’s stack pointer could point anywhere. It saves the user registers so they can be put back exactly. Then it looks the service number up in its table, rejects a number that is out of range, and calls the kernel’s own NtReadVirtualMemory.

Section: Inside the kernel.

Most of the kernel’s work is checking.

The address ranges must lie inside user space. The request covers this value up to this value + 4 equals this value, and the tool’s buffer is also a user address. Both are far below the top of user space, which is a little under this value on 64-bit Windows. A range that reached into the kernel’s half, or one long enough to run past the largest 64-bit number and wrap around to a small address, would be rejected here. The user/supervisor bit cannot do this job for the kernel: the copy runs in ring 0, and ring 0 may touch supervisor pages. So the kernel checks every range itself, and that check is why ReadProcessMemory cannot read kernel memory, whatever handle you hold.

The handle must carry the right the operation needs. The kernel finds the handle in the tool’s handle table and reads the rights granted when the handle was opened. Reading needs PROCESS_VM_READ, which is hexadecimal 0 0 1 0. This handle was opened with PROCESS_QUERY_LIMITED_INFORMATION and PROCESS_VM_READ, so its rights are hexadecimal 1 0 0 0 + hexadecimal 0 0 1 0 equals hexadecimal 1 0 1 0. Written as bits, one byte at a time:

The test is a single AND. The kernel keeps only the bits that are set in both the handle’s rights and the rights it needs, and allows the operation only if every needed bit survived. hexadecimal 1 0 1 0 AND hexadecimal 0 0 1 0 equals hexadecimal 0 0 1 0, the whole requirement, so the read is allowed.

Alternative: An access mask is a stencil: retain the requested bits that were granted, then confirm every required bit survived.

WriteProcessMemory needs PROCESS_VM_WRITE, hexadecimal 0 0 2 0. That is 2 times 16 equals 32 equals 2 to the power of 5, bit 5, and bit 5 of hexadecimal 1 0 1 0 is 0, so hexadecimal 1 0 1 0 AND hexadecimal 0 0 2 0 equals 0: denied, whatever the tool’s author intended. The rights were fixed when the handle was created, and nothing done with the handle afterward can add to them.

In brief: An existing handle keeps its granted rights; a later operation cannot add permissions by asking more forcefully.

Only then does it copy. The source address belongs to the game’s address space and the destination buffer belongs to the tool’s. The kernel must interpret each in the correct process context while copying; the exact internal mapping and copy strategy is a Windows implementation detail. If a page becomes unavailable during the operation, the A P I, application programming interface, may report a failed or partial read. The caller must check the returned byte count instead of assuming that asking for four bytes means four arrived.

Section: Returning.

The kernel places a status code in r a x and executes sysret, the reverse of syscall: the level drops back to 3, and execution resumes at the address saved in r c x, which is the ret right after syscall in the stub.

The status is an NTSTATUS, a 32-bit code whose top two bits give its severity: 00 success, 01 information, 10 warning, 11 error. STATUS_SUCCESS is 0. STATUS_ACCESS_DENIED is this value; hex C is binary 1100, so its top two bits are 11, an error. STATUS_PARTIAL_COPY is this value; hex 8 is 1000, so its top two bits are 10, a warning, because some of the bytes did arrive. kernelbase.dll translates the status into a Win32 error code for GetLastError, 5 for access denied and 299 for a partial copy, and reports success or failure to your tool.

The book’s Windows labs are 32-bit programs. A 32-bit process on 64-bit Windows uses WoW64 (“Windows 32-bit on Windows 64-bit”) to translate the call into the native 64-bit service path. That may require converting pointer-sized arguments and structures; it is not a blind widening of every number. The two modes use different code segments, which is why cs reads 0023 in a 32-bit program and 0033 in a 64-bit one. The four-instruction stub above illustrates the native 64-bit path, not every instruction a 32-bit caller runs.
