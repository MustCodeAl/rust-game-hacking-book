Emulator Timing and State

Lesson 13.9 explained how an emulator works and ran one instruction of a made-up 8-bit console through the fetch–decode–execute loop. This lesson builds the whole console, follows a complete program through it cycle by cycle, and ends with a lab that runs it.

Section: A toy 8-bit C P U, central processing unit.

In brief: The opcode chooses the operation. The operand supplies a number or an address. An address operand needs another memory read.

The C P U is made up, but it is built like the 8-bit processors in 1980s consoles. It has four registers:

PC, 8 bits, the program counter. Eight bits can name 2 to the power of 8 equals 256 addresses, hexadecimal 0 0 to hexadecimal F F, so the whole machine has 256 addresses.

A, 8 bits, the accumulator, where arithmetic happens.

X, 8 bits, a second register, used here as a loop counter.

Z, 1 bit, the zero flag: 1 when the last result was zero, 0 otherwise.

It understands seven instructions. Each begins with its opcode, and some carry an operand byte:

The toy C P U’s instructions

A # marks an immediate: #5 means the number 5 itself, while an operand without # is an address, and the instruction uses the byte stored there. STA and J N Z leave Z alone. Every other byte value is not an instruction, and the lab reports it as an error instead of guessing.

Every number in the last column comes from one rule: the C P U spends one cycle on each memory access, meaning each instruction byte it fetches and each data byte it reads or writes, plus one extra cycle when a jump is taken, to load the new address into PC. So L D X #n and ADD #n each fetch 2 bytes, 2 cycles; L D A a fetches 2 and reads 1, 3 cycles; STA a fetches 2 and writes 1, 3 cycles; D E X and H L T each fetch 1, 1 cycle; and J N Z a fetches 2, plus 1 if it jumps. Real 8-bit CPUs, such as the 6502 inside the NES, have similar costs for similar reasons.

fetch reads the byte at PC and adds 1 to PC, so each call consumes one byte of the instruction. Opcode::decode is a match on the byte that returns None for anything that is not an instruction, and the ? turns that into an IllegalOpcode error that names the address. A real C P U meeting an unknown opcode might raise an exception, as x86 does, or do something undocumented. An emulator that guessed would hide bugs in the guest program and in itself.

Narration: The number travels from R A M, random access memory, into A. R A M keeps its copy. Later arithmetic can change A before a store changes R A M.

The same instruction can load a different value. Change the memory byte below, then step through the fetches and the data read. Try zero: the loaded value also changes the zero flag. Each memory read costs one cycle in this toy C P U.

Because step decodes every instruction each time it runs, the loop body from hexadecimal 0 2 to hexadecimal 0 A is decoded afresh on both passes. That repetition is what the dynamic recompilers of Lesson 13.9 remove.

hexadecimal 0 0..=hexadecimal E F is Rust’s range from hexadecimal 0 0 to hexadecimal E F with both ends included. That is hexadecimal F 0 equals 15 times 16 equals 240 addresses, exactly the length of the ram array. DISPLAY and BUTTONS are constants holding hexadecimal F 0 and hexadecimal F 1. So step 12’s STA hexadecimal F 0 calls write with address hexadecimal F 0 and value 20, the second arm stores 20 in the display register, and nothing in step has to know that hexadecimal F 0 is not R A M.

Real consoles work the same way on a larger scale. The NES has 2 KiB of R A M at hexadecimal 0 0 0 0 to hexadecimal 0 7 F F; hexadecimal 0 8 0 0 is 8 times 256 equals 2,048 bytes. Its address decoder ignores the top address bits for R A M, so the same 2,048 bytes answer again at hexadecimal 0 8 0 0, hexadecimal 1 0 0 0, and hexadecimal 1 8 0 0: the range up to hexadecimal 2 0 0 0, which is 2 times 16 to the power of 3 equals 2 times 4,096 equals 8,192 bytes, holds 8,192 divided by 2,048 equals 4 copies. This is called mirroring. The picture chip’s registers start at hexadecimal 2 0 0 0, and the controllers answer at hexadecimal 4 0 1 6 and hexadecimal 4 0 1 7. An NES emulator’s read is a bigger version of the one above.

Section: Frame budgets and overshoot.

In brief: An instruction finishes as a whole. A frame budget can be exceeded by the final instruction’s cost.

A real frame’s budget, like the one in Lesson 13.9, runs to thousands of cycles, while the whole traced program takes only 29. So the lab uses a tiny budget of 18 cycles, which ends a frame partway through the program. Its run loop steps whole instructions until the budget is used or the C P U halts:

Code example. The surrounding prose explains this example; the full lesson contains the exact code.

The check used less than budget happens before each instruction, never during one, because an instruction cannot stop halfway. After step 7 the run has used 17 cycles, which is less than 18, so it runs step 8, an ADD worth 2 cycles, and reaches 19. That is not less than 18, so the frame ends. It overshot by 19 minus 18 equals 1 cycle, and the emulator gives the next frame 18 minus 1 equals 17 cycles, which keeps the long-run average at exactly 18 per frame. The overshoot can never exceed 2: the frame’s last instruction starts with at most 17 cycles used and costs at most 3, and 17 + 3 equals 20 equals 18 + 2.

Alternative: Saving R A M alone suits a data backup. Resuming this emulator also needs the registers, flags, counters, and device state.

At that frame boundary the new gold total exists only in A, so a snapshot of R A M alone would restore gold equals 15 and lose the 20. The lab’s SaveState copies every part of the machine and converts it to a row of bytes:

The halted flag records whether H L T has run, and the cycle count is the emulator’s position in time, so a loaded state resumes at the same point in the frame. Reading a state back refuses anything that is not exactly 255 bytes long, and refuses a Z or halted byte that holds anything other than 0 or 1, because no real run of the machine could have produced it.
