Emulator Timing and State

Lesson 14.7 explained how an emulator works and ran one instruction of a made-up 8-bit console through the fetch–decode–execute loop. This lesson builds the whole console, follows a complete program through it cycle by cycle, and ends with a lab that runs it.

Section: A toy 8-bit CPU, central processing unit,.

The CPU is made up, but it is built like the 8-bit processors in 1980s consoles. It has four registers:

PC, 8 bits, the program counter. Eight bits can name 2 to the power of 8 equals 256 addresses, hexadecimal 0 0 to hexadecimal F F, so the whole machine has 256 addresses.

A, 8 bits, the accumulator, where arithmetic happens.

X, 8 bits, a second register, used here as a loop counter.

Z, 1 bit, the zero flag: 1 when the last result was zero, 0 otherwise.

It understands seven instructions. Each begins with its opcode, and some carry an operand byte:

The toy CPU's instructions

Table columns: Bytes; Written as; Length; What it does; Cycles.

Bytes: 01 n; Written as: LDX #n; Length: 2; What it does: X equals n; Z equals 1 if X is 0; Cycles: 2.

Bytes: 02 a; Written as: LDA a; Length: 2; What it does: A equals the byte at address a; Z equals 1 if A is 0; Cycles: 3.

Bytes: 03 n; Written as: ADD #n; Length: 2; What it does: A equals A + n, wrapping past 255 back to 0; Z equals 1 if A is 0; Cycles: 2.

Bytes: 04 a; Written as: STA a; Length: 2; What it does: store A at address a; Cycles: 3.

Bytes: 05; Written as: DEX; Length: 1; What it does: X equals X minus 1, wrapping below 0 to 255; Z equals 1 if X is 0; Cycles: 1.

Bytes: 06 a; Written as: JNZ a; Length: 2; What it does: if Z is 0, jump: PC equals a; Cycles: 2, or 3 if it jumps.

Bytes: FF; Written as: HLT; Length: 1; What it does: stop; Cycles: 1.

A # marks an immediate: #5 means the number 5 itself, while an operand without # is an address, and the instruction uses the byte stored there. STA and JNZ leave Z alone. Every other byte value is not an instruction, and the lab reports it as an error instead of guessing.

Every number in the last column comes from one rule: the CPU spends one cycle on each memory access, meaning each instruction byte it fetches and each data byte it reads or writes, plus one extra cycle when a jump is taken, to load the new address into PC. So LDX #n and ADD #n each fetch 2 bytes, 2 cycles; LDA a fetches 2 and reads 1, 3 cycles; STA a fetches 2 and writes 1, 3 cycles; DEX and HLT each fetch 1, 1 cycle; and JNZ a fetches 2, plus 1 if it jumps. Real 8-bit CPUs, such as the 6502 inside the NES, have similar costs for similar reasons.

In hex, 15 is hexadecimal 0 F and 20 is 1 times 16 + 4 equals hexadecimal 1 4. At step 11, fetching JNZ and its operand has already moved PC from hexadecimal 0 9 to hexadecimal 0 9 + 2 equals hexadecimal 0 B, so not jumping needs no extra work: the next instruction is simply the next one.

The whole run takes 29 cycles: 2 for LDX, then 3 + 2 + 3 + 1 + 3 equals 12 for the first pass, 3 + 2 + 3 + 1 + 2 equals 11 for the second, and 3 + 1 equals 4 for the ending. 2 + 12 + 11 + 4 equals 29. When the machine stops, it looks like this:

Labelled memory diagram. PC: hexadecimal 0 E; A: 20; X: 0; Z: 1; hexadecimal 8 0 dot gold: 20; hexadecimal F 0 dot display: 20. Groups: CPU registers; RAM; I/O. After HLT. PC is hexadecimal 0 E, one past the HLT at hexadecimal 0 D, because fetching the opcode moved it on.

Section: The interpreter in Rust.

The lab’s step function is that trace, as code. It fetches the opcode, decodes it, and runs one arm of a match. Each arm’s last value is the instruction’s cost in cycles:

fetch reads the byte at PC and adds 1 to PC, so each call consumes one byte of the instruction. Opcode::decode is a match on the byte that returns None for anything that is not an instruction, and the ? turns that into an IllegalOpcode error that names the address. A real CPU meeting an unknown opcode might raise an exception, as x86 does, or do something undocumented. An emulator that guessed would hide bugs in the guest program and in itself.

Diagram walkthrough: One LDA instruction: bytes become CPU state. Step 1: Start at step 2 of the trace. State: PC=02 A=0 X=2 Z=0 cycles=2. The earlier LDX has finished: PC equals hexadecimal 0 2, A equals 0, X equals 2, Z equals 0, and the cycle count is 2. RAM at hexadecimal 8 0 contains gold equals 10. The next instruction bytes are 02 80. Step 2: Fetch the opcode. State: opcode=02 PC=03. fetch reads byte hexadecimal 0 2 at PC equals hexadecimal 0 2, then advances PC to hexadecimal 0 3. This byte identifies the operation; it has not loaded the gold value into A. Step 3: Decode the operation. State: 02 to LDA. Opcode::decode maps hexadecimal 0 2 to LDA. The LDA arm requires one address operand followed by a data read. An unrecognized opcode would return IllegalOpcode before this arm runs. Step 4: Fetch the address operand. State: operand=80 PC=04. The second fetch reads byte hexadecimal 8 0 at PC equals hexadecimal 0 3 and advances PC to hexadecimal 0 4. The operand names RAM address hexadecimal 8 0, whose stored byte is the value the instruction will load. Step 5: Update A and the zero flag. State: A=10 Z=0 X=2 RAM[80]=10. read(hexadecimal 8 0) returns 10, so A becomes 10. Because A is nonzero, Z remains 0. X remains 2, and RAM still holds gold equals 10 because LDA only reads it. Step 6: Finish the instruction. State: PC=04 cycles=2+3=5. The arm returns a cost of 3 cycles: opcode fetch, operand fetch, and data read. The total becomes 2 + 3 equals 5. PC equals hexadecimal 0 4 now selects ADD #5, matching step 2 of the trace. An instruction can use several emulated cycles. The later ADD changes A, and STA writes that result back to RAM; following those separate changes explains why a saved register and a saved memory byte can disagree.

Because step decodes every instruction each time it runs, the loop body from hexadecimal 0 2 to hexadecimal 0 A is decoded afresh on both passes. That repetition is what the dynamic recompilers of Lesson 14.7 remove.

The toy console maps RAM from hexadecimal 0 0 to hexadecimal E F, the display at hexadecimal F 0, the buttons at hexadecimal F 1, and nothing from hexadecimal F 2 to hexadecimal F F. hexadecimal 0 0..=hexadecimal E F is Rust’s range from hexadecimal 0 0 to hexadecimal E F with both ends included. That is hexadecimal F 0 equals 15 times 16 equals 240 addresses, exactly the length of the ram array. DISPLAY and BUTTONS are constants holding hexadecimal F 0 and hexadecimal F 1. So step 12’s STA hexadecimal F 0 calls write with address hexadecimal F 0 and value 20, the second arm stores 20 in the display register, and nothing in step has to know that hexadecimal F 0 is not RAM.

Real consoles work the same way on a larger scale. The NES has 2 KiB of RAM at hexadecimal 0 0 0 0 to hexadecimal 0 7 F F; hexadecimal 0 8 0 0 is 8 times 256 equals 2,048 bytes. Its address decoder ignores the top address bits for RAM, so the same 2,048 bytes answer again at hexadecimal 0 8 0 0, hexadecimal 1 0 0 0, and hexadecimal 1 8 0 0: the range up to hexadecimal 2 0 0 0, which is 2 times 16 to the power of 3 equals 2 times 4,096 equals 8,192 bytes, holds 8,192 divided by 2,048 equals 4 copies. This is called mirroring. The picture chip’s registers start at hexadecimal 2 0 0 0, and the controllers answer at hexadecimal 4 0 1 6 and hexadecimal 4 0 1 7. An NES emulator’s read is a bigger version of the one above.

Section: Frame budgets and overshoot.

A real frame’s budget, like the one in Lesson 14.7, runs to thousands of cycles, while the whole traced program takes only 29. So the lab uses a tiny budget of 18 cycles, which ends a frame partway through the program. Its run loop steps whole instructions until the budget is used or the CPU halts:

Code example. The surrounding prose explains this example; the full lesson contains the exact code.

The check used less than budget happens before each instruction, never during one, because an instruction cannot stop halfway. After step 7 the run has used 17 cycles, which is less than 18, so it runs step 8, an ADD worth 2 cycles, and reaches 19. That is not less than 18, so the frame ends. It overshot by 19 minus 18 equals 1 cycle, and the emulator gives the next frame 18 minus 1 equals 17 cycles, which keeps the long-run average at exactly 18 per frame. The overshoot can never exceed 2: the frame’s last instruction starts with at most 17 cycles used and costs at most 3, and 17 + 3 equals 20 equals 18 + 2.

Section: A save state, byte by byte.

At that frame boundary the new gold total exists only in A, so a snapshot of RAM alone would restore gold equals 15 and lose the 20. The lab’s SaveState copies every part of the machine and converts it to a row of bytes:

Labelled memory diagram. PC: hexadecimal 0 6; A: 20; X: 1; Z: 0; halted: 0; cycles: 19. Groups: CPU registers; emulator bookkeeping. The first 13 bytes. PC, A, X, Z, and the halted flag take 1 byte each; the cycle count is a 64-bit number, and 64 divided by 8 equals 8 bytes. So 5 + 8 equals 13.

Labelled memory diagram. RAM: 240 bytes; display: 0; buttons: 0. Groups: all of RAM; I/O registers. The other 242 bytes: 240 for RAM and 1 each for the two I/O registers. In all, 13 + 240 + 2 equals 255 bytes.

The halted flag records whether HLT has run, and the cycle count is the emulator’s position in time, so a loaded state resumes at the same point in the frame. Reading a state back refuses anything that is not exactly 255 bytes long, and refuses a Z or halted byte that holds anything other than 0 or 1, because no real run of the machine could have produced it.
