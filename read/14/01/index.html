Lesson 11.10 / Listening edition

What an Operating System Kernel Does

The processor separates user and kernel authority. System calls, scheduling, memory, interrupts, and drivers show what the kernel does for a running game.

About 18 minutes

The tools so far have asked Windows for something: a handle to a game, a copy of four bytes, a list of loaded modules. Each time, something checked whether the tool was allowed to ask, did the work, and sometimes said no. The kernel is the core of the operating system that coordinates those requests with the processor’s highest operating-system privilege. Ordinary programs go through its controlled services to reach shared resources such as another process’s memory, the disk, the display, or a network device.

This lesson answers four questions. How does the processor keep ordinary programs away from the kernel’s powers? How does a program ask the kernel for something anyway? What does the kernel do with its authority? And why can one kernel bug stop the whole computer, when a bug in a game only ends the game? A four-byte ReadProcessMemory request will carry these questions through the user/kernel boundary. The next lesson reads the exact bits the processor checks and follows the request one layer at a time.

The A P I, application programming interface, layers in the previous lesson showed the route a request takes. Here we examine the authority that makes that route work. After the privilege checks, a crash dump will bring threads, modules, and saved registers back together into one process snapshot. Chapter 12 then follows requests across D L L, dynamic link library, and device boundaries; Chapter 14 builds on that foundation to explain virtual machines and hardware.

Section: Two modes, enforced by the processor.

The kernel and a game run on the same processor, often on the same core, taking turns many times a second. What stops the game from doing what the kernel does: rewriting another process’s memory, reprogramming the disk controller, or simply never giving the processor back?

A rule written only in software could not stop it. If the kernel’s protections were ordinary code and data, the program being restricted could overwrite them, the same way a debugger overwrites an instruction with a breakpoint. The rule has to live somewhere the restricted program cannot reach, and the only such place is the processor itself.

So the processor tracks a privilege level for the code it is running. It checks privileged instructions and page translations against that level. x86 processors define four levels, numbered 0 to 3 and usually drawn as nested rings, with ring 0 the most privileged. Windows uses two of them:

kernel mode, ring 0, for the kernel and drivers;

user mode, ring 3, for everything else: games, browsers, debuggers, and every tool in this book.

Lesson 11.9 introduced the two modes as permission levels. The processor records the current level in two bits of one of its registers, which Lesson 11.11 reads in a debugger. What matters here is what the processor refuses to do while the level is 3.

Section: What ring 3 is not allowed to do.

At ring 3 the processor refuses two kinds of thing.

Privileged instructions. Some instructions only make sense for whoever runs the machine. hlt stops the processor until the next interrupt. cli turns interrupts off, which would silence the timer the kernel relies on to take the processor back. mov c r 3, r a x switches to a different set of page tables, which selects a process’s whole view of memory. The physical-memory lessons in Chapter 12 will follow those page tables. wrmsr rewrites the processor’s internal settings. At ring 3, each of these raises a general-protection fault instead of running, and the kernel turns the fault into an exception that normally ends the program.

Memory marked for the kernel. Page-table entries carry a user/supervisor bit, bit 2. When it is 0 on a present mapping, a ring-3 access causes a page fault. Windows reserves a system range of virtual addresses for the kernel. In a traditional shared page table, kernel pages can be mapped there alongside a game’s pages, but their supervisor bit still blocks the game. With KVA shadow, the user-mode page table omits most kernel mappings and keeps only the pages needed to enter the kernel; entry code switches to the fuller kernel page table. In either arrangement, a game cannot read or write the kernel’s privileged pages. Lesson 11.11 compares the flag bits of a user page and a kernel page.

Put the two checks together and user-mode code is boxed in. It cannot run the instructions that change the rules, and it cannot touch the memory where the rules are kept, including the page tables themselves.

Section: A system call is how a program asks.

If ring 3 cannot touch kernel memory or raise its own level, how does ReadProcessMemory ever reach code that can read another process? Through a system call: an instruction that switches the processor to ring 0 and jumps to an address the kernel chose. On x86-64 the instruction is syscall. When the processor executes it, it:

copies the address of the next instruction into r c x and the flags register into r 1 1, so the kernel can come back later;

switches the privilege level to 0;

jumps to an address held in a processor setting that only ring 0 can change. The kernel wrote that address during boot, using wrmsr.

Step 3 is what makes the design safe. A program chooses when to request a service, never an arbitrary kernel instruction to run. The processor enters a kernel-controlled path, which identifies the requested service and checks its untrusted arguments. This is the controlled crossing promised in Chapter 11, now seen from the processor’s side.

Section: Follow one call into the kernel and back.

Take a read like the ones in Lesson 11.5: a handle to the game opened with only query and read rights, and a request for 4 bytes at address shown here. Here is the whole round trip:

Your tool’s call passes through kernel32.dll and kernelbase.dll, the layers that Lesson 11.9 followed down the stack, to NtReadVirtualMemory in ntdll.dll. That function is only a few instructions long: it puts a service number, which tells the kernel which of its routines to run, into the e a x register, and executes syscall.

On the other side, the kernel’s entry code moves onto a stack of its own and saves your registers. Then the kernel’s own NtReadVirtualMemory checks the request before touching anything. Both address ranges, the 4 bytes in the game and your tool’s buffer, must lie in user space, which is why ReadProcessMemory can never read kernel memory, whatever handle you hold. And the handle must carry the right the operation needs: PROCESS_VM_READ for a read, which this handle has, or PROCESS_VM_WRITE for a write, which it lacks. A handle’s rights are fixed when it is opened, and nothing done with it afterward can add one.

Only then does the kernel copy the 4 bytes into your buffer. It puts a status code in e a x, here STATUS_SUCCESS, which is 0, and executes sysret, the reverse of syscall, which drops the level back to 3 and resumes your thread after its syscall. On a failure, kernelbase.dll turns the status into the error number that GetLastError reports, such as 5 for access denied. Lesson 11.11 follows each step with the values involved, including the arithmetic of the rights check.

Section: How the kernel regains control.

A system call is one common way execution crosses from a user thread into the kernel. Two others are exceptions, raised by the instruction that is running (a page fault, a division by zero, the int3 breakpoint), and interrupts, signals that arrive between instructions whether or not the running program expects them.

The kernel does not interpret each ordinary game instruction. These entries bring a user thread into kernel code when work needs its authority. Windows also schedules its own kernel worker threads for work that need not begin in a game’s call. Both facts fit the same model: the kernel is code with privileged responsibilities, and the processor enforces who may run it.

The processor finds exception and interrupt handlers through the interrupt descriptor table, which the kernel fills in at boot. Each entry is chosen by a one-byte vector number. One byte holds 2 to the power of 8 equals 256 values, so the table has at most 256 entries, numbered 0 to 255. The processor fixes the meaning of vectors 0 to 31: vector 3 is the breakpoint exception that the byte hexadecimal C C, int3, raises (Lesson 2.4), vector 13 is the general-protection fault, and vector 14 is the page fault. Devices are given vectors from 32 up.

Section: What the kernel does with its authority.

Section: It schedules threads.

A computer has a handful of processor cores and, at any moment, hundreds or thousands of threads (Lesson 11.8 described ready, running, and waiting threads). The kernel’s scheduler decides which ready thread runs on each core. Timer interrupts are one opportunity to reconsider that choice; a thread blocking for input or a lock is another. Timer resolution and interrupt scheduling vary by Windows version, hardware, and power state, so a fixed tick interval is not a reliable description of every game session.

When a running thread stops to wait for input, a lock, or a timer, or when its turn is interrupted, the scheduler can pick another thread. Changing threads is a context switch: the kernel saves the old thread’s registers into its context, loads the new thread’s registers, and, if the new thread belongs to a different process, loads that process’s top-level page-table address into c r 3. The program never sees the switch. Its registers come back exactly as they were.

Section: It manages every process’s memory.

Each process has its own page tables, and only the kernel writes them. Reserving an address range and committing storage are distinct operations, as Lesson 11.7 showed. Even after a page is committed, Windows may assign its physical frame only on first access. That access faults, the kernel supplies a zeroed page so old data cannot leak between processes, updates the mapping, and retries the instruction. The game normally never sees this handled fault. Lesson 11.7 looked at the result from outside, and Lesson 12.7 will examine how physical memory fits beneath that view.

Section: It handles interrupts.

When a device needs attention, because a key was pressed, a disk transfer finished, or a network packet arrived, it raises an interrupt. The processor finishes its current instruction, saves where it was, enters ring 0 if it was not there already, and runs the handler for that vector. The interrupted code, kernel or user, resumes afterward as if nothing had happened. Handlers must be short, because other work on that core waits while they run; Lesson 12.4 shows how drivers split the work.

Section: It owns devices through drivers.

Ordinary user programs reach devices through operating-system interfaces rather than writing device registers directly. A driver knows a device’s registers and rules, and Windows routes requests through the relevant driver stack. Lesson 12.4 follows one request down to the hardware.

Section: It enforces security checks.

The processor enforces privileged-instruction and page-permission checks in hardware. Windows checks handle rights and validates request ranges in the kernel, where the caller cannot simply skip the decision. The kernel also enforces the access tokens and integrity levels from Lesson 11.5, the page protections from Lesson 11.7, and the signing rules that decide which drivers may load at all (Lesson 12.4).

Section: Why a kernel bug takes the whole machine down.

When user-mode code follows a bad pointer, the processor raises a page fault and the kernel handles it. The kernel checks its records, finds that nothing valid lives at that address, and turns the fault into an access-violation exception for that one process. The program’s own handler, a debugger, or Windows Error Reporting deals with it, and in the worst case one process ends. The kernel is the safety net under every user-mode program.

There is no separate part of Windows that can repair arbitrary damage to its own kernel state. A hypervisor may isolate a whole guest from the host, as Lesson 14.1 will show, but it cannot resume a guest kernel whose internal records are already corrupted. Kernel code does catch faults it expects, such as touching a user buffer that another thread may have freed; the copy behind ReadProcessMemory is written to catch exactly those. But a driver that follows a bad pointer by mistake can raise an unexpected fault inside the kernel, and kernel code and drivers share an address space and a set of data structures: the scheduler’s lists, the memory manager’s page records, and the locks that guard them. The fault may have struck halfway through updating one of those structures, with a lock still held. Windows cannot generally prove which of its own records remain sound, and carrying on could write corrupted data to disk. For an unrecoverable kernel failure, Windows stops on purpose.

That deliberate stop is a bug check, better known as the blue screen. Windows shows a stop code, such as hexadecimal 5 0 PAGE_FAULT_IN_NONPAGED_AREA or hexadecimal D 1 DRIVER_IRQL_NOT_LESS_OR_EQUAL, writes a crash dump of the whole machine if it can (Lesson 11.12 will capture a dump of one process), and restarts.

This is why the book keeps its labs in user mode and inside a virtual machine. The kernel trust lesson will make that design choice concrete with a read-only driver inventory. A crash in a user-mode lab ends one process, and even a bug check inside a virtual machine stops only that virtual machine (Lesson 14.1).

Section: Why some anti-cheat runs a kernel component.

Anti-cheat software exists to notice when another program interferes with a game. If an anti-cheat and an interfering tool both run in user mode, both are subject to process handles, access rights, and other Windows rules from Chapter 11. Running at the same processor privilege does not itself grant either process access to the other. It does limit what either can establish about system-wide events and privileged components from inside its own process.

A kernel component changes that balance. Running in ring 0 lets it use documented Windows facilities that user-mode code cannot reach:

process and image-load notifications, so it learns about every new process and every D L L or driver as it loads, instead of scanning for them afterward;

handle-operation callbacks, which run while another process opens a handle to the game and may remove rights from the request. A tool that asks for read and write rights can receive a handle without them, and its ReadProcessMemory then fails at exactly the rights check described above;

a view of loaded drivers and system state that user-mode code cannot quietly alter.

The costs are the other half of this lesson. Anti-cheat code in the kernel has the same authority as the rest of the kernel, so its bugs become bug checks on players’ machines, and a vulnerability in it becomes a vulnerability in every machine it is installed on. It asks players to trust a game company with ring-0 code. Kernel placement also creates another boundary to protect: which drivers may load and what authority they expose. Windows uses signing rules, vulnerable driver block policies, and memory integrity to reduce that risk. Chapter 12’s driver pair explains what such code actually does and why its interface must be narrow, then examines the trust placed in a loaded driver.
