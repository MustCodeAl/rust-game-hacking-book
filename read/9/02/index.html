The two-save comparison is a controlled experiment, not proof that every changed byte belongs to gold. Games may update play time, random state, timestamps, object order, or integrity data during the same save. Repeat the comparison with several values and one intentional change at a time. A real field should follow the chosen change consistently; unrelated changing bytes are background state.

Writing directly truncates the original before the new bytes are safely stored. A crash or full disk can leave half a save. The sibling temporary file keeps the original untouched during construction, sync_all asks the operating system to flush it, and closing the handle before replacement avoids Windows sharing conflicts. The complete Windows lab uses ReplaceFileW so replacement and backup creation are one filesystem action.

On Windows, replacing an existing file may require a platform-specific replace operation. Keep the backup until the game successfully loads the new save.

Section: Prepare, validate, commit, and recover.

Use four explicit stages: prepare, validate, commit, recover:

Prepare: read the original and build new bytes somewhere else.

Validate: confirm the target field , format, ranges, and complete output .

Commit: replace the directory entry in one filesystem operation.

Recover: keep enough information to return to the last known-good save.

Atomic replacement and durability solve different problems. Atomic means an observer should see the old file or the new file, not a half-written mixture. Durable means completed data survives the failures the system promises to handle. Flushing the temporary file improves durability, but no single call can make the edit, the game’s other save files, cloud synchronization, and a power failure one universal transaction.

The property we are designing is crash consistency: after interruption, the files should describe an old valid state, a new valid state, or an unambiguous recoverable state. “The normal path completed once” is weaker; crash consistency also accounts for every point where execution could stop.

Design the on-disk states so each one has an obvious response:

Table columns: Files present; Meaning; Safe response.

Files present: original only; Meaning: no edit in progress; Safe response: open normally.

Files present: original + temporary; Meaning: preparation was interrupted; Safe response: validate or remove only the temporary.

Files present: new original + backup; Meaning: replacement completed; Safe response: test the new save; retain backup.

Files present: missing original + backup; Meaning: recovery is needed; Safe response: restore backup before launching.

Do not choose by modification time alone. Validate the expected filename, format, and contents, then ask the user before replacing the only known-good copy.

Diagram walkthrough: Follow the Flare save through a recoverable edit. Step 1: Read the closed-game save. State: build=5,1,1,2. Close Flare and read the known avatar.txt save. Keep the original bytes available while preparing the replacement; do not edit the only copy in place. Step 2: Validate the target field. State: exactly one build= line. Require one target field and check the intended complete value. Preserve every other line and the original LF or CRLF newline style. Step 3: Construct the replacement. State: build=30,30,30,30. State: complete temporary file. Write all replacement bytes to a sibling temporary file, flush it, and close its handle. Interrupted preparation leaves the original save available. Step 5: Replace and keep the backup. State: new original + backup. The complete Windows lab uses ReplaceFileW to install the new save and preserve the old one at avatar.txt.gha-backup. An existing backup causes refusal. Step 6: Verify through the game. State: four attributes equals 30. Reload the disposable character, check the four visible values, and let Flare save normally. Keep the backup until the loader and serializer have accepted the edit. This is the successful route through prepare, validate, commit, and recover. The temporary file and backup make interruptions distinguishable; atomic replacement does not make every possible failure durable.

Section: Checksums and integrity fields.

If one small value change also changes a separate fixed-size region, the file may contain a checksum.

Do not patch until you understand:

which bytes are covered;

which algorithm is used;

where the expected checksum is stored;

byte order;

whether a secret key is involved.

If the format is cryptographically signed, use supported modding tools instead of attempting to defeat the signature.

Section: Debug the loader only if needed.

Process Monitor can show the file read, and a debugger breakpoint on file APIs can show the buffer passed into parsing.

Image description: A file read observed in the debugger

In 32-bit Flare on Windows, open x64dbg’s Symbols tab, choose kernelbase.dll, find CreateFileA, and break at its first instruction. Saving the game puts the same avatar.txt path on the stack, independently confirming the location found with Process Monitor.

The aim is to learn the format, not to disable validation.

Section: Validate the result.

keep the original backup;

load the disposable character;

confirm only the intended field changed;

save again normally;

confirm the game can reload that new save.

If loading fails, restore the backup and compare the serializer’s whitespace, encoding, terminators, ordering, and integrity field.
