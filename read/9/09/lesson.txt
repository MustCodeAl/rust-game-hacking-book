Binary Saves and Hex Editing

Section: A binary save is not text.

Lesson 9.2 edited Flare’s text avatar.txt save. Its build=5,1,1,2 line records a character whose Physical attribute is 5 and is readable in any text editor. Many saves are not. They store numbers as raw bytes, the same way a u32 sits in memory, because that is smaller and faster to load. Open one in a text editor and most bytes turn into boxes, blanks, or stray symbols. Worse, saving it from a text editor can quietly change bytes, for example by converting line endings, which corrupts the file.

A hex editor shows a file as what it is: a numbered sequence of bytes, each written as two hexadecimal digits. In byte-overwrite mode, it can save the exact replacement bytes without decoding the whole file as text. HxD and ImHex are common examples; they show the same three columns, so nothing in this lesson depends on which one you use.

This lesson uses a toy save format made for the book, GSAV, and a Rust lab that reads and writes it. Here is the complete save for a character called Nia, at level 3, with 250 gold. It is 19 bytes long:

Section: The three columns of a hex editor.

Opened in a hex editor, those 19 bytes look like this:

The offset column on the left gives the position of the first byte on each row, counted in hex from the start of the file. A row holds 16 bytes, numbered 00 to 0F along the top, so the second row starts at byte 16, which is hexadecimal 1 0 (1 times 16 + 0).

The byte column in the middle shows each byte as two hex digits. To find the offset of any byte, add its row offset and its column number: the last byte sits on row 00000010 in column 02, so its offset is hexadecimal 1 0 + hexadecimal 0 2 equals hexadecimal 1 2, which is 16 + 2 equals 18.

The character column on the right shows each byte as a character. ASCII is the standard table that gives every English letter, digit, and common symbol a number from 0 to 127. Bytes from hexadecimal 2 0 (a space) to hexadecimal 7 E ( ~ ) are printable ASCII and appear as themselves; every other byte appears as a dot.

The character column is where text stands out: GSAV at the start and Nia in the middle. It also shows things that are not text. The byte at hexadecimal 0 F is 4A, which is 4 times 16 + 10 equals 74, the ASCII code for the letter J, so the column shows a J even though that byte is part of a number. Nothing in the file marks which bytes are meant as text, so the editor shows every byte both ways.

Each byte belongs to one field of the format. A strip of 16 boxes is one row:

Section: A file offset is not a memory address.

An offset in a file is a distance in bytes from the file’s first byte: offset hexadecimal 0 6 means “skip six bytes, then read.” It is not a memory address. When the game loads this save, it reads the bytes and copies each field into its own structures somewhere in its memory, so the gold that sat at file offset 6 ends up at an address that has nothing to do with 6 and usually changes from one run to the next. Two things follow:

Changing byte 6 on disk does not change a running game. The game sees the new value only when it loads the file again, and a game that is still running can overwrite the edit when it saves on exit, so close it first.

An address found with a memory scanner cannot be typed into a hex editor’s “go to offset” box, or the other way round. Lesson 5.1 met the same split for executables, where the section table translates between file offsets and addresses.

Section: The magic number and the version say what the file is.

The first four bytes, 47 53 41 56, are ASCII codes. In decimal they are 4 times 16 + 7 equals 71 (G), 5 times 16 + 3 equals 83 (S), 4 times 16 + 1 equals 65 (A), and 5 times 16 + 6 equals 86 (V). A fixed byte pattern at the start of a file that identifies its format is called a magic number. The loader checks it before anything else: a file that does not begin with GSAV is some other kind of file, and reading its bytes as gold and levels would produce nonsense. A PNG image likewise begins with a fixed signature; renaming either file does not change its bytes or format. We will use that same idea again when checking mod archives.

The next two bytes, 01 00, are the version: a number the game’s developers raise whenever they change the layout. A loader reads the version to choose the right layout, and an editor that meets a version it does not know has to refuse the file, because the fields may have moved. The lab returns an UnsupportedVersion error for anything other than 1.

Section: Multi-byte numbers are stored lowest byte first.

Games for x86 PCs usually write numbers to disk exactly as they sit in memory, which is little endian: the byte worth the least comes first. Lesson 1.8 explains why each box is worth 256 times the one before it. Gold occupies offsets 6 to 9:

Labelled memory diagram. hexadecimal 0 6: FA; hexadecimal 0 7: 00; hexadecimal 0 8: 00; hexadecimal 0 9: 00. Groups: times 1; times 256; times 65,536; times 16,777,216; hexadecimal F A is 15 times 16 + 10 equals 250, and every other byte is 0. The gold field. Read lowest byte first, FA 00 00 00 is 250.

The version works the same way with two bytes: 01 00 is 1 times 1 + 0 times 256 equals 1. The level at offset 10 is a single byte, 03, so there is no order to get wrong: it is 3.

Reading in the wrong order gives a number that is obviously off, which makes a useful check. FA 00 00 00 read with the most significant byte first is hexadecimal F A 0 0 0 0 0 0, which is 250 times 16,777,216 equals 4,194,304,000 gold. When one byte order gives a plausible value and the other gives billions, the plausible one is almost always the right one.

Section: A length-prefixed string.

A name has no fixed size, so this format stores its length first. The byte at offset 11 (hexadecimal 0 B) is 03, so exactly 3 bytes of text follow, at offsets 12, 13, and 14. Text stored this way is a length-prefixed string.

Labelled memory diagram. hexadecimal 0 B: 03; hexadecimal 0 C: 4E; hexadecimal 0 D: 69; hexadecimal 0 E: 61. Groups: length: 3; N i a; 4 times 16 + 14 equals 78, 6 times 16 + 9 equals 105, 6 times 16 + 1 equals 97. The length byte says how many bytes of text follow. There is no end marker.

This layout has two consequences:

Everything after the name moves when the name’s length changes. With Nia, the checksum starts at 12 + 3 equals 15. With a five-letter name such as Grace, it starts at 12 + 5 equals 17, and the file grows to 17 + 4 equals 21 bytes. A tool that assumes the checksum always sits at offset 15 breaks on the first longer name.

The length byte has to be checked against the file before it is trusted. A damaged save whose length byte reads C8, which is 12 times 16 + 8 equals 200, claims a name that runs up to offset 12 + 200 equals 212, far past the end of a 19-byte file. The lab compares 12 + length + 4 with the real file size and returns an error instead of reading past the end.

Other formats mark the end of a string instead, most often with a 00 byte after the text, the convention C uses. In an unfamiliar save, a byte just before some text that equals the number of characters after it is the fingerprint of a length-prefixed string.

Section: Find a field by comparing two saves.

The layout above was handed to you. A real game’s layout usually is not, so its fields are found by comparison, the byte-level version of Lesson 9.2’s two-save diff: save once, change exactly one value in the game, save again, and compare the two files. Most hex editors have a compare view that highlights the bytes that differ.

Suppose Nia earns 1,000 gold, taking her from 250 to 1,250, and nothing else changes. Offsets hexadecimal 0 0 to hexadecimal 0 5 are identical in both saves, so the strips start at hexadecimal 0 6:

Save A, with 250 gold.

Labelled memory diagram. hexadecimal 0 6: E2, highlighted; hexadecimal 0 7: 04, highlighted; hexadecimal 0 8: 00; hexadecimal 0 9: 00; hexadecimal 0 A: 03; hexadecimal 0 B: 03; hexadecimal 0 C: 4E; hexadecimal 0 D: 69; hexadecimal 0 E: 61; hexadecimal 0 F: 36, highlighted; hexadecimal 1 0: 03; hexadecimal 1 1: 00; hexadecimal 1 2: 00. Groups: gold; checksum. Save B, with 1,250 gold. Exactly three bytes differ: hexadecimal 0 6, hexadecimal 0 7, and hexadecimal 0 F.

Offsets 6 and 7 changed from FA 00 to E2 04. hexadecimal E 2 is 14 times 16 + 2 equals 226, so reading lowest byte first gives 226 + 4 times 256 equals 226 + 1,024 equals 1,250: the new gold. Gold therefore starts at offset 6. Offsets 8 and 9 hold 00 in both saves, so they could be the upper half of a 4-byte gold field or something unrelated that happens to be zero. Two bytes can hold at most 256 times 256 minus 1 equals 65,535, so a third save with more gold than that settles it: if byte 8 changes, the field is wider than two bytes.

Offset hexadecimal 0 F changed as well, from 4A to 36, although nothing else in the game changed. A byte that changes whenever any other value changes is the mark of a checksum, the subject of the next section.

In a real game the diff also catches bytes that change on their own, such as play time, a timestamp, or a random seed. Lesson 9.2 separates those by repeating the comparison with several values; the real field follows the in-game number every time.

Section: Why one edited byte breaks the save.

The last four bytes are a checksum: a number computed from the other bytes and stored beside them, so the loader can detect damage. This format uses the simplest checksum there is. Step 4: Compute the checksum. State: sum(bytes 0–14) equals 842. Add every byte before the checksum, including the header, numeric fields, length, and name. For this exact save, the total is 842. Step 5: Compare the stored total. State: 4A 03 00 00 to 842. Read the final four bytes as a little-endian u32. The stored 842 equals the computed 842; a mismatch refuses the file instead of loading damaged state. Step 6: Decode the accepted record. State: Nia: level 3, gold 250. The checked layout now gives gold 250 at offsets 6–9, level 3 at offset 10, and the three name bytes Nia at offsets 12–14. This traces the unchanged sample save. Editing gold also changes the required checksum; a correct offset and byte order cannot bypass a failed integrity check.

Now type gold over as 9,999 and change nothing else. 9,999 is 39 times 256 + 15, and 39 equals 2 times 16 + 7 equals hexadecimal 2 7 while 15 equals hexadecimal 0 F, so 9,999 is hexadecimal 2 7 0 F and its little-endian bytes are 0F 27 00 00. The old gold bytes added 250 to the sum; the new ones add 15 + 39 equals 54. The loader’s total becomes 842 minus 250 + 54 equals 646, the stored checksum still says 842, and the loader refuses the save as corrupt.

The fix is to do what the game does when it saves: recompute the checksum. For 1,250 gold, the gold bytes E2 04 00 00 add 226 + 4 equals 230 instead of 250, so the total is 842 minus 250 + 230 equals 822. That is 3 times 256 + 54, and 54 equals 3 times 16 + 6 equals hexadecimal 3 6, so the checksum is hexadecimal 3 3 6, stored as 36 03 00 00: exactly what save B contained. A plain sum has a blind spot: adding numbers in a different order gives the same total, so swapping two bytes goes unnoticed. That is why real formats more often use a CRC-32, a 32-bit checksum designed to change when bytes are reordered, or a hash. The editing procedure stays the same: work out which bytes are covered, which algorithm runs, where the result is stored, and in which byte order, as listed in Lesson 9.2. If the check uses a secret key, as a MAC does, or a digital signature, it cannot be recomputed without that key; Lesson 9.9 explains why.

Section: Edit without losing the original.

A hex editor writes straight back to the file it opened, so a few mechanical details decide whether an edit can be undone:

Keep an untouched copy of the save before the first edit, and keep it until the game has loaded the edited save and saved it again. A wrong byte is only undone by that copy.

Type over bytes; do not insert them. Hex editors have an overwrite mode, which replaces bytes in place, and an insert mode, which adds bytes and pushes everything after them along. In a fixed layout, one inserted byte moves every later field: the loader then reads the checksum from the wrong place and finds the file one byte too long. Changing gold overwrites exactly four bytes.

A longer name is the one edit that must insert bytes. Renaming Nia to Grace means inserting two bytes, changing the length byte from 03 to 05, and recomputing the checksum at its new offset, 17. Getting any one of the three wrong makes the loader refuse the file.

A program that edits saves should write the result to a temporary file and then replace the original in one step, as in Lesson 9.2, so a crash mid-write cannot leave half a save.

Section: When a hex editor cannot help.

Everything above depends on each field being stored as plain bytes at a known place. Two common designs break that assumption:

A compressed save stores an encoded form of the data. gzip, a common compression format, starts its files with 1F 8B, the same bytes Lesson 8.2 found at the start of Wesnoth’s network payloads. The gold field is not anywhere in the file as plain bytes, and changing one compressed byte changes how everything after it decompresses; gzip’s own CRC-32 at the end of the stream then fails. The file has to be decompressed, edited, and compressed again with a tool that understands the format.

An encrypted save looks like random bytes: no readable text in the character column, and every value from 00 to FF appearing about equally often. Changing the encrypted bytes, the ciphertext, changes what they decrypt to in ways nobody can choose, and authenticated encryption, covered in Lesson 9.9, refuses the altered file outright. Without the key there is nothing to edit.

The two-save comparison tells these cases apart quickly. A plain format changes a handful of bytes, as it did above; a compressed file, or one encrypted afresh on every save, changes almost everything from the first difference onward. If the save turns out to be text after all, Lesson 9.2’s key/value editing is simpler than any hex edit.

Section: The lab.

hex_save_lab.rs implements the GSAV format in portable safe Rust:

every offset is a named constant, such as GOLD_OFFSET (6) and NAME_LENGTH_OFFSET (11), so no bare numbers are scattered through the code;

parse checks, in the loader’s order, that the file is long enough, the magic is GSAV, the version is 1, the length byte agrees with the file size, and the stored checksum equals the recomputed sum, and it returns a distinct SaveError for each failure, such as BadMagic, TooShort, or ChecksumMismatch, instead of panicking;

patch_gold overwrites the four gold bytes in a copy and then recomputes the checksum, while patch_gold_without_checksum makes the broken edit so its rejection can be seen;

patch_gold runs parse on the original first, because recomputing the checksum of an already damaged save would give the damage a valid checksum;

hex_dump prints bytes in the three-column layout above, and differing_offsets is the compare view.
