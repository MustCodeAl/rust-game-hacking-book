Windows Input: Polling, Events, and Messages

Section: “Send a key” can mean three different things.

Our DLL, dynamic link library, now has a controlled lifecycle, and the scanner can do work off the game thread. A local tool also needs a deliberate way to start or stop a feature. Pressing a menu hotkey, sending a synthetic key to an offline game, and calling a window procedure solve different problems, even though all three sound like “input.”

Windows has several input paths because programs receive interaction in different ways:

Table columns: Path; What it really does; Good course use; Common surprise.

Path: GetAsyncKeyState; What it really does: Samples the current physical key state; Good course use: Toggle a local tool menu; Common surprise: It does not wait for an event.

Path: SendInput; What it really does: Inserts keyboard or mouse events into the system input stream; Good course use: Drive an offline game while its window is active; Common surprise: It does not target one HWND.

Path: SendMessageW / PostMessageW; What it really does: Calls or queues a message for a window procedure; Good course use: Control a window you created or a documented local test window; Common surprise: Many games read Raw Input or device state instead.

Each path lands on a different destination, which is the real reason to pick carefully:

Diagram. From your code asks: is this key down right now? to desktop-wide physical key state. From your code inserts an event into the system input stream to whichever window currently has keyboard focus. From your code calls or queues a message for a window procedure to one specific HWND's window procedure.

There is no general Win32 function named SendKey. .NET’s SendKeys is a separate convenience layer, while the old keybd_event function has been superseded by SendInput. Naming the path correctly prevents a lot of confused debugging. ⌨️

Section: State, events, and messages are not interchangeable.

GetAsyncKeyState answers a state question: “is this key down at the instant I sample it?” SendInput submits input events to the desktop input pipeline. SendMessageW invokes a window-procedure message contract. Similar names do not put them on the same path.

A game may combine several paths: Raw Input for aiming, ordinary window messages for menus, and polled key state for a developer console. Observe how the target consumes input before choosing an API, application programming interface,. Sending WM_KEYDOWN to a window that reads device state is not a failed keyboard event; it is the wrong abstraction.

Always pair a down transition with an up transition, including cancellation and error paths. A state machine should own which synthetic inputs are currently held so shutdown can release exactly those inputs.

Section: A window receives messages through a loop.

The message path makes more sense if we first follow an ordinary window. A key press or resize can place a message in the thread’s queue. A message loop retrieves it and DispatchMessage calls the window’s window procedure. That procedure is a callback: a function the application provides so Windows can call it when a message is dispatched. For example, it might respond to WM_SIZE by updating the window’s layout. TranslateMessage can post character messages derived from key messages; DispatchMessage sends a retrieved message to its window procedure. PeekMessage reports no available queued message without waiting, which is why the game-style loop can continue its own work. The exact handling of Raw Input and other message types varies by application; do not assume every game consumes WM_KEYDOWN as its gameplay input. See Microsoft’s GetMessageW and PeekMessageW references for their return and queue rules.

The callback must also return promptly. While a window procedure is busy reading a large file or waiting on a network request, other messages for windows on that thread cannot be handled. The window may stop repainting or responding to input. Microsoft’s window-procedure guidance explains this bottleneck. The same concern appears when a hook adds work to a game’s time-sensitive path: move slow work elsewhere and make overload visible, as Lesson 4.10 does for a recorder.

Groups: these messages wait until the first handler returns. One thread's message queue. A slow first handler delays movement, repainting, and close handling.

Polling is the other side of this distinction. If no one sends your tool a message when the game’s gold changes, the tool can check the value on its own schedule. It does work even when nothing changed. Lesson 4.9 shows how to compare successive snapshots so many polls produce one meaningful event instead of many repeated actions.

Section: Read a hotkey with GetAsyncKeyState.

The current windows crate exposes GetAsyncKeyState as an unsafe function taking a virtual-key number and returning an i16. Windows puts “down right now” in the most significant bit. Because that is the sign bit of an i16, a negative result means down:

Labelled memory diagram. bit 15 (sign): 1 if down now, highlighted; bits 14-1: unused here; bit 0: stale “pressed since last call” flag. GetAsyncKeyState returns an i16. A negative result (bit 15 set) means the key is down right now. Bit 0 is kept for old compatibility, but another process's call can consume it first, which is why the edge detector below is built from bit 15 instead.

Poll at a modest rate such as every 8–16 milliseconds. A tight loop wastes a CPU, central processing unit, core. A zero result can also mean the desktop is inactive or Windows integrity rules prevent the query; “zero” does not prove a keyboard is broken.

Sampling can miss a very short press between polls. That is a property of polling, not a reason to trust the ambiguous low bit. For a tool hotkey, choose a comfortable key and polling interval, then test focus changes, key repeat, and shutdown while held.

Always release a key or mouse button during shutdown, even if a feature fails. SendInput is subject to User Interface Privilege Isolation (UIPI): Windows blocks input from a lower-integrity process into a window owned by a higher-integrity one, such as a game running as administrator while your tool does not. Windows does not tell you why: neither SendInput’s return value nor GetLastError identifies UIPI as the cause, and the target window simply never reacts, which looks identical to a wrong virtual-key code or an unfocused window.

If synthetic input silently does nothing, check whether the target is elevated before suspecting your own code. Some games also intentionally use Raw Input or device APIs that do not behave like a normal text box. Do not respond by repeatedly flooding input.

Section: SendMessageW is not simulated keyboard input.

Every Win32 window has a window procedure that receives numbered messages. SendMessageW invokes that procedure synchronously and waits for it to finish. PostMessageW puts a message on the owning thread’s queue and returns. For a window outside your process, a bounded wait is usually safer than an unlimited one:

Code example. The code’s comments explain: 🛡️ This custom message belongs to our own lab window. It carries only // integer values—never a pointer into this process. let delivered equals unsafe { SendMessageTimeoutW( window, WM_LAB_REFRESH, WPARAM(0), LPARAM(0), SMTO_ABORTIFHUNG, 100, Some(&mut message_result), ) }; anyhow::ensure!(delivered.0 not equal to 0, "lab window did not answer in 100 milliseconds"); Ok(message_result)}

Use PostMessageW when the receiver’s documented contract says queuing is correct and no immediate result is required. Never pass a local pointer in LPARAM to an unrelated process: Windows automatically marshals only certain system messages below WM_USER. A custom WM_APP message is appropriate when both sides share a pointer-free contract.

Most 3D games do not treat WM_KEYDOWN as authoritative gameplay input. They may poll device state, consume Raw Input, or ignore messages while unfocused. Sending a window message is therefore not a stronger version of SendInput; it is a different communication path.

An HWND is also called a handle, but it is owned by the window manager and is not closed with CloseHandle. This is why “wrap every H... value in the same RAII type” is wrong. Learn the creation, borrowing, and destruction contract for each API family.

Section: A controlled lab checklist.

Start only the course’s local/offline target.

Discover its window by PID and confirm it is foreground.

Use Insert only to toggle your menu; detect the rising edge yourself.

Send one balanced input pair and count the events SendInput accepted.

Move focus to Notepad and verify the tool pauses instead of typing there.

Shut down while a feature is active and verify every held input is released.

Log errors and stop; never escalate privileges or flood retries automatically.
