Tool Architecture, Commands, and Cleanup

Several small labs can work on their own and still fail when combined. The input thread changes settings while a worker is reading them. Two features install a patch at the same address. Closing a menu leaves a worker running inside a D L L, dynamic link library, that is about to unload. These failures come from the connections between components, even when each component’s main calculation is correct.

The D L L, hook, input, and menu lessons have supplied the pieces. This lesson gives each piece an owner and a place in the tool’s control flow. We will use a small monitor of a local player’s health and gold to express the design; the same rules later support camera snapshots and rendering features.

Section: Combining code exposes hidden problems.

Five prototypes can each work alone and still fail when combined. Common causes include:

each feature reads the same memory separately;

two features try to own the same patch;

global booleans get out of sync;

shutdown happens while a worker is still running;

one feature’s error crashes every other feature.

Adding conditions to each feature does not settle who owns shared resources. An explicit architecture does: it names the stages, the data crossing between them, and the component responsible for cleanup.

CycleDisplay advances one variant at a time and wraps back to Off. Stop returns true, which the worker uses to leave its update loop and start cleanup. A stop command is a lifecycle decision; changing the label on a menu cannot stop a thread.

The input thread sends commands through a channel. The worker owns and changes the settings, avoiding shared mutable globals. If a command enables a patch, the worker sends an acknowledgement only after the patch owner reports success. The menu can then distinguish requested state from applied state.

Section: Shut down in reverse order.

Do not unload code while another thread may still execute it. Stop accepting new commands first, request worker shutdown, and wait for those workers to finish before restoring their patches and releasing handles. A restoration failure must remain visible; a vanished window is not proof that cleanup completed.

Narration: The window may disappear before a worker exits. Waiting for that worker keeps its final operations from reaching already-released code or handles.

Load one profile only after fingerprinting the executable. At every address that will be patched, compare the live bytes with the expected original instruction signature before enabling the feature. A changed build must produce a clear rejection, not a plausible-looking value from the wrong field.

Section: Reuse without surrendering judgment.

Reusing proven work is normal engineering. Rebuilding everything wastes time; adding a dependency for every five-line problem creates a different kind of fragility. Make the decision in this order:

Can the standard library or an existing project abstraction do it clearly?

Is there a maintained crate whose A P I, application programming interface,, license, and safety model fit?

Is there a small licensed example you can adapt and test?

If not, what is the smallest implementation you can own confidently?

When a dependency is large, isolate it behind a small interface. When copied functionality needs heavy modification in several places, either make one reusable project module or choose a library that already owns that problem. When configuration changes more often than low-level mechanics, a scripting layer such as Lua may be a better boundary than recompiling the whole tool.

Reading other projects shows how several tools model the same problem. Test their assumptions against your target, then write the smallest design that fits. When code is actually reused, preserve its required license notices and attribution; when only an idea is reused, explain it in your own structure and words.

Porting a small licensed tool can be good practice. Begin with its tests or observable behavior, reproduce one behavior at a time, and explain why your ownership and error model differ. This teaches the boundary instead of rewarding blind copy-and-paste.

Separate Windows-only checks can verify handle ownership and byte copying. When one fails, you know whether the problem is the build-verification rule or the ReadProcessMemory boundary. 🧪

A one-shot memory scanner can print its matches directly. A long-running in-process menu should log the same fields for every state change: target_game, target_build, feature, address, expected_bytes, found_bytes, action, and restored. Those log entries show which patch was enabled and whether its original bytes were restored. Keep them separate from the visible menu so closing or redesigning the UI does not erase the log needed to debug a failed cleanup.

Section: Know when the combined tool is ready.

Combining separate features into one D L L is what the original course called the multihack. The useful engineering question is whether the combination preserves every feature’s ownership and cleanup rules.

A multifeature tool is ready when:

starting it twice does not double-hook;

every feature can be toggled repeatedly;

disabling restores its changes;

target closure stops the tool cleanly;

unknown versions are rejected;

one feature error does not corrupt the rest;

the offline target behaves normally after exit.
