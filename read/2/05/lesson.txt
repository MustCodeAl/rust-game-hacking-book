Tracing an Action Through Its Callers

Finding one instruction is useful. Understanding the surrounding feature is better.

Section: Start from a known anchor.

In an offline Wesnoth 1.14.9 match, recruiting a unit reduces the player’s four-byte gold value by that unit’s price. The instruction that writes the reduced gold is our anchor. Set a code breakpoint on the instruction you verified in the debugger, recruit one unit, and let the breakpoint fire.

The current function probably handles a small part of recruitment. To discover who asked for that work, look at the call stack or run until the function returns.

Now you are back in the caller. Repeat this carefully to move from the low-level write toward the broader decision that requested it.

Section: Why the caller is visible.

When x86 executes call, it places a return address on the stack before jumping to the callee. That address points to the instruction the caller expects to run next. A debugger’s call stack combines return addresses with known module ranges and function information to show the nested route that reached the breakpoint.

The call stack a debugger shows is a reconstruction, and it may be incomplete. Optimizations can inline functions, reuse stack space, or omit traditional frame pointers. Confirm an important caller by returning to it or placing a breakpoint at its call site and reproducing the action.

Step 7 leave leave is mov e s p, e b p (e s p equals this value) followed by pop e b p: e b p equals the word at this value equals this value, then e s p equals this value + 4 equals this value. The locals are released; their bytes are not erased.

Step 8 ret ret pops the return address: e i p equals the word at this value equals this value, then e s p equals this value + 4 equals this value. Execution resumes right after the call.

Releasing stack space does not erase it: after leave and ret the old bytes are still in memory, but they are no longer part of any live frame. A compiler can also omit the e b p frame; this is the conventional layout.

Section: What can a write past the end of a local buffer reach?.

Suppose the function copies bytes into a 8-byte local buffer and never checks the length. A copy goes from lower to higher addresses, so past the end of the buffer lie, in order, the rest of the frame: saved e b p, the return address, then the caller’s own data. When the function runs ret, the C P U, central processing unit, loads e i p from those bytes, so the function returns wherever the written data says. This is the classic stack buffer overflow bug.

Section: Establish context by following the observed call chain.

Here, establishing context means connecting a stored change to the specific player, requested action, operands, and checks that caused it. At the gold write, knowing “subtract 25” is incomplete: is that an item price, a fine, or a different player’s payment?

Reproduce one action, confirm its write, inspect the caller, and repeat until you can explain that action. Compare a second action that shares the helper: it can reach the same write for a different reason. A breakpoint above the shared helper needs that caller context to distinguish them.

The final steps inspect a recorded path; they do not rewind or repeat a purchase. In a live debugger, Run until return executes the rest of the current function. Step over executes a call and pauses after it returns; Step into follows its executed instructions. None undoes previous writes. Note the current values again after running, and distinguish an inferred call stack from a call site you reproduced. Inlining and tail calls can remove an ordinary call/return boundary.

In brief: Bubbling follows confirmed callers toward the action. Keep the player, arguments, checks, and result together so one shared helper is not mistaken for one feature.

Section: Separate “where” from “why”.

The gold instruction tells you where a change happens. The menu dispatcher tells you why execution reached it.

That distinction matters:

patching the subtraction changes the stored cost result;

changing a branch may select a different feature;

hooking the dispatcher lets you observe every menu action.

Do not make all three changes at once. Test one layer at a time.

This is also a lesson about abstraction levels. The subtraction is a low-level side effect. The recruitment function groups validation and side effects into one operation. The dispatcher chooses among operations. Moving upward explains more behavior but also adds more unrelated branches, so stop when the original question is answered.

In brief: The write shows where gold changes, and the callers show why. Stop climbing once you can answer your question.

Section: Follow dependencies, not just nearby instructions.

“Backward” does not simply mean scrolling upward in the disassembly. It means following the facts that had to be true for the anchor instruction to run.

A data dependency asks where an operand came from. If e a x is the price, find the instruction or argument that produced e a x.

A control dependency asks which comparison allowed this block to run. If a branch skipped the subtraction, determine what value controlled that branch.

A call dependency asks which caller requested this operation and what arguments it supplied.

Compilers can move calculations away from the source statement that inspired them. The instruction immediately above the anchor may be unrelated, while the important value was loaded twenty instructions earlier or passed by the caller. Track one value and one decision at a time.

A practical stopping condition is: stop tracing callers when you can name the input, the decision, and the observable result in plain English. Going farther may reveal the whole menu framework, but it no longer answers the focused gold question.

Alternative: Think of tracing a delivery: who ordered it is the caller, where the goods came from is data, and which check let it ship is the branch.
