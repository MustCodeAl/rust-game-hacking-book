Lesson 11.8 / Listening edition

Threads, Contexts, and Stacks

A game's threads share process resources while retaining separate execution contexts and call stacks; scheduling and races shape what an observer sees.

About 33 minutes

Section: A process owns resources; threads execute code.

The memory map says which pages existed when the tool asked. It cannot tell whether the game is changing an object at the same moment. To understand that time gap, we need to know who executes the game’s instructions and which state each execution path shares.

A process supplies the address space, handles, modules, and security boundary. A thread is a path of execution inside that process.

Every process begins with at least one thread. Games commonly add threads for rendering, audio, networking, asset loading, input, and background work. Those names describe roles chosen by the program; Windows fundamentally schedules thread IDs, priorities, and CPU, central processing unit, state.

Threads in the same process share code and most data, but each thread has its own:

thread ID, or TID;

instruction pointer and general CPU registers;

stack and stack pointer;

thread-local storage;

scheduling state and priority information;

TEB, introduced in the PEB/TEB lesson.

Two threads can access the same object at nearly the same time. That is why games use mutexes, events, atomics, queues, and other synchronization tools.

The process supplies shared resources, while each execution path keeps its own paused CPU state and call history:

Diagram. From Game process to Shared memory, modules, handles. From Game process to Thread A. From Game process to Thread B. From Thread A to Context and stack A. From Thread B to Context and stack B.

This shared-versus-private split explains both communication between threads and the races that communication can create.

Section: Scheduling is not the same as parallel execution.

Windows schedules runnable threads by giving them turns on CPU cores. On one core, threads can interleave: one runs, pauses, and another runs. On several cores, some threads can also run truly in parallel. The program must be correct under both possibilities.

Suppose the update thread changes a player record in two steps while an overlay thread reads between them:

Diagram labels, in drawing order: overlay thread; player record; update thread; sees the new x with the old; y and health — a state that; never existed; write x position; read x, y, and health; write y position.

The overlay may observe a combination that was never a complete game state. This is an interleaving problem. “It worked ten times” does not prove it is safe, because the scheduler may choose a different order on the next run.

Section: A race that loses an update.

A bug whose result depends on which thread happens to run first is a race condition. The torn read above is one. The most common kind loses a write.

“Add 500 gold” is one line of source code, but the CPU does it in three steps: read the value into a register, add, and write the result back. Put two threads on the same gold field, one adding a 500-gold quest reward and one taking 300 for a purchase, and let the scheduler interleave them:

Table columns: Step; Reward thread; Purchase thread; gold in memory.

Step: 1; Reward thread: reads 1,000; Purchase thread: ; gold in memory: 1,000.

Step: 2; Reward thread: ; Purchase thread: reads 1,000; gold in memory: 1,000.

Step: 3; Reward thread: 1,000 + 500 equals 1,500; Purchase thread: 1,000 minus 300 equals 700; gold in memory: 1,000.

Step: 4; Reward thread: writes 1,500; Purchase thread: ; gold in memory: 1,500.

Step: 5; Reward thread: ; Purchase thread: writes 700; gold in memory: 700.

Diagram walkthrough: Two correct calculations, one lost reward. Step 1: Reward thread reads gold. State: gold equals 1000. The reward thread reads the shared gold field as 1,000. It now has a local copy to which it will add the 500-gold reward; memory still holds 1,000. Step 2: Purchase thread reads gold. State: purchase reads 1000. Before the reward is written back, the purchase thread also reads 1,000. Both threads now calculate from the same old value, even though their changes should accumulate. Step 3: Calculate in separate registers. State: reward 1500; purchase 700. The reward thread computes 1,000 + 500 equals 1,500. The purchase thread computes 1,000 minus 300 equals 700. Neither result has reached the shared field, which still contains 1,000. Step 4: Publish the reward result. State: gold equals 1500. The reward thread writes 1,500 to gold. This write completes its work, but it does not update the purchase thread’s local result of 700. Step 5: Overwrite with the stale result. State: gold equals 700; expected 1200. The purchase thread writes 700 last. The shared field loses the reward, although both arithmetic operations were correct. The intended combined result was 1,000 + 500 minus 300 equals 1,200. The changing memory value makes this particular interleaving visible. The mutex described below makes the purchase wait, then read 1,500 and write 1,200, preserving both changes.

The player should have 1,000 + 500 minus 300 equals 1,200 and has 700. The reward vanished, because the purchase thread wrote a result computed from a value that was already out of date. Most runs interleave harmlessly, with one thread finishing before the other starts, which is why a race can pass every test and still fail for a player.

A mutex fixes it by making read, add, and write one unit: the purchase thread waits at step 2 until the reward thread has written 1,500, then reads 1,500 and writes 1,200. For a single number, an atomic add does the same job more cheaply; on x86, lock xadd performs the whole read, add, and write as one indivisible instruction.

The lock has its own failure, deadlock. Moving gold from player A to player B means locking both. If one thread locks A and then waits for B, while another thread locks B and then waits for A, each holds what the other needs and neither ever continues. Taking locks in one agreed order, say always the lower player ID first, makes that cycle impossible, as Lesson 12.2 shows for the Windows loader lock.

The same lost update appears whenever two writers share one value: a tool that writes a value the game is also updating every frame is racing the game, and one of the two writes will be lost.

Synchronization creates an agreement about ordering or exclusive access. A mutex can protect a group of fields as one critical section. An atomic operation can make one small value indivisible. A queue can transfer ownership of work from one thread to another. These tools solve different problems; adding an atomic flag does not automatically make the object around it coherent.

Two common non-deadlock failures deserve names:

An atomicity violation happens when several operations must behave as one unit, but another thread can observe or change state in the middle. “Check pointer, then use pointer” is unsafe if another thread can free it between those steps.

An order violation happens when one action assumes another action already occurred, but no synchronization enforces that order. A render worker reading a snapshot before initialization finishes is one example.

Here is the pointer version of the first problem. A true check does not reserve the object for the next line:

Diagram labels, in drawing order: The game; Your tool; The enemy dies and its memory is freed; Is the enemy pointer non-null?; Yes; Read health through that pointer; Bytes from whatever occupies that memory now.

The fix must enforce the required relationship, not merely make the timing less likely. A lock can protect one compound state change. An event, condition variable, or channel can establish that initialization completed before consumption begins.

Section: Ask both safety and progress questions.

Concurrent code needs two kinds of reasoning:

Safety: can something bad happen, such as a torn state, double update, or use-after-free?

Progress: can the intended work eventually happen, or can threads wait forever?

A mutex may improve safety but create a deadlock if two threads acquire locks in opposite orders. A thread may be safe yet suffer starvation if other work continually wins access. A spin loop may make progress in a test and waste an entire core in the real game.

For an observer tool, prefer immutable snapshots and message passing when possible. One component reads a bounded snapshot, validates it, and hands owned data to rendering or logging. That reduces the amount of shared mutable state whose interleavings you must reason about.

Section: Ready, running, and waiting explain thread activity.

A thread that is not executing is not necessarily broken. In a simplified state model, a thread can be:

running: currently executing on a core;

ready: able to run, waiting for the scheduler to choose it;

waiting: blocked until I/O, a timer, lock, event, or another condition changes.

Windows transitions threads between these states. A network thread may spend most of its life waiting and still be perfectly healthy. A CPU profiler mainly samples running work; wait analysis explains why a thread is not running. Use the tool that matches the question.

Section: A thread context stores paused register values.

A thread context is a structure containing register state for a particular architecture. On 32-bit x86, useful fields include:

Eip : the next instruction address;

Esp : the top of the current stack;

Ebp : a frame pointer when the compiler uses one;

Eax , Ebx , Ecx , Edx , Esi , and Edi : general-purpose registers;

EFlags : condition and control bits, including the trap flag used for single-stepping.

On x86-64, those names become Rip, Rsp, Rbp, Rax, and so on, with additional registers.

The context is meaningful only at a controlled instant. Reading or writing a running thread’s registers while it continues executing would race with the CPU. A debugger receives an event while Windows has stopped the relevant threads, or a tool explicitly suspends a thread and must later resume it.

This course’s debugger uses the debugger event model. It does not randomly freeze a game thread and hope cleanup succeeds.

Section: A stack records nested work.

When function A calls function B, the program must remember where B should return. Arguments, saved registers, local variables, and return information may be stored in a stack frame.

Labelled memory diagram. newest frame: spend_gold(), highlighted; cell 2: end_turn(); cell 3: process_player_action(); oldest shown: game_loop(). A stack trace lists frames newest first: spend_gold was called from inside end_turn, called from inside process_player_action, called from game_loop.

A stack trace walks from the current frame toward older callers. Optimized code can inline functions, omit frame pointers, move values into registers, or reuse stack slots, so the neat classroom picture is a guide rather than a promise.

That complexity is why Microsoft recommends StackWalk64 instead of inventing a stack walker from raw pointers. Matching symbols and unwind information make the result much more reliable.

Section: Start with a read-only thread inventory.

Before opening a thread or asking for its context, identify which threads belong to the target process. TH32CS_SNAPTHREAD creates a system-wide snapshot, even when a PID, process identifier, is supplied. The program must filter th32OwnerProcessID itself:

dwSize tells Windows how large a THREADENTRY32 the caller prepared. The final ERROR_NO_MORE_FILES is not a failure; it is the documented end of enumeration.

The count may change between runs because games create and retire worker threads. A TID is temporary and can eventually be reused. Do not store it as a version-specific constant.

Base priority is scheduling input, not “importance.” The currently busy rendering thread might have the same base priority as an idle worker. ETW, Event Tracing for Windows, CPU samples and debugger stacks show which threads are actually doing work.

Likewise, a TID does not identify a permanent role. A thread’s role shows up in several places: its start address or module, its stack sampled over time, its CPU and wait activity, its thread description when the game sets one, and which game events line up with that activity. One paused stack shows only what the thread was doing at that instant. In an engine with a job system, the same worker thread can be mixing audio in one sample and decompressing a texture in the next.

Section: How the Wesnoth debugger uses a context safely.

When Windows reports the course breakpoint, the event thread is stopped. The debugger:

opens that exact event thread with context rights;

reads its x86 CONTEXT ;

moves Eip back over the one-byte int3 ;

sets the trap flag in EFlags ;

continues the event so one original instruction runs;

receives the single-step event;

clears the trap flag and rearms the breakpoint.

Section: Why this lesson does not hijack threads.

Changing another thread’s instruction pointer, queuing executable work to it, or suspending service threads is not required to understand game execution. Those operations can deadlock a process, strand locks, corrupt state, or stop the diagnostics that would explain the failure.

The course inventories threads read-only and changes a context only inside the explicit breakpoint lifecycle of the version-matched Wesnoth debugger, where every event is continued exactly once.

The inventory is thread_inventory.rs. The controlled context example is wesnoth_debugger.rs.
