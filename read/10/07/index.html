Lesson 11.9 / Listening edition

From Win32 Calls to Kernel Services

A Windows API call crosses layers of exports, native APIs, and system calls before a kernel service acts on a request.

About 28 minutes

Section: One function call can cross several layers.

The course tool can now name a process, open and own a limited handle, inspect page metadata, and observe threads. Each operation was a call to a Windows A P I, application programming interface. The remaining question is where such a call goes when the tool asks the operating system to do something it cannot do directly.

A call to a Windows function such as VirtualQueryEx does not instantly jump into the deepest part of Windows. It usually passes through layers.

Use three separate ideas: contract, implementation path, and privilege transition. Win32 documents the contract application code may rely on. User-mode DLLs implement or forward that contract. A system-call instruction performs the controlled C P U, central processing unit, transition for work that requires kernel privilege.

The boxes are software layers, not necessarily four separate processes. kernel32.dll and ntdll.dll are mapped into the same user-mode process as our program. Microsoft may change the implementation path while preserving the Win32 contract, which is why “calling a deeper layer” is usually less stable rather than more capable.

Section: User mode and kernel mode are permission levels.

Most game code, application code, and Windows D L L, dynamic link library, code runs in user mode. A user-mode mistake should not be able to overwrite the kernel or another process merely by using a bad pointer.

The Windows kernel and drivers run in kernel mode, where code can manage page tables, devices, scheduling, and other system-wide resources. A bug there can affect the whole computer. That is why the course does not turn ordinary game experiments into kernel-driver experiments.

The C P U enforces this border. A system call changes privilege through a defined entry point; it is not a magic function name and it is not the same thing as calling a normal function.

This design is often described as limited direct execution. The game normally runs directly on the C P U for speed, but in user mode and inside its address-space rules. Timers and interrupts let Windows regain control for scheduling. A system call lets the game request a restricted operation through a validated entry path.

The model resolves a common confusion: Windows is not interpreting every ordinary game instruction. Most instructions execute natively. Hardware privilege, address translation, interrupts, and controlled entries provide the limits that let the O S, operating system, remain in control.

Section: Win32 is the documented application interface.

The documented Win32 A P I is the part application developers are normally expected to call. Examples from this course include:

ReadProcessMemory for a read-only inspector with query-and-read rights;

VirtualQueryEx for page metadata;

CreateFileW for files and local named pipes;

CreateFileMappingW for a shared-memory object.

Microsoft can change how a supported function is implemented while keeping its documented behavior. On modern Windows, an export in kernel32.dll may forward to another D L L such as KernelBase.dll. Your source code still calls the stable Win32 name.

A forwarded export is not a jump instruction the loader inserts. The export table entry itself can hold a string such as KERNELBASE.CreateFileW in place of a code address. When GetProcAddress resolves that entry, it reads the string, locates the named D L L, and looks up the function there instead — following another forward if that entry also happens to be one. Section: Native APIs sit closer to the system call.

ntdll.dll exposes many functions whose names begin with Nt, such as NtQueryVirtualMemory. Some native functions are documented for limited uses and many are not stable application contracts.

This is the important rule:

“Closer to the kernel” does not mean “better for normal application code.”

Calling an undocumented entry point or copying a system-call number from one Windows build can make a tool fragile. Numbers and internal structures can change. The course resolves one native export so you can see the layer, but it deliberately does not call it or build a direct-syscall bypass.

Section: D L L exports are names offered to other code.

A D L L can publish an export table. Each exported name maps to an entry that the loader can resolve. GetProcAddress asks a loaded module for one of those exports.

The returned address is a virtual address in the current process. Address Space Layout Randomization, or A S L R, address space layout randomization,, means the same D L L can be mapped at a different base address in another process or after a reboot. Store the name or an R V A, relative virtual address, when that is the stable identity; do not paste a displayed absolute address into tomorrow’s program.

Section: Why GetModuleHandleW instead of LoadLibraryW?.

Both DLLs are already present in a normal Windows console process. GetModuleHandleW borrows their existing module handles; it does not request another load or add a loader reference that we would later need to release.

Section: Why does GetProcAddress use an A S C I I name?.

P E, portable executable, export names are byte strings. The s! macro creates a terminated static PCSTR. D L L file names use Windows wide strings, so GetModuleHandleW receives values from the w! macro instead.
