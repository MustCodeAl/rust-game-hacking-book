Lesson 15.8 / Listening edition

Control Gaps in Game Logic

Three toy game controls reveal a recurring mismatch between the checked proxy and the effect that actually changes state.

About 58 minutes

The next three examples each fit in one small state model. For each, identify the invariant and canonical state, then compare a checksum or environment signal with the decision telemetry and the effect. A paired regression test should show both the control gap and the legitimate behavior a repair must retain.

Section: What all three examples have in common.

Every control in this lesson makes a promise, and all three break it the same way: each one checks something near the thing it cares about instead of the thing itself.

A greyed-out button stands in for “this player is allowed to do that.” A checksum over one field stands in for “this record is intact.” A debugger flag stands in for “this request is honest.” Every stand-in is easier to check than the real property, which is precisely why someone reached for it — and every one of them can be true while the real property is false.

Once you see that shape, the repair stops being a guess. It is never “add more stand-ins.” It is to move the check to the place where the effect actually happens, and demote the stand-in to a clue that helps explain what went wrong.

Section: Why it fails.

Presentation state answers “should the button look available?” It does not answer “may the simulation perform this effect?” Multiple inputs, scripts, and restored UI state can reach the same engine operation. The weak control places authority in a copy used for presentation.

Alternative: A disabled button is a sign on a doorway; the engine’s effect boundary is the actual gate. Other request paths may never pass the sign.

Section: Repair and telemetry.

The repaired relation covers player ID, health, maximum health, and generation, then separately checks health less than or equal to maximum_health. Emit a specific failure such as ChecksumMismatch or OutOfRange; do not compress every failure into one boolean in production code.

The regression suite mutates every covered field individually and asserts that the complete relation fails. It also keeps a valid record to prove verification is not permanently closed.

This checksum detects example-data corruption; it is not authentication. If the system needs to defend against a party who can recompute an unkeyed checksum, the design needs an authenticated owner and key lifecycle, not a more obscure formula.

Section: Compare the three failures.

All three mistakes confuse a proxy with the property that actually matters. The repair is not “add more proxy checks.” It is to enforce the invariant where the effect becomes real, then use proxy signals as supporting telemetry.

Section: Glossary terms introduced here.

Proxy: an observable value used as indirect evidence for another property.

Coverage bypass: a meaningful change outside the data examined by a control.

Effect boundary: the shared point where a requested state change becomes canonical.

Negative regression test: proves the previously failing case is refused.

Positive regression test: proves valid behavior still works after repair.

Contradiction: evidence that a control decision and resulting state cannot both satisfy the promised invariant.

The three toy failures differ in their proxies, but each lets an effect happen without checking the promised invariant at the shared boundary. Each repair keeps both sides of the evidence: the formerly accepted invalid case is rejected, and valid behavior still works. Lesson 12.10 applies the same rule to eight more failure modes.
