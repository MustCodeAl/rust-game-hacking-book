Failure Modes at Trust Boundaries

The first three control gaps were a client flag trusted as permission, a checksum that covered only part of what it protected, and an environment signal standing in for validation. Eight more failures show how the same mismatch appears in arithmetic, paths, errors, timing, and batches.

Every example lives in bypass_patterns_lab.rs, which uses no Windows APIs, no processes, no filesystem, and no network. The “attacker” is a test function calling an intentionally bad policy. That keeps the computer-science shape of each failure visible while keeping the code useless as a recipe aimed at someone else’s machine.

Section: Pattern 9: a decision cached past the state it described.

Promise: turning writes off stops the tool from writing.

Code example. The surrounding prose explains this example; the full lesson contains the exact code.

The first call stores the answer; every later call reuses it. Turn writes off afterwards and the tool keeps writing, because it is still answering a question asked at start-up.

This is a cousin of the check/use gap from Lesson 15.7, with one instructive difference: nothing raced. There is no unlucky timing to reproduce and no second thread involved. The answer simply outlived the input it was computed from. Single-threaded code can have this bug, which is why “we are single-threaded” is not a reason to skip the review.

Alternative: A cached permission resembles yesterday’s opening hours: the answer can be correct for its old input and wrong for the current situation without any race.

The repair is to re-read the setting where the write happens. A cache is only safe when something invalidates it, and nothing here does.

The repair is two phases: validate every item, then apply every item. Nothing is written until the whole request is known to be acceptable, so a denial genuinely means no change. When the effect cannot be made atomic, the alternative is an explicit rollback path — never a comment saying callers should re-check.

Section: Glossary terms introduced here.

Fail-open: treating an inconclusive check as permission.

Choke point: the single place every route to an effect must pass through.

Freshness: the property that a message has not been used before, which integrity alone does not provide.

Tolerance budget: an allowance spent across a window rather than granted per event.

Two-phase apply: validating an entire request before performing any part of it.

The eleven game-and-boundary patterns in Lessons 15.8 and 12.10 are variations on one question: does the check guard the state and effect it claims to guard? Chapter 14 extends the machine model beyond one running operating system: a hypervisor provides a guest with virtual hardware, a console begins from a trusted boot chain, and an emulator reconstructs a machine in software. In each case, ask which component owns the state and which boundary controls an effect.
