Lesson 13.8 / Listening edition

Failure Modes at Trust Boundaries

Eight further failure modes, from wrapping arithmetic to partial commits, show where an invariant must be enforced.

About 55 minutes

The first three control gaps were a client flag trusted as permission, a checksum that covered only part of what it protected, and an environment signal standing in for validation. Eight more failures show how the same mismatch appears in arithmetic, paths, errors, timing, and batches.

Every example lives in bypass_patterns_lab.rs, which uses no Windows APIs, no processes, no filesystem, and no network. The “attacker” is a test function calling an intentionally bad policy. That keeps the computer-science shape of each failure visible while keeping the code useless as a recipe aimed at someone else’s machine.

Section: The shape every one of these shares.

Diagram. From A control promises something to It checks a proxy for that thing. From It checks a proxy for that thing to The proxy and the thing come apart. From The proxy and the thing come apart to The effect happens anyway. From The effect happens anyway to Move the check to the effect.

The interesting question is never “what was the trick?” It is always “what did the control measure, and how did that stop matching what it promised?” Each section below names the promise first, because a control with no stated promise cannot be bypassed — only surprised.

Section: Pattern 9: a decision cached past the state it described.

Promise: turning writes off stops the tool from writing.

Code example. The surrounding prose explains this example; the full lesson contains the exact code.

The first call stores the answer; every later call reuses it. Turn writes off afterwards and the tool keeps writing, because it is still answering a question asked at start-up.

This is a cousin of the check/use gap from Lesson 13.6, with one instructive difference: nothing raced. There is no unlucky timing to reproduce and no second thread involved. The answer simply outlived the input it was computed from. Single-threaded code can have this bug, which is why “we are single-threaded” is not a reason to skip the review.

The repair is to re-read the setting where the write happens. A cache is only safe when something invalidates it, and nothing here does.

Slot 0 was written before slot 9 was rejected. A caller that reads “denied” and assumes nothing happened is now working from a state nobody intended, and the half-applied change is exactly the sort of thing that survives a restart.

The repair is two phases: validate every item, then apply every item. Nothing is written until the whole request is known to be acceptable, so a denial genuinely means no change. When the effect cannot be made atomic, the alternative is an explicit rollback path — never a comment saying callers should re-check.

Section: Compare all eight.

Table columns: Pattern; What was checked; What actually mattered; Where the repair belongs.

Pattern: Wrapping bound; What was checked: a sum that wrapped; What actually mattered: whether the range exists; Where the repair belongs: the slice that owns the bytes.

Pattern: Path prefix; What was checked: the requested text; What actually mattered: the resolved location; Where the repair belongs: after resolution.

Pattern: Fail-open; What was checked: two outcomes; What actually mattered: three outcomes; Where the repair belongs: the error branch.

Pattern: Second route; What was checked: one entry point; What actually mattered: every route to the effect; Where the repair belongs: the single choke point.

Pattern: Replay; What was checked: integrity; What actually mattered: integrity and freshness; Where the repair belongs: a sequence the receiver remembers.

Pattern: Cached decision; What was checked: state at start-up; What actually mattered: state at the effect; Where the repair belongs: the write itself.

Pattern: Tolerance drift; What was checked: one tick; What actually mattered: accumulated excess; Where the repair belongs: a budget over a window.

Pattern: Partial batch; What was checked: each item in turn; What actually mattered: the request as a unit; Where the repair belongs: validate-then-apply.

Read the middle two columns together. In every row the control measured something true, and something true was not the same as the thing promised. That gap is the whole subject.

Section: Place a bypass claim in the table.

When you meet an evasion claim in the wild, the useful response is not to run it. It is to work out which row of that table it belongs to:

Table columns: Question; Where the answer comes from.

Question: What did the control promise?; Where the answer comes from: documentation, or the check’s own comment.

Question: What does it actually measure?; Where the answer comes from: the code at the branch.

Question: How can the two come apart?; Where the answer comes from: the pattern table above.

Question: What shows the gap in practice?; Where the answer comes from: a decision that contradicts the promise.

Question: Where does the invariant belong?; Where the answer comes from: the shared point where the effect becomes real.

Question: What test keeps it fixed?; Where the answer comes from: one negative case and one positive case.

The last row is the one people skip. A repair with only a negative test tends to be over-tightened until ordinary behavior breaks; a repair with only a positive test tends to drift back. Both, or it will not hold.

Section: Glossary terms introduced here.

Fail-open: treating an inconclusive check as permission.

Choke point: the single place every route to an effect must pass through.

Freshness: the property that a message has not been used before, which integrity alone does not provide.

Tolerance budget: an allowance spent across a window rather than granted per event.

Two-phase apply: validating an entire request before performing any part of it.

The eleven game-and-boundary patterns in Lessons 13.7–13.8 are variations on one question: does the check guard the state and effect it claims to guard? Chapter 14 extends the machine model beyond one running operating system: a hypervisor provides a guest with virtual hardware, a console begins from a trusted boot chain, and an emulator reconstructs a machine in software. In each case, ask which component owns the state and which boundary controls an effect.
