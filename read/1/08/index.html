Lesson 1.8 / Listening edition

How Memory Actually Works

Trace one game value through bytes, types, addresses, pointers, and offsets, then see why a found address can change.

About 25 minutes

Before scanning a running game, we need to know what the scanner reads. Suppose a health bar says 100. The player takes a hit, and the bar says 75. Somewhere inside the running game, a stored value changed.

This lesson gives you the first map of where that number lives and what it is made of. You will use the same map when you find a value, follow a pointer, or read another program’s memory later in the book.

We will distinguish locations, contents, types, and pointers here. Lesson 3.2 later takes the bits apart one at a time, including exactly how a fractional number like 10.0 is stored.

Section: “Memory” means more than one thing.

People use the word for several kinds of storage, and mixing them up causes a lot of early confusion.

Table columns: Layer; How big, how fast; What lives there.

Layer: CPU, central processing unit, registers and caches; How big, how fast: tiny, extremely fast; What lives there: the handful of values the CPU is working on right now.

Layer: RAM, random access memory,; How big, how fast: large, fast; What lives there: the running game’s code, objects, and current state.

Layer: storage drive; How big, how fast: huge, slow; What lives there: the game’s files, art, settings, and saved games.

There are layers because no single technology is fast, large, cheap, and permanent all at once. Fast memory costs a lot, so you get a little of it. Cheap storage is slow, so it holds the things you are not using this instant.

From here on, when this book says “memory” it means RAM. That is where your health value lives while you are playing. Turn the computer off and it is gone — which is exactly why saving a game has to write a file to the drive.

Section: Memory is a very long row of numbered boxes.

Picture a process’s memory as an enormous row of boxes. Each box holds one byte, and each box has a number called its address. The number tells the process where to look during that run; it need not identify the same data after the game restarts.

That really is most of the idea. Memory is boxes, one byte each, each with an address. Here are four of them:

Labelled memory diagram. hexadecimal 1 0 0 0: 64; hexadecimal 1 0 0 1: 00; hexadecimal 1 0 0 2: 00; hexadecimal 1 0 0 3: 00. Four boxes of RAM. The small label is each box's address; the number inside is the byte stored there.

Lesson 1.2 introduced hexadecimal as another way to write numbers. The 0x prefix on an address announces it. Inside the boxes, each byte is shown as two hex digits with the prefix left off, which is also how debuggers and hex dumps display bytes. The next two sections show why the first byte, 64, represents decimal 100.

Section: Inside a byte: eight bits and their place values.

A bit is a single switch that is either 0 or 1. A byte is eight bits in a row. The question is how eight 0s and 1s can mean a number like 100.

The answer is the same trick ordinary numbers use: position. In the decimal number 100, the 1 is worth a hundred only because of where it sits. Each position in decimal is worth ten times the position to its right — ones, tens, hundreds, thousands.

Binary works the same way, except each position is worth two times the position to its right. Starting from the right, the eight positions in a byte are worth:

To read a byte, add up what the positions holding a 1 are worth. The positions holding a 0 add nothing. As a formula, where b at position i is the bit that sits i places from the right:

Labelled memory diagram. 128: 0; 64: 1, highlighted; 32: 1, highlighted; 16: 0; 8: 0; 4: 1, highlighted; 2: 0; 1: 0. Groups: 64 + 32 + 4 equals 100. The byte hexadecimal 6 4, bit by bit. Each small label is what that position is worth. The three highlighted 1 bits add up to 100.

With every bit set, a byte holds 128 + 64 + 32 + 16 + 8 + 4 + 2 + 1 equals 255. With none set, it holds 0. So a byte has exactly 256 possible values, 0 to 255.

Section: Why everything is in hex.

Eight 0s and 1s are tiring to read, so people write bytes in hexadecimal, which is base 16. It counts with sixteen digits: 0 to 9, then A to F standing for 10 to 15.

Hex fits bits perfectly. Four bits have the place values 8, 4, 2, and 1, so they can hold anything from 0 (all off) to 15 (all on) — exactly the range of one hex digit. Split a byte into two halves of four bits and each half becomes one hex digit:

Labelled memory diagram. 8: 0; 4: 1, highlighted; 2: 1, highlighted; 1: 0; 8: 0; 4: 1, highlighted; 2: 0; 1: 0. Groups: 4 + 2 equals 6, hex 6; 4 equals 4, hex 4. The same byte split into two four-bit halves. Each half is one hex digit, so the byte is written hexadecimal 6 4.

That is the whole reason debuggers use hex: two hex digits are always exactly one byte, so you can see where each byte starts and ends. The same number written in decimal, 100, hides that. It gets more obvious with bigger numbers: decimal 4096 looks arbitrary, while hexadecimal 1 0 0 0 is clearly a round figure in memory terms.

You do not need to convert hex in your head. Recognise the 0x, and use a calculator until it becomes familiar. Converting by hand works like decimal with sixteens instead of tens: hexadecimal 6 4 is six sixteens plus four, 6 times 16 + 4 equals 100.

Section: Bigger values use neighbouring boxes.

One box holds one byte, and one byte only goes up to 255. Anything bigger has to spill into the boxes next door. A u32 — the type name for an unsigned 32-bit whole number, explained properly below — uses four boxes in a row.

Section: Byte order, and why hex dumps look backwards.

Once a value spans several boxes, the CPU needs a rule for which box holds which part.

Think about the decimal number 1,234. The leading 1 is worth the most — it means a thousand. The trailing 4 is worth the least. The bytes inside a multi-byte value work the same way, and the byte worth the least is called the least-significant byte.

Windows games on x86 and x86-64 put the least-significant byte in the lowest-numbered box (Alternative: The opposite order, most-significant byte first, is called big endian. Internet protocols traditionally use it, and Lesson 8.3 reads Wesnoth's four-byte frame length that way.). That arrangement is called little endian.

Example1,000 in four boxes

Each box counts in units 256 times bigger than the box before it, because one byte holds 256 different values — the same reason each decimal column counts in units ten times bigger than the one to its right. So the four boxes of a u32 count ones, 256s, 256 times 256 equals 65,536s, and 256 times 256 times 256 equals 16,777,216s. Here is the number 1,000, which is hexadecimal 3 E 8 in hex:

Labelled memory diagram. hexadecimal 1 0 0 0: E8; hexadecimal 1 0 0 1: 03; hexadecimal 1 0 0 2: 00; hexadecimal 1 0 0 3: 00. Groups: times 1; times 256; times 65,536; times 16,777,216; hexadecimal E 8 is 232, and 232 times 1 + 3 times 256 equals 1,000. Little endian: the byte worth the least sits in the lowest-numbered box.

The practical effect is that reading a hex dump left to right shows the bytes in the opposite order from how you would write the number: E8 03 00 00, not 00 00 03 E8.

This trips up nearly everyone at least once. Expect the reversal every time you compare a number you worked out against bytes you actually saw.

Now the four boxes from the start of the lesson make sense. 64 00 00 00 is hexadecimal 6 4 ones plus nothing else, which is 100.

Section: Three facts that are easy to blur together.

Look again at those four boxes. There are three separate things going on:

hexadecimal 1 0 0 0 is a location — which box;

64 00 00 00 is a pattern of bytes starting in that box;

100 is one interpretation of that pattern.

Labelled memory diagram. hexadecimal 1 0 0 0: 64, highlighted; hexadecimal 1 0 0 1: 00; hexadecimal 1 0 0 2: 00; hexadecimal 1 0 0 3: 00. Groups: the byte pattern 64 00 00 00; one interpretation: the u32 value 100. The address names one box. The pattern spans four. The number 100 appears only when something reads those four boxes as a u32.

The third one does not follow automatically from the first two, and this is the single most important idea in the lesson. Those bytes only become the number 100 once something decides to read four boxes, treat them as one whole number, and use little-endian byte order. Read the same boxes with a different set of rules and the very same bytes mean something else, as the next section shows.

So never treat “address” and “value” as the same word. An address tells you where to look. A value is what you get after you look and decide how to read what is there.

Section: A type is the instruction for reading bytes.

A type answers two questions: how many bytes to read, and what the bits inside them mean.

The names are for you. The types are for the compiler. These are the ones you will meet most often:

Number types at a glance

Table columns: Rust type; Size; What the bits mean.

Rust type: u8; Size: 1 byte; What the bits mean: a whole number from 0 to 255.

Rust type: u16; Size: 2 bytes; What the bits mean: a whole number from 0 to 65,535.

Rust type: u32; Size: 4 bytes; What the bits mean: a whole number from 0 to 4,294,967,295.

Rust type: i32; Size: 4 bytes; What the bits mean: a whole number from minus 2,147,483,648 to 2,147,483,647.

Rust type: f32; Size: 4 bytes; What the bits mean: a number that can have a fractional part, such as 3.5.

Rust type: f64; Size: 8 bytes; What the bits mean: the same idea as f32, with more precision.

Rust type: bool; Size: 1 byte; What the bits mean: 0 means false, 1 means true.

The names follow a pattern. The number is the size in bits. u means unsigned: the value can never be negative. i means a signed integer, which can be. f means floating point, a number with a fractional part.

The ranges come from counting patterns. One bit has 2 patterns, and every extra bit doubles the count: two bits have 4, three have 8, and eight have 256, which is why a u8 stops at 255. Sixteen bits have 256 times 256 equals 65,536 patterns, and thirty-two bits have 65,536 times 65,536 equals 4,294,967,296. An i32 has exactly as many patterns as a u32, but it spends half of them on negative numbers, which is why its range is split around zero.

Section: One pattern, two readings.

u32 and f32 are both four bytes, but they use those 32 bits in completely different ways. A u32 reads all 32 bits as one whole number. An f32 splits them into three parts — a sign, a power of two, and the digits of the number — much as scientific notation writes 1,500 as 1.5 times 10 to the power of 3.

So one four-byte pattern holds two totally different numbers, depending on which type you ask for:

Labelled memory diagram. cell 1: 00; cell 2: 00; cell 3: 20; cell 4: 41. Groups: read as u32: 1,092,616,192; read as f32: 10.0. One four-byte pattern, read two ways. Both readings are correct; they answer different questions.

The u32 reading uses only what this lesson has covered: written most significant first, the bytes are hexadecimal 4 1 2 0 0 0 0 0, and a calculator turns that into 1,092,616,192. The f32 reading follows rules for its three parts that are not covered here; Lesson 3.2 works through them bit by bit, all the way to 10.0. What matters now is that nothing in memory changed between the two readings. Only the type did.

Floats have one habit worth knowing from the start: most fractions cannot be stored exactly. Ask an f32 to hold 10.1 and it actually holds 10.100000381…, the nearest value its 32 bits can express (Explanation: Numbers from 8 up to 16 sit 1 divided by 1,048,576 apart in an f32, about 0.00000095. 10.1 times 1,048,576 equals 10,590,617.6, so the nearest stored value is 10,590,618 divided by 1,048,576 equals 10.100000381…). That is why float values in games are rarely round, and why memory scanners let you search for a float within a small range instead of only an exact value.

Section: Values side by side.

An array puts equal-sized values back to back. A 3D position is often three f32 values in a row, one each for x, y, and z:

Labelled memory diagram. +hexadecimal 0 0: 00; cell 2: 00; cell 3: 80; cell 4: 3F; +hexadecimal 0 4: 00; cell 6: 00; cell 7: 00; cell 8: 40; +hexadecimal 0 8: 00; cell 10: 00; cell 11: 60; cell 12: C0. Groups: x equals 1.0; y equals 2.0; z equals minus 3.5. A position stored as three f32 values. The labels are offsets from the start of the position.

Each value is four bytes, which is why the labels go up by 4 and not by 1.

Text and lists add their own rules on top. A C string (Reference: Lesson 3.8 shows how text becomes bytes in UTF-8, UTF-16, and null-terminated C strings.) just runs until it hits a zero byte. Other kinds of string store a pointer and a length. A growable list usually stores a pointer to its contents plus a length and a capacity. The code that reads a string or list is what tells you which layout a game uses.

Section: Working out types in a running game.

When you inspect a compiled game without useful debug information, many source names and type declarations are unavailable. The compiler used them to choose instructions, and those instructions provide clues about how the game uses the bytes:

how many bytes an instruction reads or writes at once: 1, 2, 4, or 8;

which kind of instruction does it — x86 has separate instructions for floating-point values, so a float load means an f32 or f64;

what the code does with the result — compares it with a signed or unsigned test, adds it to an address, passes it to a drawing function;

how the bytes change when you make the game change;

whether nearby bytes behave like parts of the same object.

This is also why a memory scanner asks what kind of value you are hunting before it searches. The whole number 10 is stored as 0A 00 00 00. The float 10.0 is stored as 00 00 20 41. The two patterns do not share a single byte, so a search for one can never find the other.

Section: A pointer is a number that happens to be an address.

Every value so far has been data about the game: 100 gold, 10.0 metres per second. A pointer is a value too — an ordinary number, stored in ordinary bytes, in an ordinary box. What makes it a pointer is only what that number means: it is the address of something else.

Nothing in the bytes marks them as a pointer. 00 50 00 00 could be the number 20,480 — hexadecimal 5 0 is 80, and 80 times 256 equals 20,480 — or it could be a pointer to address hexadecimal 5 0 0 0, which is the same number written in hex. As always, the code that reads them decides which.

Here is the whole idea. Four ordinary bytes at hexadecimal 2 0 0 0:

Labelled memory diagram. hexadecimal 2 0 0 0: 00; hexadecimal 2 0 0 1: 50; hexadecimal 2 0 0 2: 00; hexadecimal 2 0 0 3: 00. Groups: read together as a u32: the number hexadecimal 5 0 0 0, where the player object starts.

Diagram. From box hexadecimal 2 0 0 0 holds the number hexadecimal 5 0 0 0 to box hexadecimal 5 0 0 0 the player object starts here. The connection is labelled: read it, then go to that address.

Three different numbers are involved, and running them together is the most common early mistake by a wide margin:

Table columns: Number; What it is; Here.

Number: where the pointer lives; What it is: an address; Here: hexadecimal 2 0 0 0.

Number: the pointer’s own value; What it is: also an address; Here: hexadecimal 5 0 0 0.

Number: what it points at; What it is: the actual data; Here: the player object.

Read address hexadecimal 2 0 0 0 and you get hexadecimal 5 0 0 0. That is not the player. To reach the player you read a second time, now from hexadecimal 5 0 0 0. That second read is called dereferencing the pointer.

Think of a library catalogue card. The card is not the book. It sits in a drawer at its own location, and all it carries is a shelf number. Finding the book is two separate steps: read the card, then walk to the shelf.

That comparison is worth keeping because it survives being pushed on. The drawer slot is hexadecimal 2 0 0 0. The shelf number written on the card is hexadecimal 5 0 0 0. The book is the player object. And here is the part that matters most: if a librarian removes that book and shelves a different one in the gap, your card still reads hexadecimal 5 0 0 0 and still sends you confidently to a real shelf holding a real book — the wrong one. Nothing about the card looks damaged.

That is not a flaw in the comparison. It is precisely what can go wrong with a stale pointer. Lesson 3.6 shows the address-reuse example in memory.

Section: Why bother with the extra hop?.

Because the object can move. It can be destroyed and rebuilt somewhere else. When the game updates the pointer at hexadecimal 2 0 0 0, code that reads it again can follow the new address instead of holding on to the old one.

So hexadecimal 5 0 0 0 is where the object sits in this example, while hexadecimal 2 0 0 0 is where the example’s pointer is stored. That first location is useful only while the pointer storage itself remains valid. Lesson 2.7 builds a repeatable pointer path with that condition in mind.

A pointer is not guaranteed to stay good, either. The object can be removed, the memory reused, a module unloaded. An address that is not zero can still be completely wrong.

Section: What a pointer’s type tells you.

In source code a pointer usually has a type attached. Rust writes a raw pointer to a u32 as *const u32, read aloud as “a pointer to a u32”. That type describes the data at the other end, not the pointer itself, and it is called the pointee type. It tells the program how many bytes to read at the destination and how to interpret them.

Follow one pointer value, hexadecimal 5 0 0 0, with three different pointee types. The bytes waiting at hexadecimal 5 0 0 0 are the 00 00 20 41 pattern from the type section:

Labelled memory diagram. hexadecimal 5 0 0 0: 00; hexadecimal 5 0 0 1: 00; hexadecimal 5 0 0 2: 20; hexadecimal 5 0 0 3: 41. Groups: through a *const u32: 4 bytes, 1,092,616,192; through a *const f32: 4 bytes, 10.0; through a *const u8: 1 byte, 0. One address, three pointee types, three different reads. The pointer held the same number every time.

The pointer’s own size has nothing to do with its pointee type. For the plain raw pointers to sized values used in this book’s x86 labs, it is set by the process architecture: 4 bytes in a 32-bit game and 8 in a 64-bit game, whether it leads to a single byte or a 2,000-byte player object. Lesson 3.2 shows why, and how the pointee type also decides how far a pointer moves when it steps to the next item in a list.

Section: An offset is a distance, not a place.

Say a player object starts at hexadecimal 5 0 0 0, and its health sits 48 bytes into it.

Code example. The surrounding prose explains this example; the full lesson contains the exact code.

Labelled memory diagram. hexadecimal 5 0 0 0: object starts; cell 2: dot dot dot ; hexadecimal 5 0 3 0: health, highlighted. Groups: the offset: hexadecimal 3 0, or 48 bytes along. The base says where the object starts. The offset is the distance to the field. Their sum, hexadecimal 5 0 3 0, is where health is read.

Three different numbers, doing three different jobs. The base says where the object starts. The offset says how far in the field is. The sum says where to read.

An offset is not an address and it is not the health value. On its own it means nothing at all — hexadecimal 3 0 is just “48 bytes along from something.”

Offsets matter because they may outlast one address. The object’s base address may land somewhere new every time the game starts, while the health field can remain 48 bytes into the same object layout for that build. Verify the offset again when the game or layout changes.

Watch the pointer read and the field calculation together. Notice when a number is being read from memory and when it is being used as an address:

Watch it happenFrom a stored pointer to a field of the object it points to

Four bytes at hexadecimal 2 0 0 0, 00 50 00 00, are reversed and read as the little-endian address hexadecimal 5 0 0 0, the base of a player object. An address marker then moves hexadecimal 3 0 bytes along the object from hexadecimal 5 0 0 0 to hexadecimal 5 0 3 0, and the health field is read at that destination.

Additional detail: Read the steps.

The pointer lives at hexadecimal 2 0 0 0, and its four bytes are 00 50 00 00. This is where the pointer is stored, not where the player object starts.

Read the four bytes as one little-endian number. The byte at the lowest address counts least, so reading from the highest address back gives 00 00 50 00, which is hexadecimal 5 0 0 0: the start of the object.

Locate the field: add the verified health offset, hexadecimal 3 0. This only calculates an address: hexadecimal 5 0 0 0 + hexadecimal 3 0 equals hexadecimal 5 0 3 0. Nothing has been read from there yet.

Read the health field at hexadecimal 5 0 3 0 using its verified type. The value comes from the bytes there, not from the pointer value hexadecimal 5 0 0 0 or the offset hexadecimal 3 0.

Two memory reads with an address calculation between them: first obtain the object base, then locate and read its health field.

Section: Why an address can stop working.

The pointer and offset example gives you a way to find a field now. It does not promise that the object will occupy the same address later. Two common ways of handing out memory help explain why.

A function can use its thread’s stack for temporary values. Its stack frame lasts through that call; later calls can reuse the same bytes. An allocator can give a longer-lived game object space on the heap. That object may survive many calls, but the game can eventually remove it and reuse its address for a different object. A growing collection can also move its contents. Lesson 3.4 draws a call frame in memory, and Lesson 3.6 follows a heap address from one object to another. Lesson 2.7 then builds pointer paths that can survive a moving object base.

Section: The process is part of the address.

A debugger shows virtual addresses in a particular process. The game’s hexadecimal 5 0 0 0 and your tool’s hexadecimal 5 0 0 0 need not name the same bytes. An external tool therefore opens a process handle and asks Windows to read an address in that game’s address space. Windows also divides the space into protected pages; a number that looks like an address may not be readable at the moment you try it. Lesson 3.3 works through a remote read, and Lesson 11.7 examines the page map in detail.

Section: A running game is not a frozen picture.

A scanner copies bytes while the game continues to update them. Its result is a snapshot gathered over a short stretch of time, not a promise that every field describes one instant. This is a copy of selected memory, unlike the whole virtual-machine recovery snapshot from Lesson 1.7. For example, if the game removes one enemy after you read its pointer and reuses that address before you read its health, both reads can succeed while your combined answer describes neither enemy correctly. Re-check a promising candidate and its object identity before trusting it. Lesson 3.3 shows that sequence and the checks an external reader needs.

Section: Keep these words separate.

The words of this lesson

Table columns: Word; Direct meaning.

Word: bit; Direct meaning: one binary digit, 0 or 1.

Word: byte; Direct meaning: eight bits.

Word: address; Direct meaning: a location in one process’s virtual memory.

Word: type; Direct meaning: how many bytes to read, and what their bits mean.

Word: value; Direct meaning: bytes interpreted using a type.

Word: pointer; Direct meaning: a value that stores an address.

Word: pointee type; Direct meaning: the type of the data a pointer leads to.

Word: dereference; Direct meaning: read or write through a pointer.

Word: offset; Direct meaning: a distance from a chosen base address.

Word: lifetime; Direct meaning: how long an object or location remains valid.

Word: snapshot; Direct meaning: bytes copied from a running program over a short stretch of time.

Section: What the scanner sees.

A byte is the sum of the place values of its set bits. On x86, a hex dump shows a multi-byte u32 least-significant byte first. An address, the bytes at that address, and the value produced by interpreting those bytes are different things; four identical bytes can mean a whole number or a float when read with different types.

A pointer has a size set by the process, while its pointee type controls the value read after following it. base + offset computes the address of a field. Stack and heap allocations have different lifetime patterns, and another process has its own virtual address space. A memory scan reads state while the game can continue changing it; it is not an instantaneous frozen copy.

Lesson 1.9 uses these distinctions to scan a real gold value, narrow the candidates, and test one of them in the game.
