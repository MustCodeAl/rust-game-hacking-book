Hacking Fundamentals

Imagine an offline game whose display shows 100 gold. Buying an item for 25 changes the display to 75. The screen shows the result, but it does not identify the rule or the stored value that caused it. Game hacking in this book means investigating that behavior and making a deliberate, testable change to the game or its data.

Section: Start with evidence, not a scan result.

An observation is what you can actually see: after a 25-gold purchase, the display changes from 100 to 75. An explanation is a hypothesis: perhaps a four-byte value in the game’s memory stores the gold used by the purchase rule. Other explanations are possible. The game may keep a display copy, recalculate gold from other data, or let a server decide the result. A matching number is therefore a candidate, not a conclusion.

Diagram walkthrough: Follow one controlled game experiment. Step 1: Act. State: cost equals 25. Buy one item whose cost is known. Step 2: Observe. State: 100 to 75. The displayed amount falls from 100 to 75. Step 3: Hypothesize. State: which value?. A stored value may govern the purchase. Step 4: Test one candidate. State: one controlled change. Change one candidate and repeat the purchase. Step 5: Judge the evidence. State: rule / text / neither. Check whether the rule, the display, or neither changed. The visible change motivates a hypothesis; the second purchase tests whether the candidate affects game state or only its display.

The fastest way to get completely lost is to open a memory scanner and start searching before deciding what you are asking. You can end up with hundreds of addresses—numbered locations in the game’s running memory—with no way to tell which matters and no record of which ones you have ruled out. A scanner finds values that match a question; a debugger can later show the instruction that reads or writes a candidate. Neither tool supplies the meaning by itself.

Section: Four steps for a controlled experiment.

One way to keep the work in order is to split it into four steps. Treat them as a suggestion to adapt, not a rule the rest of the book relies on:

Identify the exact behavior.

Understand how that behavior should work.

Locate the data and code involved.

Change one thing and measure the result.

The steps can repeat. A failed change often sends you back to improve what you understand or locate a different copy:

Section: 1. Identify the behavior.

Choose something you can observe and reproduce.

❌ “Find player stuff.”

✅ “Find the value that decreases by exactly 25 when the local player buys one known item.”

The behavior is only repeatable if it starts from the same conditions each time:

exact game build;

map, save, or level;

starting value;

action you will perform;

result you expect to observe.

Good starting behaviors include spending gold, taking damage, moving along one axis, or toggling one graphics setting. Avoid changing several things at once.

The steps also have dependencies: a successful write needs a successful read of the intended field in the intended build. A failed read does not mean the player has zero gold. Stop at that failed step and preserve its error, rather than letting later code act on an invented value. The purchase itself depends on the current gold and price; the display depends on an update of its copy. Following those relationships tells you which earlier assumption to check when a later result is wrong.

Section: 3. Locate the data and code.

Use the least complicated technique that can answer the question. A breakpoint is a debugger rule that pauses execution at a chosen instruction or memory access; we will use one only after learning the debugger.

scan for the visible value;

make one controlled game change;

filter the candidate addresses;

repeat until the list is small;

later, set a breakpoint on the strongest candidate;

observe which instruction reads or writes it;

follow the stored address leading to the object and inspect nearby fields.

The first lab stops after scanning, filtering, and testing a candidate. The breakpoint and object steps become practical after Chapters 2 and 3 teach the required tools and pointer model.

Inside one scan, the scanner follows an algorithm over readable regions: ranges of numbered locations the operating system currently permits it to read. It copies one limited chunk at a time:

Diagram. From visit the next readable region to read a bounded chunk. From read a bounded chunk to compare each position with the search value. From compare each position with the search value to record matching addresses. From record matching addresses to more regions?. From more regions? to visit the next readable region. The connection is labelled: yes. From more regions? to later: re-read only earlier candidates and keep matches. The connection is labelled: no.

An algorithm is a repeatable set of steps. The scanner does not know what gold means; it compares bytes according to the value and type you supplied. Even a small choice such as checking only every fourth byte can miss a value starting at one of the positions between those checks.

Each controlled change throws away the candidates that did not change the same way. The numbers below are only an example, but the shape is typical:

Labelled memory diagram. first scan for 100: 4,012; after spending 25 gold: 37; after a second purchase: 3; write breakpoint: 1 instruction, highlighted. Scanning narrows the addresses; a write breakpoint then names the instruction that stores to the survivor, which ties the address to the game's own code rather than to a coincidence of values.

An address found once is only a candidate for that run; its object can even disappear before the run ends. Restarting the game shows whether it is repeatable. If the absolute address moves but a module-relative path keeps working, the path is what carries over, and only for the exact build it was found in.

Each kind of check rules out a different mistake. A second scan with a different amount rules out an unrelated value that happened to match once. A write breakpoint pauses the game when an instruction writes to a chosen address. Chapter 2 teaches how to use one. It shows which instruction changed the candidate; a restart shows whether the path survives a new process.

Section: Find the step that actually takes time.

If a scanner is slow, ask where its time goes. A bottleneck is the step that limits the overall work. It might be reading another process, comparing many values locally, sorting the remaining candidates, or writing a large log. Finding a number and accessing its bytes are different operations, and neither requires sorting the results unless the tool needs that order.

Measure a repeatable scan before changing its design. Record how many reads it made, how many bytes it compared, how many matches it kept, and the time spent in the expensive stages. Improving comparisons will do little if most time is spent waiting for reads. Keep the first working experiment small enough to understand; Sampling Game State Under Load later handles repeated observations and slow log writes. Larger collections and more workers are choices to evaluate against a measured need.

Then:

save the original bytes or value so you can restore them;

confirm the value still matches what you expect;

apply one bounded change;

observe the immediate and next-update results;

restore the original state;

repeat from a known starting condition.

If only the text changes, you probably found a display copy. If the value snaps back, another system owns or recomputes it. If unrelated fields break, your type, width, or address may be wrong.

Section: Choose diagnostics that fit the failure.

Compare the expected and observed result at the first step where they diverge. Suppose you expected to read 75 before a write but actually read 74. Investigate that mismatch before explaining the later failed purchase.

A debugger lets you pause at the suspicious step and inspect its values and instructions. Pausing changes timing: other work may wait, or an input or timeout may behave differently. Logging also adds work, especially when it writes to disk. If a failure disappears when you add diagnostics, that is evidence to investigate the timing change; it does not establish that the underlying problem is fixed. Begin with the smallest implementation that satisfies the contract: identify the target, read one value, decide whether the change is allowed, apply one allowed change, then restore the original value. Keep the decision separate from process access so you can test it with ordinary values. Reuse an existing tool or library when it supports your target and you can check its behavior, version, error handling, and maintenance. Writing every dependency yourself does not make the experiment more reliable.

As repeated code or new use cases appear, give each responsibility a small interface. Refactoring changes the organization while preserving the intended behavior; keep the existing examples and tests working as you do it. Tool Architecture, Commands, and Cleanup develops this separation when several features share observations and must coordinate changes.

Review small changes as you work. A diff compares edited source with its previous version, making an accidentally changed field width or missing check easier to see. A walkthrough follows one example through the complete read, decision, write, and restoration path, often with another reader. Automated checks and these reviews answer different questions: passing a logic test does not prove that the live address is the game’s gold field.

Section: Leave a record another reader can repeat.

Start documentation with the question, the tool’s purpose, and its limits. Then show the route through the experiment before detailing each step. A reader needs to know which file or command to begin with, what result to expect, and what a failure means. Define names consistently: if gold means the rule’s stored amount, call the screen copy displayed_gold throughout.

Keep a compact experiment record:

Reference environment: game version and build identity, architecture, operating system, tool versions, and the save or map used.

Reproduction: starting state, exact actions or commands, expected result, observed result, and how to restore the original state.

Evidence: candidate values, relevant instructions or logs, failed checks, and which explanations remain possible.

Decisions: why you chose this candidate, data type, limit, or dependency; include the observation that would make you reconsider it.

For a tool you build, document one complete supported path from a fresh source checkout to a runnable artifact, including the compiler, target, dependency versions, required options, and tests. Keep that path consistent with the instructions you actually verify. Reproducible steps let another person repeat the experiment; they do not automatically guarantee an identical executable byte for byte. How Source Becomes a Running Process explains the build stages, and the next lab fixes the environment for this book’s first scan.

Read the record from a newcomer’s position. If an instruction says “use the usual settings,” supply the settings. If a screenshot is the only record of a result, write down the important value and condition too. Update the record when the tool or target changes so an old address or command is not mistaken for a current promise.

Section: What a candidate address tells you.

A matching address is a lead. A repeatable behavior and an expected rule give it meaning; controlled changes and a breakpoint narrow the lead. A reversible edit tests whether that address affects the game rule or only a copy. The compiler and tests check the tool’s logic, while the debugger observes what the running game actually does.
