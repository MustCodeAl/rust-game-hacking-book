Lesson 2.2 / Listening edition

How Source Becomes a Running Process

Compare native compilation, bytecode interpretation, REPLs, and type checking; then follow a native program through linking and loading.

About 28 minutes

The debugger shows instructions and addresses, while the programmer wrote functions, fields, and variable names. Why are those two views different? And why can an address found by a memory scan move after a restart even though the game still applies the same rule?

These differences come from the stages that turn source into a running process. First, distinguish several ways a language implementation can run code. Then we can follow the native executable used in the Windows memory labs and see which facts survive a restart, which require the exact build, and which must be rediscovered after an update.

Section: Source code can take different routes to execution.

Source code is the text a programmer edits. A C P U, central processing unit, eventually executes machine instructions, but the source does not always become a standalone machine-code file first. Two routes used in this book are:

Rust application: source becomes native code before the program runs.

Lua script: source becomes instructions for the Lua virtual machine when a game loads the script.

Compilation translates code from one representation to another. The Rust route above compiles ahead of time to native instructions for a particular target. A virtual machine is a program that understands its own instruction set. Its bytecode is instructions for that virtual machine, not the x86 instructions a debugger shows for the C P U. Lua also compiles when it loads a source chunk; its virtual machine then interprets the resulting bytecode by carrying out those instructions. This is why “compiled” and “interpreted” are not mutually exclusive labels. The Lua reference manual describes this load-and-execute sequence. Lesson 10.1 shows what changes when a game embeds a Lua interpreter.

A R E P L, read eval print loop, is a way to interact with a language tool: read a line, evaluate it, print the answer, then loop for another line. For instance, an interactive Lua session can evaluate 2 + 3 and show 5 immediately. A file can contain the same calculation and be run later. R E P L describes the interaction, not whether the tool uses bytecode, native compilation, or dynamic typing. The Lua interpreter manual describes both interactive and file-based use.

The rest of this lesson follows the native executable route used for Rust tools and the Windows game builds in the early memory labs. Lua’s virtual-machine route returns when we study scripting.

Section: Four stages, each deciding something different.

A Windows EXE is an executable file for a program. A D L L, dynamic link library, (dynamic-link library) is compiled code that a running program can load and call. Once loaded, either one is a module with a starting address and a range of code and data in the process.

Each stage keeps what the next stage needs. A release build may omit information that helped the programmer but is unnecessary for execution. Debug information can preserve some names separately; we will distinguish that case below.

Section: The compiler decides layout, and stops needing your names.

The compiler translates source into object code, often stored in .obj files by the Microsoft toolchain used for these Windows C++ examples. Two of its decisions matter throughout this book.

First, it chooses a compiled layout according to the language’s rules. For an example player structure, it may leave unused bytes between fields so each field starts at an address suited to its type. Those gaps are padding, explored in the later object-layout lesson. If health begins 48 bytes into the object, an instruction can identify it by that distance rather than its name. A debugger may write this as [e c x+hexadecimal 3 0]: read at the address held in the e c x register, plus hexadecimal hexadecimal 3 0, which is decimal 48. The assembly lesson explains this notation in detail; here it shows why a compiled field can survive without the word health.

Second, the machine instruction no longer needs the word health. The name helped the programmer refer to the field; the instruction uses its distance from the object base. A normal release executable often omits local and field names, though debug information can preserve them. A missing name is not evidence that it was encrypted or hidden.

In brief: A compiled game keeps distances, not names. A missing name usually means the program never needed it to run.

Function names survive slightly longer, because the linker still has work to do with them.

Section: The linker resolves names, then it does not need them either.

Your game is many object files plus libraries, and one file’s call to a function defined in another may still be an unresolved reference. The linker matches references to definitions it has, lays the sections out into the final image, and records the references that a loader must finish later. A call to an internal game function can be resolved here; a call into a D L L still needs the D L L’s address at run time.

After that, many internal names have served their purpose. Debug information can be kept — the Microsoft toolchain often puts it in a separate .pdb file — but the EXE does not need it to run. Imports and exports can still carry names in the executable; the next section shows why an imported function name may remain.

This explains why a debugger may show an imported Windows function’s name but only a numeric address for an internal game function. A binary without debug symbols is not necessarily obfuscated; it may simply lack source names that execution does not require.

Section: Two things the linker deliberately leaves unfinished.

Not everything can be decided at build time, and the two exceptions are exactly the ones later chapters spend time on.

Where the module will be. The linker does not know which address Windows will choose, so it records a preferred base and includes a table of every location that would need adjusting if a different base is used. An offset measures a distance from the beginning of that module. The later address-movement lesson uses the distinction: for the same build, that distance can stay fixed while the loader chooses a different starting address.

Alternative: Picture a street and a house number: the street can be built at a different place each day, but the house stays the same number along it.

Where the D L L functions will be. The linker knows the game calls MessageBoxW in user32.dll, but not the address, which will not exist until the D L L is mapped. So it writes down the requirement — which D L L, which function — and leaves a table of slots for the loader to fill with real addresses. That table is the Import Address Table:

Section: The loader turns a file into a process.

The loader maps the sections into memory with the right permissions, applies those relocations if it picked a different base, fills in the import table, prepares thread-local storage (data kept separately for each thread), and runs the initialisation code. The later loader-boundary lessons follow these details. They explain why a D L L’s DllMain initialisation function cannot safely perform every task a normal function can.

The executable-file chapter will compare the two layouts: content arranged for storage on disk and content arranged for execution in memory. The loader is the connection between them; file positions do not automatically equal positions in the running process.

Section: Optimization is why the code does not match the source.

One more consequence, and it explains a lot of confusing disassembly. An optimising build is allowed to produce anything that behaves the same. It can paste a small function into each of its callers so no call remains, keep a variable only in a register so it never touches memory, drop a variable whose result is never used, reorder work, and merge two identical functions.

So when a function you expected is missing, the usual explanation is not that it was hidden. It is that the compiler decided the fastest way to do that work did not involve a separate function. This is also why a debug build and a release build of the same source can be so different to read, and why an address or offset belongs to the exact build it came from.

Section: Why the stages matter in a debugger.

The compiler chooses field layouts and may remove or transform source functions. The linker fixes positions within a native image and records D L L imports; the loader chooses a run-time base and fills in external addresses. A module-relative offset can therefore survive a restart of the same build while a raw address changes. Rebuilding after a field insertion can shift later offsets, so old offsets need rechecking. Release binaries may omit source names even while import names or separate debug information remain.

We now know why a debugger can show addresses and transformed operations instead of the source’s original names. How Assembly Describes a Running Game gives those operations a readable vocabulary and follows a small rule through its comparisons, branches, and arithmetic.
