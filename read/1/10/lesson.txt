How Source Becomes a Running Process

The debugger shows instructions and addresses, while the programmer wrote functions, fields, and variable names. Why are those two views different? And why can an address found by a memory scan move after a restart even though the game still applies the same rule?

These differences come from the stages that turn source into a running process. First, distinguish several ways a language implementation can run code. Then we can follow the native executable used in the Windows memory labs and see which facts survive a restart, which require the exact build, and which must be rediscovered after an update.

Section: Source code can take different routes to execution.

Source code is the text a programmer edits. A CPU, central processing unit, eventually executes machine instructions, but the source does not always become a standalone machine-code file first. Two routes used in this book are:

Rust application: source becomes native code before the program runs.

Diagram. From Rust source to compile to native code. From compile to native code to EXE on disk. From EXE on disk to CPU runs the program.

Lua script: source becomes instructions for the Lua virtual machine when a game loads the script.

Diagram. From Lua source to compile to VM, virtual machine, bytecode. From compile to VM bytecode to Lua VM interprets bytecode. From Lua VM interprets bytecode to CPU runs the Lua VM.

Compilation translates code from one representation to another. The Rust route above compiles ahead of time to native instructions for a particular target. A virtual machine is a program that understands its own instruction set. Its bytecode is instructions for that virtual machine, not the x86 instructions a debugger shows for the CPU. Lua also compiles when it loads a source chunk; its virtual machine then interprets the resulting bytecode by carrying out those instructions. This is why “compiled” and “interpreted” are not mutually exclusive labels. The Lua reference manual describes this load-and-execute sequence. Lesson 10.1 shows what changes when a game embeds a Lua interpreter.

A REPL, read eval print loop, is a way to interact with a language tool: read a line, evaluate it, print the answer, then loop for another line. For instance, an interactive Lua session can evaluate 2 + 3 and show 5 immediately. A file can contain the same calculation and be run later. REPL describes the interaction, not whether the tool uses bytecode, native compilation, or dynamic typing. The Lua interpreter manual describes both interactive and file-based use.

Section: Four stages, each deciding something different.

A Windows EXE is an executable file for a program. A DLL, dynamic link library, (dynamic-link library) is compiled code that a running program can load and call. Once loaded, either one is a module with a starting address and a range of code and data in the process.

Animated diagram: From source files to a running process. One program changes form in six stages. The source line player.health -= damage becomes an instruction using the distance hexadecimal 3 0; the global gold gets the address hexadecimal 0 0 4 A 3 0 1 0 in the linked image; the file records a preferred base of hexadecimal 0 0 4 0 0 0 0 0; Windows loads it at hexadecimal 0 0 A 5 0 0 0 0 and shifts that address by hexadecimal 0 0 6 5 0 0 0 0 to hexadecimal 0 0 A F 3 0 1 0; then threads run the instructions at those live addresses. Step 1: Source files describe the program for its author: names, types, comments. player.health and gold are names a person chose. Step 2: Compile: the compiler turns each source file into an object file and fixes the layout. The name health is gone; only its distance from the object base, hexadecimal 3 0, is left. gold still has no address. Step 3: Link: the linker resolves names and lays out the image. It gives gold an address inside it: the preferred base hexadecimal 0 0 4 0 0 0 0 0 plus hexadecimal 0 A 3 0 1 0 is hexadecimal 0 0 4 A 3 0 1 0. Step 4: File on disk: the EXE records its preferred base and the imports it will need. Every address inside is written as if the image will sit at that base. Step 5: Load: Windows maps the image at hexadecimal 0 0 A 5 0 0 0 0 instead. It adds the difference, hexadecimal 0 0 A 5 0 0 0 0 - hexadecimal 0 0 4 0 0 0 0 0 equals hexadecimal 0 0 6 5 0 0 0 0, to every stored address, so gold moves from hexadecimal 0 0 4 A 3 0 1 0 to hexadecimal 0 0 A F 3 0 1 0. Step 6: Run: threads execute the instructions from the mapped image, at the live addresses the loader chose. Follow one compiled route: source becomes object files, a linked image, and finally a process whose live addresses the loader chose.

Each stage keeps what the next stage needs. A release build may omit information that helped the programmer but is unnecessary for execution. Debug information can preserve some names separately; we will distinguish that case below.

Section: The compiler decides layout, and stops needing your names.

The compiler translates source into object code, often stored in .obj files by the Microsoft toolchain used for these Windows C++ examples. Two of its decisions matter throughout this book.

First, it chooses a compiled layout according to the language’s rules. For an example player structure, it may leave unused bytes between fields so each field starts at an address suited to its type (Example: In a C or C++ structure, a one-byte field followed by a four-byte field normally puts the second at offset 4, so the 3 bytes between them are padding: 1 + 3 equals 4.). Those gaps are padding, explored in the later object-layout lesson. If health begins 48 bytes into the object, an instruction can identify it by that distance rather than its name. A debugger may write this as [ecx+hexadecimal 3 0]: read at the address held in the ecx register, plus hexadecimal hexadecimal 3 0, which is decimal 48. The assembly lesson explains this notation in detail; here it shows why a compiled field can survive without the word health.

Second, the machine instruction no longer needs the word health. The name helped the programmer refer to the field; the instruction uses its distance from the object base. A normal release executable often omits local and field names, though debug information can preserve them. A missing name is not evidence that it was encrypted or hidden.

Function names survive slightly longer, because the linker still has work to do with them.

Section: The linker resolves names, then it does not need them either.

Your game is many object files plus libraries, and one file’s call to a function defined in another may still be an unresolved reference. The linker matches references to definitions it has, lays the sections out into the final image, and records the references that a loader must finish later. A call to an internal game function can be resolved here; a call into a DLL still needs the DLL’s address at run time.

After that, many internal names have served their purpose. Debug information can be kept — the Microsoft toolchain often puts it in a separate .pdb file — but the EXE does not need it to run. Imports and exports can still carry names in the executable; the next section shows why an imported function name may remain.

This explains why a debugger may show an imported Windows function’s name but only a numeric address for an internal game function. A binary without debug symbols is not necessarily obfuscated; it may simply lack source names that execution does not require.

Section: Two things the linker deliberately leaves unfinished.

Not everything can be decided at build time, and the two exceptions are exactly the ones later chapters spend time on.

Where the module will be. The linker does not know which address Windows will choose, so it records a preferred base and includes a table of every location that would need adjusting if a different base is used. An offset measures a distance from the beginning of that module. The later address-movement lesson uses the distinction: for the same build, that distance can stay fixed while the loader chooses a different starting address.

Where the DLL functions will be. The linker knows the game calls MessageBoxW in user32.dll, but not the address, which will not exist until the DLL is mapped. So it writes down the requirement — which DLL, which function — and leaves a table of slots for the loader to fill with real addresses. That table is the Import Address Table (Reference: Microsoft's PE, portable executable, format specification describes the import tables, including the Import Address Table, field by field.):

Labelled memory diagram. on disk: a reference to the name MessageBoxW in user32.dll; in memory: the address of MessageBoxW, written by the loader, highlighted. One Import Address Table slot. The game's code calls through the slot, so the call works only once the loader has written the real address there.

Lesson 6.5 hooks a program’s own copy of this table — a technique that works precisely because the linker left the address for someone else to fill in.

Section: The loader turns a file into a process.

The loader maps the sections into memory with the right permissions, applies those relocations if it picked a different base, fills in the import table, prepares thread-local storage (data kept separately for each thread), and runs the initialisation code. The later loader-boundary lessons follow these details. They explain why a DLL’s DllMain initialisation function cannot safely perform every task a normal function can.

The executable-file chapter will compare the two layouts: content arranged for storage on disk and content arranged for execution in memory. The loader is the connection between them; file positions do not automatically equal positions in the running process.

Section: Follow one location across two runs.

ExampleOne location across two runs

Suppose the linker placed an instruction hexadecimal 1 3 5 0 bytes from the beginning of the game’s module. In one run, Windows loads that module at hexadecimal 0 0 4 0 0 0 0 0; in another, it loads it at hexadecimal 0 0 6 0 0 0 0 0. The instruction did not move within the module, even though its absolute address changed:

Table columns: Run; Module base; Instruction offset; Instruction address.

Run: first; Module base: hexadecimal 0 0 4 0 0 0 0 0; Instruction offset: hexadecimal 1 3 5 0; Instruction address: hexadecimal 0 0 4 0 1 3 5 0.

Run: second; Module base: hexadecimal 0 0 6 0 0 0 0 0; Instruction offset: hexadecimal 1 3 5 0; Instruction address: hexadecimal 0 0 6 0 1 3 5 0.

The same distinction applies inside an object, but the starting point is different. If the compiler put health at +hexadecimal 3 0 within a player object, and that object begins at hexadecimal 0 1 A 2 B 0 0 0 in the first run, its health field is at hexadecimal 0 1 A 2 B 0 3 0. A newly created player at hexadecimal 0 2 0 8 C 0 0 0 puts the same field at hexadecimal 0 2 0 8 C 0 3 0. The module offset measures from the loaded module; the field offset measures from that particular object. Neither offset alone is a complete address. Later pointer work uses this distinction every time it adds an offset to a base address.

Section: How updates affect locations.

The practical payoff is knowing which kinds of location survive a new game version.

Table columns: What you found; Safe to reuse?; Why.

What you found: A raw address from one run; Safe to reuse?: No reliable reuse after a restart; Why: The module or object may have a different base.

What you found: An offset from the module base; Safe to reuse?: Usually after a restart of the same build; Why: The linker fixed its place within that image.

What you found: A field offset like +hexadecimal 3 0; Safe to reuse?: Usually for objects of that type in the same build; Why: The compiler chose the layout.

What you found: A byte pattern; Safe to reuse?: Verify it in each build; Why: Compilation or linking can change its bytes.

What you found: “Health is 48 bytes in”; Safe to reuse?: Recheck after a rebuild; Why: A new field earlier in the structure may shift it.

That last row is the one Lesson 11.4 turns into a migration procedure. In this fixed-order example, inserting a field moves the later fields and leaves the earlier ones in place. Other layout rules can change more, so measure the new build rather than assuming the same shift everywhere:

Section: Optimization is why the code does not match the source.

One more consequence, and it explains a lot of confusing disassembly. An optimising build is allowed to produce anything that behaves the same. It can paste a small function into each of its callers so no call remains, keep a variable only in a register so it never touches memory, drop a variable whose result is never used, reorder work, and merge two identical functions.

So when a function you expected is missing, the usual explanation is not that it was hidden. It is that the compiler decided the fastest way to do that work did not involve a separate function. This is also why a debug build and a release build of the same source can be so different to read, and why an address or offset belongs to the exact build it came from.

Section: Why the stages matter in a debugger.

The compiler chooses field layouts and may remove or transform source functions. The linker fixes positions within a native image and records DLL imports; the loader chooses a run-time base and fills in external addresses. A module-relative offset can therefore survive a restart of the same build while a raw address changes. Rebuilding after a field insertion can shift later offsets, so old offsets need rechecking. Release binaries may omit source names even while import names or separate debug information remain.

We now know why a debugger can show addresses and transformed operations instead of the source’s original names. How Assembly Describes a Running Game gives those operations a readable vocabulary and follows a small rule through its comparisons, branches, and arithmetic.
