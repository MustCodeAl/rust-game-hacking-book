A Windows Lab You Can Reset

Before using a scanner or debugger on the course game, set up a place where the game, tools, and starting conditions can be repeated. This lets you tell a real game change from a difference in the environment.

Use a separate Windows virtual machine for the book. A virtual machine (VM) is a computer simulated inside your main computer. It can run its own copy of Windows and can be reset without reinstalling your everyday system.

Section: Why the VM is useful.

A VM gives the experiments a controlled environment:

old game builds and debugging tools stay separate from personal files;

a snapshot can restore a known state after a crash or bad configuration;

the Windows and tool versions stay fixed, so results repeat;

optional connections to the host can stay disabled until needed.

A snapshot is not a security guarantee and does not make every action harmless. It is a recovery point. Test that you can restore it before depending on it.

The same caution covers what you bring into the VM. A program can do exactly what it advertises and something else at the same time: a “free trainer” that really does give you gold while it quietly copies the passwords saved in your browser. That is called a trojan, after the wooden horse, and it is one of the most common ways players lose accounts, because the cheat working is exactly what makes people trust it. Every tool in this book comes from its official project page or is one you build yourself.

Section: Create the Windows VM.

VirtualBox, VMware, or Hyper-V can work. A practical starting configuration is:

2 or more virtual CPU, central processing unit, cores;

4–8 GB of RAM, random access memory, ;

about 50 GB of storage;

graphics acceleration if a target game requires it.

Install Windows, apply updates, and create a normal user account. Run an individual tool with additional rights only when its operation requires them.

Keep shared folders, clipboard sharing, drag-and-drop, and USB passthrough off at first. Enable a connection only when you need it and know what crosses it.

Read the target name in parts:

i686 — 32-bit x86 instructions and plain pointers , which store 32-bit addresses ;

pc-windows — Windows is the target operating system;

msvc — use Microsoft’s Windows ABI, application binary interface, and linker toolchain.

Code loaded inside a process must match that process’s architecture. A 64-bit DLL, dynamic link library, cannot be loaded into a 32-bit game. Later code changes, register choices, stored-address widths, and calling conventions also depend on the architecture.

An external tool can sometimes have a different bitness because Windows copies bytes across the process boundary. The course keeps its Windows labs 32-bit so addresses and machine-code examples stay consistent. For another game build, inspect its executable and choose the matching target instead of copying this choice blindly.

Clean Windows — after Windows updates, before the lab tools;

Ready for lessons — after tools, the 32-bit target, and course code work.

Name snapshots by what they contain. A date alone does not explain which state is safe to restore.

Section: What a result depends on.

When you later record an address (a location in the running game), an offset (a distance from a chosen start), or a byte pattern (a sequence to search for), record the exact environment too. The next lesson develops these ideas; their usefulness depends on:

the game name, exact build, and architecture, because a different build can move every function and field ;

the executable’s file hash , a short fingerprint computed from its bytes: matching hashes are strong evidence that two copies use the same build even when their version labels are ambiguous;

the Windows version, because system DLLs change between updates;

the repository commit and the tool and debugger versions;

the starting save, map, or settings;

the VM snapshot the machine started from.

The snapshot restores files and installed tools, and source control restores the exact code. The build and file hash tell you whether an address found last week still applies to the game in front of you.

Section: Checkpoint.

Before the first memory experiment, confirm that you can:

restore the “Ready for lessons” snapshot ;

run cargo check in windows-labs ;

launch the target game in the VM ;

identify whether its executable is 32-bit or 64-bit;

name the exact build and starting state an experiment depends on.
