Lesson 15.7 / Listening edition

Cheat Categories from the Defender's Side

Connect different locations of unauthorized code and automation to the observations and boundaries a defender can use.

About 8 minutes

A defender benefits from knowing where an unfair advantage originates. That location affects which observations and protections are available. It does not change who should own the game’s accepted results.

Section: Process location changes local observations.

An external tool runs outside the game process. An internal tool runs code inside it. Depending on permissions and operating-system interfaces, a defender may observe process access, loaded modules, or unexpected integrity changes. Legitimate development and accessibility software can create some of the same observations.

Cheat Engine is a development and modding tool with memory inspection, debugging, and scripting capabilities. Those capabilities can be useful in an owned offline program, like the memory examples earlier in this book. The presence of a general-purpose tool is different from proving an unfair action in a protected match. Nor does changing client memory automatically change the server’s inventory or simulation.

Do not assume that a project having publicly visible source settles every license or distribution question. Check the actual components and current terms before redistributing software. This lesson studies tool categories; it does not ask you to install or use them against protected games.

Section: Privilege is one boundary, information is another.

Kernel-assisted abuse uses privileged operating-system code. It expands the local access problem described in Lesson 15.4. Defenders can combine driver policy, integrity protections, updates, and server validation. These controls cover different parts of the problem.

Direct memory access, or D M A, direct memory access,, lets hardware devices transfer memory without having the C P U, central processing unit, copy every byte. Lesson 12.7 explains why device access needs isolation. An IOMMU, an input-output memory management unit, restricts which memory regions a device can access under the configured policy. Firmware and operating-system configuration affect whether that protection is actually in place.

Neither greater software privilege nor device access creates a hidden server value that was never sent. In the picture, the server sends the player’s own health but excludes an unrelated hidden enemy. Observing the client’s received memory yields only the available information.

This is why local protection and server disclosure rules complement one another. Audit other channels too. Sounds, event messages, timing, or team updates can reveal information that one position filter withheld.

Section: Screen-based automation changes the observation problem.

Computer vision extracts information from images. A vision-based automation system can act on the ordinary game view and emulate input. It may not need access to the game’s internal memory.

The server still sees resulting commands and their timing. Behavioral signals, supported-input policy, and review can contribute evidence. Unusual input consistency also occurs with some permitted devices, so a pattern alone needs legitimate-device testing and context.

In brief: Defend the result and the information boundary as well as the location of code. Different tool categories can produce similar commands.

Section: Network and asset changes need their own controls.

Network abuse can involve invalid messages, repeated requests, excessive work, or inconsistent session claims. Parse bounded input, authenticate the session, validate actions against current state, and define retry behavior. A cryptographically protected connection does not make the authenticated player’s requests truthful.

An asset is stored game content such as a model, texture, or sound. Unauthorized replacement can change the information or visibility a game intends to provide. A server can require an approved asset set where the rules call for it. Use signed manifests and trusted references rather than letting the client select both the content and the expected checksum. See Lesson 9.8.

Permitted mods have a separate policy and supported loading path. They should not be silently treated as cheating merely because their bytes differ from the stock installation. Define the protected mode, authorized extensions, and review procedure before interpreting a local mismatch.
