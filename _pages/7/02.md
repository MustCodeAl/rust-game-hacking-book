## Keep four address terms separate

- a **preferred image base** is where the file would like to be loaded;
- a **live module base** is where Windows placed it in this process run;
- an **RVA** is a distance from the beginning of the module;
- a **virtual address** is the final live address used by the CPU.

An RVA is not a pointer stored in the game. It is arithmetic describing a
location inside one loaded image. The PE file’s section table maps RVAs to
sections such as code or data.

Do not confuse an RVA with a **file offset**. A file offset counts bytes in the
EXE on disk. An RVA counts from the mapped image base after Windows has arranged
sections according to virtual addresses and alignment. They can differ.

## Why an address moves

Old notes often show an address such as `0x007CCD91`. That may be the address from one run, not a permanent location.

Windows can load an executable at a different base address. This is **Address Space Layout Randomization**, or **ASLR**. The useful part that usually stays the same for an exact build is the distance from the module’s beginning: the **Relative Virtual Address**.

ASLR makes fixed absolute addresses less predictable. Windows can relocate an
image when its PE metadata supports relocation. The module’s internal layout
for that exact file usually stays the same, so base-plus-RVA reaches the same
instruction even when the base changes.

```text
live virtual address = live module base + RVA
RVA                  = observed address - observed module base
```

Imagine a classroom desk. “Desk 14” is like an RVA. The room number is like the module base. If the class moves from room 200 to room 310, desk 14 is still desk 14 inside the new room.

## Derive the Wesnoth example

For the 32-bit Wesnoth 1.14.9 course build, the original disassembly records the instruction at `0x007CCD91`. If the module was loaded at `0x00400000` during that capture:

```text
0x007CCD91 - 0x00400000 = 0x003CCD91
```

So `0x003CCD91` is the RVA. On another run, a live base of `0x00600000` would produce:

```text
0x00600000 + 0x003CCD91 = 0x009CCD91
```

Never assume the example base. Measure the module in the run you are actually debugging.

## Ask Windows where the module lives

The shared `Process` wrapper uses `CreateToolhelp32Snapshot`, `Module32FirstW`, and `Module32NextW` from the `windows` crate. The chapter tool becomes small because those unsafe Windows boundaries already live in one reviewed module:

```rust
#[cfg(windows)]
fn main() -> anyhow::Result<()> {
    use anyhow::Context;
    use gha_windows_labs::Process;

    let mut arguments = std::env::args().skip(1);
    let process_name = arguments.next().unwrap_or_else(|| "wesnoth.exe".to_owned());
    let module_name = arguments.next().unwrap_or_else(|| process_name.clone());
    let requested_rva = arguments
        .next()
        .map(|text| usize::from_str_radix(text.trim_start_matches("0x"), 16))
        .transpose()
        .context("RVA must be hexadecimal, such as 3CCD91")?;

    let process = Process::open_by_name(&process_name, false)?;
    let (base, size) = process.module(&module_name)?;
    let end = base.checked_add(size).context("module range overflowed")?;

    println!("{} (PID {})", process.name(), process.id());
    println!("  live base: {base:#010x}");
    println!("  size:      {size:#010x}");
    println!("  end:       {end:#010x}");

    if let Some(rva) = requested_rva {
        anyhow::ensure!(rva < size, "RVA {rva:#x} is outside the module");
        let address = base.checked_add(rva).context("base + RVA overflowed")?;
        println!("  {base:#010x} + {rva:#010x} = {address:#010x}");
    }
    Ok(())
}
```

The two guards matter. An RVA outside the module is probably for the wrong version, and an overflowing addition is never a valid address.

ToolHelp returns information about modules in the chosen process. The snapshot
is still a moment-in-time view: a DLL can unload after enumeration. For the
course EXE this is stable during the short calculation, but reusable tooling
should handle a later read failure normally.

## Run it against the course build

Start a local Wesnoth match, then run:

```powershell
.\target\i686-pc-windows-msvc\release\module_inspector.exe `
  wesnoth.exe wesnoth.exe 3CCD91
```

Open the printed live address in x64dbg. The bytes and disassembly must match the lesson before you use the address.

Repeat the process after restarting Wesnoth. If the base changes but `base + RVA` still reaches the expected instruction, you have separated stable location information from one-run information.

The buildable tool is [`module_inspector.rs`]({{ site.baseurl }}/windows-labs/src/bin/module_inspector.rs), and its ToolHelp implementation is in [`process.rs`]({{ site.baseurl }}/windows-labs/src/windows_impl/process.rs).

## RVA is not a version check

An RVA can move when the game is rebuilt. Keep all three checks:

1. exact supported game version;
2. live module base plus the version’s RVA;
3. exact original bytes or a unique pattern at the final address.

That is why the code-cave installers reject unknown bytes instead of hoping the address is close enough.
