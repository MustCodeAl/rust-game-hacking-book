## Why an EXE needs a map

A Windows `.exe` is not one solid blob of CPU instructions. It is a **Portable Executable**, usually shortened to **PE**. Its headers tell Windows where the code, read-only data, writable data, imports, resources, and relocation information live.

Use two layouts connected by the section table:

```text
file layout on disk                         image layout in a process
file offset -> bytes in one section   <->   RVA -> mapped bytes in that section
                                             + live module base
                                             = live virtual address
```

The layouts differ because sections have separate file and virtual alignments,
zero-initialized data may occupy memory without taking equal file space, and Windows
may apply relocations and resolve imports after mapping. A section row is the rule
for converting a location in one layout to the corresponding location in the other;
the numbers are related but not interchangeable.

## The path through the headers

```text
DOS header (starts with MZ)
└─ e_lfanew points to the PE signature
   └─ COFF header says how many sections exist
      └─ optional header holds the image base and entry-point RVA
         └─ section table describes .text, .data, .rdata, and friends
```

The “optional” header is not optional for an executable image. That old name survives because object files can omit it.

## Read numbers without pointer casts

For an on-disk file, a byte slice is safer and easier than casting random offsets to Windows structs:

```rust
fn bytes_at(bytes: &[u8], offset: usize, count: usize) -> anyhow::Result<&[u8]> {
    // 📏 Validate both the arithmetic and the slice. Either can fail for a
    // damaged file, and neither failure should become a panic or pointer cast.
    let end = offset.checked_add(count).context("PE offset overflowed")?;
    bytes
        .get(offset..end)
        .with_context(|| format!("PE field {offset:#x}..{end:#x} is outside the file"))
}

fn u32_at(bytes: &[u8], offset: usize) -> anyhow::Result<u32> {
    Ok(u32::from_le_bytes(bytes_at(bytes, offset, 4)?.try_into()?))
}
```

Three ideas are hiding in those few lines:

1. `checked_add` refuses an integer wraparound.
2. `get` refuses an out-of-file slice.
3. `from_le_bytes` states that PE numbers use little-endian byte order.

That is what “safe parsing” means: malformed input becomes an error instead of an invalid memory access.

## Find the PE and COFF headers

```rust
anyhow::ensure!(bytes_at(&bytes, 0, 2)? == b"MZ", "missing DOS MZ signature");
// 🧭 DOS field 0x3c contains a file offset, not an RVA or live address.
let pe_offset = usize::try_from(u32_at(&bytes, 0x3c)?)?;
anyhow::ensure!(
    bytes_at(&bytes, pe_offset, 4)? == b"PE\0\0",
    "missing PE signature"
);

// 📏 Skip the four-byte PE signature only after it has been verified above.
let coff = pe_offset.checked_add(4).context("COFF offset overflowed")?;
let machine = u16_at(&bytes, coff)?;
let section_count = usize::from(u16_at(&bytes, coff + 2)?);
let optional_size = usize::from(u16_at(&bytes, coff + 16)?);
anyhow::ensure!(section_count <= 96, "unreasonable section count");
```

The cap of 96 is deliberately boring. Real course targets do not need thousands of sections, so a wild count is evidence of a wrong offset or damaged file.

## Tell PE32 from PE32+

The optional-header magic is `0x10B` for PE32 and `0x20B` for PE32+. Because their fields have different sizes, the image-base offset changes:

```rust
let optional = coff.checked_add(20).context("optional-header overflowed")?;
let magic = u16_at(&bytes, optional)?;
let entry_rva = u32_at(&bytes, optional + 16)?;

let image_base = match magic {
    // 📦 PE32 stores a four-byte image base at +28.
    0x10b => u64::from(u32_at(&bytes, optional + 28)?),
    // 📦 PE32+ stores an eight-byte image base at +24.
    0x20b => u64_at(&bytes, optional + 24)?,
    other => anyhow::bail!("unsupported optional-header magic {other:#06x}"),
};
```

The games used by the memory-patching chapters are the specified 32-bit course builds, so their magic should be `0x10B`. The parser supports both formats because a tool should explain what it found instead of guessing.

## Walk the 40-byte section rows

The section table begins immediately after the optional header. Each row is 40 bytes:

```rust
let section_table = optional
    .checked_add(optional_size)
    .context("section-table offset overflowed")?;

for index in 0..section_count {
    // 📏 Multiply and add separately with checks so a hostile count cannot wrap
    // around and point an apparently valid row back into an earlier header.
    let start = section_table
        .checked_add(index.checked_mul(40).context("section index overflowed")?)
        .context("section offset overflowed")?;

    let name_bytes = bytes_at(&bytes, start, 8)?;
    // 🔍 PE names are fixed eight-byte fields and are not required to end in NUL.
    let name_end = name_bytes.iter().position(|byte| *byte == 0).unwrap_or(8);
    let name = String::from_utf8_lossy(&name_bytes[..name_end]);
    let virtual_size = u32_at(&bytes, start + 8)?;
    let virtual_address = u32_at(&bytes, start + 12)?;
    let raw_size = u32_at(&bytes, start + 16)?;
    let raw_offset = u32_at(&bytes, start + 20)?;
    let flags = u32_at(&bytes, start + 36)?;

    println!(
        "{name:<8} RVA {virtual_address:#010x} virtual {virtual_size:#010x} file {raw_offset:#010x}+{raw_size:#010x} flags {flags:#010x}"
    );
}
```

`.text` is normally readable and executable. `.rdata` is normally readable. `.data` is normally readable and writable. Names are conventions; the characteristic flags are the stronger evidence.

## Run the real lab

Build the tool, then inspect one exact course executable:

```powershell
cd windows-labs
cargo build --release --target i686-pc-windows-msvc --bin pe_inspector
.\target\i686-pc-windows-msvc\release\pe_inspector.exe `
  "C:\Games\Wesnoth 1.14.9\wesnoth.exe"
```

Write down:

- PE32 or PE32+;
- preferred image base;
- entry-point RVA;
- `.text` RVA and size;
- whether `.text` is marked executable.

Then inspect `ac_client.exe` and `Quake3-UrT.exe`. The layout changes, but the map-reading process does not.

The complete buildable parser is [`pe_inspector.rs`]({{ site.baseurl }}/windows-labs/src/bin/pe_inspector.rs). It performs checked offset math for every field and never uses `unsafe`.
