## Start from behavior

Use the offline Wesnoth target. Find gold again and set a write breakpoint. Instead of recruiting, end a turn so income changes the value.

![Wesnoth’s income display](/assets/images/2/9/wesnoth1.png)

When the breakpoint fires, inspect the instruction that reached the gold field.

![A breakpoint triggered by income](/assets/images/2/9/wesnoth2.png)

Suppose it looks conceptually like:

```nasm
add dword ptr [rcx+30], eax
```

This suggests:

- `rcx` points near the start of an object;
- offset `0x30` reaches the gold field;
- `eax` contains the income amount.

Write down the real register and offset from your build.

## Trace the object pointer

The next question is: where did `rcx` come from?

Look backward within the function or step from an earlier call. You may see a sequence that loads a pointer from another structure:

```nasm
mov rcx, [rbx+18]
add dword ptr [rcx+30], eax
```

Now the tentative path is:

```text
address in rbx
→ add 0x18 and read a pointer
→ add 0x30
→ gold field
```

Keep tracing until the first location is relative to a loaded module, not a temporary heap address.

## Build the chain manually

In Cheat Engine, add a pointer entry by hand using the module and the offsets you observed.

Be careful about order. A displayed list of offsets may be applied from the module outward or shown in reverse depending on the tool.

## Restart tests

One successful run proves very little. Test:

1. close Wesnoth completely;
2. start it again;
3. begin a new local match;
4. confirm the pointer entry resolves;
5. repeat at least three times.

Also test a state where no match is active. A good tool should report “player object unavailable,” not crash or read address zero.

## Write the algorithm before the API

The future Rust code should follow this plain algorithm:

```text
find the base of wesnoth.exe
add the stable first offset
read a pointer
if it is null, stop with a useful error
add the next offset
read a pointer
add the final gold-field offset
read the 32-bit gold value
```

We can model failures precisely:

```rust
#[derive(Debug)]
enum ResolveError {
    ModuleNotFound,
    NullPointer { step: usize },
    AddressOverflow,
    ReadFailed { address: usize },
}
```

This is one of Rust’s biggest advantages for low-level tools: failure is data we must handle, not a surprise we hope never happens.

## What counts as “stable”

The path is stable only for the target version and states you tested. Game updates can change layouts and offsets. Document:

- game version and architecture;
- module name;
- offsets in traversal order;
- the expected final type;
- how many restarts passed;
- known states where the chain is unavailable.
