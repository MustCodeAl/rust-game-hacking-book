This lab uses x64dbg only. We are learning the shape of a detour before asking Rust to manage one.

## Detour vocabulary before touching bytes

A **hook site** is the address where normal execution is redirected. A
**detour** is that redirection. A **code cave** is executable storage holding
the added instructions. A **return address** is the first untouched instruction
where normal execution resumes.

Some tools use the word **trampoline** for a small block that replays displaced
instructions and jumps back. Names vary, but every working detour must answer
the same questions:

```text
Where do we leave the original path?
Which complete instructions did we remove?
Where will the new code live?
What machine state must it preserve?
Where does normal execution resume?
How will every changed byte be restored?
```

The CPU has no concept of “our patch.” It only follows the instruction pointer.
A single wrong length or destination sends that pointer into unrelated bytes.

## Choose a harmless trigger

Use the terrain-description menu path identified in the previous lesson. It gives us an easy trigger without changing competitive or networked behavior.

![The terrain-description function]({{ site.baseurl }}/assets/images/2/7/wesnoth2.png)

Pause the game and choose a hook site with enough complete instructions for a jump. Record:

```text
Hook address:
Original instructions:
Original bytes:
Total byte length:
Return address:
```

Do not continue until the return address points to the first untouched instruction.

For the exact course build, fill the worksheet with real values:

```text
Hook address:          0x00CC_AF8A
Original instructions: mov eax,[ecx] / alignment lea
Original bytes:        8B 01 8D 74 26 00
Total byte length:     6
Return address:        0x00CC_AF90
```

The byte count comes from instruction decoding, not subtraction by guesswork.

x86 instructions have different lengths. A five-byte jump cannot safely replace
the first five bytes of a six-byte instruction. The overwrite must end exactly
on an instruction boundary, even when that means replacing six, eight, or more
bytes and filling unused space with `nop`.

## Find a suitable cave

For this historical debugger exercise, locate executable padding inside the controlled module.

![An empty-looking area near the end of the module]({{ site.baseurl }}/assets/images/2/7/wesnoth1.png)

“Looks empty” is not enough for production tooling. A robust tool allocates its own memory and assigns the correct protection. Here, the debugger-only lab is about the control flow.

## Build the smallest detour

Start with no extra behavior:

```nasm
; cave
; replay the complete instructions removed from the hook
jmp return_address
```

At the hook site, write a jump to the cave and fill any remaining whole bytes with `nop`.

![A jump from the hook into the cave]({{ site.baseurl }}/assets/images/2/7/wesnoth4.png)

Set breakpoints at:

- the hook;
- the first cave instruction;
- the return address.

Trigger the menu once. You should see the breakpoints in that order. This proves the path before new logic complicates it.

## Preserve the interrupted calculation

The hook interrupts a function in the middle of its work. Registers, flags, and
stack entries may already carry values needed by later instructions.

The cave must normally:

1. save any register or flag it will change but the original code expects;
2. run the added behavior;
3. restore that machine state;
4. replay the complete displaced instructions exactly once;
5. jump to the first untouched instruction.

Replaying an instruction twice is just as wrong as skipping it. Changing the
stack pointer without undoing the change can make a later `ret` jump to garbage.
These delayed failures are why a hook may appear to work once and crash later.

![The cave breakpoint firing]({{ site.baseurl }}/assets/images/2/7/wesnoth6.png)

## Add one observable change

Only after the round trip works, add a tiny change such as writing a known value to the already-identified gold field.

![A cave containing the test change]({{ site.baseurl }}/assets/images/2/7/wesnoth7.png)

Trigger once, observe once, and stop. If the wrong action triggers it, your hook is too broad or your model is wrong.

## Diagnose by symptom

| Symptom | Likely place to check |
|---|---|
| Crash before cave | Hook bytes or jump destination |
| Cave never runs | Wrong trigger or hook not reached |
| Crash after cave | Saved instruction or return address |
| Game acts oddly later | Register, flag, or stack state was changed |
| Runs more than once | Trigger path or re-entry assumption |

Change one variable per retry.

## Restore the target

Before closing the debugger:

1. pause the game;
2. restore the hook’s original bytes;
3. remove breakpoints;
4. verify the original behavior;
5. restore the VM snapshot if anything is uncertain.

The lasting result is your map of the detour, not the temporary patch.

replaces them with `E9 rel32 90`, runs a real naked x86 cave, sets Wesnoth gold

bytes when disabled. See the complete code in lesson 2.6 or
