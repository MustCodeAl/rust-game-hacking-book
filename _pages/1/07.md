## Start with the simplest definition

**Memory is a large collection of numbered byte-sized boxes.** A byte can hold a number from `0` through `255`. The number written on a box is its **address**.

Imagine this tiny piece of memory:

```text
address       byte stored there
0x1000        64
0x1001        00
0x1002        00
0x1003        00
```

The four bytes are `64 00 00 00` in hexadecimal. If code interprets them as a little-endian `u32`, they represent decimal `100`. That value might be gold, health, a timer, or merely the number of pixels in a menu. Memory stores bytes, not meaning. The program supplies the meaning.

This gives us three different ideas that beginners often mix together:

- **address:** where something begins;
- **bytes:** the raw contents stored there;
- **type:** the rule used to interpret those bytes.

If address `0x1000` contains the value `100`, the address is not `100`. It is the location where the bytes for `100` begin.

## RAM is temporary working space

Your drive keeps the game when the computer is turned off. **RAM** holds the parts that are actively being used: running code, loaded maps, player state, textures, audio buffers, and operating-system bookkeeping.

RAM is **volatile**, which means its contents disappear when power is removed. A save file survives because the game copies selected state from RAM to storage. Loading reverses the trip: the game reads the file, checks it, and creates new in-memory objects.

Launching a game does not copy the entire drive into RAM. Windows maps the executable and libraries, creates memory for stacks and heaps, and loads other resources when they are needed.

## A process sees virtual memory

A game usually does not work with raw labels printed on physical RAM chips. Windows gives the process a **virtual address space**: a private numbered map of addresses the process is allowed to use.

Two processes can both use virtual address `0x1000` while reaching completely different physical storage. Windows and the CPU translate each process’s virtual addresses behind the scenes.

This separation has useful consequences:

- one crashing program is less likely to damage another;
- a process cannot casually read another process;
- Windows can move physical pages without changing every pointer in the game;
- memory that looks continuous to a program does not have to be continuous in physical RAM.

When our Rust tool reads Wesnoth with `ReadProcessMemory`, it is asking Windows to copy bytes from a range in **Wesnoth’s virtual address space** into a buffer owned by our tool.

```text
Wesnoth process                     Rust tool process

0x1234A000  gold bytes   --Windows-->  Vec<u8>
0x1234A004  side number                copied snapshot
0x1234A008  other state
```

The tool cannot safely dereference `0x1234A000` as if that address belonged to itself. The same number has meaning only inside the target process’s address map.

## Pages and regions divide the map

Windows manages virtual memory in fixed-size blocks called **pages**. Nearby pages with similar purpose and permissions form a **region**.

A page can have rules such as:

| Permission | Plain-English meaning |
|---|---|
| readable | code may copy bytes from it |
| writable | code may change its bytes |
| executable | the CPU may treat its bytes as instructions |
| guarded | the next access creates a special event |
| no access | ordinary reads and writes are rejected |

These permissions are why a scanner first asks Windows which regions are readable. Blindly reading from address zero upward would repeatedly hit missing or protected pages.

Permissions describe what Windows currently allows; they do not describe what the bytes mean. A writable page can hold player objects, temporary text, an image, or unused space.

## The usual parts of a process

A process address space is not one undifferentiated pile. You will often encounter these areas:

```text
lower addresses

executable module
  machine code, read-only constants, imported function pointers

other DLL modules
  Windows libraries, graphics libraries, game libraries

heap allocations
  objects and collections created while the game runs

mapped files and large buffers
  assets, caches, networking, rendering data

thread stacks
  function calls, return addresses, some local variables

higher addresses
```

The exact order and addresses vary. Treat this as a set of neighborhoods, not a guaranteed street map.

### Modules

An EXE or DLL loaded into a process is a **module**. A module has a base address, sections, code, and data. Windows may load it at a different base after a restart because of ASLR.

If an instruction is always `0x12340` bytes from the start of `wesnoth.exe`, we can describe it with a relative virtual address:

```text
live address = module base + RVA
```

That relationship is often more useful than saving one temporary absolute address.

### The stack

Each thread owns a **stack**. Functions use it for return addresses, saved registers, arguments that do not fit in registers, and some local values.

The stack behaves roughly like a pile of trays: the most recent function call is normally removed first. It grows and shrinks as functions call and return.

A stack address is usually temporary. The same location may hold a menu variable now and an animation variable a moment later. Finding a value on the stack does not automatically reveal the long-lived game object that produced it.

### The heap

The **heap** is memory used for values whose size or lifetime is decided while the program runs. A growing `Vec`, a loaded map, a player object, or a string may obtain storage from a heap allocator.

“Heap” does not mean disorganized. The allocator tracks which blocks are in use. The game builds structures and pointers inside those blocks.

An object may receive a new heap address after a restart or map reload. That is one reason pointer paths, module-relative code, and verified patterns matter.

## Variables become byte layouts

This Rust value has friendly field names:

```rust
#[repr(C)]
struct Player {
    health: u32,
    team: u8,
    alive: bool,
    x: f32,
    y: f32,
}
```

The CPU does not store the names `health` or `team`. It stores bytes at offsets from the beginning of the object.

```text
player address + 0x00  health
player address + 0x04  team
player address + 0x05  alive
player address + 0x08  x
player address + 0x0C  y
```

Why does `x` begin at `0x08` rather than `0x06`? The compiler may insert **padding** so a four-byte `f32` begins at an address suited to its alignment. Padding bytes belong to the layout but are not a field.

The exact layout depends on the language, compiler, architecture, and representation rules. `#[repr(C)]` requests a C-compatible field order, but it does not magically prove that an unknown game object uses this struct.

Reverse engineering rebuilds a possible layout from evidence:

1. observe behavior;
2. find related bytes;
3. watch instructions access fixed offsets;
4. test the suspected type and field meaning;
5. repeat after restarts and different game states.

## Arrays, strings, and collections use patterns

An **array** stores same-sized items next to one another. If a position uses three `f32` values, an array of positions may resemble:

```text
x0 y0 z0 | x1 y1 z1 | x2 y2 z2
```

A **string** needs both bytes and a rule for finding its end. C strings use a zero byte terminator. Rust `String` keeps a pointer, length, and capacity. Other engines use UTF-16, fixed buffers, or custom string objects.

A `Vec<T>` does not place all of its elements inside the small `Vec` value itself. The `Vec` stores a pointer to heap storage plus a length and capacity. Following the pointer reaches the elements.

These differences explain why “scan for the visible text” sometimes finds the characters but not the object that owns them.

## A pointer is an address stored as data

A **pointer** is a value whose job is to hold an address.

```text
0x5000 contains 00 A0 34 12
interpreted as a pointer: 0x1234A000
memory at 0x1234A000 contains the player object
```

**Dereferencing** means following the address and accessing the bytes found there.

A pointer can be:

- **null:** intentionally points nowhere;
- **stale:** the allocation was released or replaced;
- **misaligned:** unsuitable for the expected type;
- **valid but wrong:** points to real memory that is not the object you assumed;
- **valid only briefly:** another thread may replace or free it.

That is why an address being readable is necessary but not sufficient. Good tooling also checks the expected module, range, object fields, current instruction bytes, version, and behavior.

## An offset is a distance

An **offset** is a distance from some starting point. If the player object begins at `0x1234A000` and health is at offset `0x30`, then:

```text
health address = 0x1234A000 + 0x30
               = 0x1234A030
```

An offset is not automatically a pointer. `[eax + 0x30]` means “use the address calculated by adding `0x30` to `eax`.” Whether `eax` holds a player pointer must be learned from context.

A **pointer chain** repeats the idea:

```text
module base + 0x0100 -> pointer to game state
game state + 0x20    -> pointer to current side
current side + 0x30  -> gold value
```

Every arrow requires a memory read. The final `+ 0x30` may identify the value itself rather than another pointer. Mixing those two operations is a common beginner bug.

## Lifetime answers “how long is this valid?”

Memory becomes dangerous when code uses it after its meaning has ended.

A local variable may be valid only during one function call. A heap object may be valid until the game removes a unit. A module may be valid until it unloads. A copied scan buffer belongs to the moment it was read.

Rust uses ownership and lifetimes to protect memory inside our own process. Windows cannot give Rust a compile-time proof about another running process. We replace that missing proof with short operations, checked arithmetic, explicit limits, version checks, and repeated validation.

## A scanner reads snapshots, not frozen truth

When a memory scanner copies a region, the target may continue running. The scanner sees a **snapshot assembled over time**, not a magical pause of the whole game.

Suppose the game changes health between two reads:

```text
read first half of object
game updates the object
read second half of object
```

The combined bytes may never have existed together in exactly that form. For simple integer scans this is usually manageable: an unstable candidate may disappear during the next scan. For complex structures, tools may pause a controlled target, retry, validate a version field, or accept that observations are approximate.

This is also why the scanner copies bounded chunks into its own `Vec<u8>` and searches the copy. Iterating directly over a changing remote region would be slower and harder to reason about.

## Build a tiny memory model in safe Rust

This program creates fake memory, writes a player record into it, and finds the four bytes representing `100` health. It teaches the scanning idea without touching another process.

```rust
fn read_u32_le(memory: &[u8], address: usize) -> Option<u32> {
    let bytes: [u8; 4] = memory.get(address..address.checked_add(4)?)?
        .try_into()
        .ok()?;
    Some(u32::from_le_bytes(bytes))
}

fn main() {
    let mut memory = vec![0_u8; 64];

    let player_address = 16_usize;
    let health_offset = 8_usize;
    let health_address = player_address + health_offset;

    memory[health_address..health_address + 4]
        .copy_from_slice(&100_u32.to_le_bytes());

    let wanted = 100_u32.to_le_bytes();
    let matches: Vec<usize> = memory
        .windows(wanted.len())
        .enumerate()
        .filter_map(|(address, bytes)| (bytes == wanted).then_some(address))
        .collect();

    println!("matching addresses: {matches:#x?}");
    println!("health: {:?}", read_u32_le(&memory, health_address));
}
```

Walk through the important parts:

1. `Vec<u8>` is our pretend address space.
2. A vector index acts like a small address.
3. `to_le_bytes` chooses the byte representation deliberately.
4. `windows(4)` visits every four-byte candidate.
5. `read_u32_le` checks its range before converting bytes.

The real Windows scanner uses larger addresses and fills its buffer with `ReadProcessMemory`, but the searching algorithm is the same.

## Keep these words separate

| Word | Meaning |
|---|---|
| RAM | physical working memory used while the computer runs |
| virtual memory | the per-process address map managed by Windows |
| address | a numbered location in an address space |
| value | information represented by bytes |
| type | the rule used to interpret and operate on bytes |
| pointer | a value intended to hold an address |
| offset | a distance from a starting address |
| page | a fixed-size block Windows maps and protects |
| module | a loaded EXE or DLL image |
| stack | per-thread storage tied closely to function calls |
| heap | dynamically allocated storage managed at runtime |
| region | neighboring pages with related state and permissions |
