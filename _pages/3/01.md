## Why Rust fits this course

Game tooling needs low-level control: exact integer sizes, raw bytes, operating-system APIs, and sometimes pointers. Rust provides those features while checking ordinary memory use at compile time.

The guiding rule is:

> Write safe Rust for the algorithm. Put unavoidable raw-pointer work in one small wrapper, document its assumptions, and return an ordinary Rust type.

## Rust memory and game memory are different trust zones

Rust can prove many facts about memory owned by the current Rust program. A
borrowed slice has a known length and owner. A `Vec<u8>` keeps its allocation
alive. A reference cannot normally outlive the value it borrows.

Rust cannot prove equivalent facts about an address copied from another
process. The target can free an object, change page permissions, exit, or race
with our read. That is why cross-process code should not manufacture a normal
Rust reference such as `&Player` from a remote address.

Instead, use a clear boundary:

```text
remote address + requested size
→ checked Windows read
→ owned Vec<u8> in our process
→ safe parsing and searching
```

After the copy succeeds, ordinary Rust rules protect the local buffer. Before
the copy, the address is untrusted input that needs checked arithmetic, region
validation, and a useful error.

## Values and types

Memory work depends on sizes, so we use explicit integer types:

```rust
let health: u32 = 100;      // unsigned, 32 bits
let direction: i32 = -1;    // signed, 32 bits
let x: f32 = 12.5;          // 32-bit floating point
let address: usize = 0x1000; // pointer-sized integer
```

Use `usize` for address calculations, not for game values just because it is convenient.

`usize` is large enough to index memory in the current build. It is 32 bits in
an `i686-pc-windows-msvc` tool and 64 bits in an x86-64 tool. A game’s `u32`
health value stays four bytes on both. Address width and value width answer
different questions.

## Ownership and borrowing

Every Rust value has one owner. Other code can borrow it:

```rust
fn find_value(bytes: &[u8], needle: [u8; 4]) -> Option<usize> {
    bytes.windows(needle.len())
        .position(|window| window == needle)
}

let memory = vec![0_u8, 100, 0, 0, 0, 5];
let offset = find_value(&memory, 100_u32.to_ne_bytes());
assert_eq!(offset, Some(1));
```

`&[u8]` is a borrowed slice: a view into bytes owned somewhere else. The function can read them but cannot keep or change them.

A slice is two pieces of information used together: where the first element is
and how many elements are available. Indexing and `windows` use the length to
avoid walking beyond the allocation. A raw pointer by itself carries no such
length.

Borrowing is different from moving. A borrow gives code temporary permission
to use a value without taking responsibility for freeing it. Shared borrows
(`&T`) allow reading. A mutable borrow (`&mut T`) allows changing, but it must be
the only usable borrow of that value for its lifetime.

## Convert bytes deliberately

A debugger displays bytes; a game interprets them as types. Rust makes the conversion explicit:

```rust
fn read_u32(bytes: &[u8]) -> Option<u32> {
    let first_four: [u8; 4] = bytes.get(..4)?.try_into().ok()?;
    Some(u32::from_le_bytes(first_four))
}
```

The `?` means “if this step fails, return `None` now.” No out-of-bounds read and no panic are needed.

`from_le_bytes` names the byte order explicitly. `transmute` or an unchecked
pointer cast would silently depend on layout, alignment, size, and host byte
order. Low-level code is easier to review when every conversion states its
assumption.

## Errors are part of the function

Use `Result<T, E>` when callers need to know why an operation failed:

```rust
#[derive(Debug)]
enum ReadError {
    AddressOverflow,
    Unreadable { address: usize },
    WrongSize { expected: usize, actual: usize },
}

fn add_offset(address: usize, offset: usize) -> Result<usize, ReadError> {
    address.checked_add(offset).ok_or(ReadError::AddressOverflow)
}
```

For a small application, the `anyhow` crate is convenient for adding context. For a reusable library, a typed error enum—often derived with `thiserror`—gives callers more control.

## Raw pointers and `unsafe`

A raw pointer is written `*const T` for reading or `*mut T` for writing. Rust does not automatically know whether it is:

- non-null;
- aligned;
- inside readable memory;
- pointing to a real `T`;
- still valid.

Dereferencing one therefore requires `unsafe`:

```rust
/// # Safety
/// `pointer` must be non-null, aligned, readable, and point to an initialized `u32`.
unsafe fn read_raw_u32(pointer: *const u32) -> u32 {
    // SAFETY: the caller promises all requirements listed above.
    unsafe { pointer.read() }
}
```

Notice that Rust 2024 still requires an inner `unsafe` block inside an `unsafe fn`. The dangerous operation remains easy to find in review.

> Never use `unsafe` to “make the borrow checker stop complaining.” First understand the ownership problem. In this course, `unsafe` is reserved for operating-system, graphics, FFI, and verified raw-memory boundaries.
{: .block-warning }

## Set up a Windows project

```powershell
cargo new memory_lab
cd memory_lab
```

Add the libraries:

```toml
[dependencies]
anyhow = "1"

[dependencies.windows]
version = "0.62"
features = [
    "Win32_Foundation",
    "Win32_System_Diagnostics_Debug",
    "Win32_System_Threading",
]
```

The `windows` crate generates typed bindings from Microsoft’s Windows metadata. We enable only the API groups we use.

## The shape of our programs

Keep the project in layers:

```text
main.rs       parse input and print useful errors
process.rs    own the Windows process handle
memory.rs     safe read/write methods
address.rs    checked address and pointer-chain logic
```

The Windows calls may be `unsafe`. Finding a value in a byte slice, filtering candidates, parsing numbers, and printing results do not need to be.
