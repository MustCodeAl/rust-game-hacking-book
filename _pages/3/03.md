## The source code is gone, but the layout remains

Imagine that a game originally contained this C++ class:

```cpp
class Player {
public:
    virtual void update();
    Vec3 position;
    float yaw;
    float pitch;
    char name[32];
    bool dead;
};
```

The compiler does **not** normally copy that neat declaration into the finished `.exe`. Names such as `Player`, `position`, and `update` may disappear. The running program still needs a repeatable arrangement of bytes, though. It must know where each player's position begins, where the name lives, and which function to call.

Reversing a class means rebuilding a useful description of that arrangement from evidence. You are not magically restoring the original source. You are producing a tested model that explains what the machine does. 🧠

This lesson uses the authorized **AssaultCube 1.2.0.2 32-bit Windows** lab build in a local bot match. Offsets are version-specific. A different build may have a different layout.

## Climb an evidence ladder

Reverse engineering moves from facts the machine exposes to ideas humans use.
The higher you climb, the more useful the description becomes—and the more
carefully you must test it.

| Level | Example claim | Confidence source |
| --- | --- | --- |
| Bytes | Four bytes at this address changed. | Direct memory observation. |
| Instruction | `movss` read those four bytes. | Decoded machine code. |
| Data flow | The value reaches the view-angle calculation. | Register and memory tracing. |
| Field | Offset `+0x40` behaves like yaw. | Controlled turns across many instances. |
| Object | Several fields share one stable base address. | Repeated `base + offset` accesses. |
| Class behavior | Objects sharing one table dispatch related methods. | Validated indirect calls and object lifetimes. |
| Game meaning | This is the active player entity. | Behavior, call context, and lifecycle tests. |

Do not skip from “bytes changed” straight to “this is definitely a `Player`
class.” Keep each intermediate claim visible. If a later test fails, you can
step down one level and see exactly which inference broke.

## Five words that sound similar

| Word | Plain-English meaning |
| --- | --- |
| **Class** | A source-code recipe that combines data with functions. |
| **Object** or **instance** | One real player, weapon, or entity created from that recipe. |
| **Field** or **member** | One piece of data inside an object, such as health or yaw. |
| **Method** | A function that operates on an object. |
| **Structure layout** | The byte distance, size, type, and alignment of each field. |

Suppose one player object begins at address `0x12340000`, and its yaw is at offset `0x40`. The yaw address is:

```text
object base + field offset = field address
0x12340000 + 0x40        = 0x12340040
```

An **offset is a distance**, not an address by itself. Many player objects can use the same yaw offset while living at different base addresses.

## What an object looks like in memory

For the course build of AssaultCube, our recovered player model contains these useful landmarks:

| Offset from player base | Candidate field | How to test it |
| ---: | --- | --- |
| `+0x04` | X position (`f32`) | Move east/west and watch a smooth finite value change. |
| `+0x08` | Y position (`f32`) | Move north/south while X stays mostly steady. |
| `+0x0C` | Z position (`f32`) | Jump or change elevation. |
| `+0x40` | Yaw (`f32`) | Turn left/right; expect an angle-like value. |
| `+0x44` | Pitch (`f32`) | Look up/down. |
| `+0x225` | Name bytes | Compare several bots with different names. |
| `+0x338` | Dead flag (`u32`) | Observe zero while alive and a changed flag after death. |

Notice the gaps. We have not claimed that every byte between `0x0C` and `0x40` is useless. Those bytes may contain velocity, dimensions, pointers, flags, or padding. **Unknown means unproven**, not empty.

Padding is especially easy to miss. CPUs and compilers often place a field at an aligned address, leaving unused bytes between fields. If you squeeze the known fields together in your guessed structure, every later offset becomes wrong. ❌

## Find the object base from one known field

Start with behavior you can control:

1. Find the local player's yaw with a float scan while turning left and right.
2. Put a hardware access breakpoint on that address.
3. Turn again and inspect the instruction that uses it.
4. Look for an address calculation shaped like `[register + constant]`.

You may find an instruction shaped like this:

```nasm
movss xmm0, dword ptr [ecx+40h]
```

Read it as: “copy the 32-bit float located `0x40` bytes after the object in `ecx` into `xmm0`.” If the stopped yaw address is `0x12340040`, then `ecx` should be `0x12340000`.

Verify the arithmetic in the debugger:

```text
stopped field address - instruction offset = candidate object base
0x12340040 - 0x40                       = 0x12340000
```

One matching subtraction is a clue, not proof. Repeat it while turning, respawning, and starting a new match.

## The hidden `this` pointer

A C++ call such as `player.update()` looks as if it passes no player argument. A non-static member function still needs to know **which** player it should update. The compiler supplies a hidden argument called `this`.

For the 32-bit Microsoft C++ convention commonly called `__thiscall`, `this` usually arrives in `ecx`:

```nasm
mov ecx, esi        ; esi is the player-object base
call update_player
```

Inside the method, reads often use that same base register:

```nasm
mov eax, [ecx+338h] ; read one member from this player
test eax, eax
jne player_is_dead
```

On 64-bit Windows, the first integer or pointer argument normally arrives in `rcx`, so `this` is commonly in `rcx`. This is a calling-convention rule, not a promise that the compiler keeps the value in that register for the whole method. It may copy the pointer into `rbx`, `rsi`, or a stack slot.

The practical question is: **which value stays constant while several member offsets are read from it?** That value is a strong object-base candidate.

## Virtual methods leave a useful clue

A class can declare a method as `virtual`, allowing different object types to choose different implementations. Many C++ compilers implement this with:

- a **vtable**: a table containing function addresses;
- a **vptr**: a hidden pointer in each object that points to its vtable.

A 32-bit virtual call often has this general shape:

```nasm
mov eax, [ecx]      ; read the object's possible vptr
call dword ptr [eax+0Ch] ; call virtual slot 3
```

Do not label every first pointer a vptr. Test it:

1. The object field should point into a readable table, usually in a module's read-only data.
2. Several table entries should look like valid pointers.
3. Those entries should lead into executable sections.
4. Objects believed to share a class should usually share the same table pointer.
5. Breaking on one table entry should show a sensible method receiving the object as `this`.

This pattern is common, but the C++ language does not require one universal object layout. Link-time optimization, devirtualization, multiple inheritance, and custom engines can change the evidence.

## Inheritance makes the map less tidy

With single inheritance, the base-class part is often placed at the beginning of the derived object. A `BotPlayer` may therefore begin with all fields needed by `Player`, followed by bot-specific state.

Multiple inheritance can add more than one base subobject and more than one vptr. A method may even adjust `this` before using it. If two methods appear to use bases a fixed distance apart, do not immediately declare one of them wrong. You may be looking at two views of the same larger object.

RTTI, when present, can expose type-descriptor clues near virtual tables. Treat names found there as supporting evidence. Release builds can remove RTTI, and a readable name alone does not prove the full field layout.

## One object can have several useful identities

When inspecting object-oriented code, separate three questions:

1. **Allocation identity:** which complete block of memory was created and must
   eventually be released?
2. **Subobject view:** which base-class-shaped part does this particular pointer
   address?
3. **Dynamic type:** which most-derived implementation will virtual dispatch
   choose at this moment?

These answers can differ. A pointer passed to a base-class method may point a
few bytes into the complete allocation. A compiler-generated thunk may adjust
`this` before jumping to the real method. Subtracting every observed field from
that adjusted pointer can produce negative offsets and a broken layout even
though the pointer is valid for its particular base view.

When two candidate bases differ by the same small constant, record both views
and trace where the adjustment happens. Do not force them into one diagram
until constructor, destructor, and call-site evidence agree.

## Constructors and destructors reveal a timeline

A memory snapshot shows one state. Construction and destruction show how the
state came to exist and which parts belong together.

A constructor candidate often:

- receives a newly allocated or caller-provided object address;
- writes repeated default values at fixed offsets;
- calls base constructors before initializing derived fields;
- writes one or more vptr candidates, sometimes replacing an earlier base vptr;
- returns the same object or passes it into a registration system.

None of those clues proves “constructor” alone. An ordinary reset function can
also fill fields with defaults. Confidence rises when allocation, initialization,
base calls, vptr transitions, normal game creation, and later destruction form
one consistent timeline.

Destructors provide the other half: they reveal child cleanup, unregistering,
reference releases, pool returns, and the point after which a cached address is
stale. For a memory tool, this lifetime boundary matters more than recovering
the original C++ class name.

## Recover a structure as an experiment

Use this repeatable workflow rather than guessing from one memory window:

1. **Anchor one field.** Find a value with an obvious controlled behavior, such as yaw, health, or ammunition.
2. **Find code that uses it.** Break on access and record the base register plus displacement.
3. **Propose an object base.** Subtract the displacement from the known field address.
4. **Collect nearby candidates.** Observe adjacent aligned values as position, view, health, and state change.
5. **Compare instances.** Inspect the local player and several bots at the same offsets.
6. **Assign types carefully.** Check byte width, signedness, endianness, value range, and how instructions consume the field.
7. **Trace methods.** Look for repeated `this + offset` accesses and virtual calls.
8. **Test lifetimes.** Join, die, respawn, leave, and start a new match. Record when pointers become null or objects are replaced.
9. **Write confidence beside every field.** Mark it confirmed, likely, or unknown and state the experiment that would disprove it.

A useful notebook entry looks like this:

```text
+0x40  f32  yaw  CONFIRMED
Evidence: changes only with horizontal view; read by [ecx+40h]
Tested: local player + 4 bots, death/respawn, 3 clean launches

+0x48  ???? possible roll  LOW CONFIDENCE
Evidence: small float near view fields; no controlled change yet
Next test: spectate a rolling entity or trace all reads
```

That last line matters. A good reverse engineer records what would prove an idea wrong.

## Do not cast a remote address to a Rust reference

This is tempting but incorrect for an external tool:

```rust
// ❌ `remote_address` belongs to another process, not this Rust process.
let player = unsafe { &*(remote_address as *const Player) };
println!("{}", player.yaw);
```

Rust references promise that valid, correctly aligned local memory exists for a lifetime. A number copied from another process cannot keep those promises.

Copy each field through `ReadProcessMemory` instead:

```rust
// ✅ The process boundary and the fallible read remain visible.
let yaw = process.read_f32(player_base + 0x40)?;
```

Reading fields separately is also friendlier to an incomplete layout. You do not need to invent hundreds of padding bytes just to inspect three confirmed values.

## Build a read-only Rust object-layout probe

The lab implementation is [`windows-labs/src/bin/object_layout_probe.rs`](https://github.com/MustCodeAl/rust-game-hacking-book/blob/rustgamehackingreimagined/windows-labs/src/bin/object_layout_probe.rs). It opens `ac_client.exe` with read access only, follows the verified local-player and entity-list pointers, then copies the confirmed fields into local Rust snapshots.

The most important types are deliberately small:

```rust
use std::num::NonZeroUsize;

use anyhow::Context;

#[derive(Clone, Copy, Debug)]
struct ObjectAddress(NonZeroUsize);

#[derive(Clone, Copy, Debug)]
struct FieldOffset(usize);

impl ObjectAddress {
    fn new(value: usize) -> Option<Self> {
        // ✅ Once constructed, an ObjectAddress can never contain null.
        NonZeroUsize::new(value).map(Self)
    }

    fn field(self, offset: FieldOffset) -> anyhow::Result<usize> {
        self.0.get()
            .checked_add(offset.0)
            .context("object base + field offset overflowed")
    }
}

struct PlayerLayout;

impl PlayerLayout {
    const X: FieldOffset = FieldOffset(0x04);
    const Y: FieldOffset = FieldOffset(0x08);
    const Z: FieldOffset = FieldOffset(0x0C);
    const YAW: FieldOffset = FieldOffset(0x40);
    const PITCH: FieldOffset = FieldOffset(0x44);
    const NAME: FieldOffset = FieldOffset(0x225);
    const DEAD: FieldOffset = FieldOffset(0x338);
}
```

`ObjectAddress` and `FieldOffset` are both numbers underneath, but they mean
different things. The wrappers make it harder to accidentally treat a distance
as a complete address. `NonZeroUsize` also moves the null check into
construction. After `ObjectAddress::new` succeeds, every later function can
rely on that invariant instead of asking “is this zero?” again. This is what a
**strong type** does: it stores both a value and a rule about what that value is
allowed to mean.

The field reader performs bounded copies and plausibility checks:

```rust
fn read_player(process: &Process, player: ObjectAddress) -> anyhow::Result<PlayerSnapshot> {
    let position = [
        process.read_f32(player.field(PlayerLayout::X)?)?,
        process.read_f32(player.field(PlayerLayout::Y)?)?,
        process.read_f32(player.field(PlayerLayout::Z)?)?,
    ];
    let yaw = process.read_f32(player.field(PlayerLayout::YAW)?)?;
    let pitch = process.read_f32(player.field(PlayerLayout::PITCH)?)?;
    let dead_raw = process.read_u32(player.field(PlayerLayout::DEAD)?)?;

    anyhow::ensure!(
        position.iter().all(|value| value.is_finite() && value.abs() < 100_000.0),
        "implausible player coordinates"
    );
    anyhow::ensure!(yaw.is_finite() && pitch.is_finite(), "non-finite view angles");
    anyhow::ensure!(dead_raw <= 1, "unexpected dead flag {dead_raw}");

    Ok(PlayerSnapshot {
        address: player,
        name: read_name(process, player)?,
        position,
        yaw,
        pitch,
        dead: dead_raw != 0,
    })
}
```

Why validate values after a successful Windows read? Because “four bytes were copied” does not mean “our class model is correct.” A stale pointer can still lead to readable memory. Rejecting impossible coordinates and flags catches some wrong-object guesses early.

## Run the probe

Use 32-bit AssaultCube 1.2.0.2 on Windows and start a private local match with bots. From the repository root:

```powershell
cargo run --manifest-path windows-labs/Cargo.toml `
  --target i686-pc-windows-msvc `
  --bin object_layout_probe
```

The output is a set of local snapshots, not live Rust references:

```text
local      0x16f7a3c0 name="player" pos=(112.50, 86.25, 5.00) yaw=271.20 pitch=2.10 dead=false
entity[1]  0x17021480 name="bot_1" pos=(90.25, 74.00, 5.00) yaw=88.70 pitch=0.00 dead=false
```

Addresses and values will differ. The important checks are structural:

- every printed object has a different plausible base address;
- the same offsets produce the same *kind* of value for each object;
- names are bounded and readable;
- coordinates react to movement;
- view angles react to turning;
- the probe refuses a player count above 32;
- stopping the match produces a useful null-pointer error rather than a crash.

## Common false conclusions

**“Two nearby floats must be X and Y.”** They could be velocity, color, or a timer. Change one behavior at a time.

**“The first pointer proves a vtable.”** Follow several entries and verify they point to executable methods.

**“The debugger showed `ecx`, so it must always be `this`.”** Confirm the calling convention and watch how the method uses the value.

**“The structure worked once, so it is finished.”** Compare instances and repeat after object destruction, respawn, and clean launches.

**“A successful read proves the address is right.”** Windows can copy readable but unrelated bytes. Validate meaning, not only access.

## What you should be able to explain

Before moving on, explain these ideas without debugger vocabulary:

- an object base is the starting address of one instance;
- a field offset is the byte distance from that start;
- `this` tells a member function which instance it is handling;
- a vptr commonly connects an object to a table of virtual methods;
- padding and inheritance can create gaps or multiple object views;
- a recovered class is a versioned hypothesis supported by repeated experiments;
- a remote address is not a valid local Rust reference.

That mental model scales beyond games. Debuggers, crash analyzers, compatibility tools, profilers, and digital-forensics programs all recover structure from raw memory using the same evidence-first process.
