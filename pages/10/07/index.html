🪟 Lesson 10.7Processes, Handles & Threads

Follow a Windows API Call Down the Stack

Understand Win32, native APIs, system calls, user mode, kernel mode, exports, forwarded functions, and ASLR with a read-only address inspector.

About 28 minutes

One function call can cross several layers

Section titled “One function call can cross several layers”

A call to a Windows function such as VirtualQueryEx does not instantly jump into the deepest part of Windows. It usually passes through layers.

flowchart TD
    A["Application caller"] --> B["Documented Win32 contract"]
    B --> C["User-mode DLL implementation"]
    C --> D["Native service stub"]
    D --> E["System-call privilege gate"]
    E --> F["Kernel validates the request"]
    F --> G["Result returns to the caller"]

Use three separate ideas: contract, implementation path, and privilege transition. Win32 documents the contract application code may rely on. User-mode DLLs implement or forward that contract. A system-call instruction performs the controlled CPU transition for work that requires kernel privilege.

The boxes are software layers, not necessarily four separate processes. kernel32.dll and ntdll.dll are mapped into the same user-mode process as our program. Microsoft may change the implementation path while preserving the Win32 contract, which is why “calling a deeper layer” is usually less stable rather than more capable.

User mode and kernel mode are permission levels

Section titled “User mode and kernel mode are permission levels”

Most game code, application code, and Windows DLL code runs in user mode. A user-mode mistake should not be able to overwrite the kernel or another process merely by using a bad pointer.

The Windows kernel and drivers run in kernel mode, where code can manage page tables, devices, scheduling, and other system-wide resources. A bug there can affect the whole computer. That is why the course does not turn ordinary game experiments into kernel-driver experiments.

The CPU enforces this border. A system call changes privilege through a defined entry point; it is not a magic function name and it is not the same thing as calling a normal function.

This design is often described as limited direct execution. The game normally runs directly on the CPU for speed, but in user mode and inside its address-space rules. Timers and interrupts let Windows regain control for scheduling. A system call lets the game request a restricted operation through a validated entry path.

The model resolves a common confusion: Windows is not interpreting every ordinary game instruction. Most instructions execute natively. Hardware privilege, address translation, interrupts, and controlled entries provide the limits that let the OS remain in control.

Win32 is the documented application interface

Section titled “Win32 is the documented application interface”

The documented Win32 API is the part application developers are normally expected to call. Examples from this course include:

  • ReadProcessMemory for a read-only inspector with query-and-read rights;
  • VirtualQueryEx for page metadata;
  • CreateFileW for files and local named pipes;
  • CreateFileMappingW for a shared-memory object.

Microsoft can change how a supported function is implemented while keeping its documented behavior. On modern Windows, an export in kernel32.dll may forward to another DLL such as KernelBase.dll. Your source code still calls the stable Win32 name.

A forwarded export is not a jump instruction the loader inserts. The export table entry itself can hold a string such as KERNELBASE.CreateFileW in place of a code address. When GetProcAddress resolves that entry, it reads the string, locates the named DLL, and looks up the function there instead — following another forward if that entry also happens to be one. Whoever asked for kernel32!CreateFileW never sees this redirection; they get back a usable address in KernelBase.dll either way, which is exactly why Microsoft can move an implementation between DLLs across Windows versions without breaking the caller’s import:

flowchart LR
    A["GetProcAddress(kernel32,<br/>'CreateFileW')"] --> B["kernel32's export table entry:<br/>the string 'KERNELBASE.CreateFileW',<br/>not a code address"]
    B --> C["loader locates KernelBase.dll<br/>and looks up CreateFileW there"]
    C --> D["returns a usable address<br/>in KernelBase.dll"]

Native APIs sit closer to the system call

Section titled “Native APIs sit closer to the system call”

ntdll.dll exposes many functions whose names begin with Nt, such as NtQueryVirtualMemory. Some native functions are documented for limited uses and many are not stable application contracts.

This is the important rule:

“Closer to the kernel” does not mean “better for normal application code.”

Calling an undocumented entry point or copying a system-call number from one Windows build can make a tool fragile. Numbers and internal structures can change. The course resolves one native export so you can see the layer, but it deliberately does not call it or build a direct-syscall bypass.

DLL exports are names offered to other code

Section titled “DLL exports are names offered to other code”

A DLL can publish an export table. Each exported name maps to an entry that the loader can resolve. GetProcAddress asks a loaded module for one of those exports.

The returned address is a virtual address in the current process. Address Space Layout Randomization, or ASLR, means the same DLL can be mapped at a different base address in another process or after a reboot. Store the name or an RVA when that is the stable identity; do not paste a displayed absolute address into tomorrow’s program.

Build the address inspector

Section titled “Build the address inspector”

The lab gets handles to DLLs already loaded in its own process, resolves three names, and prints their process-local addresses. It never opens a game process and never calls the native function:

flowchart TD
    A["GetModuleHandleW('kernel32.dll')"] --> C["exported_address:<br/>VirtualQueryEx, ReadFile"]
    B["GetModuleHandleW('ntdll.dll')"] --> D["exported_address:<br/>NtQueryVirtualMemory"]
    C --> E["print layer, name,<br/>address in this run"]
    D --> E
Complete lab source: api_layers.rs

Why GetModuleHandleW instead of LoadLibraryW?

Section titled “Why GetModuleHandleW instead of LoadLibraryW?”

Both DLLs are already present in a normal Windows console process. GetModuleHandleW borrows their existing module handles; it does not request another load or add a loader reference that we would later need to release.

Why does GetProcAddress use an ASCII name?

Section titled “Why does GetProcAddress use an ASCII name?”

PE export names are byte strings. The s! macro creates a terminated static PCSTR. DLL file names use Windows wide strings, so GetModuleHandleW receives values from the w! macro instead.

The types make the two encodings visible instead of silently mixing them.

Run it and compare two launches

Section titled “Run it and compare two launches”

Run it again after restarting the virtual machine and compare the addresses. A difference is expected. The names and behavior are the meaningful pieces.

Then use module_inventory against wesnoth.exe, ac_client.exe, or Quake3-UrT.exe. You are looking at two sides of the same loader idea:

  • module_inventory shows which DLL images the game loaded;
  • api_layers shows how one process asks a loaded DLL for an exported name.

The complete program is api_layers.rs.

References: libraries and native-system-service entry points, using Nt and Zw routines, GetModuleHandleW, and GetProcAddress.

What happens conceptually when a user-mode API needs the Windows kernel to perform privileged work?

Win32 and native API layers prepare arguments before a processor-supported privilege transition reaches a kernel service. The boundary is controlled, not a shared address space.
