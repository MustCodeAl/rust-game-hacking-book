Lesson 4.6 — Automation as a Feedback Loop: cheatsheet

In a nutshell

  • A reliable bot closes the loop: sense, act once, then check the result before acting again. A sleep only limits the rate.

Another way to think about it

  • Think of a traffic light: it is red, amber or green, never two at once. An enum gives the bot's state the same one-at-a-time rule.

Check yourself

A: The current action, allowed next actions, and stop behavior become explicit and testable

  • Q: A simple bot presses a buy action whenever resources look high. What problem does that design have?

A: It could queue several buys before the first one shows up

In a Wyrmsun local match, a bot that presses Recruit whenever gold is high could queue several workers before the first purchase appears on screen. A useful macro needs to know whether it has requested an action, whether the game accepted it, and when to stop trying.

Find the action, then find what it requires

Section titled “Find the action, then find what it requires”

The offline Wyrmsun 5.0.1 debugger trace reaches a unit-creation call:

Do not call an internal function based on one breakpoint. Several normal calls, watched in the debugger, show its:

  • required thread;
  • argument meaning;
  • object lifetimes;
  • return or error signal;
  • resource checks;
  • cooldown or event requirements.

An action that works once under the debugger may fail when called at the wrong time.

Automation is a closed feedback loop

Section titled “Automation is a closed feedback loop”

An open-loop macro sends inputs and assumes they worked. A reliable test bot closes the loop by observing the result:

These stages have different jobs:

Stage Question
Sense What does the current snapshot report?
Validate Is it complete, current, and plausible?
Decide Which single action is allowed by the policy?
Act How is that one request sent through the validated adapter?
Confirm Did game state change in the expected way?
Correct Should the bot retry, choose another state, or stop?

The sleep between ticks only limits the rate. It does not prove success. Menus, animation locks, pauses, missed input, and object replacement can all make an action request produce no outcome. Keep “requested recruit” separate from “worker count increased,” and never treat the first as proof of the second.

TL;DR: A reliable bot closes the loop: sense, act once, then check the result before acting again. A sleep only limits the rate.

For testing, record snapshots and feed them through the decision function. The same sequence should produce the same decisions without launching the game.

Model states with an enum

Section titled “Model states with an enum”

The bot needs a state for each distinct obligation. Acting remembers that a recruitment was requested, Cooldown stores how long to wait after a confirmed action, and Recovering carries a reason for a failed one. A single enum value means the bot occupies only one of these states at a time.

Impossible combinations disappear. We cannot accidentally be both Acting and Cooldown.

Alternative: Think of a traffic light: it is red, amber or green, never two at once. An enum gives the bot’s state the same one-at-a-time rule.

Keep observations separate

Section titled “Keep observations separate”

The game snapshot below is a copy of facts the bot has validated, not the bot’s intention. next_state receives that copy, the current macro state, and a stop request. It chooses one next state without pressing a key or writing to the game. For example, Ready with at least 100 resources becomes Acting; it does not become Cooldown until a later snapshot confirms the action.

This transition function is safe, deterministic, and easy to test without a game.

Test the decision logic

Section titled “Test the decision logic”

Feed the transition function a ready, active snapshot with enough resources, then set stop to true. The expected result is Stopped, because a user stop must outrank a possible recruit action. The test pins that priority without launching Wyrmsun.

The low-level observation and action layers may be version-specific. The state machine should not be.

A reliable loop answers four questions

Section titled “A reliable loop answers four questions”

Before writing loop or while, state these four facts:

  1. Start: which state exists before the first tick?
  2. Continue: what must remain true for another tick to run?
  3. Progress: what changes so the loop does not repeat the same work forever?
  4. Stop: which event ends it, even if the game is paused or closes?

For this macro, the start is Waiting, each snapshot allows one transition, cooldown ticks count toward zero, and the shared stop request moves the machine to Stopped. A fixed sleep controls how often observations occur; it is not the thing that makes the logic correct.

Trace a few ticks before connecting the action adapter:

Current state Snapshot fact Next state Side effect
Waiting match and player ready Ready none
Ready resources are 120 Acting { attempt: 1 } request one action
Acting action confirmed Cooldown { ticks_left: 5 } none
any active state stop requested Stopped begin cleanup

If a row has two unrelated actions, the state probably owns too much work. If a row has no path to Stopped, the design is not safe to run yet.

Rate limits and stop behavior

Section titled “Rate limits and stop behavior”

Use a bounded tick rate, not a busy loop:

Before unloading an in-process library, set the stop flag, wait for the worker to exit, and restore any temporary state.

Narration: A worker thread still running when its library is unloaded would execute code that no longer exists, and the game would crash. Stopping it first avoids that.

This is the original course’s macro bot, rebuilt as an explicit state machine.

The original lab found these module-relative facts:

Purpose wyrmsun.exe offset
recruit-unit call target 0x2CF7
recruit-unit hook 0x223471
main-loop hook 0x385D34
main-loop call target 0xDBCA
gold-chain root 0x61A504

Wyrmsun relocates its module, so calculate module_base + offset every run. For one observed base of 0x00F40000, the recruit target became 0x00F42CF7 and the hook became 0x01163471.

The Cheat Engine gold path was:

Capture one legitimate worker record at the recruit hook (ecx points to the outer pointer) into a local 0x110-byte buffer. When gold is over 3000, copy that captured record back, put the expected pointer in ecx, and call the verified recruit function from the game-loop hook. The original three overwritten recruit instructions were push ecx, mov ecx, esi, and the call; replay all eight bytes before returning.

Build the DLL for the game’s 32-bit architecture, inject it into your offline match, recruit one worker normally to fill the buffer, then gather more than 3000 gold. Workers should begin recruiting automatically from the selected structure. If they do not, log the calculated module addresses and verify each original byte before allowing the hooks to install.

How the two Wyrmsun caves complete the action

What the state-machine design prevents

Section titled “What the state-machine design prevents”

The reusable skill is turning that working game hack into:

  • observable inputs;
  • named states;
  • guarded transitions;
  • a bounded action;
  • a reliable stop path.

That pattern applies to test bots, accessibility helpers, replay tools, and ordinary game AI.

Why model an offline macro as named states and guarded transitions?

A finite-state machine turns an implicit loop into inspectable rules. That makes timeouts, cancellation, and unexpected observations easier to handle safely.
