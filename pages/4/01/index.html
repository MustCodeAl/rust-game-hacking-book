♟️ Lesson 4.2Game State, Decisions, and Automation

From One Player to a Game-State Snapshot

See how one verified player layout becomes a bounded, typed snapshot of every side in a local match.

About 18 minutes

The engine owns and updates the match; our tool owns only the values it copies. A gold scan gives us one value for one player. In a strategy match, that is rarely enough: several sides may have the same gold while their identities and income differ. An observer has to turn verified fields into a useful view of the whole match without pretending it owns the game’s changing state.

The remaining lessons grow that observer into a model of game behavior. Snapshots and tile grids explain what the world contains; coordinates describe where it is; feedback, paths, and events explain how a tool reacts. A bounded recorder makes observations useful over time. Finally, an NPC shows how the game itself senses and chooses.

What an observer does

Section titled “What an observer does”

An observer reads state and presents it without trying to become the game’s state owner. It separates three layers:

The remote process may change immediately after the read. PlayerSnapshot is therefore a copy of the values at one moment, not a live reference into Wesnoth. This distinction keeps the rest of the program safe and makes timestamps and failed reads honest.

Note

📸 Snapshot idea: a snapshot is a photograph, not a live window. It records what the remote process looked like at one moment and may be stale a moment later.

A useful observer also has a sampling rate. Reading once per second answers strategy-level questions such as gold and income. Reading thousands of times per second adds overhead without making those slow values more truthful.

From one player to a collection

Section titled “From one player to a collection”

We already traced one player’s gold. Strategy games usually store several similar player records in an array, vector, or table.

An array places fixed-size records next to one another. A table may instead contain pointers to separately allocated records. The address pattern tells them apart:

For an illustrative inline table starting at 0x1000 with 32-byte records, player index 2 begins at 0x1040: two strides of 0x20 bytes after the base. In a pointer table, that same calculation locates a pointer slot; reading the slot gives the record address. The two layouts require different read steps.

The inline formula applies only once the debugger shows a consistent stride between real players.

The goal is not to guess a distance and hope. We will use two known players and the debugger to learn how the game indexes them.

Observe the income loop

Section titled “Observe the income loop”

Set a breakpoint on the gold update used at the end of a turn. Each time the instruction runs, read the object pointer it uses.

If the function loops through players, the object pointer should change while the instruction stays the same. Nearby 32-bit x86 instructions may calculate an index in this shape:

That pair is the collection indexing introduced in Lesson 1.3 and the scaled-offset formula examined in Lesson 3.6, written as two instructions. The three-operand imul multiplies the index in edx by a constant and puts the result in eax; the add then moves that distance from the table’s start. This is an illustrative shape, not a claimed byte-for-byte Wesnoth listing.

The constant is the useful part. You do not have to infer the record size by finding two players and subtracting their addresses — the instruction states it, because the compiler had to know the stride to generate this code at all. Read it off, then confirm it against two real players rather than trusting a single instruction.

This suggests:

Two known players confirm it: their record addresses should differ by exactly one record size. That difference gives the stride, not yet the complete layout of a record.

Model only confirmed fields

Section titled “Model only confirmed fields”

Do not cast an unknown memory range to a giant struct. Read confirmed fields by offset into a snapshot:

PlayerSnapshot owns copied values. It does not pretend that remote memory is a safe local reference.

The layout object keeps the offsets apart from the values read through them. gold: 4 means “gold sits four bytes from each record’s base in this build.” Storing the number does not make it true; range checks and behavior tests decide whether it still holds for this exact build.

Read until the model says stop

Section titled “Read until the model says stop”

Find the player count or another verified boundary. Never scan player records forever.

Compare that with silently skipping records that fail:

Why this version?

A missing row means a bad layout, a changing process, or an unreadable record, not that the player does not exist. Collecting Result stops at the first untrusted row, so the dashboard never presents a partial table as complete. The count cap also prevents a corrupted count from turning one bad read into thousands of reads.

collect() stops on the first error and returns it with no half-trusted table.

Print a useful dashboard

Section titled “Print a useful dashboard”

Once read_players has returned validated snapshots, display one line per side. The loop uses each snapshot’s slot, gold, and signed income; {:+} shows whether income adds to or drains gold. A failed read ends with an error before the dashboard can present a partial set as complete.

Refresh slowly—once or twice per second is enough for a learning tool. Constant reads waste CPU and make failures harder to follow.

Validate the snapshot

Section titled “Validate the snapshot”

For each field:

  1. observe it in the game;
  2. read it from the tool;
  3. change it through normal gameplay;
  4. confirm the tool follows;
  5. restart and re-resolve the table.

If one player has impossible values, stop and revisit the table base, record size, count, or offsets.

The key upgrade is conceptual: instead of “address plus magic number,” we now have a named layout, checked math, a bounded collection, and owned snapshots.

Knowledge check

Calculate a record field

Saved

Player records are 0x270 bytes apart and gold is at offset 0x04. What offset from the table base reaches the third player's gold? Use hexadecimal.

The third player has zero-based index 2. First find the record: 2 × 0x270 = 0x4E0. Then add the gold field: 0x4E0 + 0x04 = 0x4E4. Keeping stride math separate from field math makes the layout easier to verify.

Knowledge check

Observe before deciding

Saved

Why should a strategy-game observer build one validated snapshot before running rules?

Collection and validation belong in one layer; strategy can then work with meaningful bounded data.
