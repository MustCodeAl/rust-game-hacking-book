Lesson 4.11 — Sampling Game State Under Load: cheatsheet

In a nutshell

  • Split recording in two: a fast sampler captures facts, and a separate writer saves them, so a slow disk never stalls the game.

Another way to think about it

  • Think of a tap over a sink: if water arrives faster than the drain empties, you slow the tap, spill some, or stop. A full queue forces that choice.

Check yourself

  • Q: What should a debugger copy into an asynchronous telemetry event?

A: Small owned values such as timestamps, thread IDs, and relative addresses

  • Q: A debugger call logger's file writer cannot keep up, and the bounded queue is full. Which policy best protects the paused target while keeping the loss visible?

A: Send without blocking, bump a dropped counter, and stop if loss passes a limit

  • Q: What is backpressure in a recording tool?

A: The choice a system makes when samples arrive faster than storage

  • Q: Why does the pipeline split capture from storage?

Once repeated polls have become meaningful events, we may want a record of them. A log can answer when gold changed or whether an action timed out, but recording must not hold up the game or disguise samples it failed to capture. When samples arrive faster than they can be stored, the writer creates backpressure. A bounded queue makes us choose explicitly what happens when it fills.

The recorder must not stall the game

Section titled “The recorder must not stall the game”

A call logger, frame observer, or value recorder has two jobs with different timing needs:

  1. capture a small fact while it is fresh;
  2. format and store that fact somewhere durable.

Writing a file can pause for filesystem, antivirus, indexing, or device activity. If the same thread is also handling a debugger event or time-sensitive sample, one slow write can disturb the program being measured.

A telemetry pipeline separates those jobs:

The producer never waits for disk. The consumer owns the file.

TL;DR: Split recording in two: a fast sampler captures facts, and a separate writer saves them, so a slow disk never stalls the game.

Record overload and failure instead of hiding them

Section titled “Record overload and failure instead of hiding them”

A fault is one thing going wrong: the disk pauses, a queue fills, the target closes, or the writer thread exits. A failure is the recorder breaking its promise to the learner—for example, inventing continuous data after samples were lost or labeling an incomplete file as clean.

The design cannot prevent every fault. It can keep each one from becoming a misleading result:

Fault during a run Honest recorder response
queue reaches 128 events apply the declared drop policy and increment dropped
writer disconnects stop recording and return an error
target memory becomes unreadable mark the run incomplete; never repeat the last value as if it were new
an older reader sees a new schema reject the unknown version or use a reader written for it
shutdown begins close producers, drain accepted events, flush, join the writer, and report counts

This is why the current recorder counts dropped samples and versions its file. A durable clean-shutdown marker is the next extension described below. These facts let a later graph distinguish “gold stayed at 100” from “the tool stopped observing for two seconds.” 📉

Backpressure is a policy

Section titled “Backpressure is a policy”

The channel has fixed capacity:

A normal blocking send would wait when all 128 slots are occupied. The producer uses try_send instead:

The match below implements those outcomes: accepted events keep sampling, a full queue increments a visible loss count, and a dead writer stops the recorder. With a full queue, try_send returns immediately instead of waiting while the observed game runs.

Dropping an event sounds bad, but silently pausing every target thread can be worse. The important rule is make loss visible. The final report prints both written and dropped counts.

Picture the queue as 128 numbered spaces between the sampler and the writer. Suppose the writer stalls while 127 spaces are occupied. The next sample takes space 128. Another sample arrives before the writer removes anything, so try_send returns Full; the sampler increments dropped to 1 and continues. When the writer resumes and removes one event, a later sample can enter again. The queue absorbed a short delay, but it did not make the disk faster or keep every sample. In the finished log, the count of one dropped event warns that the measured timeline has a gap even if the surrounding gold values look flat.

Different tools can choose different policies:

Tool Sensible full-queue policy
Five-second call logger Drop and count; stop if loss exceeds a threshold
Turn-by-turn strategy log Block briefly or stop because every event matters
High-rate overlay metrics Keep only the newest sample
Crash report Flush synchronously because the process is already failing

Backpressure is not one library call. It is the decision a system makes when producers outrun consumers.

Alternative: Think of a tap over a sink: if water arrives faster than the drain empties, you slow the tap, spill some, or stop. A full queue forces that choice.

Let channel closure be the stop message

Section titled “Let channel closure be the stop message”

The sink owns an optional sender and writer thread. Finishing removes the final sender:

The receiver’s loop ends naturally when the channel is disconnected and empty. No special “stop event” can become stuck behind normal events in a full queue.

The writer then flushes BufWriter, returns the count, and joins. This ordering proves that a successful finish means all accepted events reached the operating-system file interface.

That promise is deliberately narrow. BufWriter::flush sends buffered bytes to the file object, but it is not a guarantee that every storage device could survive an immediate power loss. A short course telemetry run needs honest completion and visible loss; a crash-resilient journal would need a stronger, explicit durability design.

Narration: Flushing hands bytes to the operating system, not to the disk platter. After a sudden power cut, the last few lines of a log can still be missing.

Drop repeats the close-and-join path as a fallback. Explicit finish is still better because it returns errors and counts to main.

The version explains the schema. The target line records run-specific context. For a Wesnoth telemetry file you want to compare across several launches, also record:

  • executable SHA-256;

  • module base;
  • sampling period;

  • wall-clock start in UTC;

Do not silently reinterpret old columns after a format change. Create v2.

Design an explicit end record for a later format

Section titled “Design an explicit end record for a later format”

The linked gold_telemetry.rs writes a v1 header and detail rows, then prints written and dropped counts to the console. It does not yet write a trailer. If the file itself must prove how a run ended, extend it to v2 with three parts:

  1. the header says how to interpret the run;
  2. the detail rows contain repeated observations;
  3. the trailer says how the run ended.

Sampling is an observation, not perfect time

Section titled “Sampling is an observation, not perfect time”

The loop sleeps for 50 ms, which aims for about 20 samples per second. Desktop scheduling is not a metronome. The code records Instant::elapsed() for each sample instead of assuming sample 20 happened at exactly one second.

The tool opens Wesnoth without write rights, resolves the verified pointer path once, and records for 1–300 seconds. If the match ends and the address becomes unreadable, the run returns an error instead of fabricating a value.

For a longer recorder, re-resolve and validate the object identity periodically rather than trusting one pointer forever.

Connect this design to the call logger

Section titled “Connect this design to the call logger”

The call logger already knows the time-sensitive facts while Windows holds a debug event. Its advanced path should:

  1. copy registers and module-relative addresses into a compact CallEvent;
  2. restore/re-arm the breakpoint;
  3. call try_send;
  4. continue the debug event;
  5. let the writer format symbols and text later.

Never send a borrowed DEBUG_EVENT union member to the writer. Its validity belongs to the current event-handling scope. Copy only the fields whose meaning has already been checked.

Test the pipeline without a game

Section titled “Test the pipeline without a game”

A useful test can start a queue of capacity one, hold the receiver, and send three events:

  • the first is accepted;
  • later events become counted drops;
  • the producer does not block;
  • dropping the sender lets the receiver finish;
  • the written count plus dropped count equals the attempted count.

Also simulate a writer that exits early. Disconnected must become an error rather than another drop.

What the recording can claim

Section titled “What the recording can claim”

Each event owns a copy of the facts it needs; it cannot keep a borrowed debug-event buffer or process handle alive by accident. A full bounded queue means producers outran the writer, so the written and dropped counts both belong in the result. Dropping the last sender lets the writer drain accepted events and end cleanly. Each event carries a measured timestamp because a sample number alone cannot reveal delays or gaps in observation.
