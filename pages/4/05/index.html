Lesson 4.8 — From Coordinates to Target Selection: cheatsheet

In a nutshell

  • Treat a position as an observation you refresh, not a fact you keep. Choose a target from fresh, validated numbers every time.

Another way to think about it

  • Picture drawing a circle around the player and growing it until it first touches an enemy. That enemy is the nearest one.

Formulas and patterns

observe -> estimate state -> choose an intent -> act -> observe again

Check yourself

  • Q: Why should a coordinate bot first copy game data into a validated snapshot?

A: Decision logic can work from one bounded, internally consistent model

  • Q: When searching memory for a character's position, why move in just one direction at a time at first?

A: A single-axis change shows which candidates follow that axis

  • Q: How should you test whether a memory address holds a position by writing a value to it?

  • Q: The player's position offset has been confirmed. What should you do for an enemy object?

Made from the lesson text by Game Hacking Academy. Add your own notes below.

Coordinates give a position meaning, and subtracting two positions gives the direction and distance between them. Now we can use those ideas to choose an action in a moving game. The earlier Wyrmsun macro reacted to a discrete result: a unit was recruited or it was not. In Flare, an enemy keeps moving. A fixed instruction such as “hold right for one second” can be correct at the start and wrong a moment later. Position becomes an observation the bot must refresh before choosing its next action.

Begin with coordinates you can control

Section titled “Begin with coordinates you can control”

Use Flare 1.12 in an offline test area. Stand at an easy location, move only left and right, and scan for a changing floating-point value.

Then hold the first coordinate steady and move only up and down. Two independent experiments help distinguish x from y.

Validate each candidate at several positions. Teleporting a candidate a tiny distance in a disposable lab can confirm it, but restore the original value immediately.

Find related objects

Section titled “Find related objects”

Once the player position is known, inspect nearby fields and the code that reads them. Repeat the same process for:

  • one enemy position;
  • the current cursor or destination position;
  • an “is alive” or active flag.

Do not assume every object shares the same layout. Confirm offsets separately.

Copy memory into snapshots

Section titled “Copy memory into snapshots”

Copy each confirmed position into a small Vec2 value, then group the player, enemies, and cursor in one WorldSnapshot. This is the input to decision logic: the bot works from local values captured together and does not keep a remote pointer alive while it chooses what to do.

The bot should make decisions from owned snapshots. It should not hold long-lived raw pointers into game memory.

Automation is a feedback loop

Section titled “Automation is a feedback loop”

A useful bot repeats four jobs:

The action does not prove success. Movement may be blocked, the target may disappear, or the snapshot may already be stale. After every request, wait for a specific observation that confirms or rejects it before choosing the next action.

Keep time in the model. Store when the snapshot was captured, when the action was requested, and how long confirmation remains valid. A perfect position from half a second ago can be worse than a slightly noisy current position.

TL;DR: Treat a position as an observation you refresh, not a fact you keep. Choose a target from fresh, validated numbers every time.

Reject impossible floats:

NaN and infinity can poison comparisons, so is_finite matters.

Range checks prove only that a coordinate is plausible, not that it belongs to the intended object. Combine them with identity, active/alive flags, expected movement continuity, and repeated reads.

Narration: A stale pointer can still give a number that looks fine. Range checks are cheap, but identity checks and repeated reads catch the wrong-object case.

Choose a target

Section titled “Choose a target”

Given a player at (0, 0) and enemies at (3, 4) and (1, 0), the nearest valid target is (1, 0). The function below first discards implausible coordinates, then compares distance for the survivors. An empty or entirely invalid enemy list returns None rather than inventing a target.

This decision code has no raw memory access and can be unit-tested with made-up coordinates.

Alternative: Picture drawing a circle around the player and growing it until it first touches an enemy. That enemy is the nearest one.

Choosing the nearest valid enemy. This step-by-step trace needs JavaScript. Here is the code and where the run ends.

let mut best = None;
let mut best_d = f32::MAX;
for e in enemies {
    if !e.is_reasonable() { continue; }
    let d = player.distance_to(e);
    if d < best_d { best = Some(e); best_d = d; }
}
best

The loop is over, so the answer is Some((1, 0)), the enemy 1 unit away. Only coordinates that passed the check were ever compared.

Final values: enemies = (3, 4) (1, 0); best = Some((1, 0)); best_d = 1; e = (1, 0); is_reasonable = true; d = 1.

Separate decision from action

Section titled “Separate decision from action”

decide turns a snapshot into an intent, never an input event. An invalid player position means Stop; no valid enemy means Wait; otherwise the nearest enemy becomes MoveTo(position). The platform-specific action layer can later decide how to carry out that intent.

The action layer may simulate a click in the local test or call a verified in-game function. The decision layer should not know how that happens.

Add guardrails

Section titled “Add guardrails”

Stop when:

  • the match or level is no longer active;
  • any base pointer becomes null;
  • coordinates are non-finite or out of bounds;
  • the player has not moved after several attempts;
  • the user requests stop;
  • the target version check fails.

Create snapshots in unit tests:

The most valuable bot code—geometry, state, timing, and failure handling—does not need unsafe and does not need the target running.

Wire it to Flare 1.12 after the DLL lessons

Section titled “Wire it to Flare 1.12 after the DLL lessons”
Windows VM

The snapshot, target selection, and tests above require no injected library. The following pinned Flare implementation uses the verified detour and DLL lifecycle developed in Lesson 6.4. Read it now as a worked mapping from three observed positions to an action, then run it after that boundary has been taught.

This is the original course’s farming bot: it walks toward a nearby enemy and attacks while a key is held.

The original 32-bit lab identified three calls. Their absolute addresses came from a run where flare.exe loaded at 0x00830000; use module-relative offsets in the injected DLL because the base can move.

Capture Observed call Hook offset Original target offset
mouse 0x0091CBC8 0xECBC8 0x54210
player 0x0083CAC4 0xCAC4 0x20840
shared entity loop 0x0089BA94 0x6BA94 0x6B180

At those sites, the useful fields are:

  • mouse X/Y: [ebp + 0x664] and [ebp + 0x668];
  • player X/Y: [ecx + 0x240] and [ecx + 0x244];
  • current entity X/Y: [ebx - 4] and [ebx].

Store the captured addresses as atomics or copy the values into an owned snapshot. Do not let the worker hold a pointer while a hook is changing it. The historical action loop used screen positions 490/560 for left/right and 270/330 for up/down, then sent a left-button input while the M key was held:

These cursor numbers depend on the window size and UI scale. Confirm them by hovering the four attack directions and watching the captured mouse fields. In an enemy area, hold M: the player should run toward the moving enemy and attack when close. Releasing M must stop the bot immediately. On unload, stop the worker first and restore all three original five-byte calls.
