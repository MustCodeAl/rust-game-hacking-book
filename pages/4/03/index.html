Formulas and patterns

index = y × width + x

Check yourself

  • Q: A row-major visibility map is width tiles wide. Which formula finds tile (x, y) in a flat array?

A: y × width + x

  • Q: A map is 4 columns wide and 3 rows tall, stored row by row. What flat index does tile (x = 1, y = 2) have?

A: 9, since 2 x 4 + 1 = 9

  • Q: A map is 4 tiles wide and 3 tall, and tile (4, 1) is requested. Why must code check x against the width before computing an index?

A: Without it, (4, 1) silently lands on tile (0, 2), another tile

  • Q: Why use checked multiplication when working out y times the width for an index from untrusted dimensions?

A: Absurd dimensions could overflow and wrap into a small, wrong index

Made from the lesson text by Game Hacking Academy. Add your own notes below.

A player record is one object. A map asks the same memory question thousands of times: which tile is this, and what does this player know about it? In a Wesnoth match, terrain and visibility may describe the same location but live in different layers of state. Coordinates give us a way to relate them.

Make the conversion checked so an invalid tile cannot silently wrap:

On a three-column, two-row map, tile (2, 1) becomes index 1 × 3 + 2 = 5. Tile (3, 1) is outside the map and returns None. The checked multiplication also refuses dimensions so large that the index would overflow usize.

TL;DR: A flat list can hold a grid: a tile’s index is its row times the width plus its column. Check the bounds before you use it.

Never trust coordinates from remote memory until they pass bounds checks.

A grid needs a coordinate contract

Section titled “A grid needs a coordinate contract”

The formula only works after you know what x, y, width, and the base address mean. Games may store rows from top to bottom or bottom to top, pad each row, split terrain and visibility into separate layers, or keep one visibility layer per team.

For a candidate grid, recover these facts separately:

  • origin: which tile is (0, 0);
  • axis direction: which way increasing x and y move;
  • stride: how many elements or bytes separate two rows;
  • element width: how many bytes represent one tile;
  • layer: terrain, occupancy, visibility, or another property;
  • owner: global map state or one player’s derived view.

If the row stride includes padding, y * width + x is wrong even when the first row looks perfect. The byte address becomes base + y * row_stride + x * element_size. Verify it with tiles on different rows and near both edges of the map.

Visibility is often a derived view of terrain, units, teams, and line-of-sight rules. A cached visibility layer can be useful to read without being the source of truth, because the game rebuilds it from those inputs. What matters is which system recomputes it and when.

Alternative: Think of fog as a sheet of tracing paper over the map: the terrain underneath is shared, but each player has their own sheet showing what they have seen.

Find one known tile

Section titled “Find one known tile”

In an offline Wesnoth match, compare a currently visible tile with a tile hidden by fog. Search for the observed visibility value, reveal or hide the tile through normal gameplay, and filter again.

Repeat with several tiles. You are testing whether candidates belong to:

  • one tile;
  • one row;
  • one player’s visibility layer;
  • a cached drawing value;
  • the authoritative map state.

Break on a normal update

Section titled “Break on a normal update”

Set a write breakpoint on a confirmed tile and move a unit so visibility updates.

Look for:

  • a base pointer to map data;
  • row or column math;
  • a player or team index;
  • the value written for hidden, explored, and visible states.

Do not assume a value such as 0xFFFF_FFFF means “visible.” It may mean -1, a bit mask, or an uninitialized sentinel. Collect examples for every state you name.

Model visibility as states

Section titled “Model visibility as states”

Suppose repeated observations show 0 for hidden tiles, 1 for explored tiles, and 2 for visible tiles in this exact build. Decode those raw values into named states so later code cannot confuse visibility with terrain. Keep every other number as Unknown until it has been investigated.

Keep Unknown. Silently treating a new value as visible would hide the fact that the byte has a state the model does not know about.

Narration: A value you did not expect is information: it may be a state you have not met yet. Keeping Unknown makes the surprise visible instead of hiding it.

Read a bounded layer

Section titled “Read a bounded layer”

Give the reader a verified layer base and map dimensions. It first checks width × height, caps the tile count, copies four bytes per tile from the game process, then decodes each copied u32 with the mapping above. The result is an owned vector of visibility states, not a pointer into live game memory.

The unwrap is safe here because chunks_exact(4) guarantees every chunk has four bytes, but an explicit conversion helper can make that invariant clearer in shared code.

Reproduce the original Wesnoth map patch

Section titled “Reproduce the original Wesnoth map patch”

The original course called this exercise the map hack.

For Wesnoth 1.14.9, the write-breakpoint trail leads to 0x006CD519. The original eight-byte sequence updates a visibility column.

This build does not store one u32 per tile the way the model earlier in this lesson does. It packs 32 tiles into a single 32-bit column, one bit per tile, so the instructions below are bit-level field assignment rather than the y * width + x array indexing shown above. mov eax, ebp then shl eax, cl builds a single set bit, shifted into the position cl names — the bit that belongs to one specific tile in that column. not eax flips every bit, which turns that into a mask that is 0 at the tile’s position and 1 everywhere else. and dword ptr [esi], eax applies the mask to the stored column, clearing only that one tile’s visibility bit while leaving the other 31 alone.
