🦀 Lesson 3.8Types, Object Layouts, and Boundaries

How Text Becomes Bytes in a Game

Trace visible text to bytes, understand encodings and terminators, and build checked strings at FFI boundaries.

Read or listenPrint chapter or book
About 16 minutes

Text is bytes plus an agreement

Section titled “Text is bytes plus an agreement”

The screen may show “Ford,” but memory stores bytes. An encoding explains how bytes represent characters.

Common forms include:

  • UTF-8—used by String and str;
  • UTF-16—many Windows “wide” APIs (Reference: Microsoft's guide to strings in Windows programs explains wide characters, the A and W versions of an API, and Unicode.);
  • older single-byte encodings;
  • null-terminated C strings.

Keep four layers separate:

  1. a character is the human idea, such as é;
  2. a code point is the Unicode number assigned to that character idea;
  3. a code unit is one storage unit used by an encoding, such as u8 for UTF-8 or u16 for UTF-16;
  4. the bytes are the actual memory representation, with byte order relevant for multi-byte code units.

One visible character can use several code units. That is why byte count, UTF-16 unit count, Unicode scalar count, and what a reader sees on screen are not interchangeable lengths. Four short examples show every column coming apart:

The last row is e followed by a combining acute accent, which displays as a single é but is two separate scalars. The practical consequence: a buffer sized from “the name is at most 16 characters” can be far too small, and code that truncates a string at a fixed byte count can cut a character in half and produce bytes that no longer decode. Always say which of these four lengths a number refers to.

Locate a known string

Section titled “Locate a known string”

In the offline Wesnoth target, open a terrain description and search memory for one distinctive phrase using the appropriate text encoding (Tip: In Cheat Engine, choose the scan type Search for text. Tick UTF-16 to find text stored as two-byte units, and leave it unticked to find one-byte text. Try both if one finds nothing.).

Change the selected tile and repeat. A static label may stay at one address, while a formatted output buffer changes.

Set a read breakpoint on the first byte of a promising string, trigger the description, and inspect the code that consumes its address.

Follow the pointer in the dump and identify:

  • where the string begins;
  • where it ends;
  • whether a zero terminator follows it;
  • which encoding makes the bytes readable;
  • whether the memory is static or temporary.

Endianness is not encoding

Section titled “Endianness is not encoding”

Endianness controls byte order inside multi-byte numbers. Encoding controls how bytes represent text. They are different ideas.

For copied bytes 41 00 00 00, the caller first finds the two-byte zero terminator and passes the preceding 41 00 slice. The function rebuilds 0x0041 as one UTF-16 unit and returns Ok("A"). Passing an odd number of bytes returns an error instead of silently dropping the last byte.

Use CString for C boundaries

Section titled “Use CString for C boundaries”

Many C-style functions expect a zero byte at the end:

CString adds the terminator and rejects an interior \0, which would make a C function think the string ended early.

Keep the CString alive for as long as the foreign function may use pointer. Returning as_ptr() from a function after the CString is dropped creates a dangling pointer.

Also determine whether the foreign function copies the text during the call or stores the pointer for later. “The call returned” ends the borrow only in the first case. Ownership and lifetime are part of the string contract just as much as encoding and termination.

Observe a print function

Section titled “Observe a print function”

The debugger may reveal a call that receives a string pointer and screen or layout information. Calling it yourself requires knowing its:

  • calling convention;
  • parameter order and types;
  • ownership of the string;
  • required thread;
  • lifetime of any returned or stored pointer.

Do not guess a signature from one register. Collect several calls with different strings and compare them.

Trace a real text call before changing it

Section titled “Trace a real text call before changing it”

On the Den of Onis map in offline Wesnoth 1.14.9, right-click a Ford tile and open Terrain Description. Search for a distinctive part of its text, then set a read breakpoint on a confirmed byte and open the description again. In the book’s run, the live string began at 0x10CE996B. Stepping out reached the print path at 0x005ED114: edx led to the text object and the call at 0x005ED129 printed it.

At this point, answer the text questions: which bytes were read, where does the string end, who owns its buffer, and does the print call keep the pointer? The breakpoint and the changing description provide the evidence. They do not require an injected DLL.

Prefer an overlay for new UI

Section titled “Prefer an overlay for new UI”

Calling an undocumented internal print routine can be fragile. For new tool UI, a separate overlay or console is often easier to version, test, and remove.

Use an internal function only when the lesson is specifically about understanding that function and the target profile is exact.

Keep the text contract together

Section titled “Keep the text contract together”

The bytes of a string need an encoding before they become text. UTF-16LE often has a zero high byte for an ASCII-range letter; that byte alone does not end the string. A C-style terminator marks the end of the encoded sequence, and CString owns a terminated buffer while rejecting interior zeros. The pointer passed to a print function is useful only while that buffer remains alive, so tracing a text call means checking both its bytes and its lifetime. That is one part of a larger function contract: the caller and callee must also agree on argument positions, return values, and ownership. What a DLL Function Promises Its Caller reconstructs those promises later, before the in-process DLL labs.

We can now interpret a game’s primitive values, objects, collections, and text without confusing their representation with their meaning. The next chapter asks how those pieces form a changing world.
