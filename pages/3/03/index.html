Lesson 3.4 — How C++ Objects Appear in Memory: cheatsheet

In a nutshell

  • An object has one base address, and each field sits a fixed distance from it. Many objects can share the same offsets.
  • Constructors show how an object comes to exist, and destructors show when old addresses stop being safe to trust.

Another way to think about it

  • Think of parking bays marked in sets of four: a bigger car skips ahead to the next set, leaving empty bays. Padding is those empty bays inside an object.

Key terms

  • not: The compiler does not normally copy that neat declaration into the finished .exe.
  • AssaultCube 1.2.0.2 32-bit Windows: This lesson uses AssaultCube 1.2.0.2 32-bit Windows in a local bot match.
  • offset is a distance: An offset is a distance, not an address by itself.
  • Unknown means unproven: Unknown means unproven, not empty.
  • which: A non-static member function still needs to know which player it should update.
  • stack: Each thread has a stack region for return addresses and temporary call data.
  • stack frame: Calling another function claims a new stack frame; returning releases that frame.
  • vtable: - a vtable: a table containing function addresses; - a vptr: a hidden pointer in each object that points to its vtable.
  • vptr: - a vtable: a table containing function addresses; - a vptr: a hidden pointer in each object that points to its vtable.
  • RTTI: RTTI stands for run-time type information: extra data the compiler emits so that code can ask what class an object really is while the program is running.

Formulas and patterns

object base + field offset = field address
0x12340000 + 0x40        = 0x12340040
stopped field address - instruction offset = candidate object base
0x12340040 - 0x40                       = 0x12340000
ecx                  =  0x1234_0000    the object
read [ecx]           -> 0x00A1_B200    the vtable this object uses
0x00A1_B200 + 0x0C   =  0x00A1_B20C    the slot being called
read [0x00A1_B20C]   -> 0x004C_7710    the function that finally runs

Check yourself

  • Q: A player object begins at 0x12340000, and a method reads yaw from [ecx+0x40] while ecx holds that object. Which address contains yaw?

A: 0x12340040, the object base plus the 0x40 offset

  • Q: A reverse engineer sees one decoded instruction reading four bytes. What does that evidence establish?

A: That the code touches those bytes; their meaning needs more evidence

  • Q: An offset believed to be one particular field turns out to be wrong. What follows for conclusions built on it?

A: Conclusions about the object and class that depended on it must be rechecked

  • Q: Which term names one real player, weapon or entity created from the recipe in the source code?

A: An object, also called an instance

The source code is gone, but the layout remains

Section titled “The source code is gone, but the layout remains”

Imagine that a game originally contained this C++ class:

The compiler does not normally copy that neat declaration into the finished .exe. Names such as Player, position, and update may disappear. The running program still needs a repeatable arrangement of bytes, though. It must know where each player’s position begins, where the name lives, and which function to call.

Reversing a class means rebuilding a description of that arrangement from what the running program does. It does not restore the original source; it produces a layout that matches the machine code and the program’s behavior. 🧠

This lesson uses AssaultCube 1.2.0.2 32-bit Windows in a local bot match. Offsets are version-specific. A different build may have a different layout.

From changing bytes to a class

Section titled “From changing bytes to a class”

Recovering a class works upward through several levels, and each level is shown by a different technique:

Level Example What shows it
Bytes Four bytes at this address changed. Reading the memory before and after.
Instruction movss read those four bytes. Decoded machine code.
Data flow The value reaches the view-angle calculation. Register and memory tracing.
Field Offset +0x40 behaves like yaw. Controlled turns across many instances.
Object Several fields share one stable base address. Repeated base + offset accesses.
Class behavior Objects sharing one table dispatch related methods. Checked indirect calls and object lifetimes.
Game meaning This is the active player entity. Behavior, call context, and lifecycle tests.

Each level rests on the ones below it. If +0x40 turns out not to be yaw, the object and class levels built on that field have to be checked again, which is why a jump from “bytes changed” straight to “this is a Player class” is so easy to get wrong.

Word Plain-English meaning

Object or instance One real player, weapon, or entity created from that recipe.
Field or member One piece of data inside an object, such as health or yaw.
Method A function that operates on an object.
Structure layout The byte distance, size, type, and alignment of each field.

What an object looks like in memory

Section titled “What an object looks like in memory”

For the course build of AssaultCube, our recovered player model contains these useful landmarks:

Offset from player base Candidate field How to test it
+0x04 X position (f32) Move east/west and watch a smooth finite value change.
+0x08 Y position (f32) Move north/south while X stays mostly steady.
+0x0C Z position (f32) Jump or change elevation.
+0x40 Yaw (f32) Turn left/right; expect an angle-like value.
+0x44 Pitch (f32) Look up/down.
+0x225 Name bytes Compare several bots with different names.
+0x338 Dead flag (u32) Observe zero while alive and a changed flag after death.

Notice the gaps. We have not claimed that every byte between 0x0C and 0x40 is useless. Those bytes may contain velocity, dimensions, pointers, flags, or padding. Unknown means unproven, not empty.

Padding is especially easy to miss. CPUs and compilers often place a field at an aligned address — usually a multiple of that field’s own size — leaving unused bytes in between. Three fields declared in this order produce a layout with a hole in it:

The three bytes at +0x01, +0x02, and +0x03 hold nothing meaningful. They exist only so that health begins at a multiple of four. If you assume fields sit back to back and put health at +0x01, then every offset after it is wrong by three bytes, and each read returns a value stitched together from pieces of two neighboring fields. ❌

Alternative: Think of parking bays marked in sets of four: a bigger car skips ahead to the next set, leaving empty bays. Padding is those empty bays inside an object.

Virtual methods leave a useful clue

Section titled “Virtual methods leave a useful clue”

A class can declare a method as virtual, allowing different object types to choose different implementations. Many C++ compilers implement this with:

  • a vtable: a table containing function addresses;
  • a vptr: a hidden pointer in each object that points to its vtable.

The purpose is to let a single call site reach different code depending on what the object actually is. The compiler cannot know at build time whether a given entity will be a human player or a bot, so rather than writing a fixed destination it writes “call whatever address is in slot 3 of this object’s table.” Each class gets its own table, and every object carries a pointer to the right one.

A 32-bit virtual call often has this general shape:

That is two lookups before any game code runs. Followed with real numbers:

The offset 0x0C is 12, and a pointer in a 32-bit process is four bytes, so 12 / 4 = 3: this is the fourth entry counting from zero, which is why it is called slot 3. Two objects of different classes executing this identical instruction end up in different functions, because the second step read a different table.

Narration: This is how a game loop can call update on every entity, human or bot, without checking each one. The object carries the pointer to the right code.

Do not label every first pointer a vptr. Test it:

  1. The object field should point into a readable table, usually in a module’s read-only data.
  2. Several table entries should look like valid pointers.
  3. Those entries should lead into executable sections.
  4. Objects believed to share a class should usually share the same table pointer.
  5. Breaking on one table entry should show a sensible method receiving the object as this.

This pattern is common, but the C++ language does not require one universal object layout. Link-time optimization, devirtualization, multiple inheritance, and custom engines can all change it.

Inheritance makes the map less tidy

Section titled “Inheritance makes the map less tidy”

With single inheritance, the base-class part is often placed at the beginning of the derived object. A BotPlayer may therefore begin with all fields needed by Player, followed by bot-specific state.

Multiple inheritance can add more than one base subobject and more than one vptr. A method may even adjust this before using it. If two methods appear to use bases a fixed distance apart, do not immediately declare one of them wrong. You may be looking at two views of the same larger object.

RTTI stands for run-time type information: extra data the compiler emits so that code can ask what class an object really is while the program is running. It is what makes dynamic_cast possible.

When it is present it can expose type-descriptor clues near virtual tables, sometimes including a readable class name. That name tells you what the class was called and nothing more: release builds can strip RTTI entirely, and a name does not tell you where any of the class’s fields sit.

One object can have several useful identities

Section titled “One object can have several useful identities”

When inspecting object-oriented code, separate three questions:

  1. Allocation identity: which complete block of memory was created and must eventually be released?
  2. Subobject view: which base-class-shaped part does this particular pointer address?
  3. Dynamic type: which most-derived implementation will virtual dispatch choose at this moment?

These answers can differ. A pointer passed to a base-class method may point a few bytes into the complete allocation. A thunk — a tiny compiler-generated stub that fixes something up and then jumps to the real function — may adjust this before jumping to the real method. Subtracting every observed field from that adjusted pointer can produce negative offsets and a broken layout even though the pointer is valid for its particular base view.

When two candidate bases always differ by the same small constant, they are usually two views of one object. The thunk or call site that adds the constant shows where the adjustment happens, and the constructor, which writes both vptrs, shows how the two views sit inside one allocation.

Constructors and destructors reveal a timeline

Section titled “Constructors and destructors reveal a timeline”

A memory snapshot shows one state. Construction and destruction show how the state came to exist and which parts belong together.

A constructor candidate often:

  • receives a newly allocated or caller-provided object address;
  • writes repeated default values at fixed offsets;
  • calls base constructors before initializing derived fields;
  • writes one or more vptr candidates, sometimes replacing an earlier base vptr;
  • returns the same object or passes it into a registration system.

None of those clues identifies a constructor alone, because an ordinary reset function can also fill fields with defaults. What a reset function does not do is run right after an allocation, call base constructors first, and switch the vptr from the base table to the derived table.

Destructors provide the other half: they reveal child cleanup, unregistering, reference releases, pool returns, and the point after which a cached address is stale. For a memory tool, this lifetime boundary matters more than recovering the original C++ class name.

TL;DR: Constructors show how an object comes to exist, and destructors show when old addresses stop being safe to trust.

Recover a structure step by step

Section titled “Recover a structure step by step”

One memory window is not enough to recover a structure. A repeatable sequence is:

  1. Anchor one field. Find a value with an obvious controlled behavior, such as yaw, health, or ammunition.
  2. Find code that uses it. Break on access. The instruction’s base register and displacement give the field’s offset: [ecx+40h] means the field sits 0x40 bytes (4 × 16 = 64) past the address in ecx.
  3. Propose an object base. Subtract the displacement from the known field address: a yaw at 0x12340040 read through [ecx+40h] gives a base of 0x12340040 − 0x40 = 0x12340000.
  4. Collect nearby candidates. Watch adjacent aligned values as position, view, health, and state change.
  5. Compare instances. Inspect the local player and several bots at the same offsets.
  6. Assign types carefully. Check byte width, signedness, endianness, value range, and how instructions consume the field.
  7. Trace methods. Look for repeated this + offset accesses and virtual calls.
  8. Test lifetimes. Join, die, respawn, leave, and start a new match. The moments when pointers become null or objects are replaced mark where cached addresses stop being valid.

A field nobody has managed to change on purpose stays unnamed, as field_48 or plain padding, until a controlled change or a traced read shows what it holds.

Common false conclusions

Section titled “Common false conclusions”

“Two nearby floats must be X and Y.” They could be velocity, color, or a timer. Change one behavior at a time.

“The first pointer proves a vtable.” Follow several entries and verify they point to executable methods.

“The debugger showed ecx, so it must always be this.” Confirm the calling convention and watch how the method uses the value.

“The structure worked once, so it is finished.” Compare instances and repeat after object destruction, respawn, and clean launches.

“A successful read proves the address is right.” Windows can copy readable but unrelated bytes. Validate meaning, not only access.

The layout is a versioned model

Section titled “The layout is a versioned model”

An object base is the start of one instance, and each field offset is a byte distance from that base. The hidden this argument selects the instance for a member call; a vptr commonly leads to its virtual-method table. Padding and inheritance can add gaps or make one object reachable through several base views. Those observations form a layout model for the tested game build, not a promise for every build. A remote object address remains an address in the game process, never a valid local Rust reference.

The same technique appears in debuggers, crash analyzers, compatibility tools, profilers, and digital-forensics programs. Each one recovers structure from raw memory without the original source code.

A player object begins at 0x12340000, and a method reads yaw from [ecx+0x40] while ecx holds that object. Which address contains yaw?

The object base is the starting address and 0x40 is the byte distance to the member, so the field address is 0x12340000 + 0x40 = 0x12340040.
