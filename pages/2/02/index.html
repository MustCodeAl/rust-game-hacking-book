🔍 Lesson 2.3Instructions, Debuggers, and Addresses

How Assembly Describes a Running Game

Understand what assembly is, how the CPU executes it, and how registers, memory, flags, stacks, and calls fit together.

About 30 minutes

What assembly actually is

Section titled “What assembly actually is”

A CPU does not run source code or even the words mov and sub. It runs machine code: bytes whose bit patterns mean operations for one CPU architecture. Continue the 100-to-75 gold purchase from Lesson 2.1: this first instruction loads its price, 25, into a register. Later instructions will compare and subtract it.

Assembly language is a human-readable spelling of those operations. For 32-bit x86, these five bytes:

can be shown as:

The byte B8 selects one form of mov. The next four bytes hold 25 as a little-endian 32-bit number. The readable instruction and the bytes describe the same CPU action at different levels.

Note

🔍 Reading tip: each instruction changes only a few things, usually one register or one memory location, and sometimes the flags. Taken one instruction at a time, a function becomes ordinary bookkeeping.

An assembler travels from assembly text to machine code. A disassembler travels from machine code to assembly text. A debugger includes a disassembler and also shows the live register and memory values while the instructions execute.

Assembly preserves machine effects, not the author’s original explanation. A release build usually does not retain friendly variable names, comments, source loops, or the exact class boundaries that produced it. Optimization may inline two functions into one, remove a variable completely, or replace multiplication with a different but equivalent instruction sequence.

Therefore, disassembly shows what the machine does; it is not recovered source code. A decompiler can suggest source-like structure, but you still verify its types, signs, widths, branches, and calling convention against the actual instructions.

Assembly depends on the CPU architecture

Section titled “Assembly depends on the CPU architecture”

This book’s historical game builds are 32-bit x86 programs. Their main registers are named eax, ebx, ecx, edx, esi, edi, esp, ebp, and eip.

A 64-bit x86 program uses wider names such as rax and rip. ARM uses a different instruction set and different register names. Assembly is not one universal language; it is the readable face of a particular processor architecture.

The examples use Intel syntax, where the destination normally appears before the source:

Other tools may display AT&T syntax with a different order and punctuation. Pick one syntax while learning so the notation does not hide the idea.

Read the whole disassembly row

Section titled “Read the whole disassembly row”

A debugger may show:

Read it from left to right:

Part Meaning
007CCD91 address of the first instruction byte in this run
29 42 04 the three machine-code bytes
sub mnemonic: the short human name for the operation
dword ptr [edx+4] destination: a four-byte value in memory
eax source: the four-byte value to subtract

In plain English: “Take the 32-bit number stored four bytes after the address in edx, subtract eax, and store the answer back in that same memory location.”

This one sentence is far more useful than memorizing that opcode 29 means a form of subtraction.

The CPU repeats a tiny cycle

Section titled “The CPU repeats a tiny cycle”

At a simplified level, one thread repeatedly:

  1. uses eip to find the next instruction;
  2. fetches its bytes from executable memory;
  3. decodes what the bytes mean;
  4. reads the required registers or memory;
  5. performs the operation;
  6. writes the result;
  7. advances eip or jumps somewhere else.

eip is the instruction pointer. It is not a normal game variable. It tells the CPU where this thread is executing. A jump, call, return, exception, or debugger action can change it.

Registers hold the CPU’s current working values

Section titled “Registers hold the CPU’s current working values”

Registers are tiny, very fast storage locations built into the CPU. On 32-bit x86, each general-purpose register below holds 32 bits:

Register Common historical role Important warning
eax return value and arithmetic a function may use it for anything temporary
ebx preserved general value “preserved” depends on the calling convention
ecx counter or this pointer not every use is a counter or object
edx arithmetic or extra argument meaning comes from surrounding instructions
esi / edi source/destination pointers compilers also use them as ordinary storage
esp top of the current thread’s stack unbalanced changes usually crash on return
ebp stack-frame reference in some builds optimized code may use it as a normal register
eip address of the next instruction controlled by branches, calls, and returns

The role column is a clue, not a promise. Ask what the current function actually reads and writes.

Bits do not carry their own meaning

Section titled “Bits do not carry their own meaning”

The register value 0xFFFF_FFFF is only 32 one-bits. An instruction may interpret those bits as:

  • unsigned integer 4,294,967,295;
  • signed integer -1;
  • four bytes;
  • part of a pointer;
  • a bit mask where every switch is on.

Source-level types give those bits a declared meaning. In disassembly, only the instruction that uses the bits, and the code around it, tells you which meaning applies.

You do not need to memorize the whole x86 instruction set. Start with a handful of verbs, but always connect each verb to the CPU, registers, memory, and control flow described above.

The debugger changes the view, not the bytes

Section titled “The debugger changes the view, not the bytes”

The same four bytes can be displayed as hexadecimal, a signed integer, an unsigned integer, a float, four characters, or an instruction. Changing the debugger’s display format does not convert the target’s memory. It changes only the question you ask about those bits.

Use the program’s operations to choose the view:

  • a floating-point instruction supports a float interpretation;
  • sign extension or a signed conditional jump supports a signed integer;
  • a memory dereference supports an address interpretation;
  • repeated one-byte reads ending at zero support a C-string interpretation;
  • bytes that decode into valid-looking instructions are code only if control flow actually reaches them.

This last point matters because a code section can contain alignment bytes, constants, and jump tables. A disassembler can produce a plausible instruction from almost any byte sequence. What makes bytes code is that execution reaches them: a jump, call, or fall-through from other code leads there, or a debugger sees the CPU run them.

Comparing and branching

Section titled “Comparing and branching”

cmp performs a comparison and updates flags. A jump reads those flags:

je means “jump if equal.” Common jumps include:

Instruction Meaning after cmp left, right
je / jz equal / zero
jne / jnz not equal / not zero
jg greater, signed
jl less, signed
ja above, unsigned
jb below, unsigned
jmp always jump

Signed and unsigned matter because the same bits can be read in different ways. 0xFFFF_FFFF is 4,294,967,295 as a u32, but -1 as an i32.

That choice decides which branch actually runs. Imagine a price of 0xFFFFFFFF arriving at a gold check while the player holds 100 gold:

Identical bits, identical cmp, opposite outcomes. When you are reading a check that guards something valuable, the signedness of the jump is not a footnote — it is very often the entire bug.

Flags are one-bit answers from the last operation

Section titled “Flags are one-bit answers from the last operation”

eflags is a register containing many one-bit results. Common ones include:

Flag Plain-English question it helps answer
ZF, zero flag Was the result zero?
CF, carry flag Did unsigned arithmetic carry or borrow?
SF, sign flag Is the result’s top bit set?
OF, overflow flag Did signed arithmetic overflow its range?

cmp eax, ebx behaves like a subtraction that throws away the numeric answer but keeps the flags. je, jg, ja, and the other conditional jumps interpret those flags in different combinations.

This is why signed and unsigned jumps differ even though the register bits are identical.

Section titled “Calls, returns, and the stack”

Calling conventions are agreements between functions

Section titled “Calling conventions are agreements between functions”

A calling convention answers questions such as:

  • Where are arguments placed: stack or registers?
  • Which registers must the called function preserve?
  • Who removes stack arguments?
  • Where is the return value placed?

The course’s 32-bit games commonly expose cdecl, stdcall, and thiscall boundaries. The three differ mainly in who removes the arguments from the stack after the call. cdecl leaves that job to the caller, which is also what lets a cdecl function such as printf accept a varying number of arguments—only the caller knows how many it pushed. stdcall makes the callee remove its own arguments before returning. In a typical 32-bit thiscall, ecx carries the object pointer—the value an object method treats as self or this—while other arguments use the stack, and the callee cleans up like stdcall.

Do not identify a calling convention from one register alone. Inspect how the caller prepares arguments and how the callee returns. A wrong convention can leave esp incorrect even when the function address is right.

On 64-bit Windows, ordinary integer and pointer arguments start in rcx, rdx, r8, and r9; floating-point arguments use the matching XMM argument registers. The caller also reserves stack space for the register arguments and keeps the stack correctly aligned. There is one main Windows x64 convention, so do not carry the old 32-bit cdecl versus stdcall cleanup distinction into 64-bit code.

A calling convention is more than an argument list. It is the complete border contract between caller and callee:

Read both sides of a call. Code before call explains what the caller offers; the callee’s first uses explain what it expects; code after the return shows what the caller believes survived.

lea does math, not a read

Section titled “lea does math, not a read”

lea stands for “load effective address.” It works out the address the brackets describe and stores that number, instead of reading whatever lives there. It is the one common instruction where brackets do not mean a memory access:

The mov reads into eax because the elements are four bytes wide. Reading into the eight-byte rax would take the next element along with it.

The *4 is a strong hint that this is array indexing: rcx holds the start of an array, rdx holds an index, and each step of the index moves four bytes because each element is four bytes wide. So this lea computes “the address of element number rdx,” which is exactly what code does just before handing one element to another function.

Compilers also use lea as a quick way to do plain arithmetic, since it can multiply and add in one instruction without disturbing the flags. Do not assume every lea result is a pointer.

A five-question reading method

Section titled “A five-question reading method”

For each instruction, ask:

  1. What is read?
  2. What is written?
  3. How many bytes are involved?
  4. Is a number signed or unsigned?
  5. Where can execution go next?

Answer those five questions one instruction at a time. A long function becomes a trail of small facts.

Trace both data flow and control flow

Section titled “Trace both data flow and control flow”

Reading only downward through the listing works for a tiny straight-line function. Larger functions need two connected maps.

Data flow asks where a value came from and where it goes next. If eax is compared, trace backward to the instruction that last wrote eax. If [ecx+0x30] is changed, trace how ecx obtained the suspected player address and who later reads that field.

Control flow asks which instruction can run next. A straight sequence with one entry and one exit is often called a basic block. Conditional jumps connect blocks into a graph:

The graph explains the decision even when the compiler has rearranged the blocks. Source-level if, match, loops, early returns, and error paths all become control-flow edges of this kind.

Use both maps together. A branch tells you when a write occurs; data flow tells you what it changes. Guessing from only one of them is how a nearby animation counter gets mislabeled as health or a failure path gets mistaken for the normal path.

Trace a complete tiny function

Section titled “Trace a complete tiny function”

Suppose ecx points to a player and gold is the four-byte field at offset 4:

The same listing as a control-flow graph. Each box is a basic block, and the only decision is the jb:

Three details in that listing puzzle almost everyone the first time.

Why [esp+4] and not [esp]? The call that reached this function pushed a return address onto the stack, so that address is now sitting at [esp]. The argument the caller pushed just before the call is one slot further in, at [esp+4]. Whenever you see a function collecting its arguments from +4, +8, +12, the saved return address is what those offsets are stepping over.

Why xor eax, eax instead of mov eax, 0? Both leave zero in eax. Any value exclusive-ORed with itself is zero, and the xor form assembles to fewer bytes, so compilers emit it constantly. Read xor register, register as “set this register to zero” and keep going.

Why does ret have a number after it? ret 4 returns and discards four bytes of arguments from the stack, so the function cleans up after itself. A plain ret leaves that job to the caller. Which form a function uses is fixed by its calling convention, and getting it wrong corrupts esp: execution returns to the correct place, and from that point on the caller’s stack is off by four bytes.

Trace it with gold = 100 and price = 25:

Step Important state
enter ecx = player, [ecx+4] = 100, [esp+4] = 25
mov eax = 25
cmp flags describe 100 - 25; unsigned-below is false
jb branch is not taken
sub [ecx+4] = 75
mov eax = 1 return value
ret 4 caller resumes and the argument is removed

Now trace gold = 20. The jb branch skips the subtraction and returns zero. That is assembly comprehension: follow state changes and rebuild the higher-level decision.

In the example above, gold is 20 and the price is 25. What happens after the unsigned comparison?

What the debugger is showing

Section titled “What the debugger is showing”

Assembly text is a readable rendering of machine bytes for one CPU architecture; x86 and ARM bytes need different decoders. In the x86 trace, eip locates the next instruction, esp marks the stack top, and eflags holds one-bit results that branches can use. Brackets such as [edx+4] mean read or write memory at the calculated address; edx+4 without brackets is only an address calculation. A call saves a return address on the stack, and ret uses it to resume the caller. The calling convention completes that contract by fixing where arguments and results go and who removes arguments from the stack. Breakpoints in the next lesson let you inspect those facts while a real instruction is paused.
