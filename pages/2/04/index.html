🔍 Lesson 2.5Instructions, Debuggers, and Addresses

From a Game Value to the Code That Changes It

Follow a known gold address backward to the exact instruction that changes it.

About 20 minutes

Find the instruction that changes gold

Section titled “Find the instruction that changes gold”

In the previous memory lab, we found the current gold. Now we want to know:

Which instruction subtracts the price of a recruited unit?

Use the same offline Wesnoth 1.14.9 target and restore your clean VM snapshot before starting. For a concrete run, suppose you start at 100 gold and recruit a unit costing 15. The expected result is 85. Use the actual price and gold shown in your match when checking the paused instruction.

Attach x64dbg

Section titled “Attach x64dbg”

Launch Wesnoth, begin a local match, and find the gold address again. Then attach x64dbg to the running process.

The CPU view contains four useful areas:

  • disassembly—the instructions near the current position;
  • registers—the CPU’s current scratch values;
  • dump—raw memory;
  • stack—return addresses and temporary data.

Attaching may pause in Windows system code. That is normal. Resume the process before triggering your experiment.

Go to the gold address

Section titled “Go to the gold address”

Open the dump view’s “go to expression” command and enter the address found by the memory scanner.

The bytes in the dump are little-endian. If the gold is 100, the 32-bit value 0x00000064 appears as:

The least-significant byte comes first.

Break on writes

Section titled “Break on writes”

Set a hardware breakpoint on write, covering four bytes at the gold address.

A hardware memory breakpoint does not replace the game’s instruction bytes. The debugger programs special CPU debug registers with an address, access type, and width. When an instruction writes across that watched range, the CPU raises a debug exception and Windows reports it to the debugger.

The width matters. Gold is believed to be a four-byte value, so watch all four bytes. Watching one byte can still trigger, but it hides whether the game wrote the complete integer or only part of it.

This breakpoint watches a data address, not one fixed instruction. If three different functions write gold, the same watch can reveal all three. A software breakpoint placed on a code address answers the opposite question: “When does this exact instruction execute?”

Do not copy the exact register or offset from this page. Read the instruction in your own debugger. A hardware data breakpoint can report an access after the instruction has run, so the highlighted next instruction may not be the one that wrote gold. Use the breakpoint’s access information and nearby disassembly to identify the triggering write, then confirm that its calculated destination is your gold address. Builds and runs can differ.

Ask the five assembly questions

Section titled “Ask the five assembly questions”

Apply the five questions to the paused instruction:

  1. What is read? The current gold and the price in a register.
  2. What is written? Four bytes at the gold field.
  3. How many bytes? dword ptr means 32 bits.
  4. Signed or unsigned? Test nearby comparisons before deciding.
  5. Where next? The following instruction unless a branch changes the path.

Now compare the price register with the unit’s price. In the example run, it should be 15 and the destination should be the gold address that changed from 100 to 85. Matching both is stronger evidence than recognizing sub alone.

That last line matters. Later branches may inspect zero, sign, carry, or overflow flags. Replacing the subtraction changes both the stored gold and those flags. Before a temporary patch, step forward and check whether nearby conditional jumps consume them.

The effective address calculation does not dereference reg and then add an offset to the loaded value. It adds the offset to the register first, then reads memory at the resulting address. Keep “calculate an address” separate from “read the value at that address.”

Read the brackets as an address calculation

Section titled “Read the brackets as an address calculation”

For an instruction such as:

read it from the inside outward:

  1. take the address currently stored in esi;
  2. add hexadecimal offset 0x30;
  3. treat the four bytes at that final address as the destination;
  4. subtract the lower 32 bits of eax from that destination;
  5. store the result back to the same four bytes;
  6. update CPU flags for later branches.

The bracketed expression accesses memory. Without brackets, esi+30h would be an address calculation rather than a read or write of the bytes at that address.

Read the live value of esi in the register panel and add 0x30 yourself. For example, if esi holds 0x0A3C1200, the destination is 0x0A3C1200 + 0x30 = 0x0A3C1230. If the sum equals the candidate gold address, this instruction writes the gold you found.

Test with a reversible patch

Section titled “Test with a reversible patch”

Copy the original instruction bytes first, so you can write them back. Then temporarily replace the entire subtraction instruction with the same number of nop bytes.

Resume and recruit another unit. If gold no longer decreases, this instruction is the one that subtracts the price. Restore the original bytes immediately afterward.

Turn one discovery into a repeatable patch

Section titled “Turn one discovery into a repeatable patch”

Our tools will not hardcode “whatever address worked once.” They will:

  1. open the controlled process;
  2. locate a module or scan a known pattern;
  3. confirm the expected original bytes;
  4. apply a temporary patch;
  5. restore the bytes on exit.

Checking the original bytes is crucial. Refusing to patch an unknown version is safer than writing to the wrong place.

Clean up

Section titled “Clean up”

Remove the breakpoint through x64dbg’s Breakpoints tab and confirm the original instruction is restored.

The scan gave us a candidate value; the write breakpoint gave us a specific instruction and the register values from one recruitment. The reversible patch checked its effect, but the instruction may also run for other gold-changing actions. Lesson 2.6 follows the call path to find which rule brought execution here.

Watch the data, not one function

Saved

Why use a hardware write breakpoint on the gold address?

A data breakpoint watches an address range. Different code paths can trigger it, which makes it useful when you know the changing data before you know the responsible instruction.
