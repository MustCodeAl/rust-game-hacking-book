Instruction Reference: Scalar Floating-Point Values

Trace speed, position, numeric conversions, and NaN comparisons using the SSE instructions common in game code.

Read or listenPrint chapter or book
About 20 minutes
Cheatsheet for Lesson 2.13

A one-page summary of “Instruction Reference: Scalar Floating-Point Values” you can keep beside your notes. Plain Markdown.

Lesson 2.13 — Instruction Reference: Scalar Floating-Point Values: cheatsheet

  • Remember: Track the low float, the untouched upper bits, and the kind of flags involved. A 128-bit register does not mean that this instruction uses every bit as one large number.

Quick reference

  • Copy one float: movss; upper-bit behavior depends on memory versus register source.
  • Add or scale a float: addss/mulss; binary32 rounding and MXCSR status apply.
  • Integer to float: cvtsi2ss; large integers may round.
  • Float to signed integer: cvttss2si; truncate toward zero and handle invalid/out-of-range input.
  • Compare floats: comiss; handle unordered/exception behavior before equality or ordering.
  • Understand flag provenance: Arithmetic SSE status lives in MXCSR; completed comiss updates ZF/PF/CF.
  • Understand register width: Scalar operations use one low 32-bit value inside 128-bit XMM storage.

Review

  • Q: A scalar single-precision operation uses an XMM register. How much of that register holds the numeric value being calculated? A: One low 32-bit float inside the wider register storage
  • Q: Two legacy scalar float copies have the same low value, but one loads from memory and one copies another XMM register. Why inspect their forms? A: Their rules for the destination upper bits are different

Gold and ammo are often integers. Speed, position, and time are often floating-point numbers, which can represent fractions. This reference follows one float at a time in a fictional owned, resettable game. Every trace starts with a worked example; changing it is optional exploration.

These examples use the legacy two-operand SSE instructions in 32-bit x86, with Intel syntax. Their v... AVX relatives have different operand and upper-register rules. A real instruction reference must match the encoding you are actually reading. The links below point to the corresponding entries in revision 093 of Intel’s official instruction manual.

One float inside a wider register

Section titled “One float inside a wider register”

An XMM register holds 128 bits. A binary32, or single-precision float, occupies 32 bits. Scalar means these instructions operate on one float in the low 32 bits, rather than calculating four floats together. The rest of the register still exists; do not assume every scalar instruction clears it.

The suffix ss stands for scalar single precision. Memory labels such as [speed] denote valid four-byte fields in our toy game. xmm below means an XMM register, m32 a four-byte memory source, and r32 a general-purpose 32-bit register.

Floating-point encoding differs from signed integer encoding. Copying the four bytes of an integer does not convert its numeric value into a float. A conversion calculates a new representation. Some values need rounding because a fixed-size format cannot represent every number exactly.

MXCSR is a control/status register for SSE floating-point work. It records rounding direction, exception masks, and floating-point status. It is separate from integer ZF/SF/CF/OF. The arithmetic traces use round-to-nearest, ties-to-even, and ordinary finite binary32 inputs. They show selected effects, not a complete floating-point environment.

TL;DR: Track the low float, the untouched upper bits, and the kind of flags involved. A 128-bit register does not mean that this instruction uses every bit as one large number.

Copies and arithmetic

Section titled “Copies and arithmetic”

movss

Section titled “movss”

Meaning: copy one binary32 value between a low XMM field and another register or memory.

Legacy forms: movss xmm, xmm/m32, movss m32, xmm. Effects: register-to-register copies replace the low 32 bits and preserve the destination’s upper 96 bits. A memory load into XMM clears those upper 96 bits. A memory store writes only four bytes. Integer arithmetic flags are unchanged.

Move one floating-point speed value. This step-by-step trace needs JavaScript. Here is the code and where the run ends.

movss xmm0, [speed]
movss xmm1, xmm0
movss [shown_speed], xmm1

The memory store writes just four bytes, representing 2.5. It does not store all 128 bits of xmm1.

Final values: speed = 2.5; xmm0 low = 2.5; xmm0 upper 96 = zero; xmm1 upper 96 = previous contents; ZF = 0; SF = 0; CF = 0; OF = 0; PF = 1; xmm1 low = 2.5; shown_speed = 2.5.

Takeaway: distinguish a scalar load, register copy, and store before describing the rest of the register.

addss

Section titled “addss”

Meaning: add the source’s low float to the destination’s low float.

Legacy form: addss xmm, xmm/m32. Effects: write the low 32-bit floating result, rounded according to MXCSR; preserve the upper 96 XMM bits and integer arithmetic flags. It may record or raise floating-point exceptions. It does not write source memory.

Add a floating-point movement step. This step-by-step trace needs JavaScript. Here is the code and where the run ends.

movss xmm0, [position]
addss xmm0, [step]
movss [position], xmm0

Store the new position 3. SIMD floating-point status in MXCSR is separate from the ZF/SF/CF/OF shown here.

Final values: position = 3; step = 0.5; xmm0 low = 3; xmm0 upper 96 = zero; ZF = 0; SF = 0; CF = 0; OF = 0; PF = 1.

Takeaway: float addition does not produce an integer carry flag for a following jc.

mulss

Section titled “mulss”

Meaning: multiply the destination’s low float by the source’s low float.

Legacy form: mulss xmm, xmm/m32. Effects: write the low binary32 result using MXCSR rounding; preserve the upper 96 bits and integer arithmetic flags. Floating-point status and possible exceptions belong to MXCSR.

Scale a floating-point speed. This step-by-step trace needs JavaScript. Here is the code and where the run ends.

movss xmm0, [speed]
mulss xmm0, [factor]
movss [speed], xmm0

The stored speed is 5. This float multiplication does not produce an integer carry flag.

Final values: speed = 5; factor = 2; xmm0 low = 5; xmm0 upper 96 = zero; ZF = 0; SF = 0; CF = 0; OF = 0; PF = 1.

Takeaway: changing a multiplier changes the computed speed; it does not change the encoding into an integer operation.

Numeric conversion

Section titled “Numeric conversion”

cvtsi2ss

Section titled “cvtsi2ss”

Meaning: convert a signed integer into one single-precision floating-point value.

Legacy 32-bit form: cvtsi2ss xmm, r32/m32. Effects: write the low binary32 value, preserve the upper 96 XMM bits and integer flags, and leave the integer source unchanged. MXCSR rounding applies when the integer cannot be represented exactly. For example, nearest, ties-to-even rounding converts 16,777,217 to 16,777,216.

Convert integer points into a float. This step-by-step trace needs JavaScript. Here is the code and where the run ends.

mov eax, 7
cvtsi2ss xmm0, eax
movss [score_float], xmm0

Store float 7. eax still holds integer 7; the legacy conversion preserved the upper 96 XMM bits.

Final values: case = small; eax = 7; xmm0 upper 96 = previous contents; ZF = 0; SF = 0; CF = 0; OF = 0; PF = 1; xmm0 low = 7; conversion exact = true; score_float = 7.

Code note: A four-byte copy preserves the original bit pattern. A numeric conversion aims to preserve its value in a different format, which can require different bits and rounding.

Takeaway: an integer that fits 32 bits does not necessarily fit exactly into a binary32 float.

cvttss2si

Section titled “cvttss2si”

Meaning: convert a binary32 value into a signed integer by truncating toward zero.

Legacy 32-bit form: cvttss2si r32, xmm/m32. Effects: write the integer destination, preserve the float source and integer comparison flags. The tt form truncates regardless of MXCSR’s rounding direction. Thus 2.75 becomes 2, and −2.75 becomes −2.

NaN or an out-of-range result causes an invalid-operation condition. If the MXCSR invalid exception is masked, this 32-bit form writes the indefinite integer 0x80000000; if unmasked, it raises an exception. That bit pattern also represents the valid signed minimum, so checking only the output bits is insufficient. The trace explicitly assumes the invalid exception is masked.

Truncate a float toward zero. This step-by-step trace needs JavaScript. Here is the code and where the run ends.

movss xmm0, [score_float]
cvttss2si eax, xmm0
mov [score_int], eax

Store integer 2; the float source and integer comparison flags did not change.

Final values: case = positive; xmm0 low = 2.75; ZF = 0; SF = 0; CF = 0; OF = 0; PF = 1; eax = 2; eax bits = 0x00000002; valid conversion = true; MXCSR invalid raised = false; score_int = 2.

Takeaway: choose the conversion’s rounding behavior deliberately and validate the numeric range.

Comparison and unordered values

Section titled “Comparison and unordered values”

comiss

Section titled “comiss”

Meaning: compare two low binary32 values and report their ordering in integer flags.

Legacy form: comiss xmm, xmm/m32. Effects: preserve both float operands; set ZF/PF/CF as below and clear OF/SF/AF when the comparison completes. A NaN is unordered, not less, equal, or greater. comiss signals invalid operation for a NaN. With that exception masked, it produces unordered flags; with it unmasked, the exception prevents the flag update.

Completed comparison ZF PF CF
left greater than right 0 0 0
left less than right 0 0 1
left equal to right 1 0 0
unordered, with invalid masked 1 1 1

The two labels name exit paths outside this excerpt. Notice that jp reads PF, which marks unordered here. Once unordered is excluded, unsigned-style jb/ja conditions can describe float ordering; signed-integer jl/jg do not interpret these flags correctly.

Compare floats, including an unordered value. This step-by-step trace needs JavaScript. Here is the code and where the run ends.

movss xmm0, [speed]
comiss xmm0, [limit]
jp reject_invalid
jb wait_for_speed
; ordered and at least the limit: continue

The selected path is wait for speed. A float comparison needs its own flag interpretation.

Final values: case = below; xmm0 low = 2.5; limit = 3; ZF = 0; SF = 0; CF = 1; OF = 0; PF = 0; unordered = false; below limit = true; outcome = wait for speed.

Clarification: ZF is one for both equality and unordered. A jump-if-equal used alone can mistake a NaN for an equal value. Check the comparison’s complete contract, including its exception state.

Takeaway: a float comparison has four outcomes and its own flag rules.
