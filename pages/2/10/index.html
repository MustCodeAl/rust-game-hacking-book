Instruction Reference: Values and Integer Arithmetic

Look up common x86 value operations, then explore each one with a worked trace.

Read or listenPrint chapter or book

Cheatsheet for Lesson 2.11

A one-page summary of “Instruction Reference: Values and Integer Arithmetic” you can keep beside your notes. Plain Markdown.

Lesson 2.11 — Instruction Reference: Values and Integer Arithmetic: cheatsheet

  • Remember: Track which instruction most recently wrote the flag you need. A later copy may preserve a useful comparison; a later arithmetic operation may replace it.

Quick reference

  • Copy a value: mov writes a destination; source and flags survive.
  • Calculate a location: lea computes an address without reading the field.
  • Update a total: add/sub write a result and fresh arithmetic flags.
  • Count by one: inc/dec update most arithmetic flags but preserve CF.
  • Multiply signed values: imul forms choose implicit or explicit destinations; CF/OF report signed truncation.
  • Divide signed values: idiv r/m32 uses edx:eax, returns quotient/remainder, and may raise divide error.
  • Widen a field: movzx fills with zeros; movsx repeats the sign bit.
  • Interpret a boundary: CF is unsigned carry/borrow; OF is signed overflow.

Review

  • Q: A game copies an ammo count from one register into another. What happens to the original register? A: It keeps its value while the destination receives a copy
  • Q: Code calculates the address of a player field but performs no load there. What has it learned? A: A candidate location, without learning the field value yet

Use this reference when an instruction in your own resettable lab is unfamiliar. Start with its plain-English meaning, then follow its worked trace. You can change the inputs; nothing needs to be memorized or completed before continuing.

These examples use 32-bit x86, Intel syntax: destination first. A label such as [gold] stands for a valid address in our fictional game. It is not an address to paste into another process. The forms below cover common general-purpose uses, rather than every encoding or special-register form.

The authoritative details are in Intel’s Software Developer’s Manuals, especially Volume 2. The links in this table open the relevant entry in revision 093 of the instruction reference. A mnemonic names an operation; it does not identify one fixed opcode or instruction length.

Find an operation

Section titled “Find an operation”
Instruction Worked example Intel entry
mov Copy ammo MOV
lea Calculate a player’s field address LEA
add Add a gold reward ADD
sub Spend gold SUB
inc Count a coin INC
dec Use one ammo DEC
imul Multiply a signed reward IMUL
idiv Share a signed coin total IDIV
movzx Widen an unsigned byte MOVZX
movsx Widen a signed byte MOVSX

In the forms below, reg means a register, imm means a number encoded in the instruction, and r/m means either a register or a memory operand. Memory uses brackets. The operand widths must match the selected instruction form; byte ptr, word ptr, and dword ptr make one, two, or four bytes explicit.

Addressing: base + index × scale + displacement

Section titled “Addressing: base + index × scale + displacement”

An expression such as [esi+ecx*4+8] identifies a location. esi is the base, ecx is an index, 4 is the scale, and 8 is the displacement, a fixed extra distance in bytes. In these usual 32-bit addressing forms, the encoded scale is 1, 2, 4, or 8; some base/index combinations have encoding restrictions.

With base 0x1000, index 2, and a scale of 4, the address is 0x1000 + 2×4 + 8 = 0x1010. A mov with this memory source reads bytes there. A lea with the same expression only calculates the address.

Addresses do not declare record sizes. If each player occupies 16 bytes, an index must advance by 16 bytes per player, perhaps by an earlier multiplication. Also distinguish operand size from address size: reading a four-byte field does not mean that four bytes make up the whole object.

Code note: Brackets name a location; the surrounding instruction tells you whether that location is read, written, or only calculated. An offset is evidence about a field, not proof of its name or type.

Flags: four different questions

Section titled “Flags: four different questions”

Many integer operations update bits in eflags. The trace panels use these names:

Flag What it records for ordinary addition/subtraction
ZF, zero The stored-width result is zero.
SF, sign The result’s highest bit is one. That bit is the sign when the value is interpreted as signed.
CF, carry Addition carried out of the unsigned width, or subtraction needed an unsigned borrow.
OF, overflow The mathematical signed result cannot fit the selected signed width.

CF and OF answer different questions. Adding one to 0xFFFFFFFF wraps the 32-bit result to zero and sets CF, while signed −1 + 1 fits and does not set OF. Adding one to 0x7FFFFFFF sets OF because signed 2,147,483,648 does not fit, while the unsigned sum fits and does not set CF.

Some entries also mention PF: it reports even parity in the low result byte for these integer operations. AF records carry or borrow from bit 3 into bit 4. These two exist even when a game rule does not use them. An undefined flag is not an answer you may rely on; it is not a promise of zero. A preserved flag still describes an earlier operation.

TL;DR: Track which instruction most recently wrote the flag you need. A later copy may preserve a useful comparison; a later arithmetic operation may replace it.

Copies and addresses

Section titled “Copies and addresses”

mov

Section titled “mov”

Meaning: copy a value from the source to the destination, leaving the source available.

Common forms: mov reg, reg/imm/memory, mov memory, reg/imm. Ordinary mov does not copy memory directly to memory. Effects: write the destination register or memory at the selected width; leave arithmetic flags unchanged.

Copy ammo through registers into memory. This step-by-step trace needs JavaScript. Here is the code and where the run ends.

mov eax, [ammo]
mov ecx, eax
mov [display_ammo], ecx

Copy ecx into the display field. Both registers and the original ammo still contain 12.

Final values: ammo = 12; eax = 12; ZF = 0; SF = 0; CF = 0; OF = 0; PF = 1; ecx = 12; display_ammo = 12.

Takeaway: a copy can change a destination without changing its source or the last comparison.

lea

Section titled “lea”

Meaning: calculate the effective address described by the source expression.

Common form: lea reg, [base+index*scale+displacement]. Effects: write a register; do not read the addressed game bytes or change arithmetic flags. It can also serve as arithmetic when the expression is useful as a number.

Compute an address without reading the object. This step-by-step trace needs JavaScript. Here is the code and where the run ends.

mov esi, 0x1000
mov ecx, 2
shl ecx, 2
lea eax, [esi+ecx*4+8]

lea adds base 0x00001000 + 8*4 + 8 = 0x00001028. It does not read health or change the flags left by shl.

Final values: index = 2; esi = 0x00001000; ZF = 0; SF = 0; CF = 0; OF = undefined; PF = 0; ecx = 8; eax = 0x00001028; memory read by lea = none.

Takeaway: computing where a field would be does not prove that a live, valid object exists there.

Arithmetic and boundaries

Section titled “Arithmetic and boundaries”

add

Section titled “add”

Meaning: add the source to the destination and keep the selected-width result.

Common forms: add reg, r/m/imm, add memory, reg/imm. Effects: write the destination and set OF, SF, ZF, AF, CF, and PF from the addition. The CPU does not automatically reject an overflowing game reward.

Add a reward and inspect overflow. This step-by-step trace needs JavaScript. Here is the code and where the run ends.

mov eax, 0x00000064
add eax, 10
mov [gold], eax

Store 0x0000006E in gold. The mov does not repair overflow or change these flags.

Final values: case = ordinary; amount = 10; eax = 110; eax bits = 0x0000006E; ZF = 0; SF = 0; CF = 0; OF = 0; PF = 0; signed reading = 110; gold = 110.

Takeaway: the result bits and overflow flags are separate pieces of evidence.

sub

Section titled “sub”

Meaning: subtract the source from the destination and keep the selected-width result.

Common forms: sub reg, r/m/imm, sub memory, reg/imm. Effects: write the destination and set OF, SF, ZF, AF, CF, and PF. For subtraction, CF reports an unsigned borrow.

Subtract a price and inspect a borrow. This step-by-step trace needs JavaScript. Here is the code and where the run ends.

mov eax, 0x00000064
sub eax, 25
mov [gold], eax

Store 0x0000004B in gold. The mov does not repair overflow or change these flags.

Final values: case = ordinary; amount = 25; eax = 75; eax bits = 0x0000004B; ZF = 0; SF = 0; CF = 0; OF = 0; PF = 1; signed reading = 75; gold = 75.

Takeaway: subtraction alone does not enforce affordability; look for the check and branch that guard it.

inc

Section titled “inc”

Meaning: add one to the destination.

Common form: inc r/m. Effects: write the operand and update OF, SF, ZF, AF, and PF, while preserving CF. It differs from add ..., 1 when later code needs carry.

Count a collected coin while preserving carry. This step-by-step trace needs JavaScript. Here is the code and where the run ends.

mov eax, 0x00000004
inc eax
mov [count], eax

The stored count is 0x00000005. Check the new ZF/SF/OF when needed; do not treat the preserved CF as this operation's overflow test.

Final values: case = ordinary; eax = 5; eax bits = 0x00000005; ZF = 0; SF = 0; CF = 1; OF = 0; PF = 1; count = 5.

Takeaway: the carry flag after inc belongs to earlier code.

dec

Section titled “dec”

Meaning: subtract one from the destination.

Common form: dec r/m. Effects: write the operand and update OF, SF, ZF, AF, and PF, while preserving CF. Zero can become the unsigned maximum if no guard prevents it.

Use one ammo while preserving carry. This step-by-step trace needs JavaScript. Here is the code and where the run ends.

mov eax, 0x00000001
dec eax
mov [count], eax

The stored count is 0x00000000. Check the new ZF/SF/OF when needed; do not treat the preserved CF as this operation's overflow test.

Final values: case = ordinary; eax = 0; eax bits = 0x00000000; ZF = 1; SF = 0; CF = 1; OF = 0; PF = 1; count = 0.

Takeaway: a preserved CF is not a fresh underflow test for the decrement.

imul

Section titled “imul”

Meaning: multiply signed integers.

Common 32-bit forms: imul r/m32 writes the full product to edx:eax; imul reg32, r/m32 multiplies the destination by the source; imul reg32, r/m32, imm multiplies the source by the immediate. The latter two keep the low 32 bits in the named register. Effects: CF and OF tell whether that low result represents the full signed product; SF, ZF, AF, and PF are undefined. No source memory is written by these forms.

Multiply a signed reward and detect truncation. This step-by-step trace needs JavaScript. Here is the code and where the run ends.

mov eax, 6
imul eax, eax, 3
mov [reward], eax

Store the low 32 bits, 0x00000012. The signed product fits the destination.

Final values: case = ordinary; factor = 3; eax = 18; ZF = undefined; SF = undefined; CF = 0; OF = 0; PF = undefined; eax bits = 0x00000012; exact product = 18; reward = 18.

Takeaway: check the form before assuming which registers hold the product.

idiv

Section titled “idiv”

Meaning: divide a signed double-width dividend by the source, producing a quotient and a remainder.

Common 32-bit form: idiv r/m32 divides edx:eax by that register or memory value; the quotient goes to eax, the remainder to edx. There is no immediate-divisor form. cdq first sign-extends a signed eax into edx:eax. Effects: quotient truncates toward zero; arithmetic flags are undefined. A zero divisor or a quotient that does not fit raises a divide-error exception rather than an overflow flag. The trace models the zero-divisor case; signed-minimum divided by −1 is another failing boundary.

Share signed coins and keep the remainder. This step-by-step trace needs JavaScript. Here is the code and where the run ends.

mov eax, 23
cdq
mov ecx, 4
idiv ecx
mov [share], eax

Each share is 5, with 3 left over. The divisor stayed 4; a later branch needs a new comparison.

Final values: coins = 23; players = 4; eax = 5; ZF = undefined; SF = undefined; CF = undefined; OF = undefined; PF = undefined; edx = 3; ecx = 4; share = 5.

Clarification: For 32-bit division, stale edx bits change the dividend even when eax looks correct. Signed division needs sign extension; unsigned div usually needs a different preparation.

Takeaway: identify the implicit dividend, validate the divisor, and make a new comparison before relying on flags.

Widening a field

Section titled “Widening a field”

movzx

Section titled “movzx”

Meaning: copy a smaller value into a wider register and fill the added high bits with zero.

Common forms here: movzx reg32, r/m8 or movzx reg32, r/m16. Effects: write only the wider destination; preserve flags and source memory. Byte FF becomes 000000FF, numeric 255.

Widen a byte without a sign. This step-by-step trace needs JavaScript. Here is the code and where the run ends.

mov bl, 255
movzx eax, bl
mov [expanded], eax

Store the widened value 255. The original byte and the flags are unchanged.

Final values: value = 255; bl = FF; ZF = 0; SF = 0; CF = 0; OF = 0; PF = 1; eax = 255; eax bits = 0x000000FF; expanded = 255.

Takeaway: zero extension preserves the value of a small unsigned field.

movsx

Section titled “movsx”

Meaning: copy a smaller signed value into a wider register while repeating its sign bit into the added high bits.

Common forms here: movsx reg32, r/m8 or movsx reg32, r/m16. Effects: write only the wider destination; preserve flags and source memory. Byte FF becomes FFFFFFFF, signed −1.

Keep the sign when widening a byte. This step-by-step trace needs JavaScript. Here is the code and where the run ends.

mov bl, 255
movsx eax, bl
mov [expanded], eax

Store the widened value -1. The original byte and the flags are unchanged.

Final values: value = 255; bl = FF; ZF = 0; SF = 0; CF = 0; OF = 0; PF = 1; eax = -1; eax bits = 0xFFFFFFFF; expanded = -1.

Takeaway: widening the same source byte with a different rule can change its meaning.

Calculate a location lea computes an address without reading the field.
Update a total add/sub write a result and fresh arithmetic flags.
Count by one inc/dec update most arithmetic flags but preserve CF.
Multiply signed values imul forms choose implicit or explicit destinations; CF/OF report signed truncation.
Divide signed values idiv r/m32 uses edx:eax, returns quotient/remainder, and may raise divide error.
Widen a field movzx fills with zeros; movsx repeats the sign bit.
Interpret a boundary CF is unsigned carry/borrow; OF is signed overflow.

Next, follow decisions, stack operations, and bits. For numeric formats before these instructions, revisit How Bytes Become Numbers and Pointers.

Copy without consuming

A game copies an ammo count from one register into another. What happens to the original register?

An ordinary register copy writes the destination without consuming or clearing the source. The same value can remain in both registers.
