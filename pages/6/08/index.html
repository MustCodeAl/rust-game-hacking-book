🌐 Lesson 6.8Protocols, Networks & IPC

Send Framed Messages Through a Local Named Pipe

Learn named-pipe servers and clients, byte versus message mode, framing, bounded reads, connection races, local-only scope, and handle ownership.

About 38 minutes

A named pipe is a local client/server channel

Section titled “A named pipe is a local client/server channel”

A named pipe server creates a known pipe name and waits. A client opens that name. After they connect, both sides can exchange bytes through ordinary Windows read and write calls.

This resembles a tiny network service, but the lab keeps both programs on the same Windows machine:

Named pipes are useful when a supported game plug-in, launcher, capture helper, or your own engine build needs to talk to a separate tool without sharing raw pointers.

One bounded exchange has a clear beginning, two validated messages, and a clear end:

flowchart TD
    A["Server creates local pipe"] --> B["Client opens the pipe"]
    B --> C["Connection completes"]
    C --> D["Client sends framed request"]
    D --> E["Server validates request"]
    E --> F["Server sends framed reply"]
    F --> G["Both sides close handles"]

The pipe transports bytes; the frame format supplies the length and validation rules that make those bytes meaningful to both programs.

Note

🔌 IPC idea: define a small message format instead of sharing addresses. Each process keeps ownership of its own memory and exchanges bounded copies.

Message mode preserves write boundaries

Section titled “Message mode preserves write boundaries”

Windows pipes can operate in byte mode or message mode.

  • Byte mode is a stream. One read can receive part of a write or data from several writes.
  • Message mode preserves message boundaries. A read receives one message, provided the buffer is large enough.

The lab selects PIPE_TYPE_MESSAGE when creating the server and PIPE_READMODE_MESSAGE for both ends.

It still adds a four-byte length header. Why use both? Message mode keeps transport boundaries, while the length header validates the application protocol. The receiver can reject a damaged or unexpected frame instead of trusting every byte Windows delivered.

Treat IPC data like untrusted input

Section titled “Treat IPC data like untrusted input”

“Local” does not mean “automatically trustworthy.” Another program in the same account or session might know or guess the pipe name.

The receiver checks all of these facts before making a String:

  1. At least four header bytes arrived.
  2. The declared text length is no more than 1024 bytes.
  3. The received frame size equals 4 + declared length.
  4. The text bytes are valid UTF-8.
flowchart TD
    A["bytes_read >= 4?"] -->|"no"| X1["reject: no header"]
    A -->|"yes"| B["declared <= MAX_TEXT_BYTES?"]
    B -->|"no"| X2["reject: header too large"]
    B -->|"yes"| C["bytes_read == declared + 4?"]
    C -->|"no"| X3["reject: length mismatch"]
    C -->|"yes"| D["valid UTF-8?"]
    D -->|"no"| X4["reject: bad UTF-8"]
    D -->|"yes"| E["return the text"]

The server accepts one client, handles one request, sends one fixed reply, and exits. Small limits make the behavior easy to reason about.

Keep the pipe local and never impersonate

Section titled “Keep the pipe local and never impersonate”

Named pipes can support remote clients. This lab includes PIPE_REJECT_REMOTE_CLIENTS, so Windows rejects them automatically.

The program does not call ImpersonateNamedPipeClient, duplicate tokens, start a process as another identity, or change privileges. Those operations solve different identity and access-control problems; they are not part of this message channel.

Understand the connection race

Section titled “Understand the connection race”

A client can open the pipe after CreateNamedPipeW creates it but just before the server calls ConnectNamedPipe. Windows then returns ERROR_PIPE_CONNECTED. That does not mean the connection failed—it means the client already won the race.

The match arm accepts only that documented condition and returns every other error:

How to grow this design safely

Section titled “How to grow this design safely”

A larger tool could add a version number and an enum of allowed messages such as TurnStarted, MapLoaded, or PlayerPositionFromSupportedMod. It should authenticate sensitive clients, set an explicit security descriptor, rate-limit messages, keep bounded queues, and separate parsing from actions.

Do not accept a command string and pass it to PowerShell or cmd.exe. Define a small message enum and reject unknown variants. Data should select one defined action, not become code.

The buildable source is named_pipe_lab.rs.

References: named-pipe operations, CreateNamedPipeW, ConnectNamedPipe, and SetNamedPipeHandleState.

Knowledge check

Interpret the connection race

Saved

ConnectNamedPipe reports ERROR_PIPE_CONNECTED immediately after the server creates its pipe. What does that result mean here?

A fast client can connect after CreateNamedPipeW but before the server calls ConnectNamedPipe. Windows reports that race as ERROR_PIPE_CONNECTED. The server should treat this specific result as a successful connection, not tear down a healthy client.

Knowledge check

Separate pipe messages

Saved

Why put an explicit length before a named-pipe payload?

A byte stream does not preserve application message boundaries, so framing tells the parser how many bytes belong together.
