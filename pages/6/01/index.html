🌐 Lesson 8.1Messages Across Networks and Processes

Messages, Streams, and Multiplayer

See how a client and server turn a move into framed bytes, and why TCP transport does not define a game's message boundaries.

Read or listenPrint chapter or book
About 25 minutes

Client and server

Section titled “Client and server”

Imagine two players looking at copies of the same game board. One presses north while their character is at (10, 15). Their computer can draw a possible new position immediately, but the other player cannot know about that move until information crosses the network. The server checks the move against the game’s rules and replies with the accepted position, (10, 14).

A client collects your input, sends requests, receives state, and draws what you see. A server applies the shared rules. Both hold their own changing game state; a message carries information between the copies.

This chapter follows that message from intent to bytes, from captured bytes to a parsed event, and from one event to a legal session transition. A local chat client and proxy put the pieces together. The final lessons ask how two programs on one computer can exchange equally well-defined messages without using a network socket.

sequenceDiagram
    participant C as Game client
    participant S as Local test server
    C->>S: "I want to move north"
    S->>S: Validate the request
    S-->>C: "Position is now (10, 14)"
    C->>C: Draw the new state

The client’s “move north” is an intent: a request for a change, not the final truth. The reply reports what the server actually accepted. If a wall blocked the move, the reply might still say (10, 15), and the client would correct its display.

The client and server are not one program with a slow shared variable. The server may accept, reject, reorder, or combine requests according to its rules, while the client may predict a result before confirmation arrives. The next question is how the reply’s bytes become one complete message at the other end.

TCP is a stream

Section titled “TCP is a stream”

TCP is a common transport for a connection between the two programs. It delivers an ordered stream of bytes. A program calls read to take some bytes that have arrived from that stream. TCP does not preserve the game’s message boundaries for that call.

One call to read may return:

  • half of one message;
  • exactly one message;
  • one message plus part of the next;
  • several messages.

Concretely: if the sender writes two length-prefixed messages back to back, the receiver has no say in how they turn up.

Neither read lands on a message boundary. The receiver has to hold what it has in a buffer, remove complete messages when enough bytes have arrived, and keep the leftover for next time. A parser that assumes one read equals one message works flawlessly over a fast loopback connection while you are testing, then breaks the moment timing changes.

This is why a protocol needs framing.

stream supplies incoming bytes and max_size is the caller’s permitted payload limit. A successful call returns one payload as a Vec<u8>; a truncated header or payload produces an I/O error through ?. For a header 00 00 00 02 followed by 41 42, the returned vector contains just 41 42. The maximum size prevents a bad length field from requesting absurd amounts of memory. This blocking helper also needs an appropriate timeout on a real socket so a peer cannot make it wait indefinitely.

TCP reliability ends at delivering an ordered byte stream to the receiving socket. It does not prove the application parsed a complete message, accepted the request, saved the state, or sent a meaningful reply. Those guarantees belong to the application protocol. Define acknowledgments, request IDs, timeouts, and retry rules at that layer when the behavior needs them.

Byte order is part of the protocol

Section titled “Byte order is part of the protocol”

The same integer has more than one possible byte order. Decimal 258 is 1 × 256 + 2, so as a four-byte number it has one byte worth 256 (01), one byte worth 1 (02), and two zero bytes. Wesnoth’s four-byte frame length is big endian, which puts the byte worth the most first:

On little-endian x86 memory, a native u32 with the same value would usually appear in the opposite order:

Read with the wrong order, the wire bytes 00 00 01 02 become 0x02010000, which is 2 × 16,777,216 + 1 × 65,536 = 33,619,968: a frame length of more than 33 million bytes. Network code must follow the protocol, not the host CPU’s default. That is why the reader uses u32::from_be_bytes rather than a pointer cast.

Packets and protocols

Section titled “Packets and protocols”

A packet is a chunk of bytes sent across a network. That part is straightforward.

“Protocol” is usually defined with words like rules or agreement, which sound reasonable and tell you nothing. Be concrete instead. A protocol is the set of specific questions both programs must already know the answers to before a single byte means anything. There are four:

  1. Where does one message end and the next begin? A TCP connection is one long stream of bytes with no natural gaps, so something has to mark the boundaries.
  2. What is each part of a message? Which bytes are the length, which are the message type, which are the payload, and how each of those is encoded.
  3. Which messages are allowed right now? A login reply makes no sense before a login request. People routinely forget this is part of the protocol at all.
  4. What happens when something is wrong? An unknown message type, a length that does not fit, a message arriving out of turn.

None of that can be worked out by staring at the bytes, because none of it is written in them. Both programs have to know it in advance. That is precisely why reverse engineering a protocol means recovering those four answers — and why a byte layout on its own only ever answers the second one.

Note

📦 Watch for: the same bytes can be perfectly valid at one point in a conversation and meaningless at another. A protocol model has to check when a message is legal, not only what it contains.

One message is wrapped in several layers

Section titled “One message is wrapped in several layers”

Several layers cooperate when the bot sends one chat message:

WML, Wesnoth Markup Language, is Wesnoth’s own tagged text format for structured data — chat messages, maps, units, and more all get written as bracketed tags such as [message] and [/message] wrapping quoted key="value" fields. It is the serialization format this chapter keeps reversing.

When something fails, ask which layer broke. A correct TCP connection does not prove the WML is valid. A valid gzip stream does not prove the length prefix used the right byte order.

The receiver undoes the layers in the opposite order, and each step has its own way to fail:

flowchart TD
    A["Bytes arrive from the TCP stream"] --> B["Framing: split off one frame<br/>using the big-endian length"]
    B --> C["Compression: gunzip the payload"]
    C --> D["Serialization: parse the WML tags"]
    D --> E["Meaning: build a typed Message"]
    B -.->|"length above the maximum"| X["Stop with an error<br/>that names the layer"]
    C -.->|"not a valid gzip stream"| X
    D -.->|"unbalanced or unknown tags"| X

Serialization turns structured values into bytes. Framing tells the receiver where one serialized message ends. Transport moves bytes between endpoints. Keeping those jobs separate makes both the explanation and the code easier to test.

Messages can feed a data pipeline

Section titled “Messages can feed a data pipeline”

A multiplayer service handles more than packets. It may keep durable account and inventory records in a database, reuse expensive results in a cache, and build a search index for queries such as finding a match by region and mode. Those are different access patterns: keep data across restarts, avoid repeating work, and find selected records efficiently. They are not three names for the authoritative state of a running match.

Processing is asynchronous when the sender can continue before the work finishes. A request can enter a queue, then a worker handles it later. A queue acknowledgment might mean “received”; it does not by itself mean “validated, applied, and saved.” The protocol must say which stage each reply confirms.

There are also two common ways to process a sequence of events:

Processing style Game-service example What it must account for
Stream processing Update a match’s statistics as accepted events arrive Ordering, late events, duplicates, and how quickly the result is needed
Batch processing Recompute a leaderboard from a collected set of finished-match results Which results belong to the batch, when it runs, and how to repeat it safely

“Stream processing” here means processing ongoing events; it does not mean the TCP byte stream discussed earlier. A service can obtain events from many connections, files, or queues. A batch deliberately waits for a group of data and processes that group together. Neither approach implies that a game can delay its immediate rules until a leaderboard job finishes.

For example, a match event might carry match_id, event_id, and a score change. If a sender retries it after a lost acknowledgment, the receiver must recognise the same event rather than add the score twice. Event identity and retry behaviour belong to the model and protocol, not to whether TCP delivered the underlying bytes correctly.

Modularity and scaling follow the dependencies

Section titled “Modularity and scaling follow the dependencies”

Keep receiving, parsing, rule validation, and persistence as identifiable jobs. Then measure where time is spent. A slow disk write, repeated full-player search, and long logging operation need different remedies; adding workers does not remove a shared bottleneck automatically.

Several independent matches can often run on separate workers. Within one match, operations on shared state still need a defined order. Moving one job to another process also adds a message boundary, possible failures, and delay. Start with a small correct local service, preserve these contracts, and distribute work when measurements and the use case justify it.

Bound queues as well as messages. If input arrives faster than it can be processed, an unbounded queue consumes memory and makes results increasingly stale. A newer position snapshot may replace an older one under a documented policy; a one-time item grant needs different handling. That is a decision about message meaning, not a universal “drop old data” rule.

UDP is made of datagrams

Section titled “UDP is made of datagrams”

UDP preserves datagram boundaries but does not guarantee delivery, order, or uniqueness. Fast games often tolerate those tradeoffs for time-sensitive state.

A later position update can make an older one useless, so freshness may matter more than retransmission. In contrast, a one-time inventory change may need explicit ordering and acknowledgment. Choose behavior per message kind instead of labeling an entire game “reliable” or “unreliable.”

Do not assume a game uses only one protocol. It might use TCP for login/chat and UDP for movement.

Encryption changes what you can see

Section titled “Encryption changes what you can see”

If a protocol uses modern encryption correctly, a packet capture shows encrypted bytes, addresses, sizes, and timing—not readable messages. Do not try to defeat encryption or certificate checks.

For learning, use:

  • your own toy protocol;
  • a local open-source server;
  • captured bytes provided by a challenge;
  • application logs you control.

Captures in this chapter stay local

Section titled “Captures in this chapter stay local”

The capture, replay, and proxy examples use loopback or a local test server. That keeps timing, state changes, and failures observable while you learn what each protocol layer contributes.
