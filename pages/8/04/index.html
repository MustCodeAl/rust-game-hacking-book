Import Table Hooks

See how an imported function pointer can be redirected inside a controlled process and safely restored.

What the Import Address Table does

Section titled “What the Import Address Table does”

The detours in Lesson 6.4 changed instruction bytes at a verified site. Sometimes a program already calls a function through a table of imported addresses. In that case, one verified table entry can change the destination while leaving the call instruction in place.

Your program can call MessageBoxW without knowing where user32.dll will load. The PE import data says, “I need this named function.” The Windows loader finds its live address and writes that address into the Import Address Table, or IAT.

Keep the function signature exact

Section titled “Keep the function signature exact”

The replacement must accept the same arguments and use the same Windows calling convention:

extern "system" tells the compiler to use the calling convention Windows expects. If the convention, parameter sizes, or return type are wrong, the stack or registers can be interpreted incorrectly.

Find the import directory

Section titled “Find the import directory”

For a loaded PE32 image:

  1. get the current executable base with GetModuleHandleW(NULL);
  2. verify MZ and PE\0\0;
  3. require optional-header magic 0x10B;
  4. read the import-directory RVA from data-directory entry 1;
  5. walk 20-byte import descriptors until the all-zero terminator;
  6. find user32.dll;
  7. walk its lookup names and IAT slots together;
  8. find MessageBoxW by name.

Step 7 is the one that surprises people: each imported DLL has two parallel arrays, not one. The compiler writes them as identical lists of equal length, and the loader overwrites only one of them.

Before the module is loaded, both arrays hold the same name references. During loading, Windows resolves each name and writes the resulting live address into the matching IAT slot, leaving the lookup table alone. That is exactly why you walk the two together: the lookup table still records which function this entry is, while the IAT records where that function currently lives. Searching the IAT by itself gives you addresses with no names attached; searching the lookup table by itself gives you names with nothing to patch.

(Some binaries ship without the separate lookup table. In a loaded image, the IAT has already been overwritten with live function addresses, so it cannot be treated as a list of name RVAs. This name-based lab refuses that case with a clear error. Handling it would require a different, independently verified way to identify the desired slot.)

Run the complete three-message proof

Section titled “Run the complete three-message proof”
Windows VM

Run this from windows-labs in the Windows VM. The three message boxes let you observe the original import, the redirected call, and the restored call in that order.

You should see three message boxes:

  1. the untouched call displays “The normal import runs first.”
  2. the hooked call displays “Hook reached the replacement IAT entry.”
  3. after IatPatch is dropped, the restored call displays “The original import is restored.”

Those three visible states prove interception and restoration. The full buildable source—including bounded PE parsing and every unsafe invariant—is iat_hook_lab.rs.

How this connects to game labs

Section titled “How this connects to game labs”

An injected course DLL lives inside the game process, so the same idea can observe an imported graphics or file function used by that exact build. Before changing a game IAT:

  • prove the function is actually imported by the main executable;
  • use the exact function signature;
  • reject an unknown PE format or module version;
  • keep the hook tiny and non-blocking;
  • restore the original slot before unloading the DLL.

The Urban Terror OpenGL chapter uses an instruction detour because its verified draw path is not expressed as a convenient main-executable IAT slot. Choose a hook based on the real call path, not because one technique sounds fashionable.

References: Microsoft PE format, GetModuleHandleW, and importing functions using __declspec(dllimport).
