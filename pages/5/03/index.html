A wrapper records and forwards draw calls

Section titled “A wrapper records and forwards draw calls”

Lesson 7.2 showed that a draw submission combines geometry with the graphics state already in effect. To learn which submissions correlate with an entity, we need to observe calls without changing the frame they produce. OpenGL applications call functions such as glDrawElements. First consider a whole-call wrapper: it sits between the caller and the real function:

If the game makes a draw with count = 9, the wrapper records that value and then passes the same arguments to OpenGL. The picture should remain identical; only the separate observation log changes. The wrapper must preserve the exact ABI and forward every normal call. The pinned Urban Terror implementation later in this lesson instead detours an instruction inside glDrawElements, so it has a narrower restoration opportunity. Keep that difference visible when comparing the two designs.

Observe a draw without holding up rendering. This step-by-step trace needs JavaScript. Here is the code and where the run ends.

receive DrawElements(count = 9)
copy a compact sample
try to enqueue without waiting
if full: increment dropped count
forward the original arguments once
report submitted draws and stored samples

Result: one draw forwarded, one sample accepted. CPU submission does not establish GPU completion.

Final values: queue = room; sampled_count = 9; accepted = 1; dropped = 0; forwarded = 1.

What an indexed draw actually requests

Section titled “What an indexed draw actually requests”

glDrawElements(mode, count, element_type, indices) asks OpenGL to consume an ordered sequence of vertex indices:

Argument Meaning
mode how index results form primitives, such as triangles or lines
count number of indices to read
element_type width/format of each index, such as 16- or 32-bit unsigned
indices byte offset into a bound index buffer, or an address in old client-memory mode

The call does not directly identify a model. OpenGL combines those indices with the currently bound vertex attributes, textures, transforms, and other state. One character may require several draws—body, head, weapon, shadow—and one draw may contain many instances or a batch of unrelated objects.

TL;DR: A draw request identifies submitted geometry and bound state, not one complete game object.

With GL_TRIANGLES, every complete group of three indices describes one submitted triangle. The indices may repeat vertices, and some triangles may be degenerate, clipped, back-face culled, or hidden by depth. Therefore:

For example, this index buffer holds nine indices, so a call with count = 9 submits 9 ÷ 3 = 3 triangles:

The indices parameter is especially easy to misread. If an element-array buffer is bound, a small value such as 0x120 is an offset into GPU-managed buffer state, not a process pointer that should be dereferenced.

CPU submission and GPU execution overlap

Section titled “CPU submission and GPU execution overlap”

The CPU usually records commands faster than the GPU completes them. A draw call returning does not mean its pixels are finished. Reads that force the GPU to catch up can stall both processors. The hook sees submitted work: it runs when the CPU queues a draw, not when the GPU finishes its pixels.

This overlap explains why a debugger pause or synchronous query can create a much larger performance change than its own instruction count suggests.

A hook sits on the program’s critical path

Section titled “A hook sits on the program’s critical path”

The render thread has a deadline: finish enough work for the next frame. A hook adds work to a path that may execute thousands of times per second. Even memory-safe code can cause stutter if it allocates, waits for a lock, formats strings, or writes files there.

Narration: A tiny delay repeated for thousands of draws can consume the frame budget. Move formatting and disk writes away from the render thread.

Split the design into two rates:

  • the capture path copies a tiny fixed-size sample and returns immediately;
  • the analysis path runs later on a worker and may aggregate, label, or save bounded results.

The render thread’s work ends at try_send; everything slow happens on the worker’s schedule. Measure both dropped samples and time spent in the hook. A dropped sample leaves a gap in the log, while blocking slows the very frames you are trying to measure.

Write the function type

Section titled “Write the function type”

For a 32-bit Windows OpenGL 1.x target, the calling convention is significant:

The exact signature comes from the OpenGL API, not from guessing registers.

In an older fixed-function renderer, transforms and arrays may be ordinary OpenGL state. In a modern renderer, shader programs and buffer objects carry the same roles. Hooking the draw call still works, but the state needed to explain a draw changes with the API version and engine.

Keep the original function

Section titled “Keep the original function”

The wrapper needs a way to reach the real OpenGL function after it has intercepted a call. Store the resolved function pointer once during setup; every draw can then forward through that saved pointer without another lookup on the render thread:

Alternative: A forwarding wrapper is a receptionist with the original extension saved: recording the request must not route it back through the receptionist indefinitely.

Initialization must resolve and store the real function before the wrapper can forward calls. Avoid resolving it recursively through your own wrapper.

The failure is recursion: a function calls itself. Recursion is useful when each call handles a smaller case and a base case eventually returns. Here there is no smaller case. If ORIGINAL_DRAW_ELEMENTS accidentally points to draw_elements_hook, the call path is:

No call reaches OpenGL, so no call can return. Each nested call keeps a stack frame for its return address and local values, as Lesson 3.4 explained. The thread’s finite stack (often 1 MiB by default for a Windows executable, but configurable) eventually fills and Windows raises a stack-overflow exception, usually on the first draw. Resolving the real function before installing the wrapper breaks this cycle. The failure table at the end of the lesson calls this “Infinite recursion.”

Do not log every call to disk

Section titled “Do not log every call to disk”

Draw calls can occur thousands of times per frame. Synchronous file output inside the hook will destroy performance and can cause re-entry problems.

Use a bounded channel and allow drops:

A worker thread can aggregate samples later. If the channel is full, losing a sample is better than blocking the render thread.

Classify with experiments

The count argument may correlate with a model in one exact build:

But count alone is fragile. Different objects can share a vertex count, and model updates can change it.

Collect features such as:

  • draw mode;
  • element count;

Capture the smallest feature vector that can answer the current question:

call_site distinguishes engine submission paths, but compiler inlining and updates can change it. texture can identify a material in one scene, but skins, quality settings, and atlases can change it. A feature can be trusted to identify a category only after changing one thing at a time — the model, the map, a graphics setting — leaves it pointing at the same objects.

Shaders turn vertex records into pixels

Section titled “Shaders turn vertex records into pixels”

A shader is a small GPU program invoked many times in parallel. Two stages are central here:

  • a vertex shader reads one vertex (and often matrices) and produces clip-space position plus values to interpolate;
  • a fragment shader runs for candidate covered samples and produces a color, depth, or another render-target output.

Values such as texture coordinates and normals are interpolated across a triangle. The fragment shader usually does not receive the original vertex value. This is why a draw’s texture, program, uniforms, and vertex layout are part of its identity.

Older fixed-function OpenGL calls hide these programs behind predefined state, but the pipeline still performs equivalent transformations and color calculations.

What a shader reads

Section titled “What a shader reads”

A shader works only with what the draw has bound for it:

  • Interpolated inputs, the per-vertex values blended across the triangle.
  • Uniforms, values that are the same for every invocation of one draw, such as the matrices, a light’s colour, or the time since the game started.
  • Textures and buffers, images it can sample at a (u, v) position and arrays of data it can read, bound before the draw as part of the state from Lesson 7.2.

A small fragment shader that turns a texture grey shows how little a shader can be. It weights the red, green, and blue of the pixel by how bright the eye finds each:

For a pixel of (200, 100, 50), the grey is 0.299 × 200 + 0.587 × 100 + 0.114 × 50 = 59.8 + 58.7 + 5.7 = 124.2, so the pixel becomes about (124, 124, 124). A shader that reads the time as a uniform can animate: a brightness of 0.5 + 0.5 × sin(time) is 0.5 at time 0 and 1.0 at time 1.5708 (a quarter of a turn in radians), and it repeats.

Shaders are written in a shading language: GLSL for OpenGL, HLSL for Direct3D, WGSL for WebGPU. A driver, or the engine ahead of time, compiles them to the GPU’s own instructions. Engines that support several graphics APIs often write a shader once and translate it for each.

Variants, instancing, and shaders that do not draw

Section titled “Variants, instancing, and shaders that do not draw”
  • Variants. One shader source can have switches, written as #ifdef lines, such as “has a normal map” or “has fog.” Each combination compiles to a separate program, so three switches give 2 × 2 × 2 = 8 variants. Engines compile the ones a scene needs, which is why a game can hitch the first time something new appears.
  • Instancing. To draw 1,000 copies of one tree mesh, the game makes one draw call with 1,000 instances. A buffer holds each copy’s transform, a 4 × 4 matrix of 16 four-byte floats, which is 64 bytes, so 1,000 copies take 64,000 bytes. Earlier we saw that one draw can contain many objects; instancing is the deliberate version of it.
  • Compute shaders. A compute shader is not part of drawing. It is a general GPU program that runs once for each item in a grid of work, reading and writing buffers. Engines use it for particles, culling, mesh deformation, and post-processing.
  • Post-processing shaders. A fragment shader run over a full-screen rectangle, reading the finished picture as a texture, produces effects such as bloom and colour grading (Lesson 7.2).
  • Extending the standard material. Engines let a game add its own shader code and extra vertex data, such as a per-vertex wind weight, to a standard material instead of rewriting it.

Why many small draws cost frame time

Section titled “Why many small draws cost frame time”

Each draw call costs the CPU something even if the GPU’s share is tiny, because the driver checks the bound state and builds the commands. Suppose, as an illustration, one draw costs 5 microseconds of CPU time. Then 10,000 draws cost 10,000 × 5 = 50,000 microseconds, which is 50 ms, three frames of the 16.67 ms budget from Lesson 4.1, with the GPU waiting. Instancing, merging meshes that share a material, texture atlases, and culling (Lesson 7.2) all exist to cut the number of draws.

A stress test finds the limit by multiplying one thing, such as cubes, sprites, lights, animated characters, or text, and watching the frame time. If 1,000 cubes take 4 ms and 4,000 take 16 ms, each costs 0.004 ms and the 16.67 ms budget runs out at about 16.67 ÷ 0.004 = 4,167 cubes. Halving the window’s pixel count tells you which processor is the limit: if the frame time does not change, the CPU, not the GPU, is the bottleneck.

This is a classification problem. A threshold such as count > 500 separates the examples you observed, not necessarily the concept “player.” Test it against weapons, detailed scenery, menus, different models, and different graphics settings. Report false positives (something your rule caught that is not a player) and false negatives (a player your rule missed) instead of quietly turning a correlation into a definition.

Turn the wrapper into the actual Urban Terror wallhack

Section titled “Turn the wrapper into the actual Urban Terror wallhack”

The API signature, draw-count interpretation, and sampling design above stand on their own. The exact-build detour below applies the DLL and patch lifecycle from Lesson 6.4 to one verified OpenGL instruction. Recheck the displaced instruction span and restoration path before running it.

In Urban Terror 4.3.4, resolve glDrawElements from opengl32.dll. The historical build hooks the instruction at glDrawElements + 0x16 and resumes six bytes later. This is not a function-entry wrapper: it is a real code cave in the middle of the OpenGL function. At this point in this 32-bit build, EBX holds count.

Resolve these two OpenGL functions with GetProcAddress:

glDepthRange(near, far) controls where a fragment’s depth lands in the depth buffer after projection, by remapping the normalized -1..1 range onto whatever window-space interval you pass in. The default call is glDepthRange(0.0, 1.0): keep every fragment’s real depth. Calling glDepthRange(0.0, 0.0) instead collapses that mapping to a single point — every fragment’s stored depth becomes 0.0, the value reserved for the nearest possible surface, no matter how far away the vertex actually was. On its own that would not help, because the depth test would still reject a highlighted fragment sitting behind whatever was already drawn there. Switching glDepthFunc from GL_LEQUAL to GL_ALWAYS removes that objection: the test now passes unconditionally, so the fragment collapsed to depth zero is drawn regardless of what is already in the buffer. It is the combination — flatten the depth, then stop testing it — that pushes highlighted geometry through walls; neither call does it alone.

Restore graphics state

Section titled “Restore graphics state”

OpenGL is a state machine: a call changes settings that remain active until another call changes them. This middle-of-function cave cannot surround one typed glDrawElements call, so it restores the normal state when the next non-highlighted draw arrives and when the feature is disabled. Pressing End also disables the mode before removing the code patch. That ordering prevents the game from being left with GL_ALWAYS active.

State restoration must match what was changed. A robust typed wrapper queries or tracks the previous depth function, depth range, enabled client arrays, color, and bindings. Restoring guessed “defaults” works only until another legitimate render pass enters with different state. A middle-of-function cave has fewer safe options, which is a real limitation of that interception point rather than an implementation detail to ignore.
