🪟 Lesson 11.11Windows Process Internals

System Calls and Privilege Checks

Privilege bits, page permissions, API stubs, handle checks, and NTSTATUS together explain one request's route through the kernel.

Read or listenPrint chapter or book
About 13 minutes

Lesson 11.10 showed the processor keeping user-mode code away from the kernel and drew one ReadProcessMemory call crossing into the kernel and back. This lesson opens both up. It reads the bits the processor actually checks, then follows that one call a layer at a time, with every value the kernel compares along the way.

The current level is two bits of a register

Section titled “The current level is two bits of a register”

The processor keeps the current privilege level in the lowest two bits of the cs register, which tells the processor which code segment it is running. Two bits can hold 2 × 2 = 4 patterns, 00, 01, 10, and 11, which is exactly why there are four rings.

Open any 64-bit program in x64dbg and the register panel shows cs as 0033:

0x33 is 3 × 16 + 3 = 51. Each hex digit stands for four bits, so 0x33 is 0011 0011. Its lowest two bits are 11, which is 2 + 1 = 3: ring 3, user mode. The kernel’s own code segment is 0x10, which is 0001 0000; its lowest two bits are 00, ring 0.

A program cannot promote itself by loading 0x10 into cs. The processor refuses any change of code segment that would raise the privilege level, except through a few entry points that the kernel prepared in advance. The most important of them is the syscall instruction, and the rest of this lesson follows one trip through it.

Knowledge check

Read the privilege level

Saved

A 32-bit game running on 64-bit Windows shows cs = 0023 in x64dbg. At which privilege level is its code running?

Only the lowest two bits of cs hold the privilege level. 0x23 is 2 × 16 + 3 = 35, or 0010 0011 in binary, and its lowest two bits are 11 = 3. The upper bits pick a different code segment (a 32-bit one), but the level is still ring 3, user mode.

One bit marks a page as the kernel’s

Section titled “One bit marks a page as the kernel’s”

Lesson 11.10 said that a page-table entry’s user/supervisor bit, bit 2, decides whether ring 3 may touch the page. An entry combines the address of a physical page with flags describing that mapping. For the ordinary 4 KiB pages used here, the page address is aligned on a 4,096-byte boundary, leaving the low twelve bits available for flags. Chapter 12’s address-translation lesson will follow a complete walk; here we need only the permission flags in the lowest byte:

0x67 is 6 × 16 + 7 = 103, and 103 = 64 + 32 + 4 + 2 + 1, so bits 6, 5, 2, 1, and 0 are set. Bit 0 says the page is present, bit 1 that it may be written, and bit 2 that ring 3 may use it. The processor itself sets bit 5, accessed, the first time the page is used, and bit 6, dirty, the first time it is written. Bits 3, 4, and 7 control caching and are 0 here.

A page that holds kernel data looks almost the same:

0x67 − 0x63 = 4, and 4 = 2², so exactly one bit differs between these two example leaf entries: bit 2. A kernel page can be present, writable, and recently used, and still refuse access from ring 3. In a real page-table walk, the processor also considers permissions in the entries at higher levels; a single leaf byte is a teaching example, not a complete access decision.

The same call, one layer at a time

Section titled “The same call, one layer at a time”

Take a read like the ones in Lesson 11.5: a handle to the game opened with only query and read rights, and a request for 4 bytes at address 0x0050_1000. Lesson 11.10 drew the whole round trip as one sequence diagram, from your tool through kernel32.dll, kernelbase.dll, and ntdll.dll to the processor and the kernel, and back. This section follows that diagram one participant at a time.

Inside your process

Section titled “Inside your process”

ReadProcessMemory in kernel32.dll forwards to kernelbase.dll (Lesson 11.9), which calls NtReadVirtualMemory in ntdll.dll with the same arguments. The ntdll function is a stub: a few instructions whose only job is to make the system call. On 64-bit Windows its core is four instructions:

The first line exists because of the first thing syscall does. The Windows x64 calling convention passes a function’s first argument in rcx, but syscall overwrites rcx with the return address, so the stub moves the argument to r10 first, and the kernel knows to look for it there.

The number in eax is a system service number, an index into the kernel’s table of routines. The numbers are internal to Windows and change between builds, which is why this book never copies one into a program. In a debugger the stub also shows a test and a jump to an older entry instruction, int 2Eh, that some configurations use; either way, the processor arrives at an address the kernel chose.

Crossing over

Section titled “Crossing over”

The kernel’s entry code assumes that everything user mode handed it could be hostile. It switches from the program’s stack to a kernel stack that belongs to the thread, because the program’s stack pointer could point anywhere. It saves the user registers so they can be put back exactly. Then it looks the service number up in its table, rejects a number that is out of range, and calls the kernel’s own NtReadVirtualMemory.

Inside the kernel

Section titled “Inside the kernel”

Most of the kernel’s work is checking.

The address ranges must lie inside user space. The request covers 0x0050_1000 up to 0x0050_1000 + 4 = 0x0050_1004, and the tool’s buffer is also a user address. Both are far below the top of user space, which is a little under 0x0000_8000_0000_0000 on 64-bit Windows. A range that reached into the kernel’s half, or one long enough to run past the largest 64-bit number and wrap around to a small address, would be rejected here. The user/supervisor bit cannot do this job for the kernel: the copy runs in ring 0, and ring 0 may touch supervisor pages. So the kernel checks every range itself, and that check is why ReadProcessMemory cannot read kernel memory, whatever handle you hold.

The handle must carry the right the operation needs. The kernel finds the handle in the tool’s handle table and reads the rights granted when the handle was opened. Reading needs PROCESS_VM_READ, which is 0x0010. This handle was opened with PROCESS_QUERY_LIMITED_INFORMATION and PROCESS_VM_READ, so its rights are 0x1000 + 0x0010 = 0x1010. Written as bits, one byte at a time:

The test is a single AND. The kernel keeps only the bits that are set in both the handle’s rights and the rights it needs, and allows the operation only if every needed bit survived. 0x1010 AND 0x0010 = 0x0010, the whole requirement, so the read is allowed.

WriteProcessMemory needs PROCESS_VM_WRITE, 0x0020. That is 2 × 16 = 32 = 2⁵, bit 5, and bit 5 of 0x1010 is 0, so 0x1010 AND 0x0020 = 0: denied, whatever the tool’s author intended. The rights were fixed when the handle was created, and nothing done with the handle afterward can add to them.

Only then does it copy. The source address belongs to the game’s address space and the destination buffer belongs to the tool’s. The kernel must interpret each in the correct process context while copying; the exact internal mapping and copy strategy is a Windows implementation detail. If a page becomes unavailable during the operation, the API may report a failed or partial read. The caller must check the returned byte count instead of assuming that asking for four bytes means four arrived.

Returning

Section titled “Returning”

The kernel places a status code in rax and executes sysret, the reverse of syscall: the level drops back to 3, and execution resumes at the address saved in rcx, which is the ret right after syscall in the stub.

The status is an NTSTATUS, a 32-bit code whose top two bits give its severity: 00 success, 01 information, 10 warning, 11 error. STATUS_SUCCESS is 0. STATUS_ACCESS_DENIED is 0xC000_0022; hex C is binary 1100, so its top two bits are 11, an error. STATUS_PARTIAL_COPY is 0x8000_000D; hex 8 is 1000, so its top two bits are 10, a warning, because some of the bytes did arrive. kernelbase.dll translates the status into a Win32 error code for GetLastError, 5 for access denied and 299 for a partial copy, and reports success or failure to your tool.

A 32-bit game takes one extra hop

The book’s Windows labs are 32-bit programs. A 32-bit process on 64-bit Windows uses WoW64 (“Windows 32-bit on Windows 64-bit”) to translate the call into the native 64-bit service path. That may require converting pointer-sized arguments and structures; it is not a blind widening of every number. The two modes use different code segments, which is why cs reads 0023 in a 32-bit program and 0033 in a 64-bit one. The four-instruction stub above illustrates the native 64-bit path, not every instruction a 32-bit caller runs.

Knowledge check

Predict the kernel's answer

Saved

A tool opened a game with PROCESS_QUERY_INFORMATION (0x0400) and PROCESS_QUERY_LIMITED_INFORMATION (0x1000), so its handle's rights are 0x1400. It calls ReadProcessMemory, which needs PROCESS_VM_READ (0x0010). What happens?

0x0400 is 4 × 256 = 1,024 = 2¹⁰ (bit 10) and 0x1000 is 2¹² (bit 12), so 0x1400 has bits 12 and 10 set. The read needs bit 4, which is 0, so the AND is 0 and the kernel returns an error status. Nothing faults: the system call returns normally with STATUS_ACCESS_DENIED, and kernelbase.dll reports error 5. Running as administrator affects what OpenProcess may grant; it cannot add rights to a handle that already exists.

References: process security and access rights, using NTSTATUS values, and the Intel Software Developer Manuals for syscall, privilege levels, and page-table bits.

The process handle in this example authorized a copy between two processes. The processor supplied a controlled entrance; Windows checked the request inside it. The next lesson returns to the process view and saves a debugging snapshot of threads, modules, and registers in a dump. Chapter 12 then follows requests across DLL and driver boundaries, where the same checks on authority, arguments, and returned results still apply.

Knowledge check

Why the kernel checks addresses itself

Saved

Kernel pages have their user/supervisor bit cleared, so ring-3 code faults if it touches them. Why must the kernel's NtReadVirtualMemory still check that the requested range and the caller's buffer lie in user space?

The user/supervisor bit stops code running at ring 3. The copy itself runs in ring 0, inside the kernel, where the processor allows access to supervisor pages. If the kernel accepted a range in its own half of the address space, or one long enough to wrap around to a small address, it would copy kernel memory out to the caller or write the caller's bytes over kernel memory. So the kernel checks every address that user mode hands it before using it.
