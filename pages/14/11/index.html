🔌 Lesson 14.7Virtual Machines, Hardware, and Consoles

Emulator Timing and State

A toy console makes instruction costs, frame timing, save states, and register races concrete inside a Rust emulator.

About 20 minutes

Lesson 14.6 explained how an emulator works and ran one instruction of a made-up 8-bit console through the fetch–decode–execute loop. This lesson builds the whole console, follows a complete program through it cycle by cycle, and ends with a lab that runs it.

A toy 8-bit CPU

Section titled “A toy 8-bit CPU”

The CPU is made up, but it is built like the 8-bit processors in 1980s consoles. It has four registers:

  • PC, 8 bits, the program counter. Eight bits can name 2⁸ = 256 addresses, 0x00 to 0xFF, so the whole machine has 256 addresses.
  • A, 8 bits, the accumulator, where arithmetic happens.
  • X, 8 bits, a second register, used here as a loop counter.
  • Z, 1 bit, the zero flag: 1 when the last result was zero, 0 otherwise.

It understands seven instructions. Each begins with its opcode, and some carry an operand byte:

Bytes Written as Length What it does Cycles
01 n LDX #n 2 X = n; Z = 1 if X is 0 2
02 a LDA a 2 A = the byte at address a; Z = 1 if A is 0 3
03 n ADD #n 2 A = A + n, wrapping past 255 back to 0; Z = 1 if A is 0 2
04 a STA a 2 store A at address a 3
05 DEX 1 X = X − 1, wrapping below 0 to 255; Z = 1 if X is 0 1
06 a JNZ a 2 if Z is 0, jump: PC = a 2, or 3 if it jumps
FF HLT 1 stop 1

A # marks an immediate: #5 means the number 5 itself, while an operand without # is an address, and the instruction uses the byte stored there. STA and JNZ leave Z alone. Every other byte value is not an instruction, and the lab reports it as an error instead of guessing.

Every number in the last column comes from one rule: the CPU spends one cycle on each memory access, meaning each instruction byte it fetches and each data byte it reads or writes, plus one extra cycle when a jump is taken, to load the new address into PC. So LDX #n and ADD #n each fetch 2 bytes, 2 cycles; LDA a fetches 2 and reads 1, 3 cycles; STA a fetches 2 and writes 1, 3 cycles; DEX and HLT each fetch 1, 1 cycle; and JNZ a fetches 2, plus 1 if it jumps. Real 8-bit CPUs, such as the 6502 inside the NES, have similar costs for similar reasons.

The program in memory

Section titled “The program in memory”

Trace the program

Section titled “Trace the program”

The first pass goes from power-on through the jump back:

Step PC Instruction What happens A X Z Gold Cycles
1 0x00 LDX #2 X = 2, not 0, so Z = 0 0 2 0 10 0 + 2 = 2
2 0x02 LDA 0x80 A = the byte at 0x80, 10 10 2 0 10 2 + 3 = 5
3 0x04 ADD #5 A = 10 + 5 = 15 15 2 0 10 5 + 2 = 7
4 0x06 STA 0x80 gold = A = 15 15 2 0 15 7 + 3 = 10
5 0x08 DEX X = 2 − 1 = 1, not 0, so Z = 0 15 1 0 15 10 + 1 = 11
6 0x09 JNZ 0x02 Z is 0, so PC = 0x02 15 1 0 15 11 + 3 = 14

The second pass repeats the loop body, and this time the counter runs out:

Step PC Instruction What happens A X Z Gold Cycles
7 0x02 LDA 0x80 A = the byte at 0x80, 15 15 1 0 15 14 + 3 = 17
8 0x04 ADD #5 A = 15 + 5 = 20 20 1 0 15 17 + 2 = 19
9 0x06 STA 0x80 gold = A = 20 20 1 0 20 19 + 3 = 22
10 0x08 DEX X = 1 − 1 = 0, so Z = 1 20 0 1 20 22 + 1 = 23
11 0x09 JNZ 0x02 Z is 1, no jump 20 0 1 20 23 + 2 = 25
12 0x0B STA 0xF0 the display shows 20 20 0 1 20 25 + 3 = 28
13 0x0D HLT stop 20 0 1 20 28 + 1 = 29

In hex, 15 is 0x0F and 20 is 1 × 16 + 4 = 0x14. At step 11, fetching JNZ and its operand has already moved PC from 0x09 to 0x09 + 2 = 0x0B, so not jumping needs no extra work: the next instruction is simply the next one.

The whole run takes 29 cycles: 2 for LDX, then 3 + 2 + 3 + 1 + 3 = 12 for the first pass, 3 + 2 + 3 + 1 + 2 = 11 for the second, and 3 + 1 = 4 for the ending. 2 + 12 + 11 + 4 = 29. When the machine stops, it looks like this:

Knowledge check

Why the loop ends

Saved

At step 11 of the trace, JNZ 0x02 does not jump. Why not?

JNZ jumps only while Z is 0, and Z records whether the last result was zero. The instruction just before it, DEX, computed X = 1 − 1 = 0, so Z became 1. ADD sets Z too, but DEX ran after it, and neither STA nor JNZ changes Z.

The interpreter in Rust

Section titled “The interpreter in Rust”

The lab’s step function is that trace, as code. It fetches the opcode, decodes it, and runs one arm of a match. Each arm’s last value is the instruction’s cost in cycles:

fetch reads the byte at PC and adds 1 to PC, so each call consumes one byte of the instruction. Opcode::decode is a match on the byte that returns None for anything that is not an instruction, and the ? turns that into an IllegalOpcode error that names the address. A real CPU meeting an unknown opcode might raise an exception, as x86 does, or do something undocumented. An emulator that guessed would hide bugs in the guest program and in itself.

Because step decodes every instruction each time it runs, the loop body from 0x02 to 0x0A is decoded afresh on both passes. That repetition is what the dynamic recompilers of Lesson 14.6 remove.

The memory map as code

Section titled “The memory map as code”

The toy console maps RAM from 0x00 to 0xEF, the display at 0xF0, the buttons at 0xF1, and nothing from 0xF2 to 0xFF. In the lab, the map is two functions. Every read the CPU makes, including every fetch, goes through read, and every store goes through write:

0x00..=0xEF is Rust’s range from 0x00 to 0xEF with both ends included. That is 0xF0 = 15 × 16 = 240 addresses, exactly the length of the ram array. DISPLAY and BUTTONS are constants holding 0xF0 and 0xF1. So step 12’s STA 0xF0 calls write with address 0xF0 and value 20, the second arm stores 20 in the display register, and nothing in step has to know that 0xF0 is not RAM.

Real consoles work the same way on a larger scale. The NES has 2 KiB of RAM at 0x0000 to 0x07FF; 0x0800 is 8 × 256 = 2,048 bytes. Its address decoder ignores the top address bits for RAM, so the same 2,048 bytes answer again at 0x0800, 0x1000, and 0x1800: the range up to 0x2000, which is 2 × 16³ = 2 × 4,096 = 8,192 bytes, holds 8,192 ÷ 2,048 = 4 copies. This is called mirroring. The picture chip’s registers start at 0x2000, and the controllers answer at 0x4016 and 0x4017. An NES emulator’s read is a bigger version of the one above.

Frame budgets and overshoot

Section titled “Frame budgets and overshoot”

A real frame’s budget, like the one in Lesson 14.6, runs to thousands of cycles, while the whole traced program takes only 29. So the lab uses a tiny budget of 18 cycles, which ends a frame partway through the program. Its run loop steps whole instructions until the budget is used or the CPU halts:

The check used < budget happens before each instruction, never during one, because an instruction cannot stop halfway. After step 7 the run has used 17 cycles, which is less than 18, so it runs step 8, an ADD worth 2 cycles, and reaches 19. That is not less than 18, so the frame ends. It overshot by 19 − 18 = 1 cycle, and the emulator gives the next frame 18 − 1 = 17 cycles, which keeps the long-run average at exactly 18 per frame. The overshoot can never exceed 2: the frame’s last instruction starts with at most 17 cycles used and costs at most 3, and 17 + 3 = 20 = 18 + 2.

A save state, byte by byte

Section titled “A save state, byte by byte”

At that frame boundary the new gold total exists only in A, so a snapshot of RAM alone would restore gold = 15 and lose the 20. The lab’s SaveState copies every part of the machine and converts it to a row of bytes:

The halted flag records whether HLT has run, and the cycle count is the emulator’s position in time, so a loaded state resumes at the same point in the frame. Reading a state back refuses anything that is not exactly 255 bytes long, and refuses a Z or halted byte that holds anything other than 0 or 1, because no real run of the machine could have produced it.

A cheat code racing a register

Section titled “A cheat code racing a register”

The lab’s run_frame runs one frame and then applies every cheat, the way a cheat cartridge wrote its values once per frame:

It returns the overshoot, which the caller takes off the next frame’s budget. saturating_sub subtracts but stops at 0 instead of wrapping around, so a frame that ends early because the CPU halted reports no overshoot.

Give it the 18-cycle frames and one cheat: write 99 to gold. Frame 1 runs steps 1 to 8, and then the cheat writes 99 to 0x80. But the game had already copied gold into A and added 5. Frame 2, with its budget of 17, starts with step 9, which stores A’s 20 over the 99, and steps 9 to 13 finish the program in 3 + 1 + 2 + 3 + 1 = 10 cycles, well inside the budget. Step 12 shows 20 on the display, and at the end of frame 2 the cheat writes 99 again:

Run the toy console

Section titled “Run the toy console”

The portable lab toy_emulator_lab.rs is the console from this lesson: the CPU, the 240 bytes of RAM, the display and buttons registers, the step interpreter, a run loop with a cycle budget, frames with constant-write cheats, and a SaveState that copies the registers and memory and converts them to and from 255 bytes.

Build it, then run it from the rust-labs folder:

The lab first runs the traced program one instruction at a time and prints the same numbers as the tables above. Then it stops a run at the 18-cycle boundary, takes a save state, runs to the end, loads the state, and runs again, arriving at an identical machine. Finally, it runs two frames with the gold cheat and shows RAM at 99 while the display says 20. The tests check every one of the 13 trace steps, both costs of JNZ, wrapping at 255, the budget stop, the save state’s round trip through 255 bytes, the rejection of damaged save states and unknown opcodes, and the cheat’s race with register A.

Then give the console a watchpoint: a watch: Option<u8> field, and an if in write that records self.cpu.pc whenever the watched address is written. Before you run the traced program with gold watched, predict which PC values it records and why they are not 0x06, the address of the STA.

Knowledge check

Paying back the overshoot

Saved

The toy console's frame budget is 18 cycles. A frame stops at 19 cycles, because the instruction that crossed the budget could not stop halfway. Why does the emulator give the next frame 17 cycles instead of 18?

An instruction always runs to its end, so a frame can pass its budget: here step 8, an ADD worth 2 cycles, started at 17 and finished at 19. If every frame then got a fresh 18, the extra cycles would pile up and the emulated machine would run ahead of real time. Subtracting each overshoot from the next budget cancels it, so over many frames the average is exactly 18.
