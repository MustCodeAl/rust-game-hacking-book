🛡️ Lesson 12.7Process Boundaries and Physical Memory

DMA and Physical Memory

DMA gives devices a path to memory, while page tables and IOMMUs determine which physical bytes correspond to an address.

Read or listenPrint chapter or book
About 40 minutes

The kernel boundary also determines how devices reach memory. A process sees virtual addresses; a device moves bytes through a physical-memory path with its own access rules. Understanding both maps makes an offline capture interpretable without assuming that a game address is a RAM offset.

DMA is a way devices move data

Section titled “DMA is a way devices move data”

DMA means direct memory access. A capable device can transfer data without asking the CPU to copy each byte. Storage, networking, graphics, and other high-throughput devices use DMA because involving the CPU in every tiny move would waste time.

Here DMA refers to device transfers. It is different from dynamically allocating memory in a program, where the program asks its allocator for space and receives an address. The shared word memory does not make those the same operation.

DMA is not automatically a cheat or an attack. It is a hardware feature. Security problems appear when a device can reach memory it should not reach, or when software trusts a device too much.

This chapter uses ordinary offline capture files from an owned machine, virtual machine, or synthetic test. It does not configure DMA hardware, install a kernel driver, disable an IOMMU, access a live game, or bypass anti-cheat.

Physical and virtual addresses are different maps

Section titled “Physical and virtual addresses are different maps”

A CPU process usually uses virtual addresses. The memory-management unit translates them through page tables to physical addresses in RAM.

Treat translation as a function with an address-space input:

That describes the CPU’s complete decision. The small offline walker in Lesson 12.8 answers a narrower question: where do the recorded, present entries lead? It checks presence and file bounds but does not emulate every read, write, execute, and user/supervisor permission check the CPU would make. A physical result alone is therefore not proof that a live process could read or write the address.

Two processes may both use virtual address 0x1000 because they supply different page-table roots. The access type matters too: a mapping may permit a read but reject a write or instruction fetch. A virtual address by itself therefore does not name a location: the address space and the access rules are part of its meaning.

It is like asking for apartment 1000 without naming the building. The apartment number is useful only after the building is chosen; likewise, 0x1000 is useful only with the correct page-table root. The analogy is limited: page tables can remap or remove a page while a program runs, and they separately record whether a read, write, or instruction fetch is allowed. The diagram below shows the same virtual number reaching two different physical places.

An offline physical capture contains bytes arranged by physical address. A debugger’s pointer such as 0x00007FF6_12341000 is virtual. To connect them, the reader needs the correct page-table root for that address space.

The idea transfers to a guest virtual machine in Lesson 14.1: a guest’s virtual address first needs its guest page tables, and the resulting guest physical address needs a second translation through the hypervisor’s map. Neither stage can be skipped just because both addresses are written as numbers.

CR3 points to the first translation table

Section titled “CR3 points to the first translation table”

On ordinary x86-64 systems using four-level paging, the CPU’s CR3 register identifies the physical base of the top table. The virtual address supplies four nine-bit indices and a twelve-bit offset:

Virtual-address bits Use
47–39 PML4 index
38–30 page-directory-pointer index
29–21 page-directory index
20–12 page-table index
11–0 byte offset inside a 4 KiB page

Each table has 512 eight-byte entries. A normal translation reads one entry at each level, checks its present bit, takes the next table’s physical address, and finally adds the page offset.

Large pages can finish earlier: a page-directory-pointer entry may map 1 GiB, and a page-directory entry may map 2 MiB.

Canonical addresses catch bad input early

Section titled “Canonical addresses catch bad input early”

With the common 48-bit virtual-address form, bits 63–48 must repeat bit 47. An address that breaks this rule is noncanonical. The lab rejects it before reading the capture:

Rejecting impossible input gives a clearer error than following nonsense offsets into a file.

An IOMMU gives devices their own map

Section titled “An IOMMU gives devices their own map”

An IOMMU is an input/output memory management unit. It does for devices what the page tables above do for processes: it sits between a device and physical memory and translates the addresses the device asks for, so the operating system can limit a device to approved physical regions instead of letting it reach all RAM.

Windows exposes protections including Kernel DMA Protection on supported hardware. Microsoft explains that it uses the IOMMU to isolate capable peripherals and protect against malicious DMA devices. Read the current Microsoft overview for requirements and behavior.

If a protected machine blocks DMA, that is the system working correctly. Keep the protections enabled and use the synthetic capture created by the tests or an offline hypervisor capture.

A capture is a snapshot, not a live process

Section titled “A capture is a snapshot, not a live process”

An offline image has important limits:

  • threads do not run while you inspect it;
  • pages may have changed immediately after capture;
  • some virtual pages may be absent, swapped, compressed, or intentionally omitted;
  • you need the correct CR3 and architecture details;
  • device memory and CPU caches may not be represented;
  • the capture may contain private data unrelated to the lesson.

A capture holds whatever was in RAM, including private data unrelated to the lesson, so it is stored securely and deleted when the lab no longer needs it. It also cannot be interpreted on its own. Its origin, capture time, build, architecture, capture method, and a cryptographic hash travel with the file, because a CR3 value or a structure layout means something only for the machine state it came from, and the hash is what shows the bytes have not changed since.

What “using DMA” means in this book

Section titled “What “using DMA” means in this book”

The useful computer-science problem is translating and validating captured memory. The complete implementation:

  1. opens a normal file read-only;
  2. accepts a physical CR3 value and virtual address;
  3. walks x86-64 page tables inside that file;
  4. checks present bits and bounds;
  5. supports 4 KiB, 2 MiB, and 1 GiB mappings while leaving live CPU access permissions as a separate question;
  6. prints a bounded hexdump.

No hardware-specific SDK is needed. This keeps the lesson reproducible and focuses attention on address translation rather than stealth, firmware, or bypasses.

For the exact paging bit definitions, use the current Intel Software Developer Manuals as the primary architecture reference.
