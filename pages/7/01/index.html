A one-page summary of “What a Windows Executable Contains” you can keep beside your notes. Plain Markdown.

Lesson 5.1 — What a Windows Executable Contains: cheatsheet

  • Remember: A PE file is a chain of headers. Each one tells the parser where the next begins, ending at the section table that maps file bytes to memory.
  • Also useful: Static storage is a lifetime term; static linking is a packaging choice. Neither makes a file offset equal to a live virtual address.

Key terms

  • Portable Executable: It is a Portable Executable, usually shortened to PE.
  • file offset: A position in the file is a file offset.
  • RVA: A position in the loaded image is an RVA, a relative virtual address, meaning a distance from wherever Windows put the module.
  • bytes: In the excerpts that follow, bytes is the whole EXE file read into a Vec<u8>; these helpers check every field access against that file.

Formulas and patterns

  • file layout on disk image layout in a process; file offset -> bytes in one section <-> RVA -> mapped bytes in that section; + live module base; = live virtual address

Review

  • Q: Why is a PE RVA not always the same number as a file offset? A: A section's place in memory can differ from its place on disk
  • Q: A PE section reports an instruction RVA of 0x1200, and Windows loads the module at 0x7FF600000000. What is the live virtual address? A: 0x7FF600001200, the live base plus the RVA

Why an EXE needs a map

Section titled “Why an EXE needs a map”

A Windows .exe is not one solid blob of CPU instructions. It is a Portable Executable, usually shortened to PE. Its headers tell Windows where the code, read-only data, writable data, imports, resources, and relocation information live.

First we will learn the file’s map and use it to translate positions on disk into live addresses. Then we will ask two different runtime questions: where are candidate bytes or values, and which instructions actually execute? Scanners, a disassembler, a debugger, and ETW each answer a different part. Knowing the map keeps their addresses anchored to a real build.

The same section occupies a place in the file and a place in memory, and those two places are numbered differently. A position in the file is a file offset. A position in the loaded image is an RVA, a relative virtual address, meaning a distance from wherever Windows put the module. Use two layouts connected by the section table:

The layouts differ because sections have separate file and virtual alignments, zero-initialized data may occupy memory without taking equal file space, and Windows may apply relocations and resolve imports after mapping. A section row supplies the mapping information for converting a location in one layout to the corresponding location in the other; the numbers are related but not interchangeable.

Alternative: Think of printed page numbers versus e-book page numbers: one text, two numbers, and a contents table converts between them. The section table does that job.

A parser follows the file’s own chain of verified offsets. Each header tells it where the next structure begins or how large that structure is:

Never skip directly to a later box using a guessed offset. A damaged or wrong header should stop the parse before its numbers are trusted.

The path through the headers

Section titled “The path through the headers”

The diagram above is a parser’s route, not six unrelated names. Each structure either confirms that this is a PE image or tells us where the next structure begins. Read this indentation as a chain of dependencies: we cannot trust a section row until the headers that locate its table have passed their checks.

The “optional” header is not optional for an executable image. That old name survives because object files can omit it. The parser’s useful result is a bounded section table; the next lesson uses its rows to translate an RVA into the corresponding file bytes.

TL;DR: A PE file is a chain of headers. Each one tells the parser where the next begins, ending at the section table that maps file bytes to memory.

Read numbers without pointer casts

Section titled “Read numbers without pointer casts”

For an on-disk file, a byte slice is safer and easier than casting random offsets to Windows structs:

Three ideas are hiding in those few lines:

  1. checked_add refuses an integer wraparound.
  2. get refuses an out-of-file slice.
  3. from_le_bytes states that PE numbers use little-endian byte order.

That is what “safe parsing” means: malformed input becomes an error instead of an invalid memory access. The three integer helpers differ only in how many bytes they take and which little-endian integer type they construct. In the excerpts that follow, bytes is the whole EXE file read into a Vec<u8>; these helpers check every field access against that file. The complete lab handles opening the path and reporting errors as well.

Narration: A parser that trusts a damaged file’s numbers can read outside its buffer. Programs that open untrusted files are a classic target for this mistake, so checks matter.

Find the PE and COFF headers

Section titled “Find the PE and COFF headers”

The COFF header, named for the older Common Object File Format it comes from, is the small fixed block right after the four-byte PE\0\0 signature. It gives the basics a parser needs before anything else: which CPU the machine code targets, how many section rows follow, and how large the next header is.

The cap of 96 is deliberately boring. Real course targets do not need thousands of sections, so a wild count means the offset is wrong or the file is damaged.

Tell PE32 from PE32+

Section titled “Tell PE32 from PE32+”

The optional-header magic is 0x10B for PE32 and 0x20B for PE32+. Because their fields have different sizes, the image-base offset changes:

PE32+ also omits BaseOfData; its eight-byte ImageBase starts in the space where PE32 has that four-byte data landmark. Offsets here are relative to the optional header, as specified by Microsoft’s PE format:

Field PE32 PE32+
BaseOfCode Four bytes at +20 Four bytes at +20
BaseOfData Four bytes at +24 Absent
ImageBase Four bytes at +28 Eight bytes at +24

BaseOfData being absent does not mean the image has no data sections. The section rows still describe their RVAs and sizes.

The games used by the memory-patching chapters are the specified 32-bit course builds, so their magic should be 0x10B. The parser supports both formats because a tool should explain what it found instead of guessing.

Walk the 40-byte section rows

Section titled “Walk the 40-byte section rows”

The section table begins immediately after the optional header. Each row is 40 bytes:

.text is normally readable and executable. .rdata is normally readable. .data is normally readable and writable. Names are only conventions; the characteristic flags are what the loader actually uses to set each section’s page protection.

Linked code still needs a file-to-image map

Section titled “Linked code still needs a file-to-image map”

Static linking copies the needed library implementation into the output module. DLL linking keeps that implementation in another module and records how to find its exported functions. An import library can help link an EXE to a DLL without copying the DLL’s implementation into the EXE. Microsoft’s DLL overview describes load-time and run-time linking. Once loaded, the DLL uses the calling process’s virtual address space and the calling thread’s stack.

Whichever linking choice produced the module, its file bytes still need the section map. For an illustrative .text row with raw start 0x400 and RVA start 0x1000, file byte 0x520 is 0x120 bytes into the section. Its RVA is 0x1120; at live base 0x00400000, its virtual address is 0x00401120. This example assumes the byte lies inside that section’s file-backed data.

use std::{fs, path::PathBuf};

use anyhow::{Context, Result};

fn bytes_at(bytes: &[u8], offset: usize, count: usize) -> Result<&[u8]> {
    let end = offset.checked_add(count).context("PE offset overflowed")?;
    bytes
        .get(offset..end)
        .with_context(|| format!("PE field {offset:#x}..{end:#x} is outside the file"))
}

fn u16_at(bytes: &[u8], offset: usize) -> Result<u16> {
    Ok(u16::from_le_bytes(bytes_at(bytes, offset, 2)?.try_into()?))
}

fn u32_at(bytes: &[u8], offset: usize) -> Result<u32> {
    Ok(u32::from_le_bytes(bytes_at(bytes, offset, 4)?.try_into()?))
}

fn u64_at(bytes: &[u8], offset: usize) -> Result<u64> {
    Ok(u64::from_le_bytes(bytes_at(bytes, offset, 8)?.try_into()?))
}

fn main() -> Result<()> {
    let path = PathBuf::from(
        std::env::args()
            .nth(1)
            .context("usage: pe_inspector <game.exe-or-dll>")?,
    );
    let bytes = fs::read(&path).with_context(|| format!("could not read {}", path.display()))?;

    anyhow::ensure!(bytes_at(&bytes, 0, 2)? == b"MZ", "missing DOS MZ signature");
    let pe_offset = usize::try_from(u32_at(&bytes, 0x3c)?)?;
    anyhow::ensure!(
        bytes_at(&bytes, pe_offset, 4)? == b"PE\0\0",
        "missing PE signature"
    );

    let coff = pe_offset.checked_add(4).context("COFF offset overflowed")?;
    let machine = u16_at(&bytes, coff)?;
    let section_count = usize::from(u16_at(&bytes, coff + 2)?);
    let optional_size = usize::from(u16_at(&bytes, coff + 16)?);
    anyhow::ensure!(
        section_count <= 96,
        "unreasonable section count: {section_count}"
    );

    let optional = coff.checked_add(20).context("optional-header overflowed")?;
    let magic = u16_at(&bytes, optional)?;
    let entry_rva = u32_at(&bytes, optional + 16)?;
    let image_base = match magic {
        0x10b => u64::from(u32_at(&bytes, optional + 28)?),
        0x20b => u64_at(&bytes, optional + 24)?,
        other => anyhow::bail!("unsupported optional-header magic {other:#06x}"),
    };
    let section_alignment = u32_at(&bytes, optional + 32)?;
    let file_alignment = u32_at(&bytes, optional + 36)?;

    println!("{}", path.display());
    println!("  machine:          {machine:#06x}");
    println!(
        "  PE kind:          {}",
        if magic == 0x10b { "PE32" } else { "PE32+" }
    );
    println!("  preferred base:   {image_base:#018x}");
    println!("  entry-point RVA:  {entry_rva:#010x}");
    println!(
        "  preferred entry:  {:#018x}",
        image_base + u64::from(entry_rva)
    );
    println!("  section alignment:{section_alignment:#010x}");
    println!("  file alignment:   {file_alignment:#010x}");
    println!("  sections:         {section_count}");

    let section_table = optional
        .checked_add(optional_size)
        .context("section-table offset overflowed")?;
    for index in 0..section_count {
        let start = section_table
            .checked_add(index.checked_mul(40).context("section index overflowed")?)
            .context("section offset overflowed")?;
        let name_bytes = bytes_at(&bytes, start, 8)?;
        let name_end = name_bytes.iter().position(|byte| *byte == 0).unwrap_or(8);
        let name = String::from_utf8_lossy(&name_bytes[..name_end]);
        let virtual_size = u32_at(&bytes, start + 8)?;
        let virtual_address = u32_at(&bytes, start + 12)?;
        let raw_size = u32_at(&bytes, start + 16)?;
        let raw_offset = u32_at(&bytes, start + 20)?;
        let flags = u32_at(&bytes, start + 36)?;
        let access = format!(
            "{}{}{}",
            if flags & 0x4000_0000 != 0 { 'R' } else { '-' },
            if flags & 0x8000_0000 != 0 { 'W' } else { '-' },
            if flags & 0x2000_0000 != 0 { 'X' } else { '-' },
        );
        println!(
            "  {name:<8} RVA {virtual_address:#010x}  virtual {virtual_size:#010x}  file {raw_offset:#010x}+{raw_size:#010x}  {access}"
        );
    }
    Ok(())
}

“The instruction is at RVA 0x003CCD91 inside .text, not at file offset 0x003CCD91, and Windows will add the live module base before the CPU can execute it.”
