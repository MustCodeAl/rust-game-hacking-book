🧰 Lesson 5.2Executable Files and Runtime Analysis

File Offsets, RVAs, and Live Addresses

Connect positions in a PE file to relative virtual addresses and the addresses Windows gives its loaded modules.

Read or listenPrint chapter or book
About 28 minutes

Keep four address terms separate

Section titled “Keep four address terms separate”

The PE map in Lesson 5.1 told us that an instruction can have one position in the EXE file and another in a running process. Suppose your debugger recorded an instruction at 0x007CCD91 yesterday. To find it after restarting the game, you need to know which part of that number belonged to the module and which part Windows chose for that run.

We will use four names for the four different positions involved:

  • a preferred image base is where the file would like to be loaded;
  • a live module base is where Windows placed it in this process run;
  • an RVA is a distance from the beginning of the module;
  • a virtual address is the final live address used by the CPU.

An RVA is not a pointer stored in the game. It is arithmetic describing a location inside one loaded image. The PE file’s section table maps RVAs to sections such as code or data.

Do not confuse an RVA with a file offset. A file offset counts bytes in the EXE on disk. An RVA counts from the mapped image base after Windows has arranged sections according to virtual addresses and alignment. They can differ.

The complete vocabulary is worth making explicit:

Name Coordinate system Typical formula
File offset Bytes from the start of the file on disk section.raw_ptr + offset_in_section
RVA Bytes from the start of the mapped image section.virtual_address + offset_in_section
Preferred VA Address requested by the PE headers preferred_image_base + RVA
Live VA Address in this process now live_module_base + RVA

These are coordinates in different spaces. Adding a live module base to a file offset is the binary-analysis version of adding meters to seconds: the numbers fit in an integer, but the operation has no useful meaning.

The mapping is valid only when the RVA lies in the section’s mapped range and offset_in_section < RS. A section can have more virtual bytes than raw bytes; the loader fills that tail with zeros, so no corresponding file byte exists. Conversely, alignment padding on disk is not necessarily meaningful mapped memory. Header RVAs below SizeOfHeaders are a special case that commonly map directly to the same file offset.

Why an address moves

Section titled “Why an address moves”

Old notes often show an address such as 0x007CCD91. That may be the address from one run, not a permanent location.

Windows can load an executable at a different base address each run; that is what ASLR randomizes. The useful part that usually stays the same for an exact build is the distance from the module’s beginning: the Relative Virtual Address.

ASLR makes fixed absolute addresses less predictable. Windows can relocate an image when its PE metadata supports relocation. The module’s internal layout for that exact file usually stays the same, so base-plus-RVA reaches the same instruction even when the base changes.

The useful invariant is algebraic: for one exact module build, an internal location’s displacement from the module base can remain stable even when the base changes. ASLR changes the first term, not the meaning of the second:

The RVA is stable only relative to that image layout. Recompiling or updating the game can move the instruction inside the module, so the build identity must travel with the RVA.

RVA is not a version check

Section titled “RVA is not a version check”

An RVA can move when the game is rebuilt. Keep all three checks:

  1. exact supported game version;
  2. live module base plus the version’s RVA;
  3. exact original bytes or a unique pattern at the final address.

That is why the code-cave installers reject unknown bytes instead of hoping the address is close enough.
