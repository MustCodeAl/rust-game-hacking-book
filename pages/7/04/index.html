Byte Signatures and Pattern Scanning

Lesson 5.4 — Byte Signatures and Pattern Scanning: cheatsheet

In a nutshell

  • A good signature keeps the stable bytes and wildcards the ones that legitimately change. It must find the same instruction in every build you support.

Another way to think about it

  • Think of searching a library by a book's first line: one hit is a lead, many hits mean your quote is too common, and none means wrong library.

Key terms

  • byte pattern: A byte pattern searches the current module for a distinctive instruction sequence.
  • overfits: A pattern overfits when it memorizes accidental details from one executable instead of describing the instruction identity you meant to find.
  • not: Notice what it does not do: it does not scan every allocation, patch the result, or assume matching bytes prove the instruction’s meaning.

Check yourself

  • Q: Why does a byte pattern use wildcards for some positions?

A: Displacements or addresses may vary between builds while the surrounding opcode structure stays meaningful

  • Q: A code pattern matches six executable locations in the exact supported build. What is the safest next step?

A: Refine the signature and verify the surrounding instructions until one meaning is proven

  • Q: After a game update, why can the old module-base-plus-RVA calculation point at the wrong code even when the base is correct?

A: The instruction may have moved within the module, so the old RVA lands on different bytes

  • Q: What does a byte pattern match give you by itself?

A: A candidate location that still needs checking in each supported build

Why patterns help

Section titled “Why patterns help”

Lesson 5.2 recovered a live address by adding the current module base to a known RVA. That works for the exact build whose RVA you measured. After a game update, the gold-changing instruction may move within the module, so the old RVA can point at different code even when the base calculation is perfect.

A byte pattern searches the current module for a distinctive instruction sequence. It gives us a candidate location to check in each explicitly supported build; it does not by itself prove that the candidate is still the gold-changing instruction.

Some bytes encode registers or opcodes and stay stable. Others encode addresses or displacements and may change.

What a signature actually describes

Section titled “What a signature actually describes”

The CPU sees one continuous byte stream. The disassembler groups that stream into instructions, and each instruction may contain several kinds of information:

Part Plain-English meaning Usually stable?
Opcode Which operation to perform, such as subtract or call Often
ModR/M and SIB Which registers and addressing shape to use Often
Displacement A field offset or distance from another address Sometimes
Immediate A number stored directly inside the instruction Depends on the rule
Relative target How far a call or jump travels Often changes when code moves

Suppose two supported builds both subtract a value and then load a nearby field. The instruction shape may stay recognizable while the relative call target between those instructions moves. A useful signature keeps the stable shape and places wildcards over the changing target bytes.

Written out, that comparison looks like this. The same two instructions, taken from two builds of one game:

The first three bytes are sub dword ptr [edi+4], eax: the operation, the registers, and the field offset, none of which the compiler had any reason to change. E8 is a call, and the four bytes after it hold a relative distance to the target, measured from the end of the call instruction. That distance shifts whenever either the calling code or the called function moves, even by a single byte, even though it still calls exactly the same function.

So the signature keeps the first four bytes and wildcards the last four:

Wildcards are not “bytes we forgot.” Each one here has a stated reason — “relative call displacement, changes whenever code moves” — and that written reason is the difference between a wildcard and a shrug. Too few wildcards make the signature fragile. Too many make it common and ambiguous.

A signature can overfit one recording

Section titled “A signature can overfit one recording”

A pattern overfits when it memorizes accidental details from one executable instead of describing the instruction identity you meant to find. An exact 30-byte sequence may work perfectly on the build used to create it and fail after an unrelated compiler layout change. The opposite mistake is a pattern so loose that it matches ordinary code everywhere.

Pattern behavior Meaning Correct response
one match only in the design build may be overfitted compare another build you actually intend to support
many matches in the design build under-specified add stable decoded context
one decoded candidate in every declared profile appropriately scoped keep each build fingerprint and semantic check

When supporting two exact builds, design the candidate signature with one build and test it against the other before calling it version-tolerant. Then reverse the test: bytes from each build should locate the same kind of instruction, not merely return one arbitrary address.

Do not weaken a pattern until it matches an unknown build and then declare success. If the course supports only one build, an exact fingerprint plus a build-specific signature is more honest than pretending the signature is portable. The goal is a pattern that finds the same instruction in every build you named, not the longest or shortest possible byte string.

TL;DR: A good signature keeps the stable bytes and wildcards the ones that legitimately change. It must find the same instruction in every build you support.

Represent exact and wildcard bytes

Section titled “Represent exact and wildcard bytes”

A written signature such as 29 47 04 E8 ?? ?? ?? ?? contains two different kinds of instruction: compare this byte exactly, or accept any byte at this position. Represent that choice in the type rather than reserving a magic value like zero. Why this version?

The direct indexes can panic near the end of the buffer, while get turns an incomplete window into false. PatternByte prevents a magic byte such as 0x00 from secretly meaning “wildcard.” zip and all state the rule directly: each discovered byte must satisfy its corresponding pattern item.

Read this function from the outside inward:

  1. bytes.get(range) requests a window without risking an out-of-bounds panic.
  2. saturating_add prevents the end calculation from wrapping to a small number.
  3. zip pairs every found byte with one pattern item.
  4. all returns true only when every pair is acceptable.
  5. Any accepts the found byte; Exact(value) accepts only that value.

The function borrows both slices. It does not copy the module again and does not own the pattern. That is why its signature uses &[u8] and &[PatternByte].

Scan safely

Section titled “Scan safely”

One safe comparison is not a scan yet. The next function tries every start position where the full pattern could fit, collecting offsets in the local buffer. If the buffer has three bytes and the pattern has two, both starts 0 and 1 must be considered; start 1 is easy to miss with an exclusive range.

Use <= so a match beginning at the final possible offset is included.

For n input bytes and an m-byte pattern, this simple algorithm does at most roughly n × m comparisons. That is easy to reason about and fast enough for bounded course modules. More advanced search algorithms matter only after measurement shows this loop is the bottleneck.

The early return handles two important edge cases. An empty pattern would otherwise “match” at every offset, and subtracting a longer pattern length from the input length would underflow.

Scan the correct range

Section titled “Scan the correct range”

Do not scan an entire process by default. Locate the intended module and executable section, copy that bounded region, and scan the local buffer.

For a PE image, confirm:

  • DOS and PE signatures;
  • section table bounds;
  • executable characteristic;
  • virtual address plus size stays in the module.

Libraries such as goblin can parse PE files, but live in-memory images still need careful address and section validation.

This separation matters. ReadProcessMemory works at the Windows boundary and can fail because a page changed. Once the bytes are in a local Vec<u8>, the matching loop uses only checked slices: no remote pointers, no changing protections, and no partial Windows reads during comparisons.

Require one match

Section titled “Require one match”

The scan returns a list because one pattern can occur more than once. Before turning an offset into a candidate instruction address, make the three possible counts explicit. Returning the first entry would disguise an ambiguous signature as a successful find.

Picking the first of five matches is not version tolerance.

Alternative: Think of searching a library by a book’s first line: one hit is a lead, many hits mean your quote is too common, and none means wrong library.

The three outcomes mean different things:

  • zero matches means the build, range, or pattern assumption is wrong;
  • one match means the signature has located one candidate, which still needs semantic verification;
  • several matches mean the signature does not contain enough identity.

Do not “fix” ambiguity by silently lengthening the scan to another unrelated section. Extend the pattern into the instructions around the intended one until only it matches.

Verify surrounding meaning

Section titled “Verify surrounding meaning”

After a match:

  • disassemble the surrounding bytes;
  • confirm whole expected instructions;
  • verify the relative target or field offset;
  • check the supported module fingerprint;
  • reject an unknown build.

A pattern only finds where bytes match. It does not replace target-version checks or instruction decoding.

Narration: A matcher that stops one position early passes every middle-of-buffer test and still misses a match at the very end. Off-by-one slips hide at the edges.

Read the complete program as a pipeline

Section titled “Read the complete program as a pipeline”

The executable at the end of the lesson has five phases:

  1. Process::open_by_name finds the exact target and owns its Windows process handle.
  2. process.module returns the current base and mapped size of wesnoth.exe.
  3. process.regions asks Windows how that module is divided and keeps readable executable regions.
  4. Each accepted region is copied before .windows(3) compares local slices.
  5. The program prints every match and refuses success unless the match count is exactly one.

Notice what it does not do: it does not scan every allocation, patch the result, or assume matching bytes prove the instruction’s meaning. Those are separate decisions with separate checks.

Run it against Wesnoth

Section titled “Run it against Wesnoth”
Windows VM

The course binary opens the live 32-bit wesnoth.exe, finds its current main-module base, visits its readable executable regions, and searches for the exact gold-subtraction instruction bytes 29 42 04. Those are measured bytes from the pinned Wesnoth build, not the illustrative 29 47 04 E8 ... sequence above. It prints every match and refuses to call the result usable unless there is exactly one.

The complete executable is pattern_scanner.rs. Shared ToolHelp module discovery, memory-region validation, and bounded reads are in process.rs.

When results are wrong

Section titled “When results are wrong”

When a scan result is wrong

Symptom Most likely question to ask
No matches Is this the exact supported executable and correct architecture?
Many matches Is the signature too short or too full of wildcards?
Read failure Did the region change, or was its protection classified incorrectly?
Match points into data Did the scan include a non-executable section?
Correct bytes, wrong behavior Did you decode enough surrounding instructions and verify the function?

Error messages should preserve this distinction. “Scanner failed” is not actionable; “pattern matched six locations in executable regions” tells the learner exactly which assumption to revisit.

Why does a byte pattern use wildcards for some positions?
