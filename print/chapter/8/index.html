Lesson 8.1

Messages, Streams, and Multiplayer

Client and server

Section titled “Client and server”

Imagine two players looking at copies of the same game board. One presses north while their character is at (10, 15). Their computer can draw a possible new position immediately, but the other player cannot know about that move until information crosses the network. The server checks the move against the game’s rules and replies with the accepted position, (10, 14).

A client collects your input, sends requests, receives state, and draws what you see. A server applies the shared rules. Both hold their own changing game state; a message carries information between the copies.

This chapter follows that message from intent to bytes, from captured bytes to a parsed event, and from one event to a legal session transition. A local chat client and proxy put the pieces together. The final lessons ask how two programs on one computer can exchange equally well-defined messages without using a network socket.

sequenceDiagram
    participant C as Game client
    participant S as Local test server
    C->>S: "I want to move north"
    S->>S: Validate the request
    S-->>C: "Position is now (10, 14)"
    C->>C: Draw the new state

The client’s “move north” is an intent: a request for a change, not the final truth. The reply reports what the server actually accepted. If a wall blocked the move, the reply might still say (10, 15), and the client would correct its display.

The client and server are not one program with a slow shared variable. The server may accept, reject, reorder, or combine requests according to its rules, while the client may predict a result before confirmation arrives. The next question is how the reply’s bytes become one complete message at the other end.

TCP is a stream

Section titled “TCP is a stream”

TCP is a common transport for a connection between the two programs. It delivers an ordered stream of bytes. A program calls read to take some bytes that have arrived from that stream. TCP does not preserve the game’s message boundaries for that call.

One call to read may return:

  • half of one message;
  • exactly one message;
  • one message plus part of the next;
  • several messages.

Concretely: if the sender writes two length-prefixed messages back to back, the receiver has no say in how they turn up.

Neither read lands on a message boundary. The receiver has to hold what it has in a buffer, remove complete messages when enough bytes have arrived, and keep the leftover for next time. A parser that assumes one read equals one message works flawlessly over a fast loopback connection while you are testing, then breaks the moment timing changes.

This is why a protocol needs framing.

stream supplies incoming bytes and max_size is the caller’s permitted payload limit. A successful call returns one payload as a Vec<u8>; a truncated header or payload produces an I/O error through ?. For a header 00 00 00 02 followed by 41 42, the returned vector contains just 41 42. The maximum size prevents a bad length field from requesting absurd amounts of memory. This blocking helper also needs an appropriate timeout on a real socket so a peer cannot make it wait indefinitely.

TCP reliability ends at delivering an ordered byte stream to the receiving socket. It does not prove the application parsed a complete message, accepted the request, saved the state, or sent a meaningful reply. Those guarantees belong to the application protocol. Define acknowledgments, request IDs, timeouts, and retry rules at that layer when the behavior needs them.

Byte order is part of the protocol

Section titled “Byte order is part of the protocol”

The same integer has more than one possible byte order. Decimal 258 is 1 × 256 + 2, so as a four-byte number it has one byte worth 256 (01), one byte worth 1 (02), and two zero bytes. Wesnoth’s four-byte frame length is big endian, which puts the byte worth the most first:

Read with the wrong order, the wire bytes 00 00 01 02 become 0x02010000, which is 2 × 16,777,216 + 1 × 65,536 = 33,619,968: a frame length of more than 33 million bytes. Network code must follow the protocol, not the host CPU’s default. That is why the reader uses u32::from_be_bytes rather than a pointer cast.

Packets and protocols

Section titled “Packets and protocols”

A packet is a chunk of bytes sent across a network. That part is straightforward.

“Protocol” is usually defined with words like rules or agreement, which sound reasonable and tell you nothing. Be concrete instead. A protocol is the set of specific questions both programs must already know the answers to before a single byte means anything. There are four:

  1. Where does one message end and the next begin? A TCP connection is one long stream of bytes with no natural gaps, so something has to mark the boundaries.
  2. What is each part of a message? Which bytes are the length, which are the message type, which are the payload, and how each of those is encoded.
  3. Which messages are allowed right now? A login reply makes no sense before a login request. People routinely forget this is part of the protocol at all.
  4. What happens when something is wrong? An unknown message type, a length that does not fit, a message arriving out of turn.

None of that can be worked out by staring at the bytes, because none of it is written in them. Both programs have to know it in advance. That is precisely why reverse engineering a protocol means recovering those four answers — and why a byte layout on its own only ever answers the second one.

Note

📦 Watch for: the same bytes can be perfectly valid at one point in a conversation and meaningless at another. A protocol model has to check when a message is legal, not only what it contains.

One message is wrapped in several layers

Section titled “One message is wrapped in several layers”

Several layers cooperate when the bot sends one chat message:

WML, Wesnoth Markup Language, is Wesnoth’s own tagged text format for structured data — chat messages, maps, units, and more all get written as bracketed tags such as [message] and [/message] wrapping quoted key="value" fields. It is the serialization format this chapter keeps reversing.

When something fails, ask which layer broke. A correct TCP connection does not prove the WML is valid. A valid gzip stream does not prove the length prefix used the right byte order.

The receiver undoes the layers in the opposite order, and each step has its own way to fail:

    A["Bytes arrive from the TCP stream"] --> B["Framing: split off one frame<br/>using the big-endian length"]
    B --> C["Compression: gunzip the payload"]
    C --> D["Serialization: parse the WML tags"]
    D --> E["Meaning: build a typed Message"]
    B -.->|"length above the maximum"| X["Stop with an error<br/>that names the layer"]
    C -.->|"not a valid gzip stream"| X
    D -.->|"unbalanced or unknown tags"| X

Serialization turns structured values into bytes. Framing tells the receiver where one serialized message ends. Transport moves bytes between endpoints. Keeping those jobs separate makes both the explanation and the code easier to test.

Messages can feed a data pipeline

Section titled “Messages can feed a data pipeline”

A multiplayer service handles more than packets. It may keep durable account and inventory records in a database, reuse expensive results in a cache, and build a search index for queries such as finding a match by region and mode. Those are different access patterns: keep data across restarts, avoid repeating work, and find selected records efficiently. They are not three names for the authoritative state of a running match.

Processing is asynchronous when the sender can continue before the work finishes. A request can enter a queue, then a worker handles it later. A queue acknowledgment might mean “received”; it does not by itself mean “validated, applied, and saved.” The protocol must say which stage each reply confirms.

There are also two common ways to process a sequence of events:

Processing style Game-service example What it must account for
Stream processing Update a match’s statistics as accepted events arrive Ordering, late events, duplicates, and how quickly the result is needed
Batch processing Recompute a leaderboard from a collected set of finished-match results Which results belong to the batch, when it runs, and how to repeat it safely

“Stream processing” here means processing ongoing events; it does not mean the TCP byte stream discussed earlier. A service can obtain events from many connections, files, or queues. A batch deliberately waits for a group of data and processes that group together. Neither approach implies that a game can delay its immediate rules until a leaderboard job finishes.

For example, a match event might carry match_id, event_id, and a score change. If a sender retries it after a lost acknowledgment, the receiver must recognise the same event rather than add the score twice. Event identity and retry behaviour belong to the model and protocol, not to whether TCP delivered the underlying bytes correctly.

Modularity and scaling follow the dependencies

Section titled “Modularity and scaling follow the dependencies”

Keep receiving, parsing, rule validation, and persistence as identifiable jobs. Then measure where time is spent. A slow disk write, repeated full-player search, and long logging operation need different remedies; adding workers does not remove a shared bottleneck automatically.

Several independent matches can often run on separate workers. Within one match, operations on shared state still need a defined order. Moving one job to another process also adds a message boundary, possible failures, and delay. Start with a small correct local service, preserve these contracts, and distribute work when measurements and the use case justify it.

Bound queues as well as messages. If input arrives faster than it can be processed, an unbounded queue consumes memory and makes results increasingly stale. A newer position snapshot may replace an older one under a documented policy; a one-time item grant needs different handling. That is a decision about message meaning, not a universal “drop old data” rule.

UDP is made of datagrams

Section titled “UDP is made of datagrams”

UDP preserves datagram boundaries but does not guarantee delivery, order, or uniqueness. Fast games often tolerate those tradeoffs for time-sensitive state.

A later position update can make an older one useless, so freshness may matter more than retransmission. In contrast, a one-time inventory change may need explicit ordering and acknowledgment. Choose behavior per message kind instead of labeling an entire game “reliable” or “unreliable.”

Do not assume a game uses only one protocol. It might use TCP for login/chat and UDP for movement.

Encryption changes what you can see

Section titled “Encryption changes what you can see”

If a protocol uses modern encryption correctly, a packet capture shows encrypted bytes, addresses, sizes, and timing—not readable messages. Do not try to defeat encryption or certificate checks.

For learning, use:

  • your own toy protocol;
  • a local open-source server;
  • captured bytes provided by a challenge;
  • application logs you control.

Captures in this chapter stay local

Section titled “Captures in this chapter stay local”

The capture, replay, and proxy examples use loopback or a local test server. That keeps timing, state changes, and failures observable while you learn what each protocol layer contributes.

Lesson 8.2

Protocol Capture and Message Framing

Separate network layers before capturing

Section titled “Separate network layers before capturing”

Lesson 8.1 showed that one game message can arrive across two TCP reads. A packet capture lets us inspect the bytes on the way, but its packet rows are not automatically game-message rows. We will send one distinctive lobby message, then follow its bytes in both directions.

An application message is not the same thing as an IP packet or TCP segment. Each layer has a different job:

TCP may split one game message across several segments or combine bytes from several messages in one segment. Retransmissions can repeat packet data. The receiving application sees an ordered stream, so protocol parsing needs its own framing rule such as a length prefix or delimiter.

A socket is an operating-system object representing one endpoint. A TCP connection is identified by source address, source port, destination address, and destination port—the four-tuple used below.

Capture answers “what crossed,” not “why”

Section titled “Capture answers “what crossed,” not “why””

A network trace records bytes and timing at one capture point. It does not contain the sender’s variable names, the receiver’s interpretation, or any record of which UI action caused which packet. That link comes from changing one thing at a time:

  1. capture a quiet baseline;
  2. perform exactly one distinctive local action;
  3. repeat the action with one changed input;
  4. compare both directions and several repetitions;
  5. confirm the candidate fields in the open-source client or server.

Build a controlled capture

Section titled “Build a controlled capture”

Direction matters

Section titled “Direction matters”

One connection has one four-tuple, and each direction reads it the other way round:

The client port is often temporary. The server port is the stable listening port.

The server first owns a listening socket on port 15000. Accepting a client creates a separate connected socket while the listener remains available for other clients. The client normally receives an ephemeral local port selected by Windows.

Follow the stream

Section titled “Follow the stream”

Wireshark’s “Follow TCP Stream” view reassembles TCP bytes for easier inspection (Tip: To open it, right-click any packet of the connection and choose Follow, then TCP Stream. The shortcut is Ctrl+Alt+Shift+T.).

Remember: this is still a stream, not necessarily a list of messages. Look for:

  • fixed-size headers;
  • length fields;
  • magic bytes;
  • repeated separators;
  • readable text;
  • compressed-looking regions;
  • request/response pairs.

“Follow TCP Stream” performs reassembly for inspection. Your client still has to handle partial reads: read() may return fewer bytes than requested even when more bytes will arrive later. read_exact is appropriate only after a validated frame length tells you exactly how many bytes belong to the next piece.

Reassembly also chooses an order from sequence numbers and removes retransmitted overlap. Preserve the original packet capture alongside any exported stream fixture so later questions about direction, timing, or retransmission can still be answered.

Do not store secrets, account tokens, or other people’s traffic in fixtures.

Lesson 8.3

Message Parsing and Serialization

Parse the real Wesnoth frame

Section titled “Parse the real Wesnoth frame”

The controlled captures from Wesnoth 1.14.9 reveal this frame:

The first four bytes do not include themselves in the length. If the header ends in 4E, the following gzip member is 78 bytes and the complete TCP payload is 82 bytes.

This four-byte prefix solves a problem TCP does not solve for us: message boundaries. A TCP read might return two header bytes now and the rest later, or it might return several complete frames together. The receiver therefore accumulates bytes until it has four, interprets the advertised length, then accumulates exactly that many payload bytes.

Big-endian means the most significant byte comes first. A length of 78 is hexadecimal 0x0000004E, so the wire contains 00 00 00 4E. u32::from_be_bytes documents that agreement directly; shifting bytes by hand would be harder to review.

The header is a claim from the sender, not permission to allocate whatever it asks for. Compare two headers followed by four bytes currently available:

The second header is four valid bytes, but its advertised size is not an acceptable frame for this parser. Code that allocates from that claim could request nearly four gigabytes. First reject any length above the configured maximum; only then wait for the advertised number of payload bytes, with a bounded buffer and a way to stop a stalled connection. Having only four payload bytes so far does not by itself prove a network frame is false, because TCP may deliver the rest later. After a complete frame is assembled, the parser checks its exact length before decoding it. This separates byte validation from the later question of whether the decoded chat message makes sense.

Keep five layers separate

Section titled “Keep five layers separate”

A protocol message has several nested layers, and each layer has its own rule:

Real-time games replicate a simulation, not just variables

Section titled “Real-time games replicate a simulation, not just variables”

Most action games advance the world in discrete ticks. If a server runs at 60 ticks per second, one simulation step is approximately:

The client samples input, labels it, and sends a command. The server processes commands during its own ticks and periodically sends a snapshot or delta. The client then draws frames between confirmed server states:

A field’s meaning depends on the kind of message carrying it. Imagine a player at (10, 15) requesting a move north to (10, 14). The request is an intent; the coordinate is a desired destination. An acknowledgment confirms that a command arrived or was applied. A snapshot reports enough state to stand alone, while a delta reports only changes from an identified earlier state. If the server replies with (10, 14), that coordinate is an accepted position. Equal-looking bytes can have different authority.

Several similar-looking states can therefore coexist:

State Purpose Important label
Last confirmed state What the server has accepted Server tick or snapshot ID
Predicted state Immediate response to local input Last locally simulated command
Interpolated state Smooth display of remote objects Render timestamp between snapshots
Historical state Rewind or lag-compensation query Past server tick or time

This explains why a coordinate found in memory can be correct yet appear to “snap back.” You may have found the predicted or rendered copy while a later server snapshot replaced it. Three facts tell the copies apart: which thread writes the field, whether its updates follow input or incoming packets, and which tick or sequence number travels beside it.

Ordering has to be carried in the message

Section titled “Ordering has to be carried in the message”

Packet arrival order is not automatically simulation order. UDP packets can arrive late or twice; even over TCP, one stream can contain application events whose own timestamps refer to different moments. Protocols commonly carry:

  • a monotonically increasing sequence number;
  • a server tick or timestamp;
  • an acknowledgment of the newest processed command;
  • a bit mask acknowledging several earlier packets;
  • a baseline ID telling which snapshot a delta modifies.

Sequence numbers often wrap. For an unsigned N-bit counter, comparisons must use modular arithmetic and accept only a bounded forward window, not a plain incoming > current test.

Work through one 16-bit wraparound. The last accepted sequence number is 65534, and the next two packets carry 65535 and then 0:

The naive test gets the first packet right and the second one wrong. 0 really is one step newer than 65535, but as a plain integer it is smaller, so the packet is thrown away. It gets worse from there: current never advances past 65535, so every sequence number after the wrap looks old in the same way, and the connection appears to stop receiving updates entirely.

The modular test asks a different question — how far forward is incoming from current, counting the wrap? (0 - 65535) mod 65536 is 1, a single step ahead, so the packet is accepted and current moves on. Accept only while that distance stays inside an agreed window such as 1..=32767. A distance of 32768 is exactly halfway around a 16-bit counter and cannot be classified as newer or older from the sequence number alone, so this rule refuses it. A genuinely old packet computes a distance near 65536, which also falls outside the window. The exact window is part of the protocol contract and deserves boundary tests; RFC 1982’s serial-number arithmetic explains the half-range limit.

A snapshot contains enough state to stand alone. A delta contains changes relative to a named baseline. Applying a delta to the wrong baseline may parse perfectly and still create nonsense. Robust tooling keeps the baseline ID with the bytes, refuses missing dependencies, and bounds how long incomplete state may wait.

Shared Memory Between Processes

Processes normally have separate address spaces

Section titled “Processes normally have separate address spaces”

The proxy copied messages between sockets. A supported game add-on and a separate visualizer could instead agree on a local shared byte region. The message still needs a layout and a lifetime; only the transport changes.

Two running programs can both use the address 0x00400000, yet those numbers can refer to completely different physical storage. Each process has its own virtual address space.

That separation is a safety feature. A map helper should not need to patch a game process merely to receive a supported event from a mod. Windows provides interprocess communication, or IPC, for programs that intentionally cooperate.

Named shared memory is one IPC option:

A mapping object is not the view

Section titled “A mapping object is not the view”

These terms describe different resources:

  • A file-mapping object tells Windows what storage is shared, how large it is, and which protections are allowed.
  • A view maps some or all of that object into one process’s virtual address space.
  • A handle names the mapping object.
  • A pointer from MapViewOfFile names the beginning of one process’s view.

Closing the handle and unmapping the view are separate cleanup operations. The lab uses OwnedHandle for the first and a small MappedView type with Drop for the second.

Paging-file-backed means no ordinary file is required

Section titled “Paging-file-backed means no ordinary file is required”

CreateFileMappingW normally accepts a file handle. Passing INVALID_HANDLE_VALUE asks Windows for storage backed by the system paging file instead. We must provide a nonzero maximum size—in this lab, 4096 bytes.

The name starts with Local\, so it lives in the current logon session’s local namespace. We do not use Global\, which can require extra privilege and makes the scope wider than this lab needs.

Named Pipes and Local Message Framing

A named pipe is a local client/server channel

Section titled “A named pipe is a local client/server channel”

Shared memory in Lesson 8.7 gave two programs views of the same bytes, but a concurrent writer needed an additional timing agreement. For one request followed by one reply, a named pipe gives us a connection with an explicit read/write order.

A named pipe server creates a known pipe name and waits. A client opens that name. After they connect, both sides can exchange bytes through ordinary Windows read and write calls.

This resembles a tiny network service, but the lab keeps both programs on the same Windows machine:

Named pipes are useful when a supported game plug-in, launcher, capture helper, or your own engine build needs to talk to a separate tool without sharing raw pointers.

One bounded exchange has a clear beginning, two validated messages, and a clear end:

flowchart TD

    B --> C["Connection completes"]
    C --> D["Client sends framed request"]
    D --> E["Server validates request"]
    E --> F["Server sends framed reply"]
    F --> G["Both sides close handles"]

The pipe transports bytes; the frame format supplies the length and validation rules that make those bytes meaningful to both programs.

Note

🔌 IPC idea: define a small message format instead of sharing addresses. Each process keeps ownership of its own memory and exchanges bounded copies.

Message mode preserves write boundaries

Section titled “Message mode preserves write boundaries”

Windows pipes can operate in byte mode or message mode.

  • Byte mode is a stream. One read can receive part of a write or data from several writes.
  • Message mode preserves message boundaries. A read receives one message, provided the buffer is large enough.

The lab selects PIPE_TYPE_MESSAGE when creating the server and PIPE_READMODE_MESSAGE for both ends.

It still adds a four-byte length header. Why use both? Message mode keeps transport boundaries, while the length header validates the application protocol. The receiver can reject a damaged or unexpected frame instead of trusting every byte Windows delivered.

Treat IPC data like untrusted input

Section titled “Treat IPC data like untrusted input”

“Local” does not mean “automatically trustworthy.” Another program in the same account or session might know or guess the pipe name.

The receiver checks all of these facts before making a String:

  1. At least four header bytes arrived.
  2. The declared text length is no more than 1024 bytes.
  3. The received frame size equals 4 + declared length.
  4. The text bytes are valid UTF-8.
flowchart TD
    A["bytes_read >= 4?"] -->|"no"| X1["reject: no header"]
    A -->|"yes"| B["declared <= MAX_TEXT_BYTES?"]

    C -->|"yes"| D["valid UTF-8?"]

The server accepts one client, handles one request, sends one fixed reply, and exits. Small limits make the behavior easy to reason about.

Section titled “Keep the pipe local and never impersonate”

The program does not call ImpersonateNamedPipeClient, duplicate tokens, start a process as another identity, or change privileges. Those operations solve different identity and access-control problems; they are not part of this message channel.

Lesson 8.9

How the Source Engine Works

You press forward. Your player moves immediately, yet the server has not received the input. Later, a reply may adjust that movement. To understand why, follow the input across the pieces of the game that own each decision. Lesson 8.1 introduced client and server messages. Source gives us a concrete engine in which those messages connect to objects and time.

Why study Source?

Section titled “Why study Source?”

Source is Valve’s game-engine family behind Half-Life 2, Counter-Strike: Source, Team Fortress 2, Left 4 Dead, and the original Counter-Strike: Global Offensive. They share architectural ideas, but their engine branches differ. Counter-Strike 2 uses Source 2, a later engine family. An interface name or memory layout from Source 1 is not a promise about Counter-Strike 2.

Valve’s public Source SDK 2013 supplies game code and interfaces for Half-Life 2, Half-Life 2: Deathmatch, and Team Fortress 2. An SDK, or software development kit, gives developers code and tools for building compatible software. This repository lets us inspect the game side of the boundary. It does not supply every implementation inside a shipping engine.

This lesson follows the SDK revision beginning b8cfb12. Treat its named interfaces and defaults as facts about that revision. Keep experiments in your own offline SDK mod. A mod supplies changed game content or rules while using the engine’s supported loading contracts.

The engine connects client and server game code

Section titled “The engine connects client and server game code”

A launcher starts the engine and selects the game to load. The engine provides common services such as files, rendering, sound, and networking. Game-specific code supplies weapons, entities, movement rules, and decisions about what happens next.

On Windows, this game code commonly comes in client.dll and server.dll. A DLL is a library loaded into a process while it runs, as introduced in Lesson 6.2. Other operating systems use their own shared-library formats for the same architectural division.

The client library handles the player’s input, local presentation, and prediction. The server library owns the simulated game rules and the state that clients must follow. Some movement code is shared so both sides can compute comparable results. Rendering a player and deciding whether that player can pass a wall are separate responsibilities.

A listen server hosts the simulation inside a game that also has a local player. A dedicated server runs the hosting side without that local player’s view. Even a local game can retain the client/server division. The boundary describes who owns a decision, whether its messages cross the Internet or stay on one machine.

TL;DR: The client presents and predicts. The server decides the game state. The engine connects their game libraries.

Modules ask for an interface by name

Section titled “Modules ask for an interface by name”

The engine cannot call an arbitrary function inside a loaded library and hope its arguments fit. The two sides need an agreed set of operations. That set is an interface: a contract describing which methods an object provides and how to call them.

Source modules expose a factory named CreateInterface. A factory is a function that supplies an object through an agreed interface. The caller passes the requested name. The module searches its registered interfaces and returns a pointer to the matching object, or a null pointer if it cannot provide one. An optional status output receives IFACE_OK or IFACE_FAILED. The pointer is the function’s result; the status is a separate output.

For this revision, VClient017 names the client game interface, while VEngineClient014 names engine services used by client code. On the server side, VEngineServer023 exposes engine services, ServerGameDLL012 exposes game callbacks, and ServerGameClients005 covers player-related callbacks. The suffix is part of the requested contract.

The SDK’s registration macros, including EXPOSE_INTERFACE, attach a name and creation function to a registration list. Lookup matches that name. The returned object’s virtual methods use the C++ calling contract already introduced in earlier lessons. A different interface version can change that contract, even when its name looks similar.

Alternative: Picture a shared menu of operations. The version name selects the menu both modules agree to use.

This explains a startup failure that otherwise looks mysterious: a library loads successfully, but it cannot provide the interface the engine asks for. Loading bytes and agreeing on their callable contract are different checks.

Entity state becomes selected network properties

Section titled “Entity state becomes selected network properties”

Once the libraries connect, the server can create an entity, an object the game tracks: a player, door, projectile, or another piece of the world. Its full object contains more information than a client needs. Some fields are server bookkeeping. Others describe what the client must display.

A SendTable declares properties that server game code makes available for network encoding. A corresponding RecvTable describes how client game code receives those properties. These are descriptions of fields and their encoding, rather than a copy of the whole C++ object. Nested tables let one class reuse another class’s networked fields.

Think of a door whose server object stores its position, opening state, and internal scheduling data. The client needs enough state to place and draw the door. It does not need every scheduling field. The property declarations make that selection explicit. The engine can also limit which entities and updates are relevant to a particular client.

Floating-point properties can trade precision for bandwidth through quantization: representing a range with a limited set of codes. As an illustration, four bits give 2⁴ = 16 codes. Spread those codes across a chosen range from 0 to 15, including both ends. The spacing is (15 − 0) ÷ (16 − 1) = 1. Values between the available steps need an encoding rule that chooses a representable value.

The SDK’s SendPropFloat accepts a bit count, range, and flags. Some settings use an unscaled float instead. The four-bit example explains the trade; it does not describe every Source float on the wire. A client-side value can therefore differ slightly from the server’s value even when both sides work correctly.

Input becomes a command record

Section titled “Input becomes a command record”

Now the player presses a movement key. The client game interface’s CreateMove produces a user command, one record of player input for simulation. Source names that record CUserCmd.

Its command_number identifies a command in the sequence. Its tick_count records the tick when the client created it. A tick is one step of the simulation clock. Command numbers and tick numbers have different jobs, even when a small example gives them matching values.

The record includes view angles and the intended movement values forwardmove, sidemove, and upmove. It also includes weapon selection and mouse movement. These inputs describe what the player requests. They do not establish the final position, damage, or inventory result.

The buttons field packs several requests into one integer. In this SDK, attack uses bit 0 and jump uses bit 1. Their values are 2⁰ = 1 and 2¹ = 2. Requesting both sets the combined mask 1 | 2 = 3, whose two lowest bits are on. The server can test each bit separately.

This memory object is not the packet format. Command encoding records changes relative to another command, and decoding rebuilds the record. Fields used for local prediction bookkeeping do not all become raw packet bytes. Keeping object layout and wire encoding separate matters just as it did for the message parsers earlier in this chapter.

A tick advances the world; prediction advances the local estimate

Section titled “A tick advances the world; prediction advances the local estimate”

The SDK’s default tick interval is 0.015 seconds. Multiply by 1000 to get 15 milliseconds per tick. Divide one second by the interval to get 1 ÷ 0.015 ≈ 66.67 simulation steps per second. A game can supply its own interval, so this default is not every Source game’s rate.

The server game interface exposes GameFrame for simulation work and GetTickInterval for its interval. Drawing frames happens on another schedule. A faster renderer can draw additional views between simulation ticks; it does not give the player additional accepted movement.

Waiting for a network reply before showing every step would make movement feel delayed. Prediction lets the client run its local player’s movement using input commands immediately. The server still runs its own simulation and returns authoritative results. Authoritative means that those results are the state the client must reconcile with.

Use a deliberately small movement model to see the reconciliation. Start at x = 0. Each accepted forward command adds one position unit. Commands 1 and 2 request +1, giving 0 + 1 = 1, then 1 + 1 = 2. These are toy displacements, not Source’s velocity and collision formulas. The scene’s 15-millisecond clock comes from the SDK default.

A barrier now closes on the server and prevents movement past x = 2. The client has not received that update. Command 3 requests another +1. The client predicts 2 + 1 = 3; server collision keeps the position at 2. Before the reply arrives, command 4 requests −1. The client’s current prediction becomes 3 − 1 = 2.

Narration: The server’s barrier has closed. The client’s earlier prediction has not heard about it yet.

The server reply acknowledges command 3 and reports position 2. An acknowledgment identifies the input already covered by the returned state. The client starts from that authoritative position and drops commands 1 through 3 from its pending history. Command 4 is still pending, so it replays that −1: 2 − 1 = 1.

That replay preserves the player’s newer input while correcting the earlier prediction. Simply replacing the displayed position would lose pending movement. Replaying commands already acknowledged would repeat work the server’s state already contains.

Snapshots smooth other players; lag compensation checks past positions

Section titled “Snapshots smooth other players; lag compensation checks past positions”

A snapshot describes server state at a point in simulation time. It may be encoded as changes from an earlier known snapshot. Snapshot delivery, tick rate, and rendering rate are separate schedules.

For another player’s movement, the client usually has received states rather than that player’s newest input. Interpolation draws intermediate positions between received states. Showing a slightly older timeline gives the renderer states on both sides of the time it wants to draw. That makes motion smooth instead of jumping whenever a message arrives.

Prediction estimates the local player’s response to input. Interpolation fills the visible gaps between other entities’ received states. Neither makes a client observation newer than the information actually received.

This delay also matters when a player fires. The target they saw may occupy an earlier position than the server’s current position. Lag compensation temporarily uses recorded earlier player states for the relevant server-side hit check, then restores the current simulation.

In this SDK, the initial target tick is the command’s tick_count minus the interpolation delay expressed in ticks. The server also checks that time against its latency estimate. A discrepancy greater than 0.2 seconds uses a latency-based target instead. The inspected sv_maxunlag default is 1 second and bounds the allowed correction. This is a bound on the decision; it is not a promise that every past state remains available for exactly one second.

The important ownership stays intact: the server performs the hit check. It temporarily adjusts eligible recorded player state and then restores it. The world does not permanently travel backward because a packet arrived.

Console variables carry rules as well as values

Section titled “Console variables carry rules as well as values”

Games need settings without recompiling each change. A console variable, or ConVar, is a named setting with a value and flags describing how it may be used. The developer console exposes these settings and named commands.

FCVAR_CHEAT restricts certain development controls to permitted cheat contexts, including the server’s sv_cheats setting. FCVAR_REPLICATED marks a server-controlled setting enforced on connected clients. Flags describe permissions and ownership as well as storage behavior.

A server can ask for a client’s variable through StartQueryCvarValue. The request returns a cookie, an identifier for matching a later reply to that request. It does not return the variable’s value immediately. OnQueryCvarValueFinished supplies the later status and value. The FCVAR_SERVER_CANNOT_QUERY flag forbids that query for the marked variable.

For a defender, a client-reported setting is evidence about what the client reported. It does not replace server-side movement, inventory, or damage validation. A timeout or failed query also needs its own interpretation; it is not automatically proof of cheating.

The same engine loads packages and compiled maps

Section titled “The same engine loads packages and compiled maps”

Those entities need geometry, models, textures, and sounds. VPK, short for Valve PacK, bundles resource files behind a directory tree. An entry identifies where its bytes live, possibly in a companion archive. Some bytes can be stored with the directory as preload data. This lets the file system locate a resource without treating every small asset as a separate loose file.

A BSP is a compiled map. The name comes from binary space partitioning, which divides space to organize geometry queries. A Source BSP contains sections called lumps, holding map data such as geometry, visibility, and starting entity definitions. It can also contain embedded resources.

The inspected header starts with VBSP, then a version and a directory of 64 lump descriptors. Each descriptor provides an offset, length, and version-related metadata. Different game branches can interpret sections differently. Reading a file therefore starts with identifying its format and validating its bounded sections, not treating its bytes as a live entity object. Chapter 9 develops that file-validation work.

Use each boundary for the question it can answer

Section titled “Use each boundary for the question it can answer”

An offline observer built with supported interfaces can record command numbers, simulation ticks, received properties, and prediction corrections. Those records answer different questions. A rendered location describes a view; a server result describes an accepted simulation step; a package entry locates stored content.

For your own mod, keep module versions explicit and record which side owns each value. Follow the DLL lifetime rules when starting and stopping tools. For defenders, validate player requests against server-owned state and keep work per client bounded. Interpolation, quantization, and correction explain some ordinary discrepancies, so one mismatch needs context. Chapter 15 builds on this separation between requests, observations, and decisions.
