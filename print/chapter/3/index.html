Lesson 3.1

Safe Boundaries for Game Memory

Chapter 2 found game state and the code that changes it. Now we need to carry that knowledge into a tool without mistaking a remote address for our own memory. This chapter begins with safe type and ownership boundaries, then derives how bytes represent numbers and pointers. An external reader turns those representations into local values; objects, collections, encoded fields, and text show what those values can mean inside a game. DLL call contracts return later when our code enters the process itself.

Start with one boundary rule

Section titled “Start with one boundary rule”

Game tooling needs low-level control: exact integer sizes, raw bytes, operating-system APIs, and sometimes pointers. Most of the program can still use compile-time checked ownership and types.

The guiding rule is:

Write safe code for the algorithm. Put unavoidable raw-pointer work in one small wrapper, document its assumptions, and return an ordinary owned type.

Note

🧠 Boundary idea: safe code should occupy most of the program. Small unsafe sections act like clearly marked doors where you check every assumption before crossing.

Local memory and game memory are different trust zones

Section titled “Local memory and game memory are different trust zones”

The compiler can prove many facts about memory owned by the current program. A borrowed slice has a known length and owner. A Vec<u8> keeps its allocation alive. A reference cannot normally outlive the value it borrows.

It cannot prove equivalent facts about an address copied from another process. The target can free an object, change page permissions, exit, or race with our read. That is why cross-process code should not manufacture a normal reference such as &Player from a remote address.

Instead, use a clear boundary:

After the copy succeeds, ordinary ownership rules protect the local buffer. Before the copy, the address is untrusted input that needs checked arithmetic, region validation, and a useful error.

Values and types

Section titled “Values and types”

Memory work depends on sizes, so we use explicit integer types:

Use usize for address calculations, not for game values just because it is convenient.

The target process does not store the words u32 or f32 beside each value. For example, 00 00 20 41 reads as 1,092,616,192 with u32 and 10.0 with f32; the type tells the reader which interpretation to use. We need the widths now to read memory safely. Lesson 3.2 derives the bit patterns behind those interpretations before we build the external reader.

usize is large enough to index memory in the current build. It is 32 bits in an i686-pc-windows-msvc tool and 64 bits in an x86-64 tool. A game’s u32 health value stays four bytes on both. Address width and value width answer different questions.

Give equal-sized values different meanings

Section titled “Give equal-sized values different meanings”

A player ID and a health amount might both fit in a u32, yet swapping them should be an error. Rust can wrap the same stored bits in distinct types:

These are newtypes. The wrapper tells the compiler that equal byte representations do not mean interchangeable values. The same technique keeps a remote address, a byte offset, and a game value from being passed to the wrong parameter just because all three happen to be integers. Chapter 1 first kept these ideas separate in words; a newtype can enforce the distinction in code.

Ownership and borrowing

Section titled “Ownership and borrowing”

An owned Rust value can be lent for reading with &T or for editing with &mut T. The Rust Primer introduced those forms and Option for a value that may be absent. Here a search returns Option<usize>: a found byte offset (Some(offset)) or no match (None).

&[u8] is a borrowed slice: a view into bytes owned somewhere else. The function can read them but cannot keep or change them.

A slice is two pieces of information used together: where the first element is and how many elements are available. Indexing and windows use the length to avoid walking beyond the allocation. A raw pointer by itself carries no such length.

Assigning an owned String to a new owner makes the old name unusable; the Primer’s interactive view shows that transfer. The remote reader here borrows a slice instead of moving its whole byte buffer into every search function.

Borrowing is different from moving. A borrow gives code temporary permission to use a value without taking responsibility for freeing it. Shared borrows (&T) allow reading. A mutable borrow (&mut T) allows changing, but it must be the only usable borrow of that value for its lifetime.

This is the borrow checker doing memory-safety bookkeeping before the program runs. Vec::push may need to move the vector’s heap allocation to a larger space. Keeping view alive across that operation could leave a dangling reference, so Rust rejects the overlap.

A debugger displays bytes; a game interprets them as types. The conversion should state that meaning explicitly:

A missing value at a memory boundary

Section titled “A missing value at a memory boundary”

Some(0) holds a valid zero; None means no value was produced. The same distinction protects a memory read. read_u32 returns Some(number) only after it has obtained four bytes and decoded them; if the local buffer is too short, it returns None instead of reading past the end. The ? operator in this Option-returning function means “return None now if this step has no value.” The next boundary needs an actual error reason, so it uses Result.

Errors are part of the function

Section titled “Errors are part of the function”

Use Result<T, E> when callers need to know why an operation failed:

For a one-purpose tool such as memory_scanner.exe, the anyhow crate is useful because each failed Windows call can say which process, address, or operation failed. Code reused by several lessons—such as a packet, PE (Portable Executable, the header-and-sections layout Windows uses for .exe and .dll files), or byte-pattern parser—benefits from a typed error enum. The caller can then handle truncated bytes differently from an unsupported size or invalid text. Those errors should also explain themselves when printed:

Debug shows the exact failure variant while you debug a parser. Separate the cause from the decision

Section titled “Separate the cause from the decision”

An error value should report what failed; the outermost tool should decide what to do about it. A memory reader should not silently retry forever, and a parser should not terminate the whole application.

Add context at each boundary without erasing the original Windows or parsing error. Then classify the final decision:

Situation Sensible tool behavior
Game exited Stop normally and close owned handles.
Pointer changed during a scene load Discard the snapshot and observe again.
Layout validation failed Refuse the action and report the build plus field.
Programmer invariant failed Stop; retrying would hide a tool bug.

This makes failure part of the design. “Keep going” is safe only when the next iteration starts from fresh, validated state.

Put uncertain reads behind one boundary

Section titled “Put uncertain reads behind one boundary”

The scanner and the game-specific logic should not each repeat Windows handle checks, byte counts, and error conversion. An abstraction gives that work one named interface. This sketch describes the operation the rest of a tool needs, without claiming that the method alone makes an address safe:

trait states a behavior another type can implement. &self lets the method use an existing reader, address is the location to request, and Result carries either the decoded u32 or an error. The implementation still must verify the target process, readable region, requested length, and actual bytes returned. The scanner can then ask for a value through read_u32 while one implementation owns the operating-system boundary. Programming Fundamentals called this an abstraction: a smaller interface hides the details of a larger operation. The reader trait now gives that idea a concrete shape.

Give each game helper one obvious import path

Section titled “Give each game helper one obvious import path”

Avoid pub use windows_impl::* in the shared lab crate. A wildcard could expose an unfinished hook or internal address helper merely because somebody marked it pub inside that module. It can also make the same type appear under several paths. Export only the tools the lessons are meant to use:

The Windows lab keeps its implementation module private, so a memory scanner imports gha_windows_labs::Process and a reversible hook imports gha_windows_labs::PatchPlan. #[doc(inline)] puts the ownership and error notes at those exact paths. A learner should not have to search several modules to discover which process wrapper is the supported one.

Raw pointers and unsafe

Section titled “Raw pointers and unsafe”

A raw pointer is written *const T for reading or *mut T for writing. Rust does not automatically know whether it is:

  • non-null;
  • aligned;
  • inside readable memory;
  • pointing to a real T;
  • still valid.

Dereferencing one therefore requires unsafe:

This function reads a pointer in the tool’s own address space only when its caller can uphold every safety condition in the comment. A numeric address from the game process is different: the external tool must ask Windows to copy those bytes rather than casting the remote address to *const u32 and dereferencing it locally.

What .offset() actually does

Section titled “What .offset() actually does”

Raw pointers have an offset method, but its number is an element count, not a byte count. If pointer has type *const u32, one element is four bytes:

The signed isize argument is what makes .offset() different from .add(). first.add(2) can move forward by two elements; third.offset(-1) can move backward by one element. When the number you recovered is a byte offset, use a byte pointer or .byte_offset() so the unit is obvious:

Calling .offset() is already unsafe, even before dereferencing the result. Rust requires the start pointer, the result, and the range between them to stay inside the same allocation (or exactly one element past its end). The byte calculation must also fit in an isize. An address that merely looks plausible does not satisfy those promises.

This distinction matters in a game-memory tool:

❌ The first version pretends memory owned by another process is part of this tool process’s allocation. It is not. ✅ The second version treats the remote location as a checked integer address and asks Windows to copy the bytes into a local buffer. Use pointer .offset() only when you can prove the allocation and bounds; use checked address arithmetic for remote memory.

Notice that Rust 2024 still requires an inner unsafe block inside an unsafe fn. The dangerous operation remains easy to find in review.

Caution

Never use unsafe to “make the borrow checker stop complaining.” First understand the ownership problem. In this course, unsafe is reserved for operating-system, graphics, foreign-function-interface (FFI) — that is, calls into code compiled from another language — and verified raw-memory boundaries.

Make the tools teach you

Section titled “Make the tools teach you”

Customize the editor enough that reading and navigating feel comfortable, then practice the few actions that shorten almost every debugging session:

  • go to a definition;
  • find every use of a name;
  • rename a symbol safely;
  • format the current file;
  • run the nearest test;

Gamers already learn key bindings and tune an environment for feedback. Apply the same skill here. A readable font, visible errors, and a reliable test key matter more than endlessly changing decorations. ⌨️

Run this small quality loop from PowerShell:

Learn syntax by typing tiny examples, but focus on the tools that matter most here: ownership, Result, enums, exact integer sizes, and small documented unsafe boundaries. If you forget a spelling, look it up. Useful programming is not a closed-book memory contest.

Reuse code without turning off judgment

Section titled “Reuse code without turning off judgment”

Crates can save months of work. Before adding one, check:

  1. Does its API match the actual problem?
  2. Does it support the toolchain and Windows versions you use?
  3. Is the license compatible with the project?
  4. Are its unsafe boundaries and maintenance history understandable?
  5. Can you cover your use of it with a small test?

Autocomplete and AI can also save typing. For every non-trivial suggestion you accept, be able to explain the types, ownership, side effects, failure path, and test. “It compiled” proves syntax and types; it does not prove the call targets the right process, preserves the right bytes, or cleans up a handle.

The boundary carried into the tool

Section titled “The boundary carried into the tool”

u32 is always four bytes; usize follows the tool’s pointer width. A borrowed slice lends access to bytes without transferring ownership. Option represents an absent value, while Result carries success or a failure reason. Raw pointers cannot prove their own validity, so every dereference needs a safety contract. Lesson 3.2

How Bytes Become Numbers and Pointers

The safe boundary keeps an address separate from an owned byte buffer. We still need to know how the copied bytes become a number or another address. The introductory memory lesson made two claims without proving them. The four bytes 00 00 20 41 are the whole number 1,092,616,192 when a u32 reads them, and 10.0 when an f32 reads them. And a pointer’s type decides what is read at the far end, while the pointer’s own size stays fixed.

This lesson proves both, one bit at a time, until you can work out every number yourself. It also explains how a whole number stores a minus sign.

Every bit position is a power of two

Section titled “Every bit position is a power of two”

The memory introduction read a byte by adding up place values: 128, 64, 32, 16, 8, 4, 2, and

  1. Each one is two times the one to its right, so each can be written as a number of twos multiplied together.

Number the positions from the right, starting at 0. Position n is then worth 2 multiplied by itself n times, which is written 2ⁿ:

Position Worth Written
0 1 2⁰ (no twos multiplied at all)
1 2 2¹
2 2 × 2 = 4 2²
3 2 × 2 × 2 = 8 2³
7 2 × 2 × 2 × 2 × 2 × 2 × 2 = 128 2⁷

Counting from 0 is what makes that line up: the rightmost position is 2⁰, and 2⁰ is 1, because no twos have been multiplied in yet.

Wider values keep going. A 32-bit value has positions 0 to 31, and its leftmost position is worth 2³¹ = 2,147,483,648.

The same notation counts patterns. Every extra bit doubles the number of patterns, so n bits make 2ⁿ of them: 8 bits make 2⁸ = 256, and 32 bits make 2³² = 4,294,967,296. Those are the ranges in the introductory type table.

Negative whole numbers

Section titled “Negative whole numbers”

A u32 spends all 32 bits on size, so it has no way to say “minus”. An i32 needs one, and it gets it with a simple change: the leftmost position is worth a negative amount. Every other position keeps its ordinary value.

It is easiest to see in a single byte, the i8 type. There, the leftmost position is worth −128 instead of +128:

Read as a u8, the same 0xFF is 255. Read as an i8, it is −1. Nothing about the byte changed; only the value given to its leftmost position did.

An i32 works the same way across four bytes, with its leftmost position worth −2³¹ = −2,147,483,648. So the bytes FF FF FF FF are 4,294,967,295 as a u32 and −1 as an i32. This scheme is called two’s complement. Its big advantage is that the CPU can use one adding circuit for both types: add 1 to 0xFF and the result carries out of the byte and leaves 0x00. Read as an i8, that is the correct answer to −1 + 1. Read as a u8, it is 255 + 1 wrapping around to 0, because 256 does not fit in a byte.

The i32 range falls straight out of this. The most negative value has only the leftmost bit set: −2,147,483,648. The most positive value has every bit set except the leftmost. Those 31 bits add up to one less than 2³¹, for the same reason 64 + 32 + 16 + 8 + 4 + 2 + 1 made 127, one less than 128. So the top of the range is 2,147,483,647.

Fractions: how an f32 splits its 32 bits

Section titled “Fractions: how an f32 splits its 32 bits”

A whole number cannot hold 3.5 or 0.25. For that, an f32 uses its 32 bits in a completely different way. It follows a standard called IEEE 754, which is the rulebook nearly every CPU uses for fractional numbers.

To see the idea, start with how scientists write very large or very small numbers:

Slide the decimal point until exactly one non-zero digit sits in front of it, then count how far you slid it as a power of ten. A negative power means the point slid the other way: 10⁻³ means “divide by 10 three times”.

An f32 does the same thing in binary. Take 10. As a binary whole number it is 1010, because the positions holding a 1 are worth 8 and 2, and 8 + 2 = 10. Slide the binary point three places to the left and count those three places as a power of two:

That number now has three parts: a sign (positive), a power of two (3), and the digits after the point (010). The 1 in front of the point is missing from that list on purpose; step 5 below explains why it never needs storing. An f32 stores exactly those three things, in three fields that together use all 32 bits:

Field Bits What it stores
sign 1 0 for positive, 1 for negative
exponent 8 the power of two, shifted by 127
fraction 23 the digits after the binary point

1 + 8 + 23 = 32. The name floating point comes from that middle field: the exponent decides where the binary point floats to.

Here is 10.0 as it sits in memory: the bytes 00 00 20 41. Little endian put the least-significant byte first, so written most-significant first, the way you write a number, they are 41 20 00 00. In binary, 0x41 is 0100 0001 and 0x20 is 0010 0000.

The fields do not follow the byte boundaries. Keep the same 32 bits in the same order and regroup them: the first bit is the sign, the next eight are the exponent, and the last 23 are the fraction.

Step 2: read the exponent field as a whole number

Section titled “Step 2: read the exponent field as a whole number”

The next eight bits, 1000 0010, are an ordinary unsigned whole number, read with the same place values as any byte:

That is where the 128 and the 2 come from. The leftmost bit of an eight-bit field sits in position 7 and is worth 2⁷ = 128. The second bit from the right sits in position 1 and is worth 2¹ = 2. No other bit is set, so the field holds 128 + 2 = 130.

Step 3: subtract the bias

Section titled “Step 3: subtract the bias”

The real power of two is not 130. It is the stored number minus 127:

That 127 is called the bias, and it exists to solve a real problem. An eight-bit field can only store 0 to 255, with no minus sign. But exponents need to be negative too, because numbers smaller than 1 are written with a negative power of two, the way 0.0025 needed 10⁻³:

One fix would be to spend one of the eight bits on a minus sign. IEEE 754 does something neater: it shifts the whole range. Every stored exponent is the real exponent plus 127, so the reader subtracts 127 to get it back.

1 1 − 127 = −126 2⁻¹²⁶, a tiny fraction

127 is used because it sits in the middle of 0 to 255, so there are about as many negative exponents as positive ones. The stored values 0 and 255 are kept aside for special cases, covered later in this lesson, which is why the table stops at 1 and 254.

The shift has a bonus. Because a bigger stored exponent always means a bigger number, two positive f32 values compare in the same order as their raw bit patterns do, which lets hardware compare floats cheaply.

Step 4: read the fraction field

Section titled “Step 4: read the fraction field”

The last 23 bits are the digits after the binary point. In decimal, the digits after the point are worth a tenth, a hundredth, a thousandth — each position a tenth of the one before. In binary each position is worth half the one before:

So the fraction 010 0000 … means 0 × ½ + 1 × ¼ + nothing else = 0.25. That matches the .010 in 1.010 × 2³ from the start of this section.

Step 5: put back the hidden 1

Section titled “Step 5: put back the hidden 1”

Scientific notation always leaves one non-zero digit in front of the point. In decimal that digit can be anything from 1 to 9. In binary the only non-zero digit is 1, so in front of the point there is always a 1.

A bit that is always 1 tells you nothing, so an f32 does not store it. It is called the hidden bit, and the reader adds it back:

The full number with its hidden 1 put back, 1.25 here, is called the significand. Many tools and older books call it the mantissa. Leaving the 1 out gives an f32 24 bits of precision from 23 stored bits.

What the rest of the fraction bits are for

Section titled “What the rest of the fraction bits are for”

For 10.0, only one fraction bit is set and the other 22 are 0. They are not wasted. They hold finer and finer halves — ⅛, 1/16, 1/32, all the way down to 1/8,388,608 — and 10.0 simply does not need any of them, because it is exactly 1.25 × 8. That is like writing 1.2500000 in decimal: the extra zeros are real digits that happen to be zero.

Most numbers are not that tidy. Take 10.1. It is 1.2625 × 8, so the fraction has to be 0.2625. In binary, 0.2625 never ends: its digits settle into 0011 repeating forever, the same way 1 ÷ 3 is 0.333… forever in decimal. The 23 bits store as much of it as fits, rounded at the last bit:

The stored fraction is 0.2625000476…, so the value is 1.2625000476… × 8 = 10.100000381…, the closest an f32 can get. A debugger that prints enough digits shows 10.10000038. This is why float values found in games are rarely round, and why memory scanners let you search for a float within a small range instead of only an exact value.

The last fraction bit sets how fine that precision is. It is worth 1/8,388,608, and for numbers near 10 it is multiplied by 2³ = 8, so neighbouring f32 values near 10 are about 0.00000095 apart. That works out to roughly seven significant decimal digits.

Where the binary digits of 0.2625 come from

To turn a fraction into binary digits, double it again and again. Each time the result reaches 1 or more, the next binary digit is 1 and you keep only the part after the point. Otherwise the digit is 0.

After the eighth line the leftover is 0.2 again, just as it was after the fourth line. So lines five to eight repeat forever, producing 0011 over and over: 0.2625 is 0.0100 0011 0011 0011 … in binary. The fraction field holds the first 23 of those digits, rounded at the last one.

Doubling works because each doubling moves the binary point one place to the right, pulling the next digit in front of it.

The exponent-0 rule also explains what the bytes for an integer 100 mean as a float. What a pointer’s type tells the program

Section titled “What a pointer’s type tells the program”

Suppose a pointer holds 0x5000, where the bytes are 00 00 20 41:

Following that address through a *const u32 reads all four bytes as 1,092,616,192. Through a *const f32, the same four bytes mean 10.0. Through a *const u8, it reads only the first byte, 0. The pointee type decides how many bytes to read at the destination and how to interpret them. Two more facts complete the picture: why the pointer’s own size never changes, and how the pointee type controls a pointer that moves.

The pointer’s size comes from the process

Section titled “The pointer’s size comes from the process”

A pointer has to be able to hold any address the process might use. A 32-bit process numbers its memory with 32-bit addresses. That gives it 2³² = 4,294,967,296 possible addresses, from 0 to 4,294,967,295, and a pointer needs all 32 bits — 4 bytes — to name any one of them. What it points to plays no part: a pointer to a single byte and a pointer to a 2,000-byte player object are both 4 bytes. A 64-bit process uses 64-bit addresses, so every pointer in it is 8 bytes.

Rust’s usize, the pointer-sized whole number from Lesson 3.1, follows the same rule: 4 bytes in a 32-bit program, 8 in a 64-bit one. So a 64-bit tool reading a 32-bit game’s pointers must read 4 bytes for each one, even though its own usize is 8.

The pointee type sets the step size

Section titled “The pointee type sets the step size”

The pointee type also decides how far a pointer moves. Adding 1 to a pointer means “the next value of this type”, not “the next byte”. Rust writes this p.add(1), and makes you wrap it in unsafe, because the compiler cannot check that the new address still lands inside the list:

0x0A is 10, 0x14 is 16 + 4 = 20, and 0x1E is 16 + 14 = 30. A pointer to a 64-byte structure would step 64 bytes at a time.

None of this is stored in memory

Section titled “None of this is stored in memory”

The pointee type lives in the source code and in the compiler, which uses it to choose the right instructions: a four-byte whole-number read, a float load, or a one-byte read. The compiled game keeps only those instructions. When you study a game, you work out what a pointer points to the same way you work out any other type: from what the code does at the destination.

The same bytes can describe a whole number, a fraction, or an address, depending on the width and interpretation selected by the code. Knowing that representation still does not prove which object the bytes belong to or whether its address remains valid. Own the handle with a type

Section titled “Own the handle with a type”

A Windows handle is an opaque ticket stored in one process’s handle table. It is not the process, file, event, or section itself, and it is not an address you should dereference. Windows uses the ticket to find the kernel-managed object and to remember which access rights this particular opening received. Two handles can therefore name the same object while granting different permissions.

That gives a handle four rules:

  1. Scope: a handle value is normally meaningful only in the process whose handle table contains it. DuplicateHandle can deliberately create another.
  2. Rights: OpenProcess(PROCESS_VM_READ, ...) asks for a capability. The returned handle carries only the rights Windows granted for that opening.
  3. Lifetime: the handle stays valid until its owner closes it. Closing the last handle to many kernel objects lets Windows destroy that object.
  4. Correct closer: many kernel-object handles use CloseHandle, but not every Windows value does. SOCKET, HKEY, HMODULE, and HWND follow their own APIs and ownership rules. Never call CloseHandle merely because a type’s name begins with H.

Section titled “Inheritance makes the map less tidy”

With single inheritance, the base-class part is often placed at the beginning of the derived object. A BotPlayer may therefore begin with all fields needed by Player, followed by bot-specific state.

Multiple inheritance can add more than one base subobject and more than one vptr. A method may even adjust this before using it. If two methods appear to use bases a fixed distance apart, do not immediately declare one of them wrong. You may be looking at two views of the same larger object.

RTTI stands for run-time type information: extra data the compiler emits so that code can ask what class an object really is while the program is running. It is what makes dynamic_cast possible.

When it is present it can expose type-descriptor clues near virtual tables, sometimes including a readable class name. That name tells you what the class was called and nothing more: release builds can strip RTTI entirely, and a name does not tell you where any of the class’s fields sit.

One object can have several useful identities

Section titled “One object can have several useful identities”

When inspecting object-oriented code, separate three questions:

  1. Allocation identity: which complete block of memory was created and must eventually be released?
  2. Subobject view: which base-class-shaped part does this particular pointer address?
  3. Dynamic type: which most-derived implementation will virtual dispatch choose at this moment?

These answers can differ. A pointer passed to a base-class method may point a few bytes into the complete allocation. A thunk — a tiny compiler-generated stub that fixes something up and then jumps to the real function — may adjust this before jumping to the real method. Subtracting every observed field from that adjusted pointer can produce negative offsets and a broken layout even though the pointer is valid for its particular base view.

When two candidate bases always differ by the same small constant, they are usually two views of one object. The thunk or call site that adds the constant shows where the adjustment happens, and the constructor, which writes both vptrs, shows how the two views sit inside one allocation.

Constructors and destructors reveal a timeline

Section titled “Constructors and destructors reveal a timeline”

A memory snapshot shows one state. Construction and destruction show how the state came to exist and which parts belong together.

A constructor candidate often:

  • receives a newly allocated or caller-provided object address;
  • writes repeated default values at fixed offsets;
  • calls base constructors before initializing derived fields;
  • writes one or more vptr candidates, sometimes replacing an earlier base vptr;
  • returns the same object or passes it into a registration system.
flowchart LR
    A["allocate the block"] --> B["base constructor:<br/>vptr = base table,<br/>base fields = defaults"]
    B --> C["derived constructor:<br/>vptr = derived table,<br/>derived fields = defaults"]
    C --> D["registered and used<br/>by the game"]
    D --> E["destructor: unregister,<br/>release children"]
    E --> F["block freed: every cached<br/>address to it is stale"]

None of those clues identifies a constructor alone, because an ordinary reset function can also fill fields with defaults. What a reset function does not do is run right after an allocation, call base constructors first, and switch the vptr from the base table to the derived table.

Destructors provide the other half: they reveal child cleanup, unregistering, reference releases, pool returns, and the point after which a cached address is stale. For a memory tool, this lifetime boundary matters more than recovering the original C++ class name.

Recover a structure step by step

Section titled “Recover a structure step by step”

One memory window is not enough to recover a structure. A repeatable sequence is:

  1. Anchor one field. Find a value with an obvious controlled behavior, such as yaw, health, or ammunition.
  2. Find code that uses it. Break on access. The instruction’s base register and displacement give the field’s offset: [ecx+40h] means the field sits 0x40 bytes (4 × 16 = 64) past the address in ecx.
  3. Propose an object base. Subtract the displacement from the known field address: a yaw at 0x12340040 read through [ecx+40h] gives a base of 0x12340040 − 0x40 = 0x12340000.
  4. Collect nearby candidates. Watch adjacent aligned values as position, view, health, and state change.
  5. Compare instances. Inspect the local player and several bots at the same offsets.
  6. Assign types carefully. Check byte width, signedness, endianness, value range, and how instructions consume the field.
  7. Trace methods. Look for repeated this + offset accesses and virtual calls.
  8. Test lifetimes. Join, die, respawn, leave, and start a new match. The moments when pointers become null or objects are replaced mark where cached addresses stop being valid.

A field nobody has managed to change on purpose stays unnamed, as field_48 or plain padding, until a controlled change or a traced read shows what it holds.

Common false conclusions

Section titled “Common false conclusions”

“Two nearby floats must be X and Y.” They could be velocity, color, or a timer. Change one behavior at a time.

“The first pointer proves a vtable.” Follow several entries and verify they point to executable methods.

“The debugger showed ecx, so it must always be this.” Confirm the calling convention and watch how the method uses the value.

“The structure worked once, so it is finished.” Compare instances and repeat after object destruction, respawn, and clean launches.

The layout is a versioned model

Section titled “The layout is a versioned model”

An object base is the start of one instance, and each field offset is a byte distance from that base. The hidden this argument selects the instance for a member call; a vptr commonly leads to its virtual-method table. Padding and inheritance can add gaps or make one object reachable through several base views. Those observations form a layout model for the tested game build, not a promise for every build. A remote object address remains an address in the game process, never a valid local Rust reference.

The same technique appears in debuggers, crash analyzers, compatibility tools, profilers, and digital-forensics programs. Each one recovers structure from raw memory without the original source code.

Lesson 3.5

Object-Oriented Clues in Machine Code

Source patterns do not survive as labels

Section titled “Source patterns do not survive as labels”

A C++ programmer may write a class named EnemyFactory, a State interface, and an Observer list. The processor never sees those friendly names. After compilation it sees addresses, loads, stores, comparisons, and calls.

That sounds discouraging, but design patterns still leave shapes in memory and code. A vtable is a row of function pointers. A factory allocates an object and initializes it. An observer loop walks a collection and calls similar functions. One shape alone is common in unrelated code, but several that fit together usually point to one pattern. 🧩

When debug symbols exist for a build, they give the real names and layouts, so they can check a layout recovered from the version-pinned executable.

A pattern name communicates intent

Section titled “A pattern name communicates intent”

Design patterns are shared names for recurring design decisions. They do not all exist merely to “remove dependencies,” and two patterns can produce similar-looking machine code. Their important difference is often intent: why the pieces are separated and what kind of change the design expects.

For example, both State and Strategy may delegate through a function table. State usually represents behavior that changes as an object moves through a lifecycle. Strategy usually selects one replaceable rule. Observed transitions and call sites matter more than the table shape.

In your own tool, use a pattern after repeated change exposes a real problem: duplicated lifecycle code, tangled ownership, or features that cannot be tested separately. Do not add a factory, observer, or trait hierarchy only because the name sounds professional. A smaller function or enum is often the clearer design.

In a compiled game, a pattern name describes a likely role. It does not recreate the original source or prove what the programmer intended.

Start from what the code does, not class names

Section titled “Start from what the code does, not class names”

Suppose three heap objects all begin with the same pointer. That pointer leads into a read-only section containing executable addresses. Several call sites do this:

flowchart LR
    A["object A<br/>+0x00: table pointer"] --> T["one read-only table<br/>of function addresses"]
    B["object B<br/>+0x00: table pointer"] --> T
    C["object C<br/>+0x00: table pointer"] --> T
    T -->|"slot 4, at +0x20"| F["the function called,<br/>with the object in rcx"]

What this code shows is small:

Objects at these addresses share a function table, and slot four receives the object address.

Slot four is at +0x20 because each slot holds one 8-byte function address on 64-bit Windows, and 0x20 is 2 × 16 = 32 bytes, which is 32 ÷ 8 = 4 slots past slot zero.

The code does not show the source class name, the inheritance tree, or the method name. Two facts can be checked directly: offset 0x00 points into read-only module memory, and the entries of that table point to executable module pages. Together they match how C++ compilers implement a vptr, so offset 0x00 is very likely one. A name such as Actor is a label chosen from the object’s behavior; nothing in the binary says what the original class was called.

Five patterns and the clues they leave

Section titled “Five patterns and the clues they leave”

Singleton or global manager

Section titled “Singleton or global manager”

A singleton is one shared object. Look for many functions loading the same global pointer before accessing fields:

flowchart LR
    F1["recruit code"] --> G["one global pointer"]
    F2["save code"] --> G
    F3["interface code"] --> G
    G --> M["the one manager object"]

One global pointer alone does not make a singleton; it might be a cache or the current scene. A singleton is allocated once during initialization, reused by many unrelated call sites, and released at shutdown.

Factory

Section titled “Factory”

A factory chooses which concrete object to create. A common compiled shape is:

  1. inspect a type ID;
  2. choose an allocation size;
  3. call an allocator;
  4. call one of several constructors;
  5. return a common base pointer.
flowchart TD
    T["type ID"] --> S{"switch"}
    S -->|"1"| A["allocate, then call<br/>the first constructor"]
    S -->|"2"| B["allocate a different size,<br/>call the second constructor"]
    S -->|"3"| C["allocate, then call<br/>the third constructor"]
    A --> R["return a pointer<br/>to the common base"]
    B --> R
    C --> R

A switch followed by several constructor calls is more useful than the word “factory.” Follow each constructor and compare its first vptr write and field initialization.

State or strategy

Section titled “State or strategy”

State and strategy patterns both replace one behavior with another. Memory may contain a pointer to a small behavior object or a function table. The owner delegates work to it each update.

stateDiagram-v2
    direction LR
    Idle --> Chase: sees the player
    Chase --> Attack: in range
    Attack --> Chase: target moves away
    Chase --> Idle: loses the player

Each arrow is a moment when the owner’s behavior pointer changes. If it changes when an enemy moves from idle to chase to attack, “state” is a useful name. If it changes when a weapon changes its aiming rule, “strategy” may fit better. The bytes do not care which textbook word you choose; behavior over time is the deciding clue.

Observer

Section titled “Observer”

An observer system keeps a collection of listeners and calls them when an event occurs. Look for one loop that:

  • walks a vector, list, or handle table;
  • passes the same event record to each element;
  • makes a direct or virtual call;
  • tolerates an empty collection.
flowchart LR
    E["event: a unit died"] --> N["notify loop:<br/>same event record for each"]
    N --> L1["score panel"]
    N --> L2["sound system"]
    N --> L3["achievement tracker"]

Do not confuse this with an ordinary entity update loop. An observer loop usually starts from an event or notification function and passes similar event data to many unlike objects.

Component or entity-component system

Section titled “Component or entity-component system”

Composition stores behavior in separate components rather than one deep inheritance tree. Useful clues include:

  • an entity ID used to index several pools;
  • type IDs mapped to separate arrays;
  • bit masks describing which components an entity owns;
  • tightly packed arrays of positions or health values;
  • systems that loop over one component type at a time.

If position records are contiguous while unrelated entity fields live elsewhere, do not force them into one giant Player structure. The game may be data-oriented.

Constructors are layout witnesses

Section titled “Constructors are layout witnesses”

A constructor often writes the vptr and then initializes fields:

The last store starts at +0x10 and writes a qword—eight bytes—so it touches offsets +0x10 through +0x17; +0x18 is the first byte after the store. That gives a minimum object size of at least 0x18 bytes, but alignment may make the allocation larger. Compare the allocator’s requested size, constructor stores, destructor reads, and ordinary methods. No single function tells the whole story.

A repeatable reconstruction method

Section titled “A repeatable reconstruction method”
  1. Collect several live object addresses from the exact local build.
  2. Group objects by their first pointer and validate that it leads to executable function entries.
  3. Find code that writes that first pointer; it may be a constructor.
  4. Find code that allocates the object and read the requested size.
  5. Label every repeated field access as field_08, field_10, and so on.
  6. Watch which actions change each field.
  7. Find virtual call slots and trace their arguments and side effects.
  8. Name a pattern only when several of these shapes agree.
  9. Compare with source or debug symbols as a final answer key.

The goal is not to make the class diagram look impressive. The goal is to build a model that correctly predicts what the program will do next.

Common mistakes

Section titled “Common mistakes”
  • ❌ Naming a class from one interesting string.
  • ✅ Naming fields provisionally, such as field_08, until their behavior is clear.
  • ❌ Treating every first pointer as a vptr.
  • ✅ Checking page permissions and several table entries.
  • ❌ Assuming inheritance because two objects share fields.
  • ✅ Checking vtables, constructors, conversions, and call behavior.
  • ❌ Forcing an entity-component design into one C-style struct.
  • ✅ Letting access patterns reveal where each component really lives.

How Collections Live and Die in Memory

A field layout is only half a model

Section titled “A field layout is only half a model”

Imagine that offset 0x40 points to a weapon. Knowing that does not answer the dangerous questions:

  • Does the player own the weapon?
  • Can several players share it?
  • Can it disappear while another system still remembers it?
  • Is the value a pointer, an index, or a generation-checked handle?

These are lifetime questions. A reliable memory tool needs them because an address that was correct one frame ago may now belong to a different allocation.

The heap is memory handed out by an allocator for objects whose lifetime does not simply end when the creating function returns. A spawned enemy, a resized list, or a text buffer can live across many calls; the game later releases or reuses its allocation. Unlike a call’s stack frame, cleanup is controlled by an owner or a game event. An individually allocated object commonly stays at one address while that allocation lives, but containers can move their elements when they grow and an allocator can reuse a freed address.

Linked structures leave different clues

Section titled “Linked structures leave different clues”

A vector keeps its elements side by side, so code finds element n with arithmetic. Three other common containers give up that arithmetic in exchange for something else, and each exchange leaves a recognisable pattern in the code that walks it.

A linked list: every element points to the next

Section titled “A linked list: every element points to the next”

A linked list stores each element in its own heap block, called a node, together with the address of the next node, and often the previous one too. It exists to make inserting and removing cheap. Taking the first of 10,000 elements out of a vector means sliding the other 9,999 down one place; taking it out of a doubly linked list means rewriting two pointers in its neighbours.

flowchart LR
    A["node A<br/>prev · payload · next"] -->|"next"| B["node B<br/>prev · payload · next"]
    B -->|"prev"| A
    B -->|"next"| C["node C<br/>prev · payload · next"]
    C -->|"prev"| B

The price is that a list has no arithmetic shortcut. Reaching the 1,000th node takes 1,000 reads, each one loading the next pointer out of the node just reached. That repeated load from a fixed offset inside the current node, such as mov eax, [eax+4] in a loop, is the list’s clue. The nodes are wherever the allocator put them, not in one block.

A search tree: each comparison discards half

Section titled “A search tree: each comparison discards half”

A binary search tree node holds a key and two child pointers: smaller keys go to the left, larger ones to the right. Finding a key means comparing and stepping left or right. In a balanced tree, each step discards roughly half the remaining possibilities, so a tree of 1,000,000 entries needs about 20 steps: 2²⁰ = 1,048,576. std::map typically maintains such a balanced tree. Its clue is a loop that compares a key and then loads one of two pointers depending on the result. Its failure is lopsidedness: keys inserted in sorted order all go the same way and turn the tree into a slow list, which is why real implementations rebalance themselves.

A hash table: arithmetic picks the bucket

Section titled “A hash table: arithmetic picks the bucket”

A hash table turns the key into a number, its hash, and uses that number to pick one slot, or bucket, in an array of buckets. Only the entries in that bucket are checked. With a suitable hash and enough buckets for the entries, lookup is usually close to constant time as the table grows; collisions or a full table can make it slower. With 16 buckets, a hash of 0x5A3 selects bucket 0x5A3 & 0xF = 3, because the mask 0xF keeps only the last hex digit. The clue is arithmetic on the key (multiplies, shifts, XORs), then that mask or a remainder, then a short walk through one bucket. Two keys can land in the same bucket, a collision, which is why each bucket may hold a short list. Lesson 10.2 shows the same idea inside Lua’s tables.

Validate structural invariants:

  • a doubly linked node’s next.prev should return to the node;
  • tree children should eventually end at a sentinel or null;
  • bucket indices must stay below the bucket count;
  • traversal needs a maximum-node limit and a visited-address set.

The visited set is important. Corrupted data could form a cycle and otherwise trap a scanner forever.

Before choosing a container model, ask what the game actually does with the data: does it need an ordered list, lookup by key, first-in-first-out work, a tile grid, or links between waypoints? Then ask whether items can be inserted or removed while you read them. Those questions connect the shape you observe to the operation it supports; a readable address alone cannot identify a container.

Raw pointers, smart pointers, and handles

Section titled “Raw pointers, smart pointers, and handles”

Unique ownership

Section titled “Unique ownership”

If one owner’s destructor directly destroys the pointed object, and moves clear the old pointer, unique ownership is likely. That resembles C++ unique_ptr, but use a neutral label until symbols confirm it.

Shared ownership

Section titled “Shared ownership”

Shared objects often have a separate control block with strong and weak reference counts. Copies increment a count; releases decrement it; a transition to zero calls a destructor. The object pointer and control-block pointer may travel together.

flowchart LR
    P1["owner 1<br/>object pointer, control pointer"] --> O["the object"]
    P2["owner 2<br/>object pointer, control pointer"] --> O
    P1 --> CB["control block<br/>strong count 2, weak count 1"]
    P2 --> CB
    W["a weak observer"] --> CB

Never edit a suspected count. The calls around it show whether its updates are atomic, as a thread-safe reference count’s must be; a plain integer that happens to rise and fall is not enough to call something a reference count.

Handles

Section titled “Handles”

Games often avoid long-lived raw pointers by storing a small handle:

The index chooses a slot. The generation proves that the slot still represents the same logical object. If a deleted entity’s slot is reused, its generation changes and old handles stop resolving. ✅

For example, a saved handle for slot 12 with generation 3 resolves only while slot 12 still reports generation 3. If that enemy dies and a new enemy occupies slot 12 with generation 4, the old handle is rejected. The slot may hold a real living object at a valid address; the generation mismatch is what reveals that it is the wrong object.

Follow destruction as carefully as construction

Section titled “Follow destruction as carefully as construction”

Constructors show default values and vptr writes. Destructors show ownership:

  1. Which child objects are destroyed?
  2. Which pointers are merely cleared?
  3. Which reference counts are released?
  4. Which collections remove the object?
  5. Is memory freed immediately or returned to a pool?

Set a breakpoint on an owned toy object’s destructor and delete it through the normal game action. The call chain and the fields the destructor touches answer those five questions. Repeat the experiment, because one run may include unrelated cleanup.

The lab also stores a toy tag calculated from the encoded value and key. When one bit changes, the tag no longer agrees:

flowchart LR
    A["encoded value + key"] --> B["make_tag(encoded, key)"]
    B --> C{"equals the<br/>stored tag?"}
    C -->|"no"| D["Err(IntegrityError)"]
    C -->|"yes"| E["decode(encoded, key)"]

The code makes the two exits explicit. It recomputes the tag from the stored encoded value and the supplied key; a mismatch returns IntegrityError without decoding. A match permits the inverse transformation and returns the logical value in Ok.

This tag is educational, not cryptographically secure. An attacker who understands make_tag can calculate a matching tag. The useful lesson is structural: if a changed value is immediately rejected, look for another field or function that validates it.

Section titled “Dynamic keys change over time”

Some programs change a key when a level loads, an object is created, or a value is written. Reading the same field at several moments shows which events change the key:

damage 100 75 84 … same object field
reload 125 different new session state

Do not assume a value has “random encryption” merely because its bytes change. The cause may be an ordinary per-object key, a pointer-relative cookie, a checksum, or unrelated neighboring data.

The analysis, step by step

Section titled “The analysis, step by step”
  1. Start from the exact build and one object address.
  2. Trigger one controlled change in your own target.
  3. Capture the encoded field before and after.
  4. Find the code that reads the field for a meaningful decision.
  5. Trace every operand feeding the decoded result.
  6. Express the operations as a small pure function.
  7. Test the inverse over many inputs.
  8. Look for validation or duplicate fields.

What not to conclude

Section titled “What not to conclude”
  • ❌ “XOR means this is secure encryption.”
  • ✅ XOR can be one reversible step; security depends on a complete, reviewed construction and key handling.
  • ❌ “The value changed, so my offset is wrong.”
  • ✅ The representation or key may have changed.
  • ❌ “One successful decode proves the formula.”
  • ✅ Test several values, sessions, and objects.
  • ❌ “An integrity field is impossible to reproduce.”
  • ✅ First determine whether it is a checksum, a keyed MAC (message authentication code, which needs a secret key), or an authenticated-encryption tag.

How Text Becomes Bytes in a Game

Text is bytes plus an agreement

Section titled “Text is bytes plus an agreement”

The screen may show “Ford,” but memory stores bytes. An encoding explains how bytes represent characters.

Common forms include:

  • UTF-8—used by String and str;
  • UTF-16—many Windows “wide” APIs (Reference: Microsoft's guide to strings in Windows programs explains wide characters, the A and W versions of an API, and Unicode.);
  • older single-byte encodings;
  • null-terminated C strings.

Keep four layers separate:

  1. a character is the human idea, such as é;
  2. a code point is the Unicode number assigned to that character idea;
  3. a code unit is one storage unit used by an encoding, such as u8 for UTF-8 or u16 for UTF-16;
  4. the bytes are the actual memory representation, with byte order relevant for multi-byte code units.

One visible character can use several code units. That is why byte count, UTF-16 unit count, Unicode scalar count, and what a reader sees on screen are not interchangeable lengths. Four short examples show every column coming apart:

Observe a print function

Section titled “Observe a print function”

The debugger may reveal a call that receives a string pointer and screen or layout information. Calling it yourself requires knowing its:

  • calling convention;
  • parameter order and types;
  • ownership of the string;
  • required thread;
  • lifetime of any returned or stored pointer.

Do not guess a signature from one register. Collect several calls with different strings and compare them.

Keep the text contract together

Section titled “Keep the text contract together”

The bytes of a string need an encoding before they become text. UTF-16LE often has a zero high byte for an ASCII-range letter; that byte alone does not end the string. A C-style terminator marks the end of the encoded sequence, and CString owns a terminated buffer while rejecting interior zeros. The pointer passed to a print function is useful only while that buffer remains alive, so tracing a text call means checking both its bytes and its lifetime. That is one part of a larger function contract: the caller and callee must also agree on argument positions, return values, and ownership.
