Lesson 1.1

Reasoning from Evidence

You do not need to prove that you already know something before you study it. The next lesson starts with the parts of a computer and builds each idea from there. You do not need to look up its missing foundations before you begin.

The nine lessons in this opening chapter connect four views of one game action: the computer runs instructions, the game applies a rule, Rust expresses the rule, and memory holds the changing state. A Windows lab and a gold scan then make those ideas visible. The chapter ends with that first scan; the next chapter follows the value into the code that changes it. Read the sequence as a tutorial; later, the concept lessons are also places to return when an unfamiliar term appears.

Here is one study loop that works well for unfamiliar technical ideas. It is a suggestion, not a requirement: the later lessons explain their subjects directly and do not depend on it, so use it when an idea will not stick and skip it when it does.

  1. Look up the exact part you need.
  2. Close or hide the answer.
  3. Explain the idea in your own words.
  4. Check and correct what you said.

That loop gives you fast feedback. It also prevents a common mistake: reading the same paragraph several times and confusing recognition with understanding.

TL;DR: Look up, hide, explain, check. Explaining from memory is the real test; rereading only tests recognition.

Choose a goal you can recognize

Section titled “Choose a goal you can recognize”

Give a study session a specific goal. “Understand game hacking” does not say what you should be able to do afterward. “Explain what I observed after one jump, and distinguish that observation from my guess about its cause” does. You can finish that goal with a short explanation and a repeatable observation; you do not need to understand the entire game first.

Choose a goal that matters to the next task. If you want to follow a gold purchase, learning how to distinguish the stored amount from its display is useful. Collecting unrelated facts about every game engine can wait. As the book introduces code and tools, a goal can become more concrete: run one example, explain its inputs and result, or reproduce one error.

Ask a question small enough to answer

Section titled “Ask a question small enough to answer”

Broad questions make it hard to tell whether an answer is complete.

❌ Too broad: “How do games work?”

✅ Better: “When I press the jump button, what changes on the screen?”

✅ Better: “If I press jump while the character is standing still, does the character rise before landing again?”

A useful technical question usually names:

  • the object you are studying;
  • the relationship you want to understand;
  • the evidence or example you can check.

The jump question names the action you control, the change you want to observe, and a way to check it: try the same button press while standing still and watch the character. If nothing happens, you have a more useful next question: was the button received, or does this situation prevent jumping? You can investigate one possibility at a time.

Alternative: Treat a question like a bug report. It points at one thing to try, so a small test can answer it.

Write down what you know, what you do not know, and what you are assuming. For the jump question, you know which button you pressed and whether the character visibly rose. You do not yet know whether the game received the input or which rule allowed the jump. “The character was standing on the ground” may be an assumption until you check the starting position. These distinctions keep an attractive explanation from silently becoming a fact.

Read the source before answering an unfamiliar question

Section titled “Read the source before answering an unfamiliar question”

If you encounter an unfamiliar idea, read the explanation and its example before trying to answer a question about it. For a detail that depends on a particular tool or version, consult that tool’s documentation too.

Then hide the source and answer without looking at it. This matters because copying a sentence tests your eyes, while rebuilding its meaning tests your understanding.

Suppose a lesson says:

A game’s state is the information that describes what is happening now.

A good answer in your own words could be:

State is what the game currently remembers, such as a character’s health or position.

The wording changed, but the meaning stayed accurate. Do not add a claim the lesson did not support, such as “state is only what I can see on the screen.”

Check whether the evidence answers your question

Section titled “Check whether the evidence answers your question”

A source can be accurate and still answer a different question. Instructions for another game version or another processor architecture may explain the general mechanism while giving the wrong steps for your experiment. Check the target, version, conditions, and actual claim before using the source.

Prefer evidence you can inspect: the relevant code, the tool’s documentation, or a controlled observation you can repeat. Each has limits. Documentation describes an intended contract; an experiment shows what happened under the conditions you recorded. One successful jump does not establish that jumping works from every position. Several sites repeating the same original claim also do not provide several independent checks.

Consider another explanation before settling on the first one. If a jump fails, perhaps the input was missed, or perhaps the character was already airborne. Reset to a known position and repeat the press, then vary one condition. A useful test produces different predictions for the competing explanations.

Occam’s razor is a useful preference for an explanation that needs fewer unsupported assumptions while still accounting for the evidence. It helps you choose what to investigate first. Simplicity does not prove an explanation true; a more complicated cause may fit a later observation better.

Narration: Checking the cheap explanation first saves time. A missed button press takes seconds to rule out; a theory about hidden game rules can take an afternoon.

Correct mistakes immediately

Section titled “Correct mistakes immediately”

After answering, compare your answer with the source or ask for a correction that uses the source. Mark each important part as:

  • correct — the meaning matches;
  • missing — an important part was left out;
  • incorrect — the answer says something the source does not support;
  • unclear — the idea may be right, but the wording hides it.

Rewrite only the parts that need work. A correction should tell you why the old answer failed, not merely show a replacement sentence.

If you miss the same question in the same study session, look it up again and retry with different wording. This tests whether you can express the idea in more than one way. If you retry on another day, answer as accurately as you can after reviewing it again. Save repeated weak spots for spaced review.

Accuracy and flexible wording are different skills

Section titled “Accuracy and flexible wording are different skills”

Answering in your own words means preserving the original meaning without copying the sentence.

Explaining it a different way means keeping that meaning while changing the example, order, or comparison. For instance:

  • accurate answer: “Game state describes what is happening now.”
  • different explanation: “If a character loses health, the game’s remembered health changes; the health bar may then show that change.”

The first checks precision. The second checks whether you can use the idea.

Use a worked example before making a prediction

Section titled “Use a worked example before making a prediction”

First follow an example whose starting point, action, and result are explained. Suppose a game shows 100 gold. Buying an item for 25 gold leaves 75: subtracting 25 from 100 gives 75. After seeing that worked through, you can predict what a second 25-gold purchase would do, then check in the game. Later lessons use this same visible change to ask where the value is kept and how code updates it.

When you reach a code example, read its explanation before predicting a result. If you use an AI completion or copy a line, explain every accepted line. “It compiles” is useful feedback, but it is not the same as understanding.

Make progress when you get stuck

Section titled “Make progress when you get stuck”

An error is information about this attempt. It does not establish that you cannot learn the subject. Keep the exact message or unexpected result, return to the last step you can explain, and reduce the task to one small example. For the jump problem, check one press from one known position before studying the whole movement system.

Change one thing and record what happened. If you keep making the same guess, take a short break, explain the problem aloud, or ask another reader to walk through the example with you. Practice should include checking and correcting the result; repeatedly rehearsing an incorrect explanation preserves the mistake. Over time, keep a few worked examples and corrected errors that you can return to when the same difficulty appears.

Ask for debugging help someone can reproduce

Section titled “Ask for debugging help someone can reproduce”

“It does not work” gives another person almost nothing to inspect. A useful help request includes:

  • what you expected;
  • what actually happened;
  • the smallest relevant code;
  • the exact error message;
  • the target version and architecture;
  • what you already tested.

That information turns a complaint into a question someone can reproduce. Here is that list as a request you can fill in and send to a person or an assistant:

PromptAsk for help someone can reproduce

I expected [what you expected]. Instead [what actually happened]. The smallest code that shows it is [the code]. The exact error message is “[the message]”. I am using [the tool or game, its version, and 32-bit or 64-bit]. I already tried [what you tested]. What should I check next? Please say which part of my report your answer depends on.

Ask for the missing observation or explanation directly: “I expected the character to rise from this position; the input was recorded but the position did not change. What should I check next?” When helping someone else, recognize what they already tested and ask a useful question about the remaining gap. Avoid treating a mistake as a judgment about the person.

Use AI as a helper, not as the source of truth

Section titled “Use AI as a helper, not as the source of truth”

AI can create practice questions, compare your explanation with supplied source material, simplify a difficult paragraph, or suggest a small test. Give it the actual source, version, and code when those details matter.

Always check important claims against the program, documentation, or source code. If the answer cannot show where a fact came from, treat it as a lead to verify—not as evidence.

The marks from “Correct mistakes immediately” work as a request too:

PromptCheck my explanation against the lesson

Here is a paragraph from a lesson: “[paste the paragraph]”. Here is my explanation in my own words: “[paste your answer]”. Using only the paragraph, mark each important part of my answer as correct, missing, incorrect, or unclear, and say why each part that is not correct fell short. Do not add facts the paragraph does not contain.

A short study session

Section titled “A short study session”

If you want a routine, this one fits in 20–40 minutes:

  1. skim the lesson headings for a few minutes;
  2. choose one question you can test;
  3. read one explanation and one small example;
  4. hide them and explain the idea;
  5. run or inspect the example;
  6. check your explanation against the source and retry the parts you missed.

Checkpoint

Section titled “Checkpoint”

Before moving on, you should be able to:

  • turn a broad topic into a checkable question;
  • choose a useful goal and separate known facts from assumptions;
  • look up an unfamiliar idea before answering;
  • check that evidence fits the target and consider another explanation;
  • explain it without copying the source;
  • compare, correct, and retry your answer;
  • give a helper enough detail to reproduce your problem.

Lesson 1.2

How a Computer Runs a Game

Suppose a game shows 100 gold. You collect one coin, and the display changes to 101. What had to happen inside the computer for that small change to appear? We can answer without knowing a programming language yet.

The parts work together

Section titled “The parts work together”

The game’s files stay on a storage drive when the game is closed. When you start it, the computer puts the code and the information needed soon into RAM (random-access memory). RAM is fast working storage; its contents are temporary. The CPU (central processing unit) runs the code and changes values such as your gold. A keyboard, mouse, or controller supplies input. The GPU (graphics processing unit) helps turn the game’s drawing work into the picture you see.

These parts have different jobs in our coin example. The stored game file contains the instructions for collecting a coin. While the game runs, RAM holds the current gold value. The CPU updates that value from 100 to 101, and the game draws the new number on the screen. The parts communicate through the computer’s hardware; none of them is the whole game by itself.

The CPU follows small instructions

Section titled “The CPU follows small instructions”

The CPU is sometimes called the computer’s brain. That is a useful first picture of its central job, but the CPU does not understand a game as a person does. It executes instructions: small, specified operations such as copying a number, adding two numbers, comparing them, or going to another instruction.

The CPU has tiny working places called registers. Imagine one register currently holds 100. An add-one instruction changes that register’s value to 101. It did one small job; it did not decide what a coin means or draw the number. Later, the program can store the result in RAM for continued use.

A program combines instructions

Section titled “A program combines instructions”

A program is a collection of instructions arranged to do a larger job. Our example becomes a tiny program if we let a number come in and send the new number out:

The input is the value supplied to this calculation. The output is its result. A running program can also remember values, cause effects, and keep working rather than stop after one output. In a game, the gold count is part of the game’s changing state: information describing what is happening now. The input might be the event “collect a coin,” and the new state has 101 gold.

A function names work we want to reuse

Section titled “A function names work we want to reuse”

A larger program may need to add one in many places. We can give that small behavior a name: add_one. A named piece of program behavior is a function. Instead of describing its steps every time, another part of the program can ask add_one to work on a number.

This is explanatory pseudocode, not code you can run as written. The name number stands for the input supplied on each use; result is the value after adding one. A function can also do work without taking an input or returning a useful value. Naming behavior lets the program reuse and organize it.

A branch chooses which work to do

Section titled “A branch chooses which work to do”

What if a game can award a coin or charge one? We can name the second operation subtract_one. Both operations change the same starting number by one. Now the program needs another input: which action occurred?

For “collect,” the program follows the add path and ends at 101. For “spend,” it follows the subtract path and ends at 99. It must compare the action with the choices and then follow one path. This choice is a branch. A branch lets the same program respond differently to different input. It does not run both outcomes for one action.

In a real game, spending may also need a rule such as “do not spend when gold is zero.” That is another comparison and branch. Lesson 1.4 will turn this small calculation into a program written in Rust.

Alternative: Picture a branch as a fork in a road: the program reads a sign, then walks down exactly one path.

How the numbers are represented

Section titled “How the numbers are represented”

We have treated 100 and 101 as ordinary numbers. To find them in a running game, we also need to know how computers represent numbers.

In familiar decimal notation, each place is worth ten times the place to its right. The number 101 means one hundred, zero tens, and one unit: 1 × 100 + 0 × 10 + 1. Binary uses only 0 and 1. Each place is worth twice the place to its right. One binary digit, either 0 or 1, is a bit.

Eight bits make one byte. The eight places in a byte are worth 128, 64, 32, 16, 8, 4, 2, and 1. For example:

Writing eight bits for every byte gets tiring. Hexadecimal, or hex, uses sixteen digits: 0–9 followed by A–F for values ten through fifteen. One hex digit represents four bits, so two hex digits represent one byte. The byte above splits into 0110 (six) and 0100 (four), written 0x64. The prefix 0x tells you it is hex. Its value is still decimal 100: 6 × 16 + 4. Decimal, binary, and hex are different ways to write the same number, not three different kinds of gold.

Narration: Memory tools often show bytes in hex because two digits fit one byte exactly. That is why you may meet 0x64 where the game says 100.

One byte can represent 0 through 255. Larger values use several bytes. The memory lesson just before the first scan will show where those bytes sit and how a program reads them together.

Languages help people write programs

Section titled “Languages help people write programs”

The CPU executes instructions represented by patterns of bits. Writing a whole game as bit patterns would be difficult. Assembly language gives human-readable names to operations such as moving and adding values (Example: In x86 assembly, add eax, 1 adds 1 to the register eax. It is the add-one step from earlier, written as one CPU instruction.). A higher-level language lets us express larger ideas, such as functions and branches, without spelling out every CPU operation.

The operating system helps programs use the computer

Section titled “The operating system helps programs use the computer”

Even our tiny add-one program needs more than arithmetic if a person must type a number and see an answer. It needs a way to receive input and display output. A game also needs files, sound, windows, and access to devices.

An operating system (OS) provides common services for those jobs and coordinates programs that use the computer. This book uses Windows for its practical examples. A program written for Windows can ask Windows to read a file or show a window instead of controlling each device from scratch.

An application is a program made for a user to do something. A game is an application: it uses the OS’s services, runs its own instructions, and keeps its own changing state.

From a file to a running game

Section titled “From a file to a running game”

The Rust source a developer writes has already been translated into machine instructions and linked with other code before the native game file exists. Other games may load scripts that an interpreter runs while the game is open. Either way, the CPU eventually carries out instructions. Lesson 2.2 follows those routes in detail; here we start with the native game file.

The game file on storage contains code and other saved information. Starting it creates a process: one running instance of that program (Tip: To see processes on Windows, open Task Manager and choose the Details tab. Each row is one process, with the process ID (PID) that tools show when you pick a process to attach to.), with its own memory and resources. Windows loads the code and needed data into memory and starts a thread, a path that executes instructions in the process. A process may have more than one thread, but one is enough to picture this first example.

Many games repeat a broad game loop while you play:

  1. receive input, such as the event “collect a coin”;
  2. update state, changing gold from 100 to 101;
  3. draw the current state, so the display shows 101;
  4. repeat for the next action.

One player has related values

Section titled “One player has related values”

Suppose Ada starts with 100 gold, 80 health, and a maximum of 100 health. These values are part of the changing game state.

The labels tell us what each value means. If the player buys an item for 25 gold, gold becomes 75, while health stays 80. If the player then takes 20 damage, health becomes 60, while gold stays 75. The changes belong to one player, but each rule uses a different part of that player’s state.

Give things identities and responsibilities

Section titled “Give things identities and responsibilities”

Gold and health describe Ada, but the game also needs to distinguish Ada from another player, a coin, or the shop door. A thing the game treats as having its own identity is an entity. Depending on the game, entities can include characters, pickups, projectiles, doors, or even an invisible object that controls a round.

The game can assign Ada an identifier, such as player ID 17. The ID answers “which player?” Her gold and health answer “what is true about that player now?” Buying an item changes her gold; it does not turn her into a different player. A display name is another field and need not be unique. Two players called Ada can still have different IDs.

An entity can also need several kinds of information. Ada has health, money, a position, and a picture the game can draw. Games often group related information into components, each describing one responsibility:

We need this distinction because the information visible on one character need not occupy one uninterrupted block of memory.

An entity also has a lifetime: the interval from its creation to its removal. A coin entity stops being available after Ada picks it up. A later coin can reuse its storage without being the same coin. Some games reuse IDs too, so an ID is meaningful only within the identity rules of that game. Shared assets create separate instances

Section titled “Shared assets create separate instances”

The game does not need a different image file for every coin. It can load one coin image and use it to draw many coin entities. An asset is a resource the game uses, such as an image, a three-dimensional model, a sound, a map, or a set of starting values. An instance is one particular use of a definition or resource in the running world.

Suppose two coins use the same image. One coin is beside Ada and one is near the shop. Each has its own identity, position, and availability. If Ada collects the nearby coin, that instance disappears and her gold rises by one. The coin image remains loaded, and the coin near the shop remains available. Changing a shared image can change how both coins look; removing one coin instance affects that one coin.

The same distinction applies to player setup. A character definition might specify a starting maximum health of 100. Ada’s current health of 60 is state belonging to her running instance. A definition’s default and an instance’s current value can be equal when the instance starts, then diverge during play.

Inputs request actions

Section titled “Inputs request actions”

We have said “Ada buys an item,” but a computer first receives something more mechanical: a mouse click, a key press, or a controller button. The game maps that input to an action, such as “buy this item” or “move right.” Keeping the action separate from its physical input allows the same rule to work with several devices and different key bindings.

An action is a request. The purchase rule still checks the price and Ada’s gold before accepting it. Context matters too: pressing the right arrow might move Ada during play but select the next item while a shop menu is open. The same physical input can request different actions in different parts of the game.

A game also distinguishes a button being pressed now from being held down. In our game, one press of the buy button requests one purchase. Holding the movement button requests continued movement. If the purchase rule ran on every update while the button was held, one press could accidentally buy many items. This makes the input’s timing part of the behavior we need to understand.

To move Ada, the game needs a way to describe where she is. In a small two-dimensional world, use two numbers: x for horizontal position and y for vertical position. Together, (x, y) are coordinates. Ada starts at (2, 3). Moving one unit right gives (3, 3): x changes from 2 to 3 and y stays 3. These are world coordinates, describing Ada’s location in the game. Her screen coordinates describe where her picture appears on the display. If the camera follows Ada, she can move through the world while staying near the middle of the screen. Moving the camera changes the view without moving Ada in the world. Chapter 7 develops these coordinate relationships for 3D games.

The world updates between pictures

Section titled “The world updates between pictures”

The work that advances movement, health, timers, and other rules is the simulation. The work that makes an image of the current world is rendering. One displayed picture is a frame. A simulation update is often called a tick. These names let us distinguish advancing the world from drawing it.

Why does the distinction matter? Suppose a game moves Ada one unit each time it draws a frame. A computer drawing 120 frames in one second would move her twice as far as one drawing 60. Our speed calculation instead asks how much game time passed. Sixty updates of 1/60 second each produce the same four units of unobstructed movement as 120 updates of 1/120 second each: both add up to one second.

A game can use the measured time since the last update, or advance the simulation in fixed steps, such as 1/60 second. With fixed steps, it can run zero, one, or several simulation updates while preparing the next picture. These are two useful scheduling models; real games also decide how to handle stalls and paused time. A frame count alone cannot tell us how many gameplay updates occurred.

This also explains change without input. Once a projectile has a speed, the simulation can move it on later ticks. A timer can count down, and an enemy can act. The player does not need to press a new button for each change. A pause menu might stop the simulation while still rendering the menu, so a visible animation is not proof that every game timer is running.

Collisions connect movement to rules

Section titled “Collisions connect movement to rules”

Our movement calculation proposes a new position. It has not yet checked whether Ada would pass through a wall or touch a coin. The game gives objects simplified shapes for detecting contact. The test for whether these shapes meet or overlap is collision detection.

For a simple worked example, treat Ada as a point starting at x = 2 and place a wall at x = 3. She requests movement to x = 4, keeping the same y. Looking only at her destination could miss the wall: the point at 4 is past it. Testing the movement from 2 to 4 finds the crossing. Our game then stops Ada just before the wall. Actual characters have width, but the point example shows why a path and a final position answer different questions.

Detecting contact and deciding its consequence are separate jobs. A wall blocks movement. A coin allows movement but awards gold and removes its own entity. A trap allows movement but applies damage. All three can begin with a contact test and then follow different game rules.

A physics system can calculate motion using speed, forces, gravity, and contact responses. A game can also use simple movement rules without a general physics system. The drawn image and the collision shape may have different sizes or levels of detail, so touching an image is not always the same as touching the shape the rules test.

Modes and events organize change

Section titled “Modes and events organize change”

The same contact need not have the same outcome in every situation. Our game gives Ada three modes: alive, defeated, and respawning. At health zero, she changes from alive to defeated and movement requests are ignored. After a two-second wait, she enters respawning. Placing her at the spawn point and restoring her health makes her alive again.

A change between modes is a transition. A set of allowed modes and rules for moving between them is a state machine. Here, “state” names one behavior mode. Earlier, “game state” meant all the information the game remembers, including gold, health, position, and this mode. The mode is one part of that larger state.

For this example, the game changes Ada’s mode while keeping her player identity. A different game could remove the old character entity and create another. The visible respawn alone does not tell us which lifetime rule it uses.

The game can also announce a particular occurrence: “Ada collected coin 42.” Such an occurrence is an event. The coin rule can award one gold, then notify the sound system and the display so they can play a pickup sound and show the changed amount. Those systems can react to the same event without each deciding whether the coin was available.

The distinctions are useful when following a change. An action requests something, current state describes what is true, and an event reports what happened. “Collect coin 42” is the request; “Ada has 76 gold” is the resulting state; “coin 42 was collected” is the event. If the coin was already removed, the game can reject a second request instead of awarding gold again. Chapter 4 develops decisions and events in more detail.

The display can hold a copy

Section titled “The display can hold a copy”

After Ada collects a coin, the game may store 76 as her current gold and also prepare the text "Gold: 76" for the screen. The text is derived from the number, but it is not necessarily the number that the purchase rule reads.

If someone changes only the display text to "Gold: 999", the screen may show 999 while the purchase rule still sees 76. Changing a displayed copy can affect appearance without changing gameplay. This is why observing a matching number in memory is only the start of an investigation. Later lessons compare what changes after a purchase with what the game actually uses to decide whether the purchase is allowed.

Which copy decides the result?

Section titled “Which copy decides the result?”

In our local example, the purchase rule reads Ada’s gameplay gold. That value is authoritative for the purchase: the rule accepts it as the amount Ada actually has. The display copy reports the result but does not decide it. Authority describes this role, not a special numeric type.

In a multiplayer game, a client is the program a player uses to take part. A server is a program that coordinates the shared game (Reference: Lesson 8.1 follows a move from a game client to a server and back as framed bytes.). A common design lets the client send “Ada requests this item” while the server looks up the item’s price and checks its own gold value before accepting or rejecting the request. Different games divide responsibility differently, so the important question is which side has authority over this particular decision.

Suppose the server has 76 gold for Ada and the client’s display shows 999. The server accepts one 25-gold purchase and updates its value to 51. It sends the accepted result back to the client, which can then show 51. The display’s 999 did not give the server more gold. A network delay can also leave a client temporarily showing an older result, even when neither program has a bug.

Narration: This is why servers do not trust a number a client shows: the client only sends a request, and the server checks it against its own copy.

Some clients show an expected result before the server replies so an action feels responsive. If the server rejects the action, the client must correct that expectation. For now, distinguish the player’s request, the local picture, and the accepted shared result. Chapter 8 follows the messages that connect them.

Save files preserve chosen state

Section titled “Save files preserve chosen state”

The running game holds live state: what it needs for play now. Closing the game ends that running instance. To continue later, it writes selected information to storage. Keeping information beyond the running process is persistence; a save file is one way to provide it.

Consider the local version of our game, after Ada reaches 76 gold and 60 health. A save could keep those values, her maximum health, position, and which coins she has collected. It need not keep the current pickup sound’s playback position or the already prepared text "Gold: 76". The game can recreate the display from gold when it loads the save.

Saving selects state at a particular moment. If the file stores 76 gold and Ada later spends 25 without saving again, live gold becomes 51 while the file still records 76. Loading that file can restore the earlier state. A save file and live state can disagree simply because they describe different moments.

Loading also creates new running records. A saved player ID can help the game reconnect related information, but a past RAM address does not give the new process a valid player record. Persistence keeps chosen meaning across runs; it does not promise the same memory locations. Chapter 9 develops save files and other game resources.

The game represents the parts its rules need as entities and fields, such as player ID 17 with 76 gold. This chosen representation is a game-data model. Ada’s health number likewise models how the game’s damage rules work; it is not a complete description of a person’s body.

To save that information or send it to another program, the game chooses a format: rules specifying which fields are included and how to write and read them. A save might include gold and collected coins. A movement message might include only a player ID and the requested direction. They serve different purposes, so they need not contain the same information or resemble the live record’s layout.

Hacking Fundamentals

Imagine an offline game whose display shows 100 gold. Buying an item for 25 changes the display to 75. The screen shows the result, but it does not identify the rule or the stored value that caused it. Game hacking in this book means investigating that behavior and making a deliberate, testable change to the game or its data.

Start with evidence, not a scan result

Section titled “Start with evidence, not a scan result”

An observation is what you can actually see: after a 25-gold purchase, the display changes from 100 to 75. An explanation is a hypothesis: perhaps a four-byte value in the game’s memory stores the gold used by the purchase rule. Other explanations are possible. The game may keep a display copy, recalculate gold from other data, or let a server decide the result. A matching number is therefore a candidate, not a conclusion.

The fastest way to get completely lost is to open a memory scanner and start searching before deciding what you are asking. You can end up with hundreds of addresses—numbered locations in the game’s running memory—with no way to tell which matters and no record of which ones you have ruled out. A scanner finds values that match a question; a debugger can later show the instruction that reads or writes a candidate. Neither tool supplies the meaning by itself.

TL;DR: A match is only a candidate. Decide your question first, because scanners and debuggers find things but do not explain them.

How Memory Actually Works

Before scanning a running game, we need to know what the scanner reads. Suppose a health bar says 100. The player takes a hit, and the bar says 75. Somewhere inside the running game, a stored value changed.

This lesson gives you the first map of where that number lives and what it is made of. You will use the same map when you find a value, follow a pointer, or read another program’s memory later in the book.

We will distinguish locations, contents, types, and pointers here. Lesson 3.2 later takes the bits apart one at a time, including exactly how a fractional number like 10.0 is stored.

“Memory” means more than one thing

Section titled ““Memory” means more than one thing”

People use the word for several kinds of storage, and mixing them up causes a lot of early confusion.

Layer How big, how fast What lives there
CPU registers and caches tiny, extremely fast the handful of values the CPU is working on right now
RAM large, fast the running game’s code, objects, and current state
storage drive huge, slow the game’s files, art, settings, and saved games

There are layers because no single technology is fast, large, cheap, and permanent all at once. Fast memory costs a lot, so you get a little of it. Cheap storage is slow, so it holds the things you are not using this instant.

From here on, when this book says “memory” it means RAM. That is where your health value lives while you are playing. Turn the computer off and it is gone — which is exactly why saving a game has to write a file to the drive.

Picture a process’s memory as an enormous row of boxes. Each box holds one byte, and each box has a number called its address. The number tells the process where to look during that run; it need not identify the same data after the game restarts.

Inside a byte: eight bits and their place values

A bit is a single switch that is either 0 or 1. A byte is eight bits in a row. The question is how eight 0s and 1s can mean a number like 100.

Bigger values use neighbouring boxes

Section titled “Bigger values use neighbouring boxes”

One box holds one byte, and one byte only goes up to 255. Anything bigger has to spill into the boxes next door. A u32 — the type name for an unsigned 32-bit whole number, explained properly below — uses four boxes in a row.

Byte order, and why hex dumps look backwards

Section titled “Byte order, and why hex dumps look backwards”

Once a value spans several boxes, the CPU needs a rule for which box holds which part.

Think about the decimal number 1,234. The leading 1 is worth the most — it means a thousand. The trailing 4 is worth the least. The bytes inside a multi-byte value work the same way, and the byte worth the least is called the least-significant byte.

Windows games on x86 and x86-64 put the least-significant byte in the lowest-numbered box (Alternative: The opposite order, most-significant byte first, is called big endian. Internet protocols traditionally use it, and Lesson 8.3 reads Wesnoth's four-byte frame length that way.). That arrangement is called little endian.

So the four boxes of a u32 count ones, 256s, 256 × 256 = 65,536s, and 256 × 256 × 256 = 16,777,216s. Here is the number 1,000, which is 0x3E8 in hex:

Three facts that are easy to blur together

Section titled “Three facts that are easy to blur together”

Look again at those four boxes. There are three separate things going on:

  • 0x1000 is a location — which box;
  • 64 00 00 00 is a pattern of bytes starting in that box;
  • 100 is one interpretation of that pattern.

The third one does not follow automatically from the first two, and this is the single most important idea in the lesson. Those bytes only become the number 100 once something decides to read four boxes, treat them as one whole number, and use little-endian byte order. Read the same boxes with a different set of rules and the very same bytes mean something else, as the next section shows.

So never treat “address” and “value” as the same word. An address tells you where to look. A value is what you get after you look and decide how to read what is there.

TL;DR: An address is where to look, the bytes are what sits there, and the value appears only after you choose a type to read them.

A type is the instruction for reading bytes

Section titled “A type is the instruction for reading bytes”

A type answers two questions: how many bytes to read, and what the bits inside them mean.

The names are for you. The types are for the compiler. These are the ones you will meet most often:

Number types at a glance

Rust type Size What the bits mean
u8 1 byte a whole number from 0 to 255
u16 2 bytes a whole number from 0 to 65,535
u32 4 bytes a whole number from 0 to 4,294,967,295
i32 4 bytes a whole number from −2,147,483,648 to 2,147,483,647
f32 4 bytes a number that can have a fractional part, such as 3.5
f64 8 bytes the same idea as f32, with more precision
bool 1 byte 0 means false, 1 means true

The names follow a pattern. The number is the size in bits. u means unsigned: the value can never be negative. i means a signed integer, which can be. f means floating point, a number with a fractional part.

The ranges come from counting patterns. One bit has 2 patterns, and every extra bit doubles the count: two bits have 4, three have 8, and eight have 256, which is why a u8 stops at 255. Sixteen bits have 256 × 256 = 65,536 patterns, and thirty-two bits have 65,536 × 65,536 = 4,294,967,296. An i32 has exactly as many patterns as a u32, but it spends half of them on negative numbers, which is why its range is split around zero.

One pattern, two readings

Section titled “One pattern, two readings”

u32 and f32 are both four bytes, but they use those 32 bits in completely different ways. A u32 reads all 32 bits as one whole number. An f32 splits them into three parts — a sign, a power of two, and the digits of the number — much as scientific notation writes 1,500 as 1.5 × 10³.

So one four-byte pattern holds two totally different numbers, depending on which type you ask for:

The u32 reading uses only what this lesson has covered: written most significant first, the bytes are 0x41200000, and a calculator turns that into 1,092,616,192. The f32 reading follows rules for its three parts that are not covered here; Lesson 3.2 works through them bit by bit, all the way to 10.0. What matters now is that nothing in memory changed between the two readings. Only the type did.

Floats have one habit worth knowing from the start: most fractions cannot be stored exactly. Ask an f32 to hold 10.1 and it actually holds 10.100000381…, the nearest value its 32 bits can express (Explanation: Numbers from 8 up to 16 sit 1 ÷ 1,048,576 apart in an f32, about 0.00000095. 10.1 × 1,048,576 = 10,590,617.6, so the nearest stored value is 10,590,618 ÷ 1,048,576 = 10.100000381…). That is why float values in games are rarely round, and why memory scanners let you search for a float within a small range instead of only an exact value.

Narration: So a scan for exactly 10.1 can miss a bar that shows 10.1, because the stored number is a hair off. A small range finds it.

Working out types in a running game

Section titled “Working out types in a running game”

When you inspect a compiled game without useful debug information, many source names and type declarations are unavailable. The compiler used them to choose instructions, and those instructions provide clues about how the game uses the bytes:

  • how many bytes an instruction reads or writes at once: 1, 2, 4, or 8;
  • which kind of instruction does it — x86 has separate instructions for floating-point values, so a float load means an f32 or f64;
  • what the code does with the result — compares it with a signed or unsigned test, adds it to an address, passes it to a drawing function;
  • how the bytes change when you make the game change;
  • whether nearby bytes behave like parts of the same object.

This is also why a memory scanner asks what kind of value you are hunting before it searches. The whole number 10 is stored as 0A 00 00 00. The float 10.0 is stored as 00 00 20 41. The two patterns do not share a single byte, so a search for one can never find the other.

A pointer is a number that happens to be an address

Section titled “A pointer is a number that happens to be an address”

Every value so far has been data about the game: 100 gold, 10.0 metres per second. A pointer is a value too — an ordinary number, stored in ordinary bytes, in an ordinary box. What makes it a pointer is only what that number means: it is the address of something else.

Nothing in the bytes marks them as a pointer. 00 50 00 00 could be the number 20,480 — 0x50 is 80, and 80 × 256 = 20,480 — or it could be a pointer to address 0x5000, which is the same number written in hex. As always, the code that reads them decides which.

Here is the whole idea. Four ordinary bytes at 0x2000:

Three different numbers are involved, and running them together is the most common early mistake by a wide margin:

Number What it is Here
where the pointer lives an address 0x2000
the pointer’s own value also an address 0x5000
what it points at the actual data the player object

Read address 0x2000 and you get 0x5000. That is not the player. To reach the player you read a second time, now from 0x5000. That second read is called dereferencing the pointer.

Think of a library catalogue card. The card is not the book. It sits in a drawer at its own location, and all it carries is a shelf number. Finding the book is two separate steps: read the card, then walk to the shelf.

That comparison is worth keeping because it survives being pushed on. The drawer slot is 0x2000. The shelf number written on the card is 0x5000. The book is the player object. And here is the part that matters most: if a librarian removes that book and shelves a different one in the gap, your card still reads 0x5000 and still sends you confidently to a real shelf holding a real book — the wrong one. Nothing about the card looks damaged.

That is not a flaw in the comparison. It is precisely what can go wrong with a stale pointer. Lesson 3.6 shows the address-reuse example in memory.

Why bother with the extra hop?

Section titled “Why bother with the extra hop?”

Because the object can move. It can be destroyed and rebuilt somewhere else. When the game updates the pointer at 0x2000, code that reads it again can follow the new address instead of holding on to the old one.

So 0x5000 is where the object sits in this example, while 0x2000 is where the example’s pointer is stored. That first location is useful only while the pointer storage itself remains valid. Lesson 2.7 builds a repeatable pointer path with that condition in mind.

A pointer is not guaranteed to stay good, either. The object can be removed, the memory reused, a module unloaded. An address that is not zero can still be completely wrong.

What a pointer’s type tells you

Section titled “What a pointer’s type tells you”

In source code a pointer usually has a type attached. Rust writes a raw pointer to a u32 as *const u32, read aloud as “a pointer to a u32”. That type describes the data at the other end, not the pointer itself, and it is called the pointee type. It tells the program how many bytes to read at the destination and how to interpret them.

An offset is a distance, not a place

Section titled “An offset is a distance, not a place”

Say a player object starts at 0x5000, and its health sits 48 bytes into it.

Three different numbers, doing three different jobs. The base says where the object starts. The offset says how far in the field is. The sum says where to read.

An offset is not an address and it is not the health value. On its own it means nothing at all — 0x30 is just “48 bytes along from something.”

Offsets matter because they may outlast one address. The object’s base address may land somewhere new every time the game starts, while the health field can remain 48 bytes into the same object layout for that build. Verify the offset again when the game or layout changes.

Alternative: Picture a flat in a building: the building’s street address can change, but the flat stays the same number of floors up. The offset is the floors.

Why an address can stop working

Section titled “Why an address can stop working”

The pointer and offset example gives you a way to find a field now. It does not promise that the object will occupy the same address later. Two common ways of handing out memory help explain why.

A function can use its thread’s stack for temporary values. Its stack frame lasts through that call; later calls can reuse the same bytes. An allocator can give a longer-lived game object space on the heap. That object may survive many calls, but the game can eventually remove it and reuse its address for a different object. A growing collection can also move its contents. Lesson 3.4 draws a call frame in memory, and Lesson 3.6 follows a heap address from one object to another. Lesson 2.7 then builds pointer paths that can survive a moving object base.

The process is part of the address

Section titled “The process is part of the address”

A debugger shows virtual addresses in a particular process. The game’s 0x5000 and your tool’s 0x5000 need not name the same bytes. An external tool therefore opens a process handle and asks Windows to read an address in that game’s address space. Windows also divides the space into protected pages; a number that looks like an address may not be readable at the moment you try it. Lesson 3.3 works through a remote read, and Lesson 11.7 examines the page map in detail.

A running game is not a frozen picture

Section titled “A running game is not a frozen picture”

A scanner copies bytes while the game continues to update them. Its result is a snapshot gathered over a short stretch of time, not a promise that every field describes one instant. This is a copy of selected memory, unlike the whole virtual-machine recovery snapshot from Lesson 1.7. For example, if the game removes one enemy after you read its pointer and reuses that address before you read its health, both reads can succeed while your combined answer describes neither enemy correctly. Re-check a promising candidate and its object identity before trusting it. Lesson 3.3 shows that sequence and the checks an external reader needs.

What the scanner sees

Section titled “What the scanner sees”

A byte is the sum of the place values of its set bits. On x86, a hex dump shows a multi-byte u32 least-significant byte first. An address, the bytes at that address, and the value produced by interpreting those bytes are different things; four identical bytes can mean a whole number or a float when read with different types.

A pointer has a size set by the process, while its pointee type controls the value read after following it. base + offset computes the address of a field. Stack and heap allocations have different lifetime patterns, and another process has its own virtual address space. A memory scan reads state while the game can continue changing it; it is not an instantaneous frozen copy.

Lesson 1.9

What a Memory Scan Really Finds

An address names a location, while a type tells a program what its bytes mean. We will use a memory scanner on Wesnoth: observe a gold value, search for matching bytes, make one in-game change, and filter the results.

The goal is not merely to reach a final address. The goal is to understand why each scan removes some candidates and why one test still does not prove that a candidate is the main game-play value.

Prepare the target

Section titled “Prepare the target”

Use the course build of Wesnoth 1.14.9 in the Windows VM. Start a local match and pause before recruiting a unit.

Suppose the screen shows 100 gold and the unit you plan to recruit costs 15. After recruiting, the visible value should become 100 − 15 = 85.

Attach Cheat Engine to the game process

Section titled “Attach Cheat Engine to the game process”

Open Cheat Engine, choose the process button, and select the running Wesnoth process.

Attaching tells Cheat Engine which process address space to read. It does not yet tell the scanner where gold is or how it is stored.

Perform the first value scan

Section titled “Perform the first value scan”
Windows VM

Enter the visible gold amount. Use:

  • Value Type: 4 Bytes (Explanation: Four bytes hold one 32-bit whole number, the same size as Rust’s i32 or u32. The scanner must read all four bytes at an address to see the number the screen shows.);
  • Scan Type: Exact Value (Alternative: If a game never shows the number, scan for an unknown initial value instead. After each change in the game, keep the addresses that changed, increased, decreased, or stayed the same.);
  • Value: the current gold amount.

Start the first scan.

The scan will probably find many addresses. That is expected. The number 100 can appear in timers, object fields, capacities, interface data, and unrelated allocations.

At this point, each result proves only this:

These four bytes were readable as the integer 100 when the scanner checked them.

It does not prove that the address controls gold.

Change the game once

Section titled “Change the game once”

Return to Wesnoth and perform the planned action. Recruit the unit and read the new gold value off the screen.

If the value changed from 100 to 85, return to Cheat Engine, enter 85, and choose Next Scan.

The scanner does not search the whole process from the beginning. It checks the previous candidate addresses and keeps only those that now contain 85 (Example: Say the first scan found three addresses holding 100: A, B, and C. After the purchase only B and C hold 85, so A is dropped, and the next scan checks just B and C.). In set notation:

You do not need the symbol memorized. It means “keep items that are in both groups.”

TL;DR: Each Next Scan only re-checks the old candidates and keeps the ones that now match, so the list shrinks every time.

What Next Scan does with each candidate. This step-by-step trace needs JavaScript. Here is the code and where the run ends.

candidates = [A, B, C]  # every address that held 100
# you recruit a unit; the screen now shows new_gold
kept = []
for addr in candidates:
    now = read_4_bytes(addr)
    if now == new_gold:
        kept.append(addr)  # keep it
  # otherwise it is dropped
candidates = kept

Next Scan leaves B and C. Both followed the gold, so one may be the field and the other a copy for the screen. Repeat with a different change to tell them apart.

Final values: candidates = B, C; new_gold = 85; kept = B, C; addr = C; now = 85.

Repeat with a different change

Section titled “Repeat with a different change”

Make another controlled change with a different result. For example, recruit a unit with another cost or end a turn if the scenario changes gold in a known way. Enter the new gold value and perform another Next Scan.

Using different values is important. If you repeat only 100 → 85 → 100, an unrelated value that happens to follow the same pattern can remain in the list.

Continue until you have a small number of candidates. Do not assume the first remaining address is correct.

Alternative: Think of a guessing game with yes or no questions: each new gold value removes addresses that could not be the answer.

Test one candidate reversibly

Section titled “Test one candidate reversibly”

Add one candidate to the address list. Before changing it:

  1. copy its current value so you can put it back;
  2. confirm the game still shows the expected gold;
  3. choose a small replacement value;
  4. write the replacement once;
  5. observe the screen and one real purchase;
  6. restore the original value (Recommended: Do this before any other test, even if the change looked harmless. A leftover value can make the next test start from a different state, and then two results can no longer be compared.).

Different results support different explanations:

What happens Likely meaning
the number and purchase rules change strong candidate for game-play state
only the text changes likely a display copy
the value changes back on the next update another system recomputes or owns it
nothing visible changes unrelated value or a copy used elsewhere
nearby behavior breaks wrong address, type, or field width may have been changed

A single run can mislead, because an unrelated value might change at the same moment by coincidence. Getting the same result again from the same starting state makes that explanation less likely.

Narration: Another value, such as a timer, can change at the same moment by coincidence. Repeating the test from the same start separates luck from cause.

Why several copies may all be related

Section titled “Why several copies may all be related”

The game can legitimately keep more than one gold-related value:

  • the current simulation value;
  • a previous value used by an animation;
  • text prepared for the interface;
  • a value in a replay, event, or network message;
  • a temporary calculation.

That is why value scanning is usually the start of reverse engineering. A write breakpoint later shows which instruction changes the strongest candidate. The surrounding instructions can reveal the object base and other fields.

Treat the address as temporary

Section titled “Treat the address as temporary”

The address you found belongs to this run of the game. After a restart, gold may live somewhere else, because the process layout and the heap can change between runs. A later lesson on building and loading a program explains why some distances stay fixed within one build even when absolute addresses move. First, a debugger lets us follow the candidate value to the instruction that changes it.

What the scan established

Section titled “What the scan established”

The first scan returned readable candidates that matched while it ran; it did not identify “the gold address.” Each controlled game change filtered that candidate set. Changing one survivor and then making a real purchase showed whether it affected gameplay, only the display, or neither. Restoring the original value leaves the game in a known state for another run.

The candidate address tells us where to look, but not why the value changes.
